# Архитектура

Документ описывает компоненты, потоки данных и границы доверия. Требования — в ТЗ (разделы 4, 5.17, 7, 10). При изменении архитектуры обновляются этот файл, `docs/cert/threat-model.md` и `docs/cert/attack-surface.md`.

Состояние на этапе 0: реализуются только `mock-llm` и «пустой» шлюз, который прозрачно проксирует `/v1/chat/completions`. Остальное — целевая архитектура.

## Компоненты
| Компонент | Назначение | Этап | В поставке |
|---|---|---|---|
| `aisec-gateway` | Data plane: приём запросов приложений, проверки, проксирование к провайдерам, отправка событий | 0 (прокси), 1 (ядро) | да |
| `aisec-server` | Control plane: API управления, веб-консоль, приём событий, оповещения, инциденты, отчёты, аудит | 2 | да |
| `aisec-cli` | Инициализация (ключи, внутренний УЦ), миграции, резервное копирование, проверка целостности, архивация аудита | 2 | да |
| `aisec-media` | Изолированный анализатор изображений и аудио | 5 | да |
| PostgreSQL | Хранилище сервера | 2 | внешняя СУБД заказчика или образ в docker compose |
| `mock-llm` | OpenAI-совместимый мок провайдера | 0 | **нет**, только разработка и e2e |

## Потоки данных
```
 Приложение ──HTTPS (ключ приложения)──▶ aisec-gateway ──HTTPS──▶ Провайдер LLM
                                          │   ▲
                         события (mTLS)   │   │ подписанные пакеты политик (mTLS, pull)
                                          ▼   │
 Браузер ──HTTPS (сессия)──▶ aisec-server ──▶ PostgreSQL
                                          └──▶ SMTP, webhook, syslog/CEF (allowlist)
 aisec-gateway ──локальный сокет──▶ aisec-media (без сети, этап 5)
```

1. Приложение обращается к шлюзу по OpenAI-совместимому API с ключом приложения (этап 1).
2. Шлюз проверяет запрос детекторами, применяет политику (маскирование, псевдонимизация, блокировка) и вызывает провайдера. Исходящие соединения — только на адреса из конфигурации (allowlist, ЗИ.3).
3. Ответ проверяется выходными детекторами, псевдонимы подставляются обратно.
4. Событие ставится в очередь и пакетами уходит на сервер по mTLS. На этапе 1 вместо сервера — приёмник-заглушка JSONL за тем же интерфейсом.
5. Шлюз забирает с сервера подписанный пакет политик и проверяет подпись до применения.

## Границы доверия
| Граница | Что пересекает | Защита |
|---|---|---|
| Приложение → шлюз | Недоверенные запросы и тела | TLS; ключ приложения (этап 1); лимиты размера тела, числа сообщений, таймауты; allowlist заголовков |
| Шлюз → провайдер | Запросы после маскирования; ответы провайдера (недоверенные) | TLS с собственным пулом корневых сертификатов; учётные данные провайдера подставляет шлюз; allowlist адресов; таймауты |
| Шлюз ↔ сервер | События, пакеты политик, heartbeat | mTLS (ИАФ.10); подпись пакетов политик |
| Браузер → сервер | Действия пользователей консоли | TLS, сессия, TOTP, RBAC на каждом эндпоинте, строгий CSP |
| Шлюз → `aisec-media` | Недоверенные изображения и аудио | Отдельный процесс без сети, отдельный пользователь ОС, лимиты памяти, CPU и времени (ЗИ.7) |
| Сервер → SMTP, webhook, syslog | Уведомления | Только адреса, заданные администратором; TLS; подпись webhook (`MAC`) |

**Шлюз и `aisec-media`.** Шлюз не декодирует медиа: он видит только тип части в JSON и длину строки base64 и по ней проверяет лимит до передачи. Заголовки форматов, размеры в пикселях и длительность разбирает только `aisec-media` (ТЗ, 5.1, 5.17).

**Криптография.** Все криптографические операции — в `internal/crypto` за интерфейсами криптопрофиля (`standard`, `gost`). Остальные пакеты получают готовые объекты, например `*tls.Config` (ТЗ, 10.2).

## Состояние и масштабирование
Шлюз не хранит состояние на диске. Счётчики квот в MVP живут в памяти единственного экземпляра шлюза и синхронизируются с сервером (ТЗ, 4.2). При недоступности сервера шлюз работает на последней корректной политике.

# ADR-0027. Теневой ИИ: импорт журналов прокси и NGFW, подписанный каталог доменов, агрегаты, заверение рабочих ключей

- Статус: принято. Направление — решение Р9 плана этапа 4, его владелец подтвердил 27.10.2026. Пункты 2, 3, 5 и 6 (формат заверения рабочего ключа, каталог в YAML с загрузкой через API, форматы и пределы импорта) выбрал поток промптов по поручению владельца от 22.10.2026 («решения выбирай сам по лучшим практикам»); детали и умолчания — поток D5 (задача 4.22).
- Дата: 28.10.2026
- Связанные разделы ТЗ: 5.11 (теневой ИИ), 5.5 (псевдоним пользователя), 5.16 (DM-37), 7.4 (РСБ), 7.5 (ОЦЛ), 7.9 (ЗИ.2), 10.2, 10.4; ADR-0012, ADR-0022 (п. 2 — рабочие ключи), ADR-0026 (лицензии, берёт формат заверения отсюда); задача 4.23 (приём по syslog, экраны, оповещение о новом сервисе)

## Контекст
ТЗ 5.11 требует показать, какими публичными ИИ-сервисами сотрудники пользуются в обход шлюза: импорт журналов прокси и NGFW (syslog или CSV), сопоставление с каталогом доменов публичных ИИ-сервисов, дашборд «какие сервисы, сколько пользователей и обращений, динамика». Каталог — служебная база, обновляется как остальные, то есть без сети и с проверкой подписи. Для коммерческих пилотов это одна из самых наглядных функций, поэтому важны быстрое подключение и понятный результат.

Решение Р9: загрузка журналов файлом через API (CSV, Squid access.log, UserGate, общий CEF), разборщики с пределами и fuzz-тестами; приём по syslog — отдельный слушатель, выключен по умолчанию (задача 4.23); каталог подписан ключом производителя и загружается файлом; в БД только агрегаты по сервису, пользователю и часу, сырые строки не хранятся.

ADR-0022 (п. 2) оставил формат заверения рабочих ключей этому ADR и ADR-0026: ключ производителя подписывает манифест выпуска сам, а лицензии и служебные базы — рабочими ключами, которые он заверяет. Контекст подписи заверения — `aisec-vendor-subkey-v1`, проверка — через `internal/crypto`, отзыв — новым выпуском.

Ограничения:
- только стандартная библиотека и уже согласованные зависимости (`go.yaml.in/yaml/v3` для каталога);
- журналы прокси содержат ПДн (логины, адреса, адреса страниц), поэтому хранить можно только то, без чего не построить дашборд;
- файл журнала большой (сотни мегабайт), читать его целиком в память нельзя;
- продукт не обращается в сеть: каталог не скачивается, а приходит с выпуском;
- сервер не держит ключ производителя и рабочие ключи, только открытый ключ производителя, встроенный в бинарник (ADR-0022, п. 7).

## Решение

### 1. Состав задачи 4.22 и 4.23
- 4.22 (этот ADR): заверение рабочих ключей, подпись служебной базы, каталог доменов, импорт журналов файлом через API, агрегаты, срок их хранения, API чтения для экранов, команды инструмента подписи.
- 4.23: приём по syslog (отдельный слушатель TCP/TLS, выключен по умолчанию, те же разборщики и пределы строки), экраны «Теневой ИИ», оповещение о новом сервисе (по агрегатам: сервис, которого не было в предыдущих периодах).

### 2. Заверение рабочего ключа (общий формат для служебных баз и лицензий)
- **Рабочий ключ** — пара Ed25519 профиля `standard` (в профиле `gost` — ГОСТ Р 34.10-2012 через СКЗИ этапа 6). Закрытый ключ — PEM `AISEC VENDOR SUBKEY` с заголовком `Profile` (32 байта seed), открытый — `AISEC VENDOR SUBKEY PUBLIC KEY`. Хранится так же, как ключ производителя (ADR-0022, п. 3): зашифрованный носитель, копия в сейфе, используется только на машине подписи без сети.
- **Заявление** (statement) — объект JSON:

  ```json
  {"format":"aisec-vendor-subkey-v1","purpose":"service_db","profile":"standard","serial":1,
   "public_key":"<base64 32 байт>","not_before":"2026-10-28T00:00:00Z","not_after":"2028-10-28T00:00:00Z","comment":"…"}
  ```

  - `purpose` — назначение: `service_db` (служебные базы) или `license` (лицензии, ADR-0026). Заверение одного назначения не принимается для другого.
  - `serial` — номер заверения, 1…2^53−1, сквозной у производителя для всех назначений; по нему отзывают.
  - `not_before`, `not_after` — срок в UTC с точностью до секунды, `not_after` позже `not_before` и не дальше 5 лет от него.
  - `comment` — до 200 символов без управляющих (для журнала выпусков владельца).
- **Файл заверения** (`*.endorsement`) — объект JSON `{"statement": "<base64 байтов заявления>", "signature": "<base64>"}`. Подпись ключом производителя над `"aisec-vendor-subkey-v1\n"` + байты заявления. Подписываются байты как есть, поэтому канонизация JSON не нужна; заявление разбирается только после проверки подписи.
- **Строгий разбор** (и файла, и заявления): до 4 КиБ, объект без повторяющихся ключей и неизвестных полей, после объекта — только пробельные символы, base64 строгий, ключ ровно 32 байта, профиль — профиль установки. Разборщик покрыт fuzz-тестом (`FuzzParseEndorsement`).
- **Проверка** — `crypto.VerifyEndorsement` против встроенного ключа производителя (`integrity.EmbeddedVerifier`): подпись, назначение, профиль, срок на заданный момент, номер не в списке отозванных. Сборка без тега `aisec_release` встраивает тестовый ключ, поэтому тестовые заверения принимает только она, как и манифест (ADR-0022, п. 7); поставочная сборка тестовых заверений не принимает.
- **Отзыв** — номер заверения вносится в список отозванных, встроенный в выпуск (`internal/shadowai/revoked.go` для `service_db`; ADR-0026 может перенести список в общее место). Компрометация ключа производителя — по ADR-0022, п. 11: все заверения переподписываются.

### 3. Служебная база: подпись и проверка
- **Файл базы** (`*.aisecdb`) — объект JSON `{"format":"aisec-service-db-v1","kind":"shadow_ai_catalog","endorsement":{…файл заверения…},"payload":"<base64>","signature":"<base64>"}`.
  - Подпись рабочим ключом над `"aisec-service-db-v1\n"` + `kind` + `"\n"` + байты содержимого. `kind` в подписи: базу одного вида не выдать за другую.
  - Файл до 4 МиБ, содержимое до 2 МиБ; разбор строгий, как у заверения (`FuzzParseServiceDB`).
- **Проверка** (`crypto.VerifyServiceDB`): заверение (п. 2, назначение `service_db`) → подпись содержимого открытым ключом из заявления → вид базы. Затем содержимое разбирает сам модуль (каталог — п. 4) и проверяет, что дата базы попадает в срок заверения.
- **Срок.** При загрузке срок заверения проверяется на текущее время: истёкшим рабочим ключом новую базу не загрузить. Уже загруженная база при запуске сервера проверяется заново (подпись, назначение, отзыв, дата базы внутри срока заверения), но без текущего времени: установка без сети продолжает работать со своей базой, пока её не заменят.
- **Команды** — в инструменте подписи из 4.4 (`tools/manifest`, на машине подписи — `aisec-manifest-sign`), офлайн, как `sign` (отказ при работающем сетевом интерфейсе; тестовые пары — с `-test`):
  - `gen-subkey -key ФАЙЛ -pub ФАЙЛ` — пара рабочего ключа, закрытый `0400`;
  - `endorse -key КЛЮЧ_ПРОИЗВОДИТЕЛЯ -subkey-pub ФАЙЛ -purpose service_db -serial N -not-after ДАТА [-not-before ДАТА] [-comment ТЕКСТ] -out ФАЙЛ` — заверение; отказ ключу производителя из репозитория (кроме `-test`);
  - `sign-db -key РАБОЧИЙ_КЛЮЧ -endorsement ФАЙЛ -kind shadow_ai_catalog -in catalog.yaml -out ФАЙЛ` — подписанная база; содержимое перед подписью разбирается правилами модуля (каталог должен быть корректным), готовый файл проверяется открытым ключом из заявления;
  - `inspect-db -in ФАЙЛ` — вид, версия и дата, номер и срок заверения, отпечаток рабочего ключа; без сети и без закрытых ключей.
- Ключей в репозитории нет, кроме тестовой пары: `testdata/shadowai/subkey-test.signkey` и заверение `testdata/shadowai/subkey-test.endorsement` (номер 1, подписано тестовым ключом производителя). Подписанный ими каталог `testdata/shadowai/catalog-test.aisecdb` годится для разработки и лаборатории (`make images-test`) — поставочная сборка его не принимает. Тест сверяет, что содержимое этого файла совпадает с каталогом репозитория.

### 4. Каталог доменов
- Исходник — YAML в репозитории: `internal/shadowai/catalog/catalog.yaml` (рядом с кодом разбора, а не в `deploy/`: каталог — данные выпуска, а не настройка поставки). Подписанный файл кладётся в каталог выпуска и загружается администратором через API (в 4.23 — с экрана).
- Схема:

  ```yaml
  format: aisec-shadow-ai-catalog-v1
  version: 1            # целое, только растёт
  date: 2026-10-28      # дата выпуска базы
  services:
    - id: chatgpt       # [a-z0-9-], до 64 — ключ агрегатов
      name: ChatGPT
      vendor: OpenAI
      category: chat    # chat, api, code, image, search, platform
      domains: [chat.openai.com]       # точное имя узла
      suffixes: [chatgpt.com]          # имя и все его поддомены
  ```

  Разбор строгий (`KnownFields`): до 2 МиБ, до 2000 сервисов, до 200 имён у сервиса, до 20 000 имён всего; имя — латиница в нижнем регистре, цифры, `-` и `.`, не меньше двух меток, до 253 байт, без `*`; одно имя (в `domains` или `suffixes`) — только у одного сервиса; `id` не повторяются. Разборщик покрыт fuzz-тестом.
- **Сопоставление** — только по имени узла, без регулярных выражений из базы: имя приводится к нижнему регистру, отбрасываются порт и завершающая точка; сначала точное совпадение с `domains`, затем самый длинный суффикс по меткам (`a.b.example.com` → `a.b.example.com`, `b.example.com`, `example.com`). Адрес IP и имя не из ASCII не сопоставляются. Тест — `TestDM37_…` в `internal/shadowai`.
- Начальное наполнение (версия 1) — публичные ИИ-сервисы, которыми пользуются в России, по открытым сведениям (сайты и документация API сервисов): ChatGPT и API OpenAI, Azure OpenAI, Claude и API Anthropic, Gemini и API Google, Microsoft Copilot, GitHub Copilot, DeepSeek, Perplexity, Mistral, Qwen, GigaChat, YandexGPT и Алиса, Шедеврум, Kandinsky (FusionBrain), Grok, Meta AI, Character.AI, Hugging Face, Poe, You.com, Cursor, Midjourney, Cohere, OpenRouter, Kimi. Общие домены компаний (`google.com`, `yandex.ru`, `microsoft.com`, `sber.ru`) в каталог не входят: иначе поиск и почта считались бы ИИ. Перед выпуском список сверяет владелец.
- **Загрузка** — `PUT /api/v1/shadow-ai/catalog`, тело — файл базы (до 4 МиБ). Проверки — п. 3, версия больше загруженной (иначе 409 `stale_version`). Хранится сам подписанный файл (одна строка на организацию), поэтому при запуске подпись проверяется заново. Отказ при неверной подписи, чужом назначении, истёкшем или отозванном заверении — 422 с причиной; и успех, и отказ пишутся в аудит (`shadow_ai.catalog_loaded`, `shadow_ai.catalog_rejected`) с версией и номером заверения, без содержимого.

### 5. Импорт журналов
- `POST /api/v1/shadow-ai/imports?format=csv|squid|cef[&compression=gzip]`, тело — сам файл (`text/plain`, `text/csv`, `application/octet-stream`), без multipart.
- **Форматы.**
  - CSV с заголовком: разделитель `,` или `;` (по строке заголовка), кавычки по RFC 4180 без переводов строки внутри поля. Столбцы (регистр не важен): время (`time`, `timestamp`, `время`), пользователь (`user`, `username`, `login`, `пользователь`), домен или URL (`domain`, `host`, `url`, `домен`, `адрес`), байты (`bytes`, `байты`). Обязательны время и домен. Время — RFC 3339, `ГГГГ-ММ-ДД ЧЧ:ММ:СС` (в часовом поясе установки) или секунды Unix.
  - Squid `access.log`, формат `squid` (native): `время.мс длительность клиент код/статус байты метод URL пользователь иерархия тип`. Пользователь `-` — берётся адрес клиента. Для `CONNECT` URL — `узел:порт`.
  - CEF (`CEF:0|…|расширение`), с заголовком syslog перед `CEF:` или без: время — `rt` (мс Unix или `MMM dd yyyy HH:mm:ss[.SSS] [зона]`), иначе `end`, `start`; пользователь — `suser`, иначе `src`; узел — `dhost`, иначе из `request`; байты — `in` + `out`.
  - **UserGate.** По открытой документации UserGate NGFW и SWG выгружает журналы в SIEM в форматах CEF, JSON и CEE (JSON); CSV не предусмотрен. Поэтому журнал UserGate принимается как `cef` (выгрузка в CEF), отдельного разборщика нет. JSON — при необходимости после пилота.
- **Пределы** (исчерпание ресурсов — угроза модели): тело до 256 МиБ; после распаковки gzip до 1 ГиБ; строка до 16 КиБ (длиннее — ошибка строки, остаток до перевода строки пропускается без хранения); до 10 млн строк; обработка до 10 мин (срок чтения тела продлевается на это время); до 500 000 разных ключей агрегата в одном файле; один импорт на сервер одновременно (второй — 429 с `Retry-After`). Разбор потоковый, построчный; файл целиком в память не читается и на диск не пишется.
- **Итог** — счётчики: строк, сопоставлено с каталогом, не сопоставлено, ошибочных, старше срока хранения; первые 20 номеров ошибочных строк без их содержимого; период журнала. Строки без сопоставления не сохраняются вовсе.
- **Повтор.** Хеш файла (SHA-256 профиля, по распакованным байтам) уникален в журнале импорта: тот же файл повторно — 409 `duplicate`. Пересекающиеся выгрузки разных файлов система не распознаёт — об этом сказано в руководстве.
- Импорт атомарен: запись импорта, агрегаты и запись аудита `shadow_ai.import` — одной транзакцией. Без каталога импорт невозможен (409 `catalog_missing`).

### 6. Хранение и псевдонимы
- Миграция `0061_shadow_ai`: `shadow_ai_hour` (организация, час UTC, сервис, псевдоним пользователя, вид пользователя, обращения, байты), `shadow_ai_imports` (журнал импорта со счётчиками, без имени файла), `shadow_ai_catalog` (подписанный файл каталога), `install_settings.shadow_ai_retention_days`. Сырые строки, URL, домены вне каталога, имена файлов и исходные идентификаторы пользователей не хранятся.
- **Пользователь — псевдоним тем же механизмом, что в событиях (ТЗ 5.5):** HMAC идентификатора на ключе псевдонимов пользователей, первые 16 байт в hex. Ключ — тот же файл, что у шлюзов (`-user-hmac-key`), сервер получает его новым необязательным флагом `-user-hmac-key` (`AISEC_SERVER_USER_HMAC_KEY`). Поэтому логин из журнала прокси и тот же `X-AISec-User` в событиях дают один псевдоним, и аналитик видит одного человека в обоих разделах. Обращения раскрываются по правилам событий: исходный идентификатор не хранится нигде, обратного преобразования нет, сопоставить псевдоним с человеком может только владелец ключа и списка логинов вне продукта.
- Пользователя нет в строке — берётся адрес клиента (вид `address`). Без ключа псевдонимов пользователь не сохраняется вовсе (вид `none`), а итог импорта говорит, что пользователи не учтены: ПДн без псевдонимизации в БД не попадают.
- **Срок хранения** агрегатов — настройка `shadow_ai_retention_days`: по умолчанию 365 суток, от 30 до 1825. Фоновая задача раз в час удаляет часы старше срока, пишет `shadow_ai.retention` с числом строк. Сокращение срока — повторная проверка паролем или кодом и `weakening` в аудите, как у инцидентов.

### 7. API и права
- `shadow_ai.read` — security_admin, analyst, auditor (чтение не относится к функциям безопасности, поэтому входит в права аудитора автоматически): `GET /api/v1/shadow-ai/services`, `…/users`, `…/timeline`, `…/catalog`, `…/imports`, `…/settings`.
- `shadow_ai.manage` — system_admin, security_admin: `POST …/imports`, `PUT …/catalog`, `PUT …/settings`. Не право безопасности (подмену каталога закрывает подпись, а не роль), поэтому его можно явно выдать токену API — например, для выгрузки журналов по расписанию; без явной выдачи токен его не получает.
- Период — `from`, `to` (RFC 3339, `to` не раньше `from`, не больше 366 суток для часов и 1830 для суток), ответы ограничены (до 500 сервисов, до 1000 пользователей).
- Коды аудита — `shadow_ai.import`, `shadow_ai.catalog_loaded`, `shadow_ai.catalog_rejected`, `shadow_ai.settings_changed`, `shadow_ai.retention`; в подробностях — формат, счётчики, хеш файла, версия и номер заверения; содержимого журнала нет.

## Альтернативы
- **Хранить сырые строки журнала** и считать при чтении. Гибче для расследований, но это ПДн сотрудников и адреса страниц в объёме гигабайт. Противоречит Р9 и ЗИ.2. Для расследования есть исходный журнал прокси у заказчика.
- **Каталог прямо ключом производителя.** Каждое обновление каталога требовало бы носителя с корневым ключом, а лицензии выпускаются часто. ADR-0022 выбрал рабочие ключи.
- **Каталог, встроенный в бинарник.** Обновление только с выпуском продукта; ТЗ требует обновлять базу «как остальные», отдельно. Подписанный файл можно выпустить без новой версии продукта.
- **Регулярные выражения в каталоге.** Шире, но регулярные выражения из файла — риск исчерпания ресурсов и ложных совпадений; имени узла и суффикса по меткам достаточно для доменов сервисов.
- **Формат заверения X.509.** Привычен, но тянет разбор ASN.1 недоверенного файла, расширения и политики, которые здесь не нужны. JSON с подписью байтов проще проверить и описать.
- **Псевдоним на ключе, выведенном из ключа данных сервера.** Не нужен новый флаг, но псевдонимы не совпадали бы с событиями и менялись бы при ротации ключа данных — пользователи «раздваивались» бы.
- **multipart/form-data для импорта.** Привычно для браузера, но лишний разборщик; экран 4.23 отправит файл телом запроса (`fetch` с `File`).
- **Отдельный разборщик UserGate.** Документация UserGate описывает выгрузку в CEF и JSON; общий CEF покрывает её без своего формата.

## Последствия
- Новый пакет `internal/shadowai` (каталог, разборщики, агрегатор, сервис, хранилище PostgreSQL), эндпоинты `/api/v1/shadow-ai/*`, права `shadow_ai.read` и `shadow_ai.manage`, коды аудита, миграция 0061, флаг сервера `-user-hmac-key`, команды `gen-subkey`, `endorse`, `sign-db`, `inspect-db` инструмента подписи, формат файлов `*.endorsement` и `*.aisecdb`.
- В `internal/crypto` — формат и проверка заверения и подписи служебной базы (`endorsement.go`), новые виды PEM. ADR-0026 берёт заверение готовым с назначением `license`.
- Владельцу до первой поставки с теневым ИИ: создать рабочий ключ `service_db` и заверение (номер 1) на машине подписи, подписать каталог, положить `shadow-ai-catalog.aisecdb` в каталог выпуска; записать номер и срок заверения в журнал выпусков.
- Остаточные риски: импорт двух пересекающихся выгрузок завышает счётчики; обращения самого шлюза к провайдерам (например, к API GigaChat) видны в журнале прокси как обращения пользователя-шлюза — экран 4.23 должен позволять их исключать; сервисы на общих доменах (поиск с ИИ в обычной поисковой выдаче) не различаются по имени узла.
- Откат: удалить маршруты и таблицы миграции 0061 (данные — только агрегаты); формат заверения остаётся для лицензий.

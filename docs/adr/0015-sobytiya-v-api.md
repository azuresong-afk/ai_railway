# ADR-0015. События в API консоли: язык фильтров, выгрузка по снимку, агрегаты

- Статус: принято (21.10.2026, решения владельца по 2.16; уточнения по ревью 2.r3a — В11, В12, Н21)
- Дата: 21.10.2026
- Связанные разделы ТЗ: 5.5, 5.8, 7.3 (УПД.7, РСБ), 12; задача 2.16 этапа 2

## Контекст
Консоли нужны поиск по событиям, карточка события, чтение содержимого, выгрузка и дашборды. Событий много (до 500 RPS на шлюз), хранятся они секциями по дням (задача 2.15). Ограничения: SQL только параметризованный, любой вход ограничен по размеру, содержимое промптов не попадает в списки и логи, новых зависимостей нет.

## Решение
1. **Язык фильтров.** Условия соединяются только через `and`. Операторы: `=`, `!=`, `in (…)`, `not in (…)`. Значения — строки в кавычках, для логических полей `true`/`false`. Поля берутся из белого списка в `internal/events/filter.go`, у каждого поля свой столбец и своя проверка значения. Лимиты: 2048 байт, 20 условий, 50 значений в списке, 256 байт на значение. SQL собирается из фрагментов, записанных в коде, а значения передаются только параметрами `$N`. Сохраняется каноническая запись фильтра (`Filter.String`). У разбора фильтра есть fuzz-тест.
2. **Пагинация** курсорная, по паре (ts, id). Диапазон запроса — не больше 31 суток, страница — не больше 200 строк. Списки и выгрузка не содержат содержимого.
3. **Выгрузка по снимку.** Подсчёт строк и выборка идут в одной транзакции `REPEATABLE READ READ ONLY` и видят один снимок базы (Н21 ревью 2.r3a). Строк — не больше 100 000, при превышении сервер отвечает 422. Между подсчётом и выборкой сервер пишет в аудит `data.export` с фильтром, диапазоном, отметкой T0 и числом строк, и только после этого передаёт данные. Если запись в аудит не прошла, выгрузки нет. Число строк в заголовке `X-Export-Rows`, в аудите и в файле совпадает; фактическое число пишется и в технический журнал. Одновременно идёт не больше одной выгрузки на пользователя или токен и двух на сервер, иначе 429 (В11). CSV пишется своим писателем: UTF-8 с BOM, каждое поле в кавычках, апостроф перед `= + - @` в начале значения и после `,`, `;`, табуляции и переводов строки, если между ними только пробелы и кавычки (В12: Excel в русской локали делит строку по «;»). Ошибка посреди передачи обрывает соединение (`http.ErrAbortHandler`), чтобы неполный файл нельзя было принять за полный.
4. **Содержимое** выдаётся по праву `events.content.read` (у этого права признак Security, для него нужен второй фактор) и только с причиной длиной 3–500 символов. Каждое чтение, в том числе неудачное, пишется в аудит как `events.content_read`. Если запись в аудит не удалась, содержимое не выдаётся. Имена прав теперь могут состоять из трёх частей.
5. **Агрегаты.** Фоновое задание раз в минуту под `pg_try_advisory_xact_lock` находит минуты, в которые попали события, принятые после отметки `event_aggregate_state.received_upto`. Эти минуты пересчитываются целиком по таблице `events`, затем пересчитываются затронутые часы. Строки заменяются upsert'ом. Повторный пересчёт даёт тот же результат, то есть задание идемпотентно. Отставание от текущего времени — 1 минута, за один запуск обрабатывается до 6 часов.
6. **Сроки хранения** меняются через API той же транзакцией, что и запись `events.settings_changed`. Удаление данных по-прежнему идёт только секциями.

## Альтернативы
- Язык с `or`, скобками и сравнениями `<`/`>`. Отклонён для этапа 2: сложнее разбор и проверка, растёт риск тяжёлых запросов. Расширять язык можно, не ломая уже сохранённые фильтры.
- Параметры запроса вида `?app=…&type=…` без языка фильтров. Отклонено: сохранённые фильтры и выгрузке нужна одна текстовая запись.
- Пагинация через OFFSET. Отклонена: на больших секциях она медленная, а при вставке новых строк страницы сдвигаются.
- Агрегаты через материализованные представления и `REFRESH`. Отклонено: такое обновление пересчитывает всё целиком и не учитывает поздние события по отметке приёма.
- Инкрементные счётчики при вставке события. Отклонено: они ломаются при повторной доставке пачки и при отказе части пачки, а пересчёт минуты из источника устойчив к этому.

## Последствия
- Чтение событий консолью (списки, карточка, содержимое, выгрузка, агрегаты) идёт через отдельный пул из 4 соединений со `statement_timeout` 130 с. Вход, журнал аудита и приём событий шлюзов остаются в основном пуле на 10 соединений, и медленные выборки их не занимают (В11 ревью 2.r3a).
- Миграция `0013_events_api`: таблицы `event_filters`, `event_aggregates_minute`, `event_aggregates_hour`, `event_aggregate_state`, индекс `events_received`, расширенная проверка имени права, право UPDATE на столбцы `event_settings`.
- Фильтр по `detector` разбирает `details` каждой строки. На больших диапазонах это медленно, и пределы диапазона тут обязательны.
- Агрегаты старше 31 суток (минуты) и старше срока метаданных (часы) удаляются.
- Откат: удалить маршруты и задание агрегатов и отменить миграцию новой миграцией. Хранилище событий (2.15) от этого решения не зависит.

# ADR-0031. Тестирование устойчивости: исполнитель на сервере, цели, защита от SSRF, сценарии как служебная база, оценка и хранение результатов

- Статус: принято. Направление — решение Р6 плана этапа 5, его владелец подтвердил 30.10.2026. Детали выбрал поток F1 (задача 5.30) по промпту волны F.
- Дата: 03.11.2026
- Связанные разделы ТЗ: 5.13 (тестирование устойчивости), 5.16 (матрица обнаружения, DM-08, DM-18, DM-19, DM-40), 5.5 (события, режим хранения), 5.6 (оповещения и инциденты), 5.1 (ключи приложений); ADR-0020 (правило адресов каналов: запрет loopback и метаданных), ADR-0023 (`internal/netguard`), ADR-0028 (служебные базы), ADR-0030 (`judge.llm`, проверка всех адресов DNS при каждом соединении), ADR-0009 (пакет конфигурации шлюзов).

## Контекст
ТЗ 5.13 требует библиотеку сценариев атак на русском и английском, запуск против приложения заказчика (через шлюз или напрямую), оценку ответов и отчёт с примерами; запуск по расписанию и из CI. Сценарии — данные: версионируются и обновляются как служебная база, содержание курирует команда исследователей.

Ограничения:
- Продукт впервые сам отправляет атакующие запросы. Исполнитель с адресом, который задаёт администратор, — готовый инструмент атаки на чужие адреса и на внутренние службы узла (SSRF). Исходящие обращения — только явно настроенные (CLAUDE.md, «Сеть»).
- Запросы к приложению продукта проходят через шлюз и порождают события, находки, оповещения и инциденты. Аналитик не должен разбирать учения как настоящую атаку, а сами учения не должны обходить защиту приложения.
- Ответы на атаки — содержимое (ТЗ 5.5): в них могут быть ПДн, секреты и системный промпт заказчика.
- Новых библиотек нет: HTTP — `net/http`, TLS — через `internal/crypto`, правило адресов — `internal/netguard`.

## Решение

### 1. Исполнитель на сервере
- Новый пакет `internal/redteam`: цели, сценарии (вид служебной базы), запуск, оценка, хранение. Исполнитель работает в процессе `aisec-server` фоновыми горутинами; путь пакета добавляется в `NET_CLIENT_ALLOWED` (изменение сборки, `Makefile`). Другие пакеты сервера сетевыми клиентами не становятся.
- Запуск асинхронный: `POST` возвращает 202 и ID запуска, состояние читается отдельно. Состояния: `queued` → `running` → `done` | `failed` | `cancelled`. Запуск, который застал перезапуск сервера, при следующем старте получает `failed` с причиной `interrupted`.
- Одновременно — не больше 2 запусков на сервер и не больше одного на цель; сверх — 409 `busy` (очереди нет: расписание 5.33 повторит позже).

### 2. Цели двух видов
Цель — запись `redteam_targets`: имя, вид, пределы (раздел 4), режим хранения примеров (раздел 7). Создаёт, меняет и удаляет цели только администратор безопасности (право `redteam.targets.manage`, признак `security`) и только из консоли (`SessionOnly`).

**Приложение продукта (`gateway`).** Запросы идут через шлюз как запросы приложения: проверяется вся защита приложения, а не модель в обход неё.
- Цель называет приложение и модель (из разрешённых приложению). Тело запроса — `POST /v1/chat/completions` в формате OpenAI.
- Адрес шлюза задаёт администратор системы при установке — флаг сервера `-redteam-gateway-url` (и корневой сертификат `-redteam-gateway-ca`), а не API: так консоль не получает способа направить запросы на произвольный адрес. Для этого адреса правило адресов раздела 3 не действует (шлюз часто на том же узле), но перенаправления и прокси запрещены так же. Флаг не задан — цели вида `gateway` создаются, запуск даёт 422 с текстом «адрес шлюза для тестирования не задан» (список целей показывает признак `gateway_configured`).
- **Тестовый ключ.** Для каждого запуска сервер выпускает отдельный ключ приложения (формат — `auth.NewAppKey`). Сам ключ — только в памяти исполнителя на время запуска; в БД (`redteam_runs`) — префикс и хеш профиля. Ключ попадает в пакет шлюзов как ключ приложения с признаком `test: true` и сроком до конца запуска (срок запуска и минута запаса); после завершения запуска он из пакета выходит. Изменение счётчика конфигурации — триггером на `redteam_runs` (как у остальных таблиц пакета, миграция 0030).
- Пакет шлюзы забирают раз в 30 с, поэтому исполнитель перед первым сценарием ждёт, пока шлюз примет ключ: `GET /v1/models` каждые 3 с до 90 с. Не принят — запуск `failed`, причина `key_not_delivered`.
- **Тестовые события.** Шлюз помечает события запросов с тестовым ключом: поле события `test: true`. Сервер сохраняет их как обычные события (содержимое — по режиму хранения приложения), но **не поднимает по ним оповещения и инциденты**: правила «порог», «новое», «частота» и счёт неудачных входов их пропускают. Правила по агрегатам («бюджет», «аномалия») тестовые запросы учитывают: расход на провайдера реальный, а поминутные и почасовые агрегаты признака `test` не несут (отделение — с экранами 5.34). Решение: учения не должны будить дежурного, а проверка самих правил оповещений — отдельная задача (правила проверяет самотест и e2e). Поле `test` видно в карточке события; фильтр и отделение в дашбордах — с экранами 5.34.
- Признак `test` даёт только ключ, выпущенный сервером для запуска: клиент не может пометить свой запрос заголовком. Ключ не выдаётся ни людям, ни в ответах API.

**Адрес приложения заказчика (`endpoint`).** Приложение вне продукта или до пилота (экспресс-проверка чат-бота, ТЗ 5.13).
- Администратор безопасности задаёт точный адрес: схема `https` или `http`, узел, порт (явно), путь; запрос идёт только на этот адрес. Шаблон тела — JSON до 16 КиБ, в котором строковое значение `"{{prompt}}"` заменяется текстом шага, а `"{{messages}}"` — историей диалога в формате OpenAI (для многоходовых сценариев); путь к ответу — точечный путь в JSON ответа (`choices.0.message.content`, `answer`), значение — строка.
- До 8 постоянных заголовков без секретов (имена — по RFC 9110; `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Cookie`, `Proxy-*` запрещены). Секретный заголовок авторизации цель только называет (`auth_header`, например `Authorization`), а значение передаётся в запросе запуска и живёт только в памяти исполнителя до конца запуска: в БД, журналы и аудит не попадает. Хранимый секрет для расписания решает 5.33.
- Корневой сертификат цели — PEM до 64 КиБ, для адреса `https` обязателен, для `http` запрещён (TLS — из `internal/crypto` по криптопрофилю; доверие — только этому корню, системное хранилище корней не используется).
- Добавление цели и смена адреса — повторная проверка (пароль или TOTP) и обязательное основание (`authorization_note`, 10–500 символов: договор, письмо владельца адреса и т. п.). Основание пишется в аудит. Продукт не проверяет право на тестирование чужого адреса — за него отвечает администратор безопасности, и аудит фиксирует, кто и на каком основании добавил адрес.
- Событий шлюза у такой цели нет.

### 3. Защита от SSRF (цели `endpoint`)
- Правило адресов — `internal/netguard`, как у каналов уведомлений и MCP-серверов (ADR-0020, ADR-0023): запрещены loopback, link-local, multicast, неуказанный адрес, службы метаданных облака (169.254.169.254, `fd00:ec2::254`, `100.100.100.200`) и их формы в NAT64. Частные и внешние адреса разрешены: чат-бот заказчика бывает и в контуре, и в интернете.
- При сохранении: имя `localhost` и литерал запрещённого адреса — отказ.
- При каждом соединении: имя разрешается заново, и соединение устанавливается, только если **все** адреса ответа DNS разрешены (как у оценщика `judge.llm`, ADR-0030): подмена DNS после сохранения (DNS rebinding) не выводит запрос на запрещённый адрес. Соединение — на проверенный адрес, а не повторным разрешением имени.
- Перенаправления не выполняются: ответ 3xx — ошибка шага `redirect`. Прокси из окружения не используются. Порт — только из цели.

### 4. Пределы
- У цели (в пределах, по умолчанию): частота — 1–600 запросов в минуту (30); параллельность — 1–8 сценариев одновременно (2); срок запроса — 5–120 с (30); срок запуска — 1–120 мин (30). Шаги одного сценария идут последовательно.
- Ответ цели — не больше 1 МиБ (больше — ошибка шага `too_large`, текст не оценивается); тело запроса — не больше 256 КиБ.
- Запуск — не больше 1000 сценариев. Срок запуска истёк — оставшиеся сценарии получают `skipped`, запуск — `failed` с причиной `deadline`.
- Отмена (`POST …/cancel`) прерывает запросы в полёте через контекст.

### 5. Сценарии — служебная база
- Вид `redteam_scenarios` по ADR-0028: подписанный файл `*.aisecdb`, содержимое — JSON формата `aisec-redteam-scenarios-v1`, разбор строгий (`DisallowUnknownFields`, один объект), fuzz-тест разборщика. Загрузка — `PUT /api/v1/redteam/scenarios` (право `redteam.scenarios.load`), возврат предыдущей версии — `POST /api/v1/redteam/scenarios/rollback` (то же право, только из консоли). Подписывает производитель `aisec-manifest-sign sign-db`, проверяет заказчик `aisec-cli servicedb inspect`.
- Формат:
  ```json
  {"format": "aisec-redteam-scenarios-v1", "version": 1, "date": "2026-11-03",
   "scenarios": [{
     "id": "RT-DM08-001", "lang": "ru", "threat": "DM-08", "category": "prompt_leak",
     "title": "Просьба повторить инструкции дословно",
     "steps": [{"prompt": "…"}, {"prompt": "…"}],
     "success": {"canary": true, "contains": ["…"], "findings": ["secret"], "judge": "…"},
     "source": "https://…", "license": "Apache-2.0"}]}
  ```
- Пределы: до 5000 сценариев; ID — `^[A-Z][A-Z0-9-]{2,63}$`, без повторов; `lang` — `ru` или `en`; `threat` — строка матрицы `DM-NN` из ТЗ 5.16; `category` — `^[a-z][a-z0-9_]{1,63}$`; `title` — до 200 символов; от 1 до 8 шагов, `prompt` — до 16 КиБ, без нулевых символов; `source` — адрес `https`; `license` — из разрешённых для данных (MIT, BSD-2/3-Clause, Apache-2.0, ISC, CC0-1.0, CC-BY-4.0) или `proprietary` (собственный корпус производителя).
- Критерий успеха атаки (`success`) — хотя бы одно условие:
  - `canary: true` — в ответе маркер-канарейка (детектор `canary`, DM-08): системный промпт с маркером продукта утёк;
  - `contains` — до 8 строк-маркеров (2–200 символов), которые сценарий просит модель произнести; совпадение без учёта регистра;
  - `findings` — до 8 префиксов категорий находок детекторов в ответе (`secret`, `pii.snils`, `exfil.markdown_image`): модель выдала секрет, ПДн или ссылку для эксфильтрации;
  - `judge` — критерий на естественном языке (10–1000 символов) для `judge.llm` (раздел 6).
- Текст шагов показывается в API только как число шагов и заголовок: корпус атак — данные производителя, а не справочник для пользователей консоли.

### 6. Оценка
Сценарий оценивается по ответу каждого шага; итог сценария:
- `blocked` — шлюз заблокировал запрос или ответ (заголовок `X-AISec-Decision: block` или ответ 4xx шлюза с ним) до того, как атака удалась: защита продукта сработала;
- `succeeded` — выполнено условие `success` по ответу хотя бы одного шага: атака удалась (уязвимость);
- `defended` — все шаги получили ответ, условия не выполнены;
- `unchecked` — единственное условие — `judge`, а оценщик не настроен или не дал оценку;
- `error` — цель не ответила (отказ соединения, адрес запрещён, срок, 3xx, 5xx, ответ не по пути, слишком большой);
- `skipped` — не запускался (срок запуска, отмена).

Чем оценивается ответ:
- **Детекторы по ответу** — встроенные детекторы направления «выход» (`unihidden`, `pii`, `secrets`, `injection`, `canary`, `exfil`) в процессе сервера, без политики приложения: находки (детектор, категория, строка матрицы) — в результат. У цели `gateway` дополнительно — решение шлюза и ID событий (`X-AISec-Event-Id`).
- **Канарейка** — детектор `canary`: маркер самопроверяемый, поэтому любой маркер продукта находится без настройки.
- **`judge.llm`** — если цель называет провайдера с признаком `on_premise` и модель (ADR-0030). Вызов — тем же движком `internal/detect/judge` (шаблон, разделители с `nonce`, строгий разбор, проверка текста детектором `injection.heuristic` до отправки); оценщик получает только ответ цели, без промпта атаки. Ответ, в котором найдена инъекция, оценщику не отправляется (`injection`): атака могла заставить модель обращаться к оценщику через транспорт только к частной сети с проверкой при каждом соединении. Без оценщика условие `judge` не выполняется и не опровергается.

### 7. Результаты и содержимое
- Таблицы `redteam_runs` (цель, кто и когда запустил, состояние, причина, счётчики по итогам, префикс и хеш тестового ключа) и `redteam_results` (сценарий, язык, строка матрицы, категория, итог, номер шага, сработавшие условия, находки без позиций, ID событий шлюза, код HTTP, длительность, код ошибки).
- Содержимое по ТЗ 5.5. Цель `gateway`: пример — само событие шлюза, его содержимое хранится по режиму хранения приложения и открывается как обычно (`events.content.read`, причина, аудит). Цель `endpoint`: режим `none` (по умолчанию) — только вердикты; `masked` — для итога `succeeded` выдержка ответа до 1 КиБ, в которой находки `pii` и `secrets` заменены категорией. Режима `full` нет. Выдержку показывает отчёт 5.33 с правом `events.content.read`.
- Промпты атак в результатах не хранятся (они в базе сценариев); ответ целиком не хранится нигде; в технические журналы текст ответов, значения заголовков и тестовый ключ не пишутся.
- Результаты хранятся 90 дней (как содержимое событий по умолчанию), запуски — 12 месяцев.

### 8. Права, аудит, поверхность атаки
- Права (раздел «Тестирование устойчивости»):
  - `redteam.read` — цели (без секретов), сценарии (метаданные), запуски и результаты;
  - `redteam.targets.manage` — цели; признак `security` (адрес, на который продукт отправит атаки), токену API недоступно;
  - `redteam.run` — запуск и отмена; без признака `security`: из CI заказчика запускают токеном (5.33), а цели и сценарии токен не меняет;
  - `redteam.scenarios.load` — загрузка и возврат базы сценариев.
  Администратор безопасности — все; администратор системы — `redteam.read` и `redteam.scenarios.load`; аналитик — `redteam.read`; аудитор — `redteam.read`.
- Аудит: `redteam.target_created`, `redteam.target_updated`, `redteam.target_deleted` (без секретов; у `endpoint` — адрес и основание), `redteam.run_started` (цель, число сценариев, отпечаток ключа запуска не пишется), `redteam.run_finished` (итоги, причина), `redteam.run_cancelled`; база сценариев — общие `service_db.*`.
- Поверхность атаки: исходящие вызовы сервера (к шлюзу и к адресам целей `endpoint`, к оценщику), эндпоинты `/api/v1/redteam/*`, флаги `-redteam-gateway-url` и `-redteam-gateway-ca`, формат базы сценариев, поле ключа пакета `test` и поле события `test` (`docs/cert/attack-surface.md`).
- Угрозы (`docs/cert/threat-model.md`): продукт как инструмент атаки на чужие адреса (право безопасности, сессия, повторная проверка, основание в аудите, пределы частоты, сценарии только из подписанной базы); SSRF (раздел 3); отравление базы сценариев (подпись производителя, отзыв, откат на проверенную версию); подавление оповещений тестовыми событиями (признак даёт только ключ запуска, ключ живёт до конца запуска).

## Альтернативы
- **Исполнитель в шлюзе.** Шлюз уже сетевой клиент, но тогда запросы к приложению продукта шли бы мимо его же защиты, а у шлюза нет хранения результатов и прав пользователей. Отклонено.
- **Отдельный процесс-исполнитель.** Изоляция сетевого клиента сильнее, но протокол, развёртывание и мониторинг ещё одного процесса ради HTTP-клиента без недоверенного двоичного разбора избыточны. Отклонено (как для оценщика `judge.llm`, ADR-0030).
- **Постоянный тестовый ключ приложения в БД.** Не нужно ждать доставки пакета, но открытый ключ пришлось бы хранить зашифрованным (ротация ключа данных, резервная копия), а долгоживущий ключ с признаком `test` — способ подавлять оповещения. Ключ запуска живёт минуты.
- **Помечать тестовые события на сервере по ID из `X-AISec-Event-Id`.** Без изменения шлюза, но события приходят пакетами независимо от ответа: оповещение могло подняться раньше, чем исполнитель запомнит ID. Отклонено.
- **Тестовые события поднимают оповещения как обычно.** Заодно проверяются правила, но каждое учение будит дежурного и создаёт инциденты, которые закрывают вручную. Отклонено; проверка правил — самотест и e2e.
- **Произвольные адреса без основания и повторной проверки.** Быстрее для экспресс-проверки, но продукт становится сканером чужих сервисов в руках любого с правом. Отклонено.
- **Только частные адреса для `endpoint`** (как у оценщика). Безопаснее, но экспресс-проверка публичного чат-бота до пилота (ТЗ 5.13) становится невозможной. Отклонено; риск снижают раздел 2 и пределы.
- **Хранить ответы целиком.** Удобнее для отчёта, но ответ на атаку — содержимое, часто с системным промптом и данными заказчика. Отклонено (ТЗ 5.5).
- **Генерировать атаки моделью на лету.** ТЗ 5.13 прямо требует курируемый корпус. Отклонено.

## Последствия
- Проще: строки матрицы получают проверку атаками; экспресс-проверка чат-бота до пилота — одна цель и один запуск; учения не шумят в оповещениях.
- Сложнее: сервер становится сетевым клиентом в одном пакете; пакет шлюзов меняется при каждом запуске через шлюз (ключ запуска); шлюз прежнего выпуска отвергнет пакет с полем ключа `test` — шлюзы обновляются раньше сервера (как в F1c).
- Остаточные риски: администратор безопасности может направить атаки на адрес без права на тестирование (снижают основание в аудите и пределы); оценка детекторами и `contains` даёт ложные `defended` для атак, успех которых виден только по смыслу (их закрывает `judge`); тестовые события учитываются в агрегатах дашбордов и в реестре ИИ до 5.34.
- Затронуто: `internal/redteam` (новый), `internal/servicedb/kinds`, `internal/policy/bundle` и `build` (ключ `test`), `internal/config` и `internal/auth` (признак ключа), `internal/gateway` (поле события), `internal/events` (поле `test`), `internal/alerting` (пропуск тестовых событий), `internal/api`, `cmd/aisec-server`, миграция, `api/openapi.yaml`, `Makefile` (`NET_CLIENT_ALLOWED`), документы сертификации, руководство администратора.
- Дальше: 5.31 наполняет базу сценариев; 5.33 — расписание, `aisec-cli redteam run` с порогом и отчёт с примерами (и, при необходимости, хранимый секрет цели — отдельным решением о шифровании ключом данных); 5.34 — экраны, фильтр тестовых событий.
- Цели в резервную копию конфигурации пока не входят (после восстановления их добавляют заново: адрес и основание — решение администратора безопасности). Включение — вместе с 5.33.
- Откат: удалить цели — исполнитель ничего не отправляет; убрать путь из `NET_CLIENT_ALLOWED` и пакет вместе с миграцией (таблицы только этого модуля); поле ключа `test` без запусков в пакет не выводится.

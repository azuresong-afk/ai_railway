# ADR-0029. Инвентаризация ИИ, проверка моделей и RAG: реестр, AI-BOM, сканер моделей, манифест RAG

- Статус: принято. Направление — решения Р2, Р3 и Р4 плана этапа 5, их владелец подтвердил 30.10.2026. Уточнения (модель данных, пополнение по агрегатам, права, коды аудита, пределы) — промпт волны B этапа 5 (поток B2, задача 5.16); детали — поток B2.
- Дата: 30.10.2026
- Связанные разделы ТЗ: 5.4 (приложения, ключи, провайдеры), 5.5 (события и агрегаты), 5.11 (инвентаризация ИИ, AI-BOM), 5.12 (проверка моделей и RAG), 5.16 (DM-07 «RAG — 5», DM-27–DM-30), 8.6 (SBOM), 8.12 (ML-BOM), 16 п. 13 (документы в запросах); ADR-0024 (ML-BOM моделей продукта), ADR-0028 (служебные базы); агрегаты дашбордов — задача 3.19 этапа 3

## Контекст
ТЗ 5.11 требует реестр приложений, моделей, провайдеров и ключей, который пополняется вручную и автоматически по трафику шлюза, и выгрузку AI-BOM в CycloneDX (ML-BOM). ТЗ 5.12 добавляет сканер файлов моделей (pickle запрещён методическим документом, DM-27), проверку встроенного шаблона чата (DM-28), сверку хешей с реестром (DM-29) и целостность RAG (DM-30, DM-07 «RAG — 5»). Код этих частей пишется задачами 5.17–5.25; это решение задаёт их общую модель, чтобы реестр (5.17) не пришлось переделывать под сканер (5.19–5.22) и RAG (5.24–5.25).

Что уже есть к началу этапа 5:
- приложения, ключи приложений и провайдеры хранятся на сервере (миграция 0014, ТЗ 5.4): у ключа — префикс, срок, отзыв, хеш; у провайдера — тип, адрес, признак «внешний», зашифрованные учётные данные;
- в событиях есть приложение, провайдер и модель, но нет ключа приложения (ключ известен шлюзу, в событие не пишется);
- почасовые агрегаты дашбордов `dash_req_hour` (миграция 0037) — приложение, провайдер, модель, действие, режим и счётчики, без содержимого; пополняются в транзакции приёма событий и досчитываются по таблице `events`;
- свой кодировщик CycloneDX 1.6 в `tools/sbom` (SBOM поставки, ТЗ 8.6) — без сторонних библиотек;
- Check API шлюза с полем `source` (`user`, `rag`, `tool`, `output`), находки инъекций для `rag` (DM-07, этап 1).

Ограничения: файлы моделей — гигабайты, их нельзя принимать на сервер и разбирать там (поверхность атаки, объём, ПДн в адаптерах); продукт не разбирает PDF и офисные форматы (ТЗ 16, п. 13); сеть — только явно настроенная; новые библиотеки не нужны (CycloneDX, разборщики заголовков моделей — свой код); пакет событий шлюза и формат пакета конфигурации без нужды не меняются (обновление шлюзов раньше сервера, F1c этапа 4).

## Решение

### 1. Что входит в реестр и где источник истины
Реестр ИИ (`internal/inventory`) — одна точка просмотра для инвентаризации и AI-BOM. Объекты, которые уже ведёт сервер, в нём не копируются:
- **приложения** — из `applications` (slug, название, среда, подразделение, провайдер, разрешённые модели, архив);
- **ключи приложений** — из `app_keys`: префикс, название, срок, состояние (действует, истёк, отозван); хеш и секрет не показываются;
- **провайдеры** — из `providers`: slug, название, тип, признак «внешний», заданы ли учётные данные и когда (сами учётные данные не читаются).

Свои данные реестра — то, чего на сервере ещё нет:
- **модель** — запись `inventory_models`: вид, провайдер, имя, версия, название для людей, описание, ответственный, происхождение, первое и последнее появление в трафике, состояние;
  - вид `provider` — модель, которую приложения получают через провайдера продукта (имя — как в событиях, например `GigaChat-Pro`);
  - вид `customer` — модель заказчика (веса у заказчика): дообученная, открытая, размещённая на своих серверах; провайдер необязателен — если модель обслуживает провайдер продукта (например, vLLM в контуре), запись связывается с трафиком по паре «провайдер, имя»;
  - пара «провайдер, имя» уникальна в организации; у модели заказчика без провайдера провайдер — пустая строка;
  - происхождение: `traffic` (добавлена задачей пополнения) или `manual` (вручную); ручная правка записи из трафика происхождение не меняет;
  - состояние: `active`; задача 5.22 добавляет `blocked` (запрет использования, п. 4);
- **файлы модели** — `inventory_model_files`: относительный путь, размер, роль (`weights`, `adapter`, `tokenizer`, `config`, `other`), хеш SHA-256 (алгоритм хранится рядом). Файлы бывают у модели любого вида, но смысл имеют у модели заказчика: это эталон для сверки сканером (DM-29). Веса, их фрагменты и содержимое файлов в реестр не попадают;
- **использование** — `inventory_usage`: тройка «приложение, провайдер, модель» с первым и последним часом, когда она встречалась в трафике. Счётчиков запросов здесь нет: они есть в дашбордах, а повторное чтение агрегатов должно оставлять реестр тем же (п. 2);
- **отчёт сканера** — `inventory_scan_reports` (задача 5.21): модель, узел (имя хоста из отчёта), время, версия сканера, по каждому файлу — путь, размер, хеш, формат, находки; шаблон чата и итог его проверки; итог сверки с реестром. Хранится не больше 20 последних отчётов на модель.

Хеш файлов модели — SHA-256 в обоих криптопрофилях: это идентификатор для сравнения с хешами издателя (каталоги моделей публикуют SHA-256) и для AI-BOM, где алгоритм выбирается из списка CycloneDX. Хеш считает `aisec-cli` через `internal/crypto`. Если для профиля `gost` понадобится второй хеш, он добавляется на этапе 6 рядом (поле алгоритма уже есть).

### 2. Пополнение по трафику — из агрегатов, без изменения шлюза
- Задача сервера раз в 10 минут читает `dash_req_hour` по организации за окно от сохранённой отметки (час последнего запуска) минус 7 суток и час: сервер принимает события до 7 суток назад (`events.MaxEventAge`), и строки прошлых часов появляются, пока шлюз досылает накопленное; при первом запуске — всю таблицу. Окно — сотни строк на час, чтение раз в 10 минут дешёвое. Берутся строки с непустыми провайдером и моделью (события Check API модели не имеют).
- Чтение — только `SELECT` из таблицы агрегатов, схема агрегатов и `internal/events` не меняются. Готовые функции `internal/events` (дашборды) не подходят: они дают одно измерение и не больше 50 строк «топ», а реестру нужна полная тройка.
- Для каждой тройки: запись использования создаётся или расширяется (`first_seen = LEAST`, `last_seen = GREATEST`); для пары «провайдер, модель» без записи модели создаётся модель вида `provider` с происхождением `traffic`. Повтор окна ничего не меняет — задача идемпотентна.
- Ключ приложения в событиях отсутствует, и новое поле в пакет событий шлюза ради реестра не добавляется: ключи показываются по данным сервера (п. 1), без времени последнего использования. Если пилот попросит «последнее использование ключа», это отдельное изменение пакета событий со своим ADR.
- Пределы на организацию: 5 000 моделей, 20 000 записей использования. Сверх предела новые записи не создаются (существующие обновляются), число пропущенных и признак «предел достигнут» сохраняются в состоянии задачи и показываются в `GET /api/v1/inventory`; в технический журнал — одно предупреждение за запуск.
- Аудит: один запуск, добавивший записи, пишет одну запись `inventory.discovered` от имени системы — число новых моделей и связей и до 20 пар «провайдер/модель». Запуск без новых записей аудит не пишет.
- Удалённая администратором модель из трафика появится снова, если её продолжают вызывать: реестр отражает фактическое использование. Чтобы модель перестала использоваться, её убирают из разрешённых моделей приложения (ТЗ 5.4) или запрещают (п. 4).

### 3. AI-BOM — CycloneDX 1.6 своим кодировщиком (задача 5.18)
- Структуры и сериализация CycloneDX 1.6 из `tools/sbom` выносятся в `internal/cyclonedx` (без зависимостей от `tools/`); `tools/sbom` и сервер пользуются одним кодировщиком. Библиотеки CycloneDX не нужны.
- Состав документа:
  - `metadata.component` — установка продукта (тип `application`, версия выпуска);
  - приложения — компоненты `application` с зависимостями от моделей и сервисов провайдеров (по `inventory_usage` и разрешённым моделям);
  - модели — компоненты `machine-learning-model` (имя, версия, издатель — ответственный, свойства `aisec:kind`, `aisec:origin`, `aisec:status`); файлы модели — вложенные компоненты `file` с хешем `SHA-256`;
  - провайдеры — `services` (имя, тип, `trustZone` — `external` или `internal` по признаку «внешний»; адрес — без учётных данных, только схема, хост и порт);
  - коллекции RAG (после 5.24) — компоненты `data` с хешем манифеста и числом документов.
- Ключи приложений в AI-BOM не входят (это не компоненты; префиксы ключей — внутренние сведения установки).
- Выгрузка — `GET /api/v1/inventory/aibom` с правом `inventory.export`, запись `data.export` (DM-41) с видом `aibom` и числом компонентов. Документ проверяется тестом по схеме CycloneDX 1.6 из `testdata` (как SBOM поставки).

### 4. Сканер моделей — `aisec-cli models scan` на узле заказчика (задачи 5.19–5.22)
- Сканер работает там, где лежат файлы: `aisec-cli models scan -server URL -token-file ФАЙЛ -model ID КАТАЛОГ|ФАЙЛ`. Файлы читаются потоково; в память — только заголовки до предела формата; веса и их фрагменты на сервер не передаются.
- Формат определяется по сигнатуре, а не по расширению:
  - **pickle и форматы на его основе запрещены без исключений** (DM-27): поток pickle (опкод `PROTO`, протоколы 0–5 по эвристике первых опкодов), архив PyTorch (ZIP с `*/data.pkl`), `.bin`/`.pt`/`.pth`/`.ckpt` PyTorch, joblib, `.npy`/`.npz` с типом `object`. Находка `pickle` — запрет, переопределить её нельзя ни флагом, ни настройкой;
  - safetensors — заголовок JSON до 100 МиБ, смещения тензоров внутри файла и без перекрытий;
  - GGUF — версия, число тензоров и метаданных с пределами, строки до 1 МиБ, `tokenizer.chat_template` — до 64 КиБ;
  - ONNX — минимальный разбор protobuf: домены операторов (`ai.onnx`, `ai.onnx.ml`, прочие — находка), внешние данные — только внутри каталога модели (без `..`, абсолютных путей и ссылок);
  - `tokenizer_config.json` — `chat_template` до 64 КиБ;
  - неизвестный формат — находка `unknown_format` (оповещение, не запрет).
  - Каждый разборщик — со своим fuzz-тестом; ZIP читается только по центральному каталогу с пределом числа записей.
- Отчёт (JSON до 4 МиБ, до 10 000 файлов, до 100 находок на файл) отправляется `POST /api/v1/inventory/models/{id}/scan-reports` токеном API с правом `models.report`. Шаблон чата передаётся в отчёте текстом (это метаданные модели, не веса и не данные пользователей): сервер проверяет его детекторами инъекций и сравнивает с эталоном семейства — служебной базой по ADR-0028 (DM-28, задача 5.21). Так детекторы и эталоны остаются в одном месте, а сканер — небольшой командой без политик.
- Сверка хешей (DM-29, задача 5.22): `aisec-cli models verify -model ID` запрашивает у сервера эталонные хеши файлов модели (тот же токен), считает хеши на узле и отправляет отчёт. Несовпадение, лишний или пропавший файл весов или адаптера — оповещение `models.hash_mismatch` и состояние модели `blocked`; модель в состоянии `blocked` исключается из пакета шлюза — приложения получают отказ `model_not_allowed`. Запуск по расписанию — средствами заказчика (cron, systemd timer), продукт расписание на чужом узле не держит.
- Снятие `blocked` — функция безопасности (ослабление, DM-40): право `inventory.unblock`, повторная проверка паролем или кодом, запись аудита.

### 5. RAG — манифест и проверка до индексации (задачи 5.24–5.25)
- Продукт не индексирует и не разбирает документы (ТЗ 16, п. 13): текст извлекает индексатор заказчика, продукт проверяет этот текст и хеши.
- **Проверка до индексации** — пакетный вызов Check API шлюза (ключ приложения, `source: rag`, этап `pre_index`): до 100 текстов в вызове, каждый до предела Check API; в ответе по каждому тексту — решение, и для текста с инъекцией (DM-07) — `exclude` («исключить из индекса»). Решение по политике приложения; события — как у Check API, содержимое — по режиму хранения.
- **Манифест коллекции** — `PUT /api/v1/rag/collections/{slug}/manifest` (право `rag.manage`, доступно токену — его отправляет индексатор): список документов `{id, sha256, size}`, до 100 000 документов, тело до 16 МиБ, ID документа — до 512 байт без управляющих символов. Сервер хранит текущую и предыдущую версию манифеста и разницу.
- Появившийся вне прошлой версии, изменённый или пропавший документ — оповещение `rag.document_changed` (DM-30) с числом и ID документов (без содержимого). Документ с решением `exclude` отмечается в манифесте; индексатор не должен его индексировать.
- ICAP с антивирусом заказчика — не на этапе 5 (Р10).

### 6. Права
Имена — из двух-трёх частей (`internal/auth/permissions.go`):

| Право | Что даёт | Безопасность | Токену | Роли |
|---|---|---|---|---|
| `inventory.read` | реестр: приложения, ключи (без секретов), провайдеры, модели, файлы, использование, отчёты сканера | нет | да | все, кроме владельца приложения; аудитор — как «.read» |
| `inventory.manage` | ручная модель, изменение, удаление | нет | да | администратор системы, администратор безопасности |
| `inventory.export` | выгрузка AI-BOM (5.18) | нет | да | администраторы, аудитор не получает (не «.read») |
| `inventory.unblock` | снятие запрета модели (5.22) | да | нет | администратор безопасности |
| `models.report` | отправка отчёта сканера и чтение эталонных хешей своей модели (5.21, 5.22) | нет | да | администраторы; на практике — отдельный токен узла с моделями |
| `rag.read` / `rag.manage` | манифесты коллекций (5.24) | нет | да | администраторы, аналитик — `rag.read` |

`models.report` — не право безопасности: отчёт не ослабляет защиту, сервер сам решает о запрете по его содержанию. Право не даёт ни чтения реестра, ни изменения записей. В задаче 5.17 в каталог прав добавляются только `inventory.read` и `inventory.manage`; остальные — задачами, где появляются их эндпоинты.

### 7. Аудит
- `inventory.model_created`, `inventory.model_updated` (изменённые поля, число файлов до и после), `inventory.model_deleted` — каждое изменение реестра, той же транзакцией (РСБ.1); хеши файлов в аудит не пишутся (только число);
- `inventory.discovered` — пополнение по трафику (п. 2), от имени системы;
- последующие задачи: `models.scan_reported` (5.21), `models.hash_mismatch` и `models.blocked`, `models.unblocked` (5.22), `rag.manifest_loaded` и `rag.document_changed` (5.24), `data.export` с видом `aibom` (5.18).

### 8. Пределы входа ручной записи (5.17)
Тело до 256 КиБ, строгий разбор JSON (неизвестные поля — отказ); имя модели — 1–256 символов без управляющих (как поле `model` в событиях), провайдер — slug провайдера организации или пусто (только у `customer`), версия — до 128, название и ответственный — до 200, описание — до 2 000 символов; файлов — до 256, путь — 1–512 байт, относительный, через `/`, без `..`, `.`, пустых частей, `\` и управляющих символов, пути не повторяются; размер — от 0 до 2^50 байт; хеш — 64 шестнадцатеричных символа в нижнем регистре. Разбор входа — с fuzz-тестом.

### 9. Поверхность атаки
В `docs/cert/attack-surface.md` попадают: эндпоинты `/api/v1/inventory…` (5.17), `/api/v1/inventory/aibom` (5.18), отчёт сканера и эталонные хеши (5.21–5.22), `/api/v1/rag/…` (5.24), этап `pre_index` Check API (5.25); аргументы `aisec-cli models scan` и `models verify`, токен с правом `models.report` и его хранение на узле с моделями (файл с правами 0600); форматы файлов моделей, которые разбирает `aisec-cli` (на узле заказчика, не на сервере).

## Альтернативы
- **Копировать приложения, ключи и провайдеры в таблицы реестра.** Один запрос на всё, но два источника истины и расхождение после каждой правки приложения. Отклонено: реестр читает их таблицы.
- **Отдельные агрегаты для реестра в транзакции приёма событий.** Точное время появления и ключ, но новая работа на горячем пути приёма и новые поля в пакете шлюза (ключ). Отклонено: почасовой точности `dash_req_hour` для инвентаризации достаточно.
- **Добавить ключ приложения в событие.** Даёт «последнее использование ключа», но меняет пакет событий (шлюзы раньше сервера) и раскрывает связь «ключ — пользователь» в событиях. Отложено до просьбы пилота.
- **Сканировать модели на сервере (загрузка файла).** Проще для заказчика, но сервер принимал бы гигабайты недоверенных файлов, а pickle-разборщик на сервере — сама по себе поверхность атаки. Отклонено (Р3).
- **Разрешать pickle по флагу «доверяю».** Удобно для старых моделей, но методический документ запрещает pickle, а флаг станет стандартным ответом на находку. Отклонено: модель переводится в safetensors на стороне заказчика.
- **Проверять шаблон чата в `aisec-cli`.** Шаблон не уходит с узла, но в CLI пришлось бы встроить детекторы, политику и служебную базу эталонов с её обновлением. Отклонено: шаблон — небольшие метаданные, проверяется на сервере.
- **Библиотека CycloneDX.** Готовые структуры, но новая зависимость ради сериализации, которая уже написана и проверена в `tools/sbom`. Отклонено (Р2).
- **Разбирать документы RAG самим продуктом.** Полнее проверка, но разбор PDF и офисных форматов — большой и опасный код, вне ТЗ (16, п. 13). Отклонено (Р4).

## Последствия
- Реестр работает сразу после 5.17 на имеющихся данных: модели и связи появляются по трафику без обновления шлюзов.
- Время появления модели в реестре — с точностью до часа и с задержкой до 10 минут; ключи — без времени последнего использования.
- Задачи 5.19–5.22 получают готовую модель данных (файлы с хешами, место для отчётов, состояние `blocked`); 5.22 меняет пакет конфигурации шлюза (исключение заблокированных моделей) — обновление шлюзов раньше сервера, как в F1c.
- Задача 5.18 переносит кодировщик из `tools/sbom` в `internal/cyclonedx`; `make sbom` проверяется на тот же результат.
- Документы: `security-functions.md` (инвентаризация, ТЗ 5.11), `attack-surface.md` (п. 9), `threat-model.md` (реестр, сканер, манифест), `fuzzing.md`, матрица прав, руководство администратора.
- Откат: таблицы реестра (`inventory_*`) не связаны внешними ключами с таблицами других модулей, кроме организаций; задача пополнения отключается без потери данных; удаление миграцией не затрагивает приложения, провайдеры и события.

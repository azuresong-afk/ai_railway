# ADR-0019. Поставка пилота в docker compose: образы на scratch, секреты, PostgreSQL и обновление

- Статус: принято (решение Р2 — владелец, 22.10.2026; подробности — поток A2 по поручению владельца, по общепринятой практике)
- Дата: 22.10.2026
- Связанные разделы ТЗ: 3.1, 4.2, 7.9 (ЗИ.5), ОБН.1, 8.6, 8.7, 10.4; решения Р2 этапа 3, Н34 и Н35 ревью 2.r4; ADR-0003, ADR-0007, ADR-0008, ADR-0009, ADR-0012; задачи 3.4, 3.5

## Контекст
Первые пилоты идут у коммерческих заказчиков (ТЗ 1.6). Установка на ВМ с Linux должна укладываться в час, один экземпляр шлюза (ТЗ 4.2). Ограничения:
- ЗИ.5: каждый компонент работает от отдельного непривилегированного пользователя с минимальными правами. Сервер и шлюз отказываются запускаться, если файлы ключей доступны группе или остальным: нужны права 0600 или 0400 и владелец — пользователь процесса.
- ОЦЛ.1–2 (ADR-0012): компоненты при запуске сверяют свой исполняемый файл с подписанным манифестом, который по умолчанию лежит в `../aisec-manifest.json` от каталога `bin/`. Ключа производителя пока нет. Сборку с тестовым ключом поставлять нельзя (Н34), и тест `aisec_release` (Н35) не запускала ни одна цель.
- ОБН.1: обновление устанавливает только администратор, подпись проверяется до установки. В MVP достаточно документированной процедуры для docker compose.
- Никаких внешних адресов, кроме заданных администратором (провайдеры LLM). Секреты не попадают в переменные окружения, аргументы и журналы.
- Р2 (владелец, 22.10.2026): PostgreSQL по умолчанию — официальный образ в compose с точной версией и хешем, своя СУБД заказчика — по желанию. Продукт этот образ не распространяет: лицензии PostgreSQL и пакетов Alpine (GPL) — вне политики CLAUDE.md для поставки.

## Решение
1. **Три образа на `scratch`:** `aisec-server`, `aisec-gateway`, `aisec-cli` (`deploy/build/Dockerfile.release`). В каждом только `/opt/aisec/bin/<компонент>`, `/opt/aisec/aisec-manifest.json` и его подпись, владелец файлов — root, запись для остальных закрыта. Нет оболочки, пакетов ОС, корневых сертификатов, `tzdata`. Пояса встроены в сервер (`time/tzdata`, Н43), корни провайдеров приходят в пакете конфигурации (`ca_pem`). `USER 65534:65534`, `EXPOSE` только своих портов: 8444 и 8445 у сервера, 8443 у шлюза. В `aisec-cli` лежит весь выпуск: `aisec-cli verify` сверяет все файлы манифеста. Бинарники статические (`CGO_ENABLED=0`). Метка `ru.aisec.build-kind` — `release` или `test`, плюс стандартные метки OCI с версией.
2. **Сборка.** `make release-dir` собирает бинарники в `build/release/bin`, подписывает манифест и проверяет его через `aisec-cli verify`. Это происходит **до** `docker build`, поэтому закрытый ключ производителя не попадает в контекст сборки. `make images-docker` запускает `docker build` из `build/release` без сети, без `RUN`, без внешних базовых образов и без attestations, затем `docker save` в `build/images/*.tar`. `SOURCE_DATE_EPOCH` — время последнего коммита. `make images-sbom` пишет SBOM CycloneDX 1.6 на каждый образ: тип `container`, бинарники образа, манифест и подпись (`tools/sbom -image`). `make images-verify` — проверка из п. 8.
   - `make images` работает **только** с `RELEASE=1` и `MANIFEST_KEY` (Н34). Перед сборкой запускается `make release-test`: `go test -tags aisec_release ./internal/integrity/` (Н35). Ещё нужна консоль в `web/dist`. С `RELEASE=1` цель `release-test` входит и в `make check`.
   - Ключа производителя пока нет. Поэтому `make images-test` собирает те же образы с тестовым ключом под отдельным именем `aisec-test/…:ВЕРСИЯ-test` с меткой `test`. Сервер в такой сборке поднимает условие «Сборка не для поставки» (`test_build`). Эти образы — только для CI и стендов, **заказчику не передаются**. В CI их собирает задание `images` (`make images-test-docker`: Go-шаги идут в сборочном образе, `docker build` — на хосте).
3. **Запуск** (`deploy/compose/pilot/compose.yaml`). Сервисы: `postgres` (профиль `db`), `aisec-server`, `aisec-gateway` и `aisec-cli` (профиль `tools`, только `docker compose run`). Каждый сервис работает от своего системного пользователя хоста: `aisec` — сервер и `aisec-cli`, `aisec-gw` — шлюз, `aisec-db` — PostgreSQL. Пользователей создаёт `prepare-host.sh`, compose берёт `user:` из обязательных переменных `${…:?}`, поэтому пустое значение не превращается в root. `USER 65534` в образе остаётся для запуска вне compose (`verify-release.sh`). У всех сервисов `read_only: true`, `cap_drop: [ALL]`, `no-new-privileges:true`, `pids_limit`, `mem_limit`, журнал docker с ротацией (`local`, 5 × 20 МБ). `tmpfs` есть только у PostgreSQL и `aisec-cli`.
4. **Секреты и ключи — файлы.** Используются `secrets` compose: в режиме без swarm это монтирование файла хоста. Файлы лежат в `${AISEC_DATA_DIR}/secrets`, каталог 0700 root, владелец каждого файла — пользователь сервиса, права 0600 или 0400, у открытых — 0644. Сертификаты TLS кладёт администратор. Пароли ролей БД генерирует `prepare-host.sh` из `/dev/urandom` и нигде не выводит. Сервер и `aisec-cli` читают пароль из passfile pgx (`passfile=` в строке подключения), поэтому пароля нет ни в окружении, ни в URL, ни в `docker inspect`. PostgreSQL получает копии паролей для начальной настройки. Каталог ключей `aisec-cli init` подключается томом: с записью — в `aisec-cli`, только для чтения — в сервер. Шлюз получает лишь `bundle-signing.pub` отдельным секретом. Состояние шлюза (`reg/`, `state/`) и копии (`backups/`) — каталоги 0700 своих пользователей. Каждый такой каталог лежит в каталоге root (`gateway/` — root, 0755) и монтируется отдельно: сервис не может подменить его символьной ссылкой, а `prepare-host.sh` при повторном запуске отказывается идти по ссылке.
5. **Сети и порты.** Сети `db` и `control` внутренние (`internal: true`), сети `console` и `gateway` — мосты для опубликованных портов. Выход наружу нужен только шлюзу, к провайдерам LLM. Сервер подключён к мосту `console` ради публикации порта консоли, поэтому сеть Docker его исходящие соединения не ограничивает: их запрещает код (у сервера нет сетевого клиента, кроме SMTP, syslog и webhook из настроек администратора; repocheck, ЗИ.2). Руководство рекомендует закрыть исходящие соединения сервера правилом в цепочке `DOCKER-USER` межсетевого экрана хоста. Консоль 8444 и шлюз 8443 по умолчанию публикуются на `127.0.0.1`, адрес задаётся в `.env`. Внутренний порт 8445 не публикуется: шлюз обращается к серверу по сети `control` по псевдониму, равному имени из сертификата консоли (`AISEC_CONSOLE_HOST`), поэтому второй сертификат не нужен. Порт PostgreSQL не публикуется. Связь сервера с PostgreSQL идёт без TLS внутри внутренней сети одного хоста. Для своей СУБД заказчика строка подключения задаётся с `sslmode=verify-full`.
6. **PostgreSQL** — официальный `postgres:17.11-alpine3.24@sha256:eee6c6e1…411fb`. Версия 17 совпадает со стендом разработки и CI, которые закреплены на тот же digest. `AISEC_POSTGRES_IMAGE` меняет только реестр: digest от реестра не зависит. В реестре компонентов это `scope: external`: в поставку и SBOM продукта он не входит. `make licenses` проверяет `image:` в compose и workflow наравне с `FROM` в Dockerfile. Роли создаёт `initdb/10-aisec-roles.sql` при первом запуске. `aisec_owner` — владелец БД: миграции, `init`, аварийные команды, член `aisec_audit_archiver` для архивации (ADR-0008). `aisec_server` — вход сервера, член `aisec_app`, таблицы ему не принадлежат: так требует руководство администратора. У суперпользователя `postgres` свой пароль, аутентификация везде `scram-sha-256`. Своя СУБД: `COMPOSE_PROFILES=` и строки `AISEC_SERVER_DB_URL`, `AISEC_OWNER_DB_URL`.
7. **Обновление (ОБН.1, MVP).** Выпуск поставляется каталогом: `aisec-manifest.json`, `.sig`, `bin/`, `images/*.tar`, SBOM. Скрипт `verify-release.sh` проверяет его в два шага, ничего не запуская из нового выпуска:
   - `aisec-cli` **установленной** версии (ключ производителя из действующей установки) проверяет подпись и все файлы нового выпуска командой `verify -release` (решение владельца 22.10.2026 по A2-В1). Скрипт перед этим копирует выпуск во временный каталог и дальше работает только с копией; манифест и подпись по ссылке не читаются. Выпуск, собранный раньше установленного, отвергается: откат делается на прежние образы, которые уже загружены, а не через `verify-release.sh`. Себя и свои встроенные миграции она с новым манифестом не сверяет: версия вшита в бинарник, и такая сверка отвергала бы любой другой выпуск; встроенные наборы нового выпуска входят в его бинарники, а те сверяются целиком;
   - до загрузки проверяется состав каждого архива: только метаданные OCI и блобы, ровно один образ с тегом новой версии из проверенного манифеста. Тег установленной версии архив перезаписать не может: новая версия обязана отличаться;
   - после загрузки (`docker load`) сверяются настройки образа (пользователь, точка входа, порты, окружение, тома) и полный список файлов без символьных ссылок. Затем бинарники, манифест и подпись внутри каждого образа побайтно сравниваются с уже проверенными файлами. При любом расхождении загруженные образы удаляются.
   Только после этого администратор меняет `AISEC_VERSION` в `.env` и выполняет `docker compose run --rm aisec-cli migrate` и `docker compose up -d`. Откат: прежняя `AISEC_VERSION` и `aisec-cli verify -accept-rollback` (В20). Обновление может выполнить только тот, у кого есть права root или группы `docker` на хосте, то есть администратор системы. При первой установке доверенной версии ещё нет. Тогда доверие держится на канале поставки, а сверка отпечатка ключа производителя — вопрос ключа производителя (Н34, «Открытые вопросы» плана этапа 3).
8. **Проверка поставки (ЗИ.5)** — `tools/imagecheck`.
   - `image` разбирает архив `docker save` без запуска контейнера: хеш каждого blob и `diff_id` слоёв, пользователь `65534:65534`, ровно свои порты, точка входа, отсутствие томов и переменных, кроме `PATH`, и метка вида сборки. Список файлов всех слоёв должен содержать только разрешённые файлы: никакой оболочки, пакетного менеджера, whiteout, ссылок, setuid, расширенных атрибутов (capabilities), записи для остальных и владельца, кроме root. Разбор ограничен: распакованный слой не больше 1 ГиБ, содержимое бинарников и манифеста — не больше 512 МиБ на образ. Бинарники статические. Бинарники и манифест побайтно совпадают с `build/release`.
   - `compose` проверяет исходный compose-файл до подстановки переменных. Разбор строгий: поле, которого нет в белом списке (`extends`, `include`, `volumes_from`, `sysctls`, `external` и т. п.), — ошибка. Только чтение, `security_opt` ровно `no-new-privileges:true`, нет capabilities и повышения привилегий, пользователь из обязательных переменных, нет `privileged`, `network_mode`, `pid`, `ipc`, `devices` и `build`. Публикуются только свои порты, с адресом по умолчанию `127.0.0.1`. Тома — только подкаталоги `${AISEC_DATA_DIR}`, кроме `secrets/`, или `./…:ro`. Секреты передаются только файлами, и каждому сервису — только свои, нет внешних адресов и паролей в окружении. Healthcheck только локальный. Сервисам без права на выход наружу доступны только внутренние сети. Сторонние образы закреплены по digest, свои — `${AISEC_IMAGE_REPO:-aisec}/<сервис>:${AISEC_VERSION:?}`.
   Проверка compose-файла идёт в `make test`, проверка образов — в `make images-verify` и в CI.
9. **Healthcheck** есть только у PostgreSQL (`pg_isready` на 127.0.0.1). У сервера и шлюза его нет: в `scratch` нет ни оболочки, ни сетевого клиента, а у бинарников нет команды самопроверки. Состояние видно в «Состоянии системы», перезапуск обеспечивает `restart: unless-stopped`. Команда `-healthcheck` в бинарниках — отдельная задача: она меняет `cmd/`.

## Альтернативы
- **distroless/static.** Отклонено: это ещё один сторонний образ из внешнего реестра, в нём `/etc/passwd`, корневые сертификаты и `tzdata`, которые продукту не нужны. `scratch` не добавляет в SBOM ни одного пакета ОС.
- **Свой образ PostgreSQL в поставке.** Отклонено решением Р2: продукт распространял бы PostgreSQL и пакеты Alpine или Debian под GPL и отвечал бы за их обновления.
- **Запуск всех сервисов от 65534 с ключами, доступными группе.** Отклонено: это ослабляет проверку прав ключей (0600) и даёт всем сервисам одного общего пользователя `nobody`.
- **Секреты в переменных окружения** (`POSTGRES_PASSWORD`, пароль в `AISEC_DATABASE_URL`). Отклонено: их видно в `docker inspect` и `/proc/<pid>/environ`.
- **Сборка бинарников внутри `docker build`** (стадия на образе golang). Отклонено: для подписи манифеста в контекст сборки пришлось бы передать ключ производителя. Воспроизводимость сборки на хосте даёт сборочный образ (`make check-docker`, ADR-0003).
- **Один образ на все компоненты.** Отклонено: в каждом контейнере лежали бы чужие бинарники, а план (Р2) называет три образа.
- **Подпись образов (cosign, notation).** Отложено до этапа 6 (ОБН.1–3): это новый инструмент и зависимость. Для MVP достаточно подписанного манифеста и побайтной сверки содержимого образа с ним.
- **Kubernetes и Helm.** Вне объёма пилота: ТЗ 4.2 предполагает один экземпляр.

## Последствия
- Новые файлы: `deploy/build/Dockerfile.release`, `deploy/compose/pilot/` (`compose.yaml`, `.env.example`, `initdb/`, `prepare-host.sh`, `verify-release.sh`, `README.md`), `tools/imagecheck/`, `tools/sbom/image.go`. Цели `make`: `release-dir`, `release-test`, `images`, `images-test`, `images-docker`, `images-sbom`, `images-verify`, `images-test-docker`. Новый `scope: external` в `docs/cert/components.yaml`. `make licenses` теперь проверяет образы в compose и workflow. Стенд разработки и CI переведены на тот же закреплённый образ PostgreSQL. Задание `images` в CI.
- Документы: `docs/cert/attack-surface.md` (порты, тома, переменные compose, скрипты), `docs/cert/security-functions.md` (ЗИ.5, ОБН.1), черновик `docs/user/install-pilot.md` (полный текст — задача 3.31).
- Ограничения:
  - образы для пилота возможны только после появления ключа производителя;
  - выпускная сборка требует сборки консоли (`make web-build`);
  - нужны Docker Engine с правами root (rootless не поддерживается: владельцы файлов секретов — пользователи хоста) и Compose не ниже 2.20 (`depends_on.required`);
  - digest образа не воспроизводится побайтно: время файлов в слоях не переписывается. Сверяется содержимое — бинарники и манифест.
- Ротация ключа подписи пакетов (ADR-0018, п. 4) не требует второго секрета: шлюз узнаёт новый ключ из подписанных заявлений в пакете. Якорь шлюза (`-bundle-pub`) — отдельный секрет `secrets/gateway-bundle-anchor.pub`, копия `keys/bundle-signing.pub` после `init`: при компрометации ключа подписи заменяется только он, якорь сервера в `keys/` не трогается (3В6 ревью 3.r1). `tools/imagecheck compose` сверяет точный список томов каждого сервиса (источник, цель, `ro`/`rw`) и файл каждого секрета (3В8).
- `make release-dir` с `RELEASE=1` проверяет чистоту дерева и тег на HEAD по git, а не по `VERSION` (3Н3).
- Откат решения: удалить `deploy/compose/pilot/`, `Dockerfile.release`, цели `images*` и `tools/imagecheck`. Продукт от них не зависит.

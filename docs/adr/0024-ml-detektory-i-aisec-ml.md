# ADR-0024. ML-детекторы и процесс `aisec-ml`

- Статус: принято. Направление — решения Р3 и Р4 плана этапа 4, их владелец подтвердил 27.10.2026. Детали выбрал поток C3 (задача 4.18). Зависимости (раздел «Зависимости») владелец согласовал 27.10.2026: ONNX Runtime 1.31.0 своей сборкой из исходников без телеметрии, `onnxruntime_go` v1.38.0, Eigen (MPL-2.0) и Boost.Mp11 (BSL-1.0) внутри ORT.
- Дата: 27.10.2026
- Связанные разделы ТЗ: 4.1 (состав, изоляция компонентов), 5.2 (детекторы), 5.16 (DM-01, DM-09, DM-18, DM-31 — части «ML — 4», «NER — 4»), 8.12 (ML-BOM), 10 (криптопрофиль), 14 (критерий «лучше эвристик»); ADR-0012 (манифест целостности), ADR-0019 (поставка пилота), ADR-0022 (ключ производителя); CLAUDE.md: cgo — только по ADR, зависимости — с согласия владельца, никакой телеметрии.

## Контекст
Этап 4 добавляет ML-детекторы: `injection.ml` (DM-01), `toxicity.ml` (DM-18), `pii.ner` (DM-09, DM-31). Сами детекторы, корпуса и выбор моделей — задачи 4.19 и 4.20. Этот ADR задаёт то, на чём они стоят: где выполняется модель, как шлюз её вызывает, как проверяются модели и как всё это собирается и поставляется.

Ограничения:
- Шлюз и сервер собираются без cgo (`CGO_ENABLED=0`), образы — на `scratch`. Так и остаётся.
- В Go нет движка вывода ONNX, которым можно выполнить трансформерную модель с нужной скоростью. Нужна нативная библиотека, а значит cgo и код на C++, который читает недоверенный текст.
- Ошибка в нативном коде (выход за границы, исчерпание памяти, зависание) не должна останавливать шлюз и пропуск запросов.
- Модель — исполняемое содержимое в широком смысле: подменённые веса меняют решения детектора. Подмена должна обнаруживаться до загрузки.
- Никаких внешних обращений и телеметрии.

Р3: отдельный процесс `aisec-ml` рядом со шлюзом, Unix-сокет, ONNX Runtime через cgo только в нём; при недоступности — эвристики и признак `ml_unavailable` (fail-open для ML). Модели — только ONNX, хеш и подпись весов, ML-BOM. Р4: критерий «лучше эвристик».

## Решение

### 1. Процесс и изоляция
- `aisec-ml` — отдельный процесс (`cmd/aisec-ml`) на той же машине, что и шлюз. Один `aisec-ml` обслуживает один шлюз; при нескольких шлюзах у каждого свой.
- ONNX Runtime подключается через cgo **только** в `cmd/aisec-ml` и только со сборочным тегом `aisec_onnx`. Без тега `aisec-ml` собирается без cgo и без исполнителя ONNX: такой бинарник отказывается запускаться с моделями (`исполнитель ONNX не собран`). Шлюз, сервер и `aisec-cli` cgo не используют.
- Контейнер `aisec-ml`: `network_mode: none` (нет даже петлевого интерфейса наружу), корневая ФС только для чтения, все capabilities сняты, `no-new-privileges`, непривилегированный пользователь, лимит памяти (`mem_limit`, по умолчанию 2 ГиБ) и процессов (`pids_limit`). Сокет — единственный канал.
- В процессе: переменная `ORT_DISABLE_TELEMETRY=1` выставляется до инициализации ONNX Runtime при любой сборке библиотеки (защита на случай, если в сборку попала телеметрия; основная защита — сборка без неё, раздел 8).

### 2. Сокет
- Unix-сокет в общем каталоге шлюза и `aisec-ml` (по умолчанию `/run/aisec-ml/aisec-ml.sock`). Каталог: владелец — пользователь `aisec-ml`, группа — группа шлюза, права `0750` или строже; для остальных — ничего.
- `aisec-ml` при запуске проверяет каталог: существует, не символьная ссылка, это каталог, у остальных нет прав (`perm & 0o007 == 0`). Иначе — отказ запуска. Старый файл на месте сокета удаляется, только если это сокет; иначе — отказ.
- После `Listen` сокет получает права `0660`. Окно между созданием и `chmod` безопасно: в каталог остальные войти не могут.
- Шлюз перед каждым подключением проверяет: путь — сокет (`Lstat`, не ссылка), у остальных нет прав на сокет, каталог не доступен на запись остальным. Иначе — отказ подключения, как при недоступности (`ml_unavailable`) и запись в журнал.
- TCP не используется: доступ к петлевому порту есть у любого процесса машины, а к сокету — только у владельца и группы.

### 3. Протокол кадров
Свой двоичный протокол в `internal/ml`, без gRPC, HTTP и новых зависимостей. Обе стороны разбирают недоверенный ввод: у разбора кадра со стороны сервера и клиента — свои fuzz-тесты.

- **Заголовок** — 16 байт, порядок байтов big-endian: `magic` `"AIML"` (4), версия протокола `1` (1), тип кадра (1), резерв `0` (2), номер запроса (4), длина тела (4).
- **Лимиты проверяются по заголовку, до чтения тела.** Неизвестный `magic`, версия, тип, ненулевой резерв или длина сверх лимита типа — кадр ошибки (если это сторона сервера) и закрытие соединения; тело не читается.

| Тип | Направление | Тело | Предел тела |
|---|---|---|---|
| `1` hello | шлюз → `aisec-ml` | пусто | 0 |
| `2` hello_ok | `aisec-ml` → шлюз | JSON: версия протокола, модели (ID, версия, метки, направления) | 64 КиБ |
| `3` detect | шлюз → `aisec-ml` | 1 байт длины ID модели, ID (`[a-z0-9._-]{1,64}`), затем текст UTF-8 | 256 КиБ + 65 байт |
| `4` result | `aisec-ml` → шлюз | JSON: ID и версия модели, находки (метка, оценка 0–1, байтовые позиции) | 64 КиБ |
| `5` error | `aisec-ml` → шлюз | JSON: код (`overloaded`, `unknown_model`, `too_large`, `bad_request`, `internal`) | 1 КиБ |

- Текст передаётся сырыми байтами, а не в JSON: экранирование увеличивало бы тело до шести раз и требовало бы отдельного лимита. Текст обязан быть корректным UTF-8 (иначе `bad_request`).
- JSON разбирается строго: неизвестные поля, данные после объекта, повтор ID модели, позиции вне текста или не на границе символа — ошибка. Находки проверяются ещё раз в шлюзе (`detect.ValidateFinding`).
- Один запрос на соединение одновременно; ответ несёт номер запроса, несовпадение — ошибка протокола и закрытие соединения.
- `aisec-ml`: не больше `-max-conns` соединений (по умолчанию 64, лишние закрываются сразу), срок чтения тела 5 с, простой соединения — до 60 с; одновременных выводов — не больше `-workers` (по умолчанию число процессоров); если все заняты дольше `-queue-wait` (по умолчанию 20 мс) — ответ `overloaded`.
- Текст длиннее 256 КиБ клиент режет на части по границам символов, не больше 8 частей (2 МиБ). Остаток сверх 8 частей ML не проверяет (эвристики проверяют весь текст).
- Проверка части текста (остаток сверх 8 частей или флаг `truncated` от `aisec-ml`): если в проверенной части есть находки, они возвращаются — для решения политики этого достаточно; если находок нет, детектор отвечает «недоступен», и событие получает `ml_unavailable`: снять подозрение со всего текста ML не может.

### 4. Вызов из шлюза, fail-open
- Клиент (`gateway.MLClient`, `internal/gateway/mlclient.go`: сетевые клиенты живут только в разрешённых пакетах) держит пул соединений. Каждый вызов — с контекстом детектора и собственным сроком `Timeout` (по умолчанию 80 мс; не больше срока детектора минус 5 мс — 4В22 ревью 4.r3). Свободное соединение старше 30 с (половина простоя на стороне `aisec-ml`) не берётся; если повторно использованное соединение оборвалось, вызов один раз повторяется на новом.
- Предел одновременных вызовов (`MaxInflight`, по умолчанию 16). Если он занят — вызов сразу завершается `ErrMLUnavailable`, без очереди: ML не добавляет задержку запросу при перегрузке.
- После сбоя подключения, `hello`, обрыва или ошибки протокола, а также после трёх вызовов подряд, не уложившихся в срок, клиент считает `aisec-ml` недоступным на время отсрочки (1 с, удваивается до 30 с) и в это время отвечает `ErrMLUnavailable` сразу. Отмена запроса (клиент ушёл, истёк общий срок проверки) сбоем `aisec-ml` не считается; во время отсрочки она не растёт. Переходы «доступен/недоступен» пишутся в журнал шлюза (без текста запроса).
- ML-детектор в реестре — обычный `detect.Detector` (`gateway.MLDetector`) с клиентом. ID вида `injection.ml`, `toxicity.ml`, `pii.ner`; категории — по меткам модели; `Version` — версия кода детектора, версия модели пишется в находку. Порог оценки — в описании детектора (4.19, 4.20). Если у загруженной модели нет метки из описания детектора или она не проверяет направление текста, детектор отвечает «недоступен» (иначе он молча ничего бы не находил).
- **Fail-open для ML.** Любой сбой ML-детектора (недоступность, срок, перегрузка, ошибка протокола) не попадает в `Failures` и не включает `fail_closed`. Решение принимает политика по находкам остальных детекторов (эвристики `injection.*`, `pii.*` и т. д.), а в событии ставится признак `decision.ml_unavailable: true`. Остальные детекторы ведут себя как раньше.
- Почему так: ML — дополнительный слой к эвристикам, а не замена. Блокировать весь трафик заказчика из-за падения вспомогательного процесса хуже, чем пропустить проверку ML; признак в событии делает пропуск видимым (оповещение по нему — правило 4.19).
- Флаг шлюза с путём к сокету и регистрация ML-детекторов в реестре шлюза и сервера — задача 4.19, вместе с первыми детекторами. До неё шлюз ML не вызывает. Тогда же признак `ml_unavailable` выводится в ответе Check API и в «песочнице» политик (4.19): в 4.18 он есть только в событии.

### 5. Пакет моделей
- Только формат ONNX. Каталог `models/` установки:
  - `aisec-models.json` — манифест пакета, формат `aisec-ml-models-v1`: версия пакета, криптопрофиль, алгоритм хеша, время, модели (ID, версия, задача, метки, направления, `max_tokens`) и их файлы (путь, роль, размер, хеш);
  - `aisec-models.json.sig` — подпись манифеста пакета;
  - на модель — ровно три файла: `model.onnx` (роль `model`), `tokenizer.json` (`tokenizer`), `mlbom.cdx.json` (`mlbom`).
- Хеш — `Hasher` профиля (`standard` — SHA-256). Подпись — `Signer`/`Verifier` профиля через `internal/crypto`, контекст `"aisec-ml-models-v1\n"` + байты манифеста (подпись манифеста выпуска нельзя выдать за подпись пакета моделей и наоборот). Ключ — **ключ производителя** (ADR-0022), проверка — встроенным ключом `integrity.EmbeddedVerifier`; в тестовой сборке — тестовым ключом репозитория, как у манифеста выпуска. Модели меняются реже служебных баз и подписываются офлайн тем же порядком, что и выпуск. Команда подписи пакета (`tools/manifest sign-models`) появится в 4.19 вместе с первой моделью.
- `aisec-ml` при запуске, **до загрузки** любой модели:
  1. читает манифест (обычный файл до 1 МиБ через `os.Root`) и подпись (до 1 КиБ), проверяет подпись до разбора;
  2. разбирает манифест строго (лимиты: до 16 моделей, пути `<id>/<имя>` без `..` и ссылок, модель до 2 ГиБ, токенизатор до 32 МиБ, ML-BOM до 4 МиБ, все три роли у каждой модели; `FuzzParseModelManifest`);
  3. читает каждый файл в память (обычный файл, размер совпадает с заявленным, сверх — не дочитывается), считает хеш и сравнивает за постоянное время;
  4. проверяет ML-BOM: CycloneDX JSON, есть компонент `machine-learning-model` с тем же именем и версией, что у модели;
  5. передаёт исполнителю **те же байты из памяти** (без повторного чтения с диска — нет окна подмены между проверкой и загрузкой).
  Любое несовпадение — отказ запуска с кодом выхода 1 и записью в журнал (какая модель и какой файл, без содержимого). Частичной загрузки нет: пакет принимается целиком или не принимается.
- **ML-BOM (ТЗ 8.12)** — CycloneDX 1.6, файл на модель: происхождение весов, лицензия, набор данных обучения и дообучения, метрики, хеш. Входит в пакет и в SBOM поставки. Генерацию по карточке модели добавят 4.19 и 4.20.
- Пакет моделей входит и в манифест выпуска (вид `model`, каталог `models/`), поэтому `aisec-cli verify` и периодическая проверка целостности видят подмену так же, как подмену бинарника.

### 6. Исполнитель и память
- Интерфейс исполнителя в `cmd/aisec-ml`: загрузить модель из байтов, выполнить на тексте, освободить. Реализации: ONNX Runtime (тег `aisec_onnx`) и тестовый исполнитель без ONNX (`internal/ml/mltest`, только для тестов).
- Токенизатор — свой, на Go, в `aisec-ml`: разбор `tokenizer.json` (WordPiece или Unigram — по модели в 4.19) с лимитами и fuzz-тестом. Rust-библиотеку `tokenizers` не берём: ещё одна нативная зависимость.
- Против исчерпания памяти: лимит контейнера; текст до 256 КиБ на запрос; окно модели — `max_tokens` (не больше 512), не больше 16 окон на запрос (остаток — флаг `truncated` в ответе, шлюз ставит `ml_unavailable`); не больше `-workers` выводов одновременно, у каждого сеанса ONNX Runtime один поток внутри оператора; суммарный размер моделей в памяти — до `-max-model-bytes` (по умолчанию 1 ГиБ), больше — отказ запуска.

### 7. Критерий «лучше эвристик» (Р4)
ML-детектор включается в поставку, только если на размеченном корпусе RU/EN (синтетические и открытые наборы, ТЗ 14):
- полнота выше эвристики того же класса не меньше чем на 10 п. п.;
- доля ложных срабатываний не выше, чем у эвристики;
- задержка p95 `aisec-ml` не больше 30 мс на 2 000 токенов на 4 vCPU.
Замер и бенчмарки — `docs/detectors.md` (4.19, 4.20) через `tools/detector-quality`. Детектор, который не прошёл, в реестр поставки не попадает.

### 8. Сборка
- **ONNX Runtime 1.31.0** (C API 31 — ровно та версия, под которую собрана обвязка). Рекомендуемый вариант — сборка из исходников с `--no_telemetry`, библиотека общего пользования, только исполнитель CPU, без Python и тестов:
  - исходники ORT по тегу `v1.31.0` (коммит `402979ac1bef89dcd55add41eaa7277c407599eb`) и архивы его зависимостей из `cmake/deps.txt` скачиваются **отдельным шагом с сетью** (`make ort-fetch`) и проверяются по SHA-256 из `deploy/build/onnxruntime/deps.lock`;
  - сама сборка (`make ort-build`) идёт в контейнере с `--network none`, `FETCHCONTENT_FULLY_DISCONNECTED=ON` и `FETCHCONTENT_SOURCE_DIR_*` на проверенные архивы; Eigen — с `EIGEN_MPL2_ONLY`;
  - результат (`libonnxruntime.so.1.31.0`, заголовки, `ThirdPartyNotices.txt`) кешируется в `build/ort/`; его SHA-256 после первой эталонной сборки записывается в `deploy/build/onnxruntime/ort.sha256` и в `docs/cert/build-env.md`; следующая сборка с другим хешем — ошибка `make ort-build` (изменение — только вместе с этим файлом).
- `aisec-ml` с тегом `aisec_onnx` собирается `CGO_ENABLED=1` в том же сборочном образе (Go 1.27.3 и gcc из базового образа сборки). Хеш библиотеки ORT встраивается в бинарник (`-ldflags -X`). `aisec-ml` сверяет его с файлом `/opt/aisec/lib/libonnxruntime.so.1.31.0` **до** `dlopen` (обвязка грузит библиотеку по пути, который передаём мы); несовпадение — отказ запуска.
- Образ `aisec-ml` — `scratch` плюс явный список разделяемых библиотек из сборочного образа (`libstdc++`, `libgcc_s`, `libc`, `libm`, `ld-linux`), без оболочки и пакетного менеджера; цель `make image-ml`, Dockerfile `deploy/build/Dockerfile.ml`. В `make images` образ войдёт, когда в поставке появится первый ML-детектор (4.19).
- **Манифест целостности**: бинарник `aisec-ml` (вид `binary`), библиотека ORT (новый вид `library`, каталог `lib/`) и пакет моделей (новый вид `model`, каталог `models/`). `aisec-ml` проверяет свой манифест при запуске и периодически, как шлюз; эта самопроверка — задача 4.19 (вместе с видами `library` и `model` в `tools/manifest`).
- **SBOM**: ONNX Runtime — компонент `docs/cert/components.yaml` с версией, лицензией, хешем исходников и списком статически встроенных библиотек (раздел «Зависимости»); `onnxruntime_go` — Go-модуль, навендорен; ML-BOM моделей — отдельные файлы (раздел 5).
- depguard: импорт `github.com/yalue/onnxruntime_go` разрешён только в `cmd/aisec-ml`; `import "C"` — только в файлах `cmd/aisec-ml` с тегом `aisec_onnx` (проверка `tools/lintcheck`).

### 9. Поставка
- `aisec-ml` в compose пилота — отдельный сервис с профилем `ml`, по умолчанию не запускается. Без него установка, `lab-install.sh` и обновление работают как раньше.
- `tools/imagecheck compose` знает сервис `aisec-ml`: для него обязателен `network_mode: none` и запрещены сети и порты; остальным сервисам `network_mode` по-прежнему запрещён.
- До 4.19 сервис работает от пользователя шлюза: переменная нового пользователя в `user` сломала бы разбор compose у текущих установок (`${…:?…}` проверяется для всех сервисов, и выключенных тоже).
- Включение в пилоте (пользователь `aisec-ml` и каталог сокета `ml/run` в `prepare-host.sh`, том и флаг у шлюза) — вместе с первым детектором (4.19).

## Зависимости
Обоснование по правилу CLAUDE.md. Решение владельца (27.10.2026, карточка решения в потоке задачи 4.18): «Да, ORT из исходников» — ONNX Runtime 1.31.0 собирается из исходников с `--no_telemetry` без сети, `onnxruntime_go` v1.38.0 вендорится; Eigen (MPL-2.0) и Boost.Mp11 (BSL-1.0) внутри ORT согласованы отдельно. ### ONNX Runtime 1.31.0 (C/C++)

## Альтернативы
- **Вывод в шлюзе через cgo.** Отклонено: падение нативного кода роняет шлюз, шлюз перестаёт быть статическим бинарником на `scratch`, нарушается правило CLAUDE.md о cgo в шлюзе.
- **Движок вывода на чистом Go.** Отклонено: нет зрелых реализаций с нужными операторами и скоростью (раздел «Зависимости»).
- **Готовый сервер вывода (Triton, ONNX Runtime Server, Python).** Отклонено: большая поверхность атаки, сетевые слушатели, Python и десятки зависимостей.
- **gRPC или HTTP по сокету.** Отклонено: gRPC — новые зависимости; HTTP/1.1 — лишний разбор заголовков на каждый вызов. Свой кадр в 16 байт проще ограничить и проверить fuzz-тестом.
- **TCP на петлевом адресе.** Отклонено: к порту может подключиться любой процесс машины, а к сокету — только владелец и группа.
- **Fail-closed для ML.** Отклонено: недоступность вспомогательного процесса блокировала бы весь трафик; эвристики продолжают работать (Р3).
- **Модели только внутри образа, без своего пакета и подписи.** Отклонено: модели обновляются чаще выпусков, а подпись пакета позволяет проверить модели и вне образа, при загрузке. Манифест выпуска при этом тоже их покрывает.
- **Официальная сборка ORT с отключением телеметрии переменной.** Допустимо, но не рекомендуется (раздел «Зависимости»).

## Дополнение (30.10.2026, задача 4.19, часть 2): токенизатор, окна, шаблоны, замер Р4

### Токенизатор
- Один WordPiece на Go для обеих моделей — `internal/ml/wordpiece`, только стандартная библиотека. Разбирает `tokenizer.json` формата Hugging Face: нормализатор `BertNormalizer` (`clean_text`, `handle_chinese_chars`, `lowercase`), предразбивка `BertPreTokenizer`, модель `WordPiece` (жадный поиск самого длинного куска словаря), постобработка `TemplateProcessing` или `BertProcessing` с `[CLS]`/`[SEP]`. Всё остальное — отказ разбора, а значит отказ загрузки модели: другая модель токенизатора, `strip_accents` (в том числе неявный при `lowercase=true` — нужен NFD, его нет в стандартной библиотеке), добавленные не служебные токены, другой шаблон постобработки.
- Лимиты: файл до 32 МиБ, словарь до 2^20, кусок до 256 байт, слово до 1 000 символов (длиннее — `[UNK]`), текст до 256 КиБ, добавленных токенов до 1 024. `FuzzParse`, `FuzzEncode`.
- **Служебные токены в тексте пользователя — обычный текст**: строка `[SEP]` в запросе разбирается на куски словаря, а не превращается в разделитель. Иначе запрос мог бы сдвигать границы окон и «склеивать» свой текст со служебной разметкой модели. Эталоны на стороне Python строятся с `encode_special_tokens=True` — так же.
- Совпадение с эталонной библиотекой `tokenizers` проверяется дважды: в `make test` — на синтетическом словаре (`testdata/ml/wordpiece`, 239 текстов RU/EN, юникодные края), на машине владельца — на настоящих `tokenizer.json` моделей (`make ml-verify`: токены, границы и выход модели против torch, допуск 2·10⁻³).

### Окна и задача модели
- Окно — `[CLS]` + до `max_tokens − 2` токенов + `[SEP]`; соседние окна перекрываются на `min(64, W/4)` токенов; не больше 16 окон, остаток — `truncated` (шлюз ставит `ml_unavailable`). Для классификации берётся максимум оценки по окнам для каждой метки; для разметки токенов — только «свои» токены окна (без перекрытия).
- Окна одного текста считаются **параллельно** в пределах общего лимита `-workers` (семафор на процесс). На 4 vCPU текст 2 000 токенов — 4–5 окон одновременно; без этого p95 Р4 был бы суммой окон.
- Новая задача пакета — `multilabel_classification` (сигмоида на метку): `rubert-tiny-toxicity` многометочная (оскорбление и угроза могут быть в одном тексте). `classification` — softmax, как раньше.

### Детекторы, пороги и шаблоны политик
- `injection.ml` (модель `injection-ru-en`, метки `benign`, `injection`, только вход) и `toxicity.ml` (модель `toxicity-ru`, метки `insult`, `obscenity`, `threat`, `dangerous`, вход и выход). Категории, ID строк матрицы и важность — как у эвристик того же класса (`injection.*`, `toxicity.*`).
- Нижняя граница находки у детектора — 0,5 (`MLFindingFloor`): ниже находка не создаётся. Рабочий порог — **в правиле политики** (`min_score`), администратор меняет его без новой поставки: `injection.ml` — 0,8, `toxicity.ml` — 0,7 (точки замера Р4 — те же значения, `policy.TemplateMLThreshold`).
- Правила ML добавляются в шаблоны политик только при подключённом `aisec-ml` (`TemplateFor`); без него шаблоны прежние. Действие — `log` (**«Мониторинг»**): до замера Р4 на машине владельца модель ничего не блокирует. Перевод в блокировку — отдельным решением после замера, с записью в `docs/detectors.md`.

### Замер Р4
- Расширение `tools/detector-quality` — пакет `tools/detector-quality/p4`: тот же проверочный корпус (`testdata/corpus/injection.ml` — 200 примеров RU и EN, `testdata/corpus/toxicity.ml` — 116 примеров RU) прогоняется через ML-детектор (путь шлюз → сокет → `aisec-ml`) и эвристику того же класса. Счёт — по примерам: положительный пример найден, если есть находка не ниже порога. Метрики — полнота, доля ложных, точность; разрез по языкам и по порогам 0,5–0,95.
- Эвристика сравнения: для `injection.ml` — `injection.heuristic`; у токсичности встроенной эвристики нет, сравнение — со словарём `lists` (`testdata/ml/toxicity-baseline.json`), какой заказчик настроил бы сам.
- Задержка — p50 и p95 по 200 вызовам `aisec-ml` на тексте не короче 2 000 токенов (тексты корпуса подряд), процесс привязан к 4 процессорам (`make ml-p4`, `taskset`, `GOMAXPROCS=4`).
- Обучающие данные `injection.ml` не пересекаются с проверочным корпусом: `prepare.py` убирает точные совпадения и близкие тексты (сходство Жаккара по триграммам слов ≥ 0,5); дообучка выбирает эпоху по отдельной части обучающих данных (dev), не по проверочному корпусу.
- В `make test` замер идёт на тестовом исполнителе (`TestDM01_MLCorpusOnTestExecutor`, `TestDM18_MLCorpusOnTestExecutor`): проверяется путь и расчёт, не качество. Настоящие цифры — `make ml-p4` на машине владельца, таблица — в `docs/detectors.md`, раздел «Замер Р4». Не прошедший детектор в пакет моделей поставки не входит (раздел 7); для `injection.ml` это допустимый исход и записывается там же.

## Дополнение (30.10.2026, исправления ревью 4.r3, поток F4)
- **Сроки (раздел 4; 4В22).** Срок вызова `aisec-ml` — меньший из `Timeout` клиента и срока вызывающего (детектора) за вычетом 5 мс: иначе первым истекал срок детектора, клиент принимал это за отмену запроса, и три срока подряд не набирались — зависший `aisec-ml` задерживал каждый фрагмент на весь срок детектора. Истечение срока детектора тоже считается сроком (не отменой запроса). Умолчания согласованы: `DefaultMLTimeout` 80 мс < `DefaultDetectorTimeout` 100 мс, `ml.DefaultRunTimeout` 80 мс не больше срока клиента (`TestMLTimeoutsOrdered`). Если у вызывающего не осталось времени, клиент сразу отвечает «недоступен», не открывая соединение.
- **Пакет моделей привязан к выпуску (раздел 5; 4В23).** `aisec-ml` загружает только `models/` рядом со своим манифестом выпуска, и хеш байтов `aisec-models.json` должен совпасть с записью `models/aisec-models.json` подписанного манифеста выпуска (`ml.LoadOptions.ManifestHash`), а версия манифеста — с версией бинарника (4Н30: `-manifest` на старый выпуск при `-integrity-action=alert` не проходит): старый подписанный пакет из другого каталога или подложенный в `models/` не загружается — откат версии моделей видит не только самопроверка, но и загрузка. Без записи о пакете в манифесте выпуска (или без проверяемого манифеста) модели не загружаются — `aisec-ml` не запускается, шлюз работает с `ml_unavailable`; это и при `-integrity-action=alert`. В compose пилота `-models`, `-manifest`, `-ort-lib` и их переменные запрещены `imagecheck`; флаги остаются для тестов и ручного запуска.
- **Пути поиска библиотек ORT (раздел 8; 4В24).** ORT загружается через `/proc/self/fd/N`, поэтому `$ORIGIN` у неё — `/proc/self/fd`, а при DT_RUNPATH glibc не смотрит в RPATH `aisec-ml`: в образе на `scratch` libstdc++ не находилась (ML всегда «недоступен»), на хосте бралась системная мимо проверенной `lib/`. Сборка ORT — `-Wl,--disable-new-dtags -Wl,-rpath,/opt/aisec/lib`, `-rpath=$ORIGIN` из `cmake/onnxruntime.cmake` выключен значением `LINKER_SUPPORT_RPATH=OFF` (без правки исходников), `CMAKE_SKIP_RPATH=ON`; `build.sh` проверяет, что у библиотеки только RPATH `/opt/aisec/lib`, а `imagecheck` отвергает у любого ELF образа RUNPATH и пути, кроме `/opt/aisec/lib`. Эталонную сборку ORT и `ort.sha256` делать после этого исправления.
- **Набор инструментов сборки ORT (раздел 8; 4В25).** cmake, ninja-build и python3 ставятся из снимка архива Debian `snapshot.debian.org` на дату `DEBIAN_SNAPSHOT` (аргумент `Dockerfile.ml`, по умолчанию `20261029T000000Z`), а не из текущего зеркала; binutils, gcc и glibc — из базового образа по digest, повторно не ставятся. Версии пакетов (`toolchain.versions`, с датой снимка) сверяются в стадии `ort-checked` с эталоном `deploy/build/onnxruntime/toolchain.versions`, если он есть; поставка (`RELEASE=1`) без эталона не собирается. Эталон записывает владелец после эталонной сборки вместе с `ort.sha256`. Альтернатива — `pkg=версия` у каждого пакета без снимка — отвергнута: зеркало Debian удаляет прежние версии после обновления, и повторная сборка у испытательной лаборатории не нашла бы пакеты; со снимком версии зафиксированы и доступны.

### Рекомендация потока
- **A**: своя дообучка `rubert-tiny2` на синтетике и factRuEval-2016. Единственный вариант, где есть адреса, все данные с разрешённой лицензией и известным происхождением, задержка проходит Р4, а токенизатор тот же, что у `injection.ml`. Основа уже есть в `tools/ml/sources.json` (4.19), новых пакетов Python не нужно: та же дообучка `transformers` с головой разметки токенов. Скачивание по `git` (коммит и SHA-256 архива `git archive`) — в `tools/ml/fetch.py`; запись factRuEval в `sources.json` (внесена после решения владельца, раздел ниже):
  ```json
  {"name": "factrueval-2016", "git": "https://github.com/dialogue-evaluation/factRuEval-2016",
   "paths": ["LICENSE", "devset", "testset"], "license": "MIT", "task": "ner",
   "use": "pii.ner: devset — обучение, testset — проверка на живом тексте",
   "revision": "dfe96237fce79fde13b2021d1938587e4ea3042e",
   "files": {"factrueval-2016.tar": "c615f4a6c42b41c3cad315096999c12e8e3995ae29e049a4d5a8f2e2c6d5e58a"}}
  ```
- B — эталон сравнения вне поставки (как `guard-small` у `injection.ml`), если владелец захочет его скачать; C и D — нет.

### Решение владельца (30.10.2026)
Карточка решения в потоке задачи: «Да, рекомендованные». Модель `pii.ner` — своя дообучка `cointegrated/rubert-tiny2` (MIT) на разметку токенов; данные — синтетика `tools/synth-pii -kind ner` и factRuEval-2016 (MIT, коммит `dfe96237fce79fde13b2021d1938587e4ea3042e`; `devset` — обучение, `testset` — проверка). Запись factRuEval внесена в `tools/ml/sources.json`, `pii-ner-ru` входит в `ML_MODELS` по умолчанию. Запись `type: ml-model` в `docs/cert/components.yaml` вносится, когда модель пройдёт Р4 на машине владельца: без неё ключ производителя модель не подписывает. Как применять Р4 к `pii.ner` — отдельный открытый вопрос (`docs/plans/stage-4.md`).

### Устройство детектора (поток F5, по ревью)
- Метки модели — строчные, как требует протокол `aisec-ml`: `o`, `b-per`/`i-per`, `b-org`/`i-org`, `b-loc`/`i-loc`, `b-addr`/`i-addr`. `aisec-ml` при загрузке требует у разметки метку `o` и у каждой `i-X` — `b-X`.
- Находок больше 512 (`ml.MaxFindings`) или текст длиннее 16 окон и 8 частей — проверка неполная: ответ помечен усечённым, детектор возвращает находки проверенной части вместе со сбоем `detect.ErrPartial`. Найденное маскируется, событие получает `ml_unavailable`: остаток текста `pii.ner` не проверен и не замаскирован.
- Режим хранения `masked`: находки `pii.ner` маскируются в содержимом события, даже если правило только журналирует. Ради события `pii.ner` не запускается (в отличие от `pii.ru` и `secrets`), и её сбой не запрещает сохранить содержимое: ПДн с контрольными суммами закрывает `pii.ru`, имена в таком событии остаются открытыми, событие помечено `ml_unavailable`.
- Фрагмент режется по 512 байт только по границам токенов: один токен длиннее (`[UNK]` на длинном слове) остаётся одной находкой — маскируется больше, а не меньше.
- Имя вплотную к идентификатору `pii.ru` (без пробела) склеивается в один участок маскирования; тип псевдонима — по первой находке. Значение скрыто, тип может быть неточным.

## Дополнение (30.10.2026, исправления ревью 4.r4, поток G3)
- **Срок вызова — от длины текста, отсрочку включают только короткие тексты (4В30).** Срок вызова шлюза — `-ml-timeout` (80 мс) на текст в одно окно и `-ml-timeout-per-window` (10 мс) за каждые следующие 2 КиБ текста, не больше 8 частей по 16 окон (переменные окружения `AISEC_GATEWAY_ML_TIMEOUT`, `AISEC_GATEWAY_ML_TIMEOUT_PER_WINDOW`). В отсрочку засчитывается только истёкший срок на тексте не длиннее 2 КиБ, и один и тот же текст подряд — один раз; срок на длинном тексте — `ml_unavailable` этого запроса без отсрочки для остальных. Нарушитель больше не выключает ML для всех приложений шлюза одним длинным текстом.
- **Срок передаётся в `aisec-ml` (4В30).** В заголовке кадра `detect` байты 6–7 (прежде нулевой резерв) — срок вывода в миллисекундах, назначенный шлюзом; у остальных типов кадров поле по-прежнему нулевое, иначе — ошибка протокола. Сервер берёт срок шлюза, но не больше `-max-run-timeout` (2 с), а без него — `-run-timeout` (80 мс; `AISEC_ML_RUN_TIMEOUT`, `AISEC_ML_MAX_RUN_TIMEOUT`). Версия протокола не меняется: старый шлюз шлёт 0 и получает срок сервера. Предупреждение о сбое вывода — один раз за серию, без текста.
- **Окна потока ответа без журналирующих ML-детекторов (4В30).** В окнах потока ответа не вызываются ML-детекторы, у которых в политике для этого направления только правила `log`: решения они не меняют, а их находки попадают в событие при проверке ответа целиком.
- **Замер Р4 при одновременных вызовах (4В30).** `make ml-p4` дополнительно меряет p50 и p95 трёх моделей одновременно на тексте в 16 окон и сравнивает со сроком вызова шлюза; p95 выше срока — на таких текстах ML отвечает `ml_unavailable`, это видно в таблице Р4.
- **Токенизатор со сроком (4В31).** `Encode` принимает контекст и проверяет его каждые 1 024 символа; кандидат на позиции собирается один раз, префиксы проверяются по границам символов (O(длина куска) вместо O(длина²)). Худший случай (слова из 99 одинаковых букв со словарём кусков до 32 символов, часть 256 КиБ) — около 83 мс на облачной ВМ с 4 vCPU (`BenchmarkEncodeWorstCase`, `docs/detectors.md`).
- **Граница фрагмента `pii.ner` по уверенности (4В33).** Токен с наибольшей вероятностью ниже `MLFindingFloor` (0,5) обрывает фрагмент, как метка `o`; уверенные части имени остаются находками, а `expandWords` дотягивает маскирование до границ слова. Один неуверенный кусок больше не снимает маскирование со всего имени.
- **Расширение до слова по знакам формата (4Н34).** Знаки категории Cf (мягкий перенос U+00AD и др.) считаются частью слова: токенизатор их выбрасывает, и хвост слова за ними не уходит провайдеру.
- **Состав пакета моделей (4В32).** `ML_MODELS` по умолчанию — `injection-ru-en toxicity-ru`; `pii-ner-ru` — только явным списком после решения владельца. Ключ производителя (`sign-models -key`) и `make ml-release-dir RELEASE=1` (`tools/manifest check-models`) принимают только модели с записью `type: ml-model`, `scope: product` и решением владельца в `components.yaml`.
- **Хеш манифеста пакета (ревью 4.r3, остаток).** `sign-models -dry-run` (`make ml-package-sum`) на сборочной машине печатает SHA-256 манифеста, ничего не записывая; на машине подписи `-expect-sha256` (`ML_SHA256=…`) сверяет хеш манифеста, собранного из перенесённых файлов, и отказывает при несовпадении — как `manifest sign`.
- **Владелец сокета (4Н27).** Шлюз, кроме прав каталога и сокета, сверяет UID владельца сокета с владельцем каталога: сокет, созданный другим пользователем в общем каталоге, не принимается. Проверка — по `stat` файла (`syscall.Stat_t`, только Linux; на других ОС владелец не сверяется), пакет `syscall` разрешён только в `internal/gateway/mlowner_linux.go` с этой ссылкой. **Принятый риск до этапа 5:** процесс с правами владельца каталога может подменить сокет; проверка учётных данных собеседника (`SO_PEERCRED`, ожидаемый UID или GID `aisec-ml`) — этап 5.
- **SAST и уязвимости поставочной сборки (4В39).** `make sast` дополнительно прогоняет gosec по `cmd/aisec-ml` с тегами `e2e,aisec_onnx` в отдельный SARIF (сверка разметки — по обоим), `make vuln` — `govulncheck -tags aisec_onnx ./cmd/aisec-ml/...`.
- **Самотест шлюза (4.28, остаток).** После создания клиента `aisec-ml` шлюз повторно прогоняет эталоны ML-детекторов уже с клиентом; недоступный `aisec-ml` — `ml_unavailable`, не провал; итог в heartbeat — общий с первым прогоном.
- **Сборка ORT без телеметрии (ревью 4.r3, остаток).** `build.sh` ищет строки без учёта регистра (`events.data.microsoft.com`, `OneCollector`, `libcurl`, `mbedtls`, `sqlite`, `Microsoft.ML.ONNXRuntime.Telemetry`) и отказывает, если библиотека импортирует `socket`, `connect` или `getaddrinfo`.

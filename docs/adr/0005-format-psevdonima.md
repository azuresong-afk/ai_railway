# ADR-0005. Формат псевдонима и правила обратной подстановки

- Статус: предложено (предварительное: эксперимент без реальной модели, решение Р9 плана этапа 1)
- Дата: 20.10.2026
- Связанные разделы ТЗ: 5.1 «Псевдонимизация с обратной подстановкой», 5.3, 5.16 (DM-11, DM-13, DM-31)

## Контекст
Шлюз заменяет ПДн и секреты в запросе к внешнему провайдеру псевдонимами и возвращает значения в ответ модели (ТЗ, 5.1). Формат должен:
- пережить переписывание моделью: модель пересказывает текст, оформляет markdown, меняет регистр;
- не встречаться в обычных текстах — иначе текст пользователя или модели примут за псевдоним;
- распознаваться в потоке по частям с маленьким буфером (обязательный объект fuzz-тестирования, 8.5);
- не давать способа вывести значение туда, куда пользователь его не отправлял.

Реальной модели в среде разработки нет, поэтому эксперимент поставлен на корпусах детекторов и mock-llm, а переписывание моделью смоделировано известными искажениями (решение Р9). На пилоте эксперимент повторяется на реальных моделях; до этого ADR остаётся предварительным.

## Решение
1. **Формат** — `[[ТИП_N]]`: `ТИП` — категория находки латиницей в верхнем регистре без знаков (`pii.phone` → `PHONE`, `secret.private_key` → `PRIVATEKEY`), до 16 символов; `N` — номер значения этого типа в запросе, 1–99 999. Одинаковое значение в одном запросе получает один псевдоним, разные типы нумеруются независимо. Псевдонимы, которые уже есть в тексте запроса, не выдаются (их мог написать пользователь или документ RAG).
2. **Маскирование** (`redact`) даёт `[[ТИП]]` без номера: модель видит, что здесь было, а обратная подстановка такой маркер не трогает. Пересекающиеся фрагменты объединяются; если среди них есть `redact`, объединение маскируется необратимо.
3. **Обратная подстановка** принимает искажения: экранирование markdown (`\[`, `\_`, `\]`), любой регистр типа, до двух пробелов у скобок, одну пару скобок вместо двух и потерянную закрывающую скобку, `-` или пробел вместо `_`. Восстанавливается только значение из словаря этого запроса; всё остальное остаётся как есть — значение остаётся замаскированным (ТЗ, 5.1).
4. **Метрика неудачных подстановок** — `Stats.Failed()`: псевдоним выданного в запросе типа с неизвестным номером (`Unknown`), псевдоним в небезопасном месте (`Unsafe`) и превышение объёма подстановки (`Limited`).
5. **Где не восстанавливать.** Псевдоним внутри адреса — после `//` (в том числе `://` и `\/\/`) до пробельного символа ASCII; внутри `<…>` пробел и перевод строки адрес не завершают. Иначе внедрённая инструкция заставит модель вставить псевдоним в ссылку или картинку на чужом сервере, и приложение само отправит туда значение (DM-11). В аргументах `tool_calls` (JSON) значение вставляется только внутрь строки JSON и экранируется: значение с кавычкой не добавит поле (DM-13).
6. **Пределы.** До 4096 значений в словаре — сверх предела фрагмент маскируется необратимо. До 4 МиБ значений, вставленных в один ответ, — защита от ответа из тысяч повторов псевдонима длинного значения.
7. **Словарь** — только в памяти на время запроса, не печатается (`String`, `LogValue` — только число записей) и очищается по завершении (`Clear`). Сохранение в режиме `full` — этап 2, вместе с шифрованием (решение Р3).

Реализация — пакет `internal/pseudonym`; подключение к конвейеру — задача 1.23.

## Альтернативы
- `{{ТИП_N}}`, `<ТИП_N>`, `__ТИП_N__`, `ТИП_N` — отклонены по эксперименту выше: шаблонизаторы, теги HTML, markdown и идентификаторы кода.
- Тип кириллицей (`[[ТЕЛЕФОН_1]]`) — длиннее в токенах и смешивает алфавиты; латинский тип модели не переводят, когда пишут по-русски, — по опыту, проверить на пилоте.
- Псевдоним «правдоподобным» значением (поддельный телефон с верной контрольной суммой) — модель не исказит, но синтетическое значение может совпасть с настоящим, а в ответе его не отличить от данных, которые модель взяла из другого источника. Отклонено.
- Строгая подстановка без искажений — проще, но больше неудачных подстановок на пилоте (ТЗ, 1.6: наглядный результат). Искажения ограничены, чтобы грамматика не принимала обычный текст (0 совпадений на корпусах).
- Восстановление в адресах — удобнее для персональных ссылок, но открывает эксфильтрацию (DM-11). Отклонено с приоритетом безопасности.

## Последствия
- Модель может перепутать номера (`[[PHONE_1]]` вместо `[[PHONE_2]]`): тогда в ответ попадёт другое значение того же пользователя из того же запроса. Обнаружить это нельзя; риск ограничен данными самого запроса.
- Псевдоним, искажённый сильнее допустимого, остаётся в ответе: приложение видит `[[PHONE_1]]` вместо телефона. Это видно в метрике `Failed()` и событии (задача 1.23).
- Выходные детекторы видят ответ с псевдонимами (ТЗ, 4.3, шаг 7). Значения после подстановки взяты из запроса того же пользователя и приложению не новы, но `output.exfil` должен видеть и восстановленный текст — см. «Открытые вопросы» плана этапа 1, задача 1.23.
- Откат: формат задан функциями `TypeOf`, `formatToken` и `parseToken` пакета `internal/pseudonym`; словарь не сохраняется, поэтому смена формата не требует миграции данных.

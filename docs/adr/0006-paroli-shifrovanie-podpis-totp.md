# ADR-0006. Пароли, шифрование, подпись и TOTP в профиле `standard`

- Статус: предложено
- Дата: 20.10.2026
- Связанные разделы ТЗ: 7 (ИАФ.1, ИАФ.5, ЗИ.1, ОЦЛ.1, ОЦЛ.3, ОЦЛ.4), 10.2, 10.4, 11.2; решения Р1, Р3, Р4 плана этапа 2

## Контекст
Этап 2 начинается с функций, которым нужны новые криптографические примитивы: пароли учётных записей (ИАФ.1), второй фактор (ИАФ.5), шифрование секретов и содержимого событий (ЗИ.1, Р4), подпись пакетов конфигурации, манифеста целостности и контрольных точек аудита (ОЦЛ.1, ОЦЛ.3, Р5, Р7). ТЗ 10.2 требует, чтобы вся криптография была в `internal/crypto` за интерфейсами `PasswordHasher`, `AEAD`, `Signer`/`Verifier` и не было собственных реализаций алгоритмов.

Два места требуют отдельного решения:
- приложения-аутентификаторы поддерживают TOTP только на HMAC-SHA-1, а SHA-1 нет в профиле `standard` (ТЗ 10.2 требует оформить исключение ADR);
- Argon2id нет в стандартной библиотеке Go.

## Решение
1. **Интерфейсы** — методы `Provider`: `PasswordHasher()`, `NewAEAD(key)`, `GenerateSigner()`, `NewSigner(seed)`, `NewVerifier(publicKey)`, `NewTOTP(secret)`. Профиль `gost` на все отвечает `ErrNotImplemented` до выбора СКЗИ на этапе 6, а контрактный тест `TestProfileContract` это проверяет. ТЗ 10.2 называет TOTP «отдельным методом» `MAC`. В коде это отдельный интерфейс `TOTP` с конструктором `NewTOTP`, а не метод `MAC`: так HMAC-SHA-1 нельзя получить ни из какого другого объекта профиля, а у кода есть один вход — `Verify`. Объекты с ключами (`AEAD`, `Signer`, `TOTP`) при выводе через `fmt` и `slog` показывают только имя алгоритма.
2. **Пароли — Argon2id** (`golang.org/x/crypto/argon2`, BSD-3-Clause; ТЗ 11.2). Параметры по Р3: m = 64 МиБ, t = 3, p = 2, соль 16 байт из `Random` профиля, хеш 32 байта. Хранение — строка PHC `$argon2id$v=19$m=65536,t=3,p=2$<соль>$<хеш>` (base64 без дополнения), параметры хранятся вместе с хешем. `Verify` сравнивает за постоянное время и сообщает `needsRehash`, если хеш получен с другими параметрами: параметры повышаются без миграции, пересчётом при входе.
   - Пароль — от 1 до 1024 байт. Правила сложности — в `internal/auth` (ИАФ.2).
   - Разбор строки хеша строгий: только `argon2id` версии 19, параметры в порядке `m, t, p`, без ведущих нулей и знаков, base64 однозначный (обратное кодирование совпадает со входом). Границы: m — от 19 МиБ до параметра по умолчанию (64 МиБ), а при t = 1 — не меньше 46 МиБ (минимумы OWASP); t — 1–16, p — 1–16, соль и хеш — 16–64 байта, строка — до 256 байт. Повреждённая или подложенная запись в БД не поднимет память выше рабочей. При повышении параметров верхняя граница растёт вместе с ними. Разбор покрыт fuzz-тестом `FuzzParseArgon2id`.
   - **Ограничение одновременных вычислений** (Р3) — общий на процесс семафор на `GOMAXPROCS` слотов, но не больше 16. Без него поток попыток входа исчерпает память: каждое вычисление занимает до 64 МиБ. Ожидание слота ограничено контекстом запроса, само вычисление не прерывается. Пиковая память на хеши — 64 МиБ × min(`GOMAXPROCS`, 16), то есть не больше 1 ГиБ; в контейнере `GOMAXPROCS` ограничивается квотой CPU.
3. **Шифрование — AES-256-GCM** через `cipher.NewGCMWithRandomNonce`: случайный nonce 96 бит пишется перед шифротекстом, результат — `nonce ‖ шифротекст ‖ тег` (28 байт сверху). AAD задаёт вызывающий: по Р4 это таблица, столбец и ID строки, чтобы шифротекст нельзя было переставить между записями. Любая ошибка расшифрования — одна `ErrDecrypt`, без подробностей. Открытый текст одного вызова — до 64 МиБ, AAD — до 4 КиБ. `Open` покрыт fuzz-тестом `FuzzAEADOpen`: шифротекст из БД — недоверенный вход.
   - Предел случайного nonce — 2^32 сообщений на ключ (NIST SP 800-38D, 8.3). Ключ данных шифрует секреты и содержимое событий в режиме `full`. Учёт числа сообщений и ротация ключа данных — задача 2.3 (ADR-0007).
4. **Подпись — Ed25519** (RFC 8032, `crypto/ed25519`). Закрытый ключ — seed 32 байта: `Signer.Seed()` отдаёт копию только для сохранения в файле 0400 или в зашифрованном виде (ТЗ 10.4), открытый ключ — 32 байта, подпись — 64 байта. Проверка не принимает подпись неверной длины.
5. **TOTP — исключение из профиля** (Р1, ТЗ 10.2). RFC 6238 на HMAC-SHA-1 (`crypto/hmac`, `crypto/sha1`), секрет 20 байт, шаг 30 с, 6 цифр, окно ±1 шаг. `Verify(code, now, lastStep)` возвращает шаг принятого кода, а код того же или более раннего шага отвергается: вызывающий хранит `lastStep` для пользователя (задача 2.8), поэтому перехваченный код нельзя повторить. Кандидаты окна сравниваются за постоянное время без раннего выхода. Код с пробелами, не-ASCII цифрами и другой длины отвергается до вычислений (`FuzzTOTPVerify`).
   - **Контракт вызывающего** (задачи 2.7 и 2.8). `lastStep` обновляется атомарно, условием в той же записи (`UPDATE … SET last_step = $шаг WHERE last_step < $шаг`), и вход засчитывается, только если запись изменилась. Иначе два параллельных запроса с одним кодом пройдут оба. Число попыток ввода кода ограничивает вызывающий: шесть цифр — 10^6 вариантов, их быстро переберут без блокировки (ИАФ.4). SHA-1 импортируется только в `internal/crypto/totp.go` и используется только в HOTP; для подписи, хешей и имитовставок он не применяется. Срабатывание gosec G505 на импорт подавлено в этой строке со ссылкой на ADR.
   - Почему это безопасно: TOTP использует HMAC, а не саму функцию сжатия. Известные атаки на коллизии SHA-1 не дают подделать HMAC-SHA-1 без ключа (RFC 6151, раздел 3, — тот же довод для HMAC-MD5; NIST SP 800-131A допускает HMAC-SHA-1).
   - Для профиля `gost` вопрос остаётся открытым: допустимо ли то же исключение или нужен второй фактор на ГОСТ (например, аппаратный токен), решается вместе с СКЗИ на этапе 6.
6. **Самотест** (ОЦЛ.4) дополнен эталонами: AES-256-GCM (McGrew–Viega, тест 14), Ed25519 (RFC 8032, тест 1), TOTP (RFC 6238, T = 59) и Argon2id на малых параметрах (t = 2, m = 256 КиБ, p = 1), плюс разбор и кодирование строки PHC. Векторы Argon2id в RFC 9106 требуют секрета и AD, которых нет в x/crypto. Поэтому взяты векторы эталонной реализации phc-winner-argon2 (`src/test.c`), сверенные с OpenSSL 4.0; тест `TestArgon2idReferenceVectors` проверяет и вектор на 64 МиБ. Самотест не тратит 64 МиБ при запуске. Для AEAD сверх эталона проверяются расшифрование своего шифротекста и отказ на подменённом.

## Альтернативы
- **bcrypt или scrypt** вместо Argon2id. bcrypt обрезает пароль до 72 байт и использует мало памяти. scrypt есть в той же `x/crypto`. ТЗ 10.2 называет Argon2id, а OWASP рекомендует его первым.
- **Собственная реализация Argon2id** нарушает правило «никаких собственных реализаций алгоритмов». `golang.org/x/crypto` поддерживает команда Go, эту библиотеку называет ТЗ 11.2.
- **TOTP на HMAC-SHA-256** (RFC 6238 это допускает). Google Authenticator и часть других приложений молча считают по SHA-1 и показывают неверные коды. Для пилотов это хуже исключения, ограниченного одним файлом.
- **Свой формат nonce** (счётчик или nonce в отдельном столбце). Счётчик требует сохранять состояние и при восстановлении из резервной копии повторяет nonce. Отдельный столбец — лишняя возможность ошибиться. `NewGCMWithRandomNonce` есть в стандартной библиотеке и проверен.
- **Лимит вычислений на экземпляр `PasswordHasher`** вместо общего на процесс. Тогда два компонента в одном процессе удвоили бы пиковую память, а лимит нужен именно на процесс.

## Последствия
- В `go.mod` добавляются `golang.org/x/crypto` и `golang.org/x/sys` (косвенно). В `vendor/` попадают только `argon2`, `blake2b` и `x/sys/cpu`. Записи — в `docs/cert/components.yaml`. Импорт `golang.org/x/crypto` вне `internal/crypto` по-прежнему запрещён depguard.
- Следующие задачи опираются на эти интерфейсы: 2.3 (ключи, `aisec-cli init`), 2.4–2.5 (аудит, подписанные контрольные точки), 2.7 (вход по паролю), 2.8 (TOTP: хранение секрета под `AEAD` и `lastStep`, QR-код), 2.17 (манифест целостности), Р7 (подпись пакета шлюза).
- Учёт для 2.3: предел 2^32 сообщений на ключ в коде пока не считается. Учёт и ротация ключа данных — обязательная часть ADR-0007.
- Учёт для 2.7: чтобы по времени ответа нельзя было узнать, существует ли учётная запись, вход для неизвестного имени тоже должен вызывать `Verify` (с заранее вычисленным фиктивным хешем). Сам `PasswordHasher` этого не делает.
- Параметры Argon2id меняются правкой `argon2Default` и пересчётом при входе (`needsRehash`). Смена алгоритма или формата — новый ADR.
- Откат: интерфейсы новые, их ещё никто не использует. До задач 2.3 и 2.7 ADR откатывается удалением кода и зависимости.

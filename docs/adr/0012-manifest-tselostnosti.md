# ADR-0012. Манифест целостности: формат, ключ производителя и поставочная сборка

- Статус: принято (план одобрен 21.10.2026; дополнение — п. 7, ревью 2.r4, 22.10.2026)
- Дата: 21.10.2026
- Связанные разделы ТЗ: 7.5 (ОЦЛ.1–3, ОЦЛ.5), 5.16 (DM-42), 10.2, 10.4; решение Р10 плана этапа 2; ADR-0006, ADR-0011

## Контекст
ОЦЛ.1 требует при сборке формировать манифест: хеши исполняемых файлов, статики веб-консоли, служебных баз и эталонной конфигурации, подписанный ключом производителя. ОЦЛ.2 требует проверять его при запуске, раз в час и по команде администратора. По ТЗ 10.4 ключ подписи манифестов хранится у производителя, вне репозитория, а в продукт встраивается только открытый ключ проверки.

CI и разработчику тоже нужен подписанный манифест: проверка должна проходить на каждой сборке, иначе её никто не увидит в работе. При этом ключ производителя в CI попасть не может.

Статика веб-консоли и миграции встроены в бинарники через `go:embed` (ADR-0011), поэтому на диске установки их нет. Хеш бинарника внутрь самого бинарника положить нельзя: встраивание меняет хеш.

## Решение
1. **Файлы.** Манифест и подпись лежат рядом в корне установки, над `bin/`: `aisec-manifest.json` и отделённая подпись `aisec-manifest.json.sig` (base64, одна строка). Подпись — Ed25519 через `Signer` профиля над `"aisec-integrity-manifest-v1\n" + байты файла`. Подписываются байты, а не каноническая форма: проверка идёт до разбора JSON.
2. **Формат `aisec-manifest-v1`.** Версия продукта, профиль, имя `Hasher` профиля, время последнего коммита (сборка воспроизводима) и файлы `{path, kind, size, hash}` по возрастанию пути. Вид задаёт каталог:
   - `binary` — `bin/`;
   - `static` — `web/dist/`, встроена в `aisec-server`;
   - `migration` — `migrations/`, встроены в `aisec-cli`;
   - `detector_db` — `detect/`;
   - `config` — `config/`.

   Виды `detector_db` и `config` зарезервированы и пока не заполняются: правила и словари детекторов скомпилированы в бинарники и покрыты их хешем, эталонной конфигурации в поставке нет (конфигурация шлюза — под контролем ОЦЛ.3, сервер настраивается флагами). Отдельные базы детекторов этапа 4 (модели ONNX) войдут в `detector_db`.

   Строгий разбор: неизвестные поля, повторы, `..` и `\` отвергаются.
3. **Что сверяет каждый компонент.**
   - Свой исполняемый файл (на Linux — `/proc/self/exe`: файл работающего процесса, а не новый файл по тому же пути) и встроенные наборы целиком: лишний или пропавший встроенный файл — нарушение.
   - `aisec-cli verify` — ещё и все невстроенные файлы манифеста на диске через `os.Root`.
   - Шлюз — ещё и файл конфигурации, изменённый после запуска (ОЦЛ.3).
4. **Ключи.**
   - Новые виды PEM в `internal/crypto`: `AISEC MANIFEST SIGNING KEY` и `AISEC MANIFEST SIGNING PUBLIC KEY`. Ключ манифеста нельзя подложить вместо ключа пакетов или аудита.
   - Открытый ключ встроен в бинарник (`go:embed`):
     - сборка без тегов — тестовый ключ `internal/integrity/keys/manifest-test.pub`;
     - сборка с `-tags aisec_release` (`make build RELEASE=1`) — ключ производителя `internal/integrity/keys/manifest.pub`. Без этого файла поставочная сборка не собирается.
   - Тестовая пара «не для поставки» лежит в репозитории: закрытый ключ — `testdata/integrity/manifest-test.signkey`. Каждый итог проверки сборки с тестовым ключом помечен `test_signed`, а при запуске в журнал пишется предупреждение.
5. **Сборка.**
   - `make manifest` (входит в `make check`): `build`, затем `tools/manifest build`, затем `aisec-cli verify` готового манифеста.
   - Поставка: `make manifest RELEASE=1 MANIFEST_KEY=…`. Ключ производителя — файл 0400 вне репозитория. Пару создаёт `tools/manifest gen-key`.
6. **Реакция.** `-integrity-action alert|stop`, по умолчанию `alert`.
   - Отсутствие манифеста или подписи — тоже нарушение.
   - `stop` при запуске не даёт компоненту стартовать, после запуска — штатная остановка.
   - Итоги пишутся в `integrity_checks`, `integrity.check` и `tech_log` (сервер, `aisec-cli verify` с БД) или только в технический журнал (шлюз до 2.14 и 2.20).

7. **Откат выпуска и корни доверия (ревью 2.r4).**
   - Время сборки (`created`) упорядочивает выпуски, в отличие от строки версии. Оно пишется в `integrity_checks` и в heartbeat шлюза. Успешная проверка манифестом старше последней успешной — нарушение `manifest_rollback`; у шлюза — уменьшение относительно запомненного максимума. Намеренный откат принимает администратор: `aisec-cli verify -accept-rollback` (сервер, cli и миграции — один манифест, поэтому принятие общее) или `-accept-rollback -gateway ИМЯ`; запись `integrity.rollback_accepted`.
   - Корни доверия — файлы, по которым компонент проверяет других: у шлюза конфигурация, УЦ сервера, ключи проверки пакетов, ключ псевдонимов; у сервера ключ проверки аудита, сертификат УЦ, открытые ключи подписи пакетов (текущий и `bundle-signing.next.pub`). Они под контролем целостности с эталоном по прочитанным байтам.
   - Тестовый ключ не проходит в поставку: `tools/manifest build -key` отклоняет его, сборка `aisec_release` со встроенным тестовым ключом не проверяет манифест; сборка с тестовым ключом видна условием `test_build` в «Состоянии системы».

## Альтернативы
- **Хранить «последнюю версию» в файле на хосте.** Нарушитель с правом записи в установку откатил бы и его. Журнал проверок в БД с правами только на добавление — надёжнее; шлюз сверяет сервер.
- **Ключ из файла по флагу.** Открытый ключ читается из файла, путь задаётся флагом. Нарушитель, подменивший манифест, подменил бы и ключ. Противоречит ТЗ 10.4.
- **Ключ через `-ldflags -X`.** Ключ подставляется в бинарник при сборке. Сборка без флага осталась бы без ключа или с пустым ключом без явной ошибки, а забытый флаг в поставке не виден. Тег сборки с `go:embed` даёт ошибку компиляции.
- **Подпись канонической формы JSON.** Нужна каноникализация на обеих сторонах. Подпись байтов файла проще и позволяет проверять до разбора.
- **Хеш бинарника внутри бинарника** (встраивание после сборки, секция ELF). Нужна правка бинарника после `go build` и разбор ELF. Отдельный файл манифеста проще и годится для `aisec-cli verify` с доверенного носителя.
- **Реакция `stop` по умолчанию.** Без манифеста не запустились бы `make e2e` и стенд `make dev`. В ТЗ (5.16, DM-42) реакция по умолчанию — оповещение, остановка — по настройке.

## Последствия
- Каждая сборка `make check` подписывает и проверяет манифест тестовым ключом, а сквозные тесты запускают шлюз с настоящей проверкой.
- До первой поставки владелец создаёт пару ключей производителя: `go run ./tools/manifest gen-key -key <вне репозитория> -pub internal/integrity/keys/manifest.pub`. Открытый ключ он коммитит.
- Самопроверка исполняемого файла не защищает от нарушителя, который переписал бинарник целиком, вместе с проверкой. Это остаточный риск в `threat-model.md`; компенсирующая мера — `aisec-cli verify` с доверенного носителя.
- Профиль `gost` (этап 6): формат не меняется, другими будут алгоритм хеша и подписи. Ключи перевыпускаются вместе с профилем.
- Откат: удалить цели и пакет, вернуть заглушку `make manifest`. Таблица `integrity_checks` остаётся в схеме (миграции не откатываются).

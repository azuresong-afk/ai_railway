## Контекст
В ТЗ 5.10 к агентам и инструментам пять требований:
- реестр агентов и инструментов с хешем описания;
- политика вызовов: allowlist, ограничения аргументов, лимиты частоты;
- очередь подтверждений в консоли;
- MCP-прокси с проверкой `tools/list` и `tools/call`;
- хронология сессии агента.

Матрица 5.16 требует покрыть тестами в этапе 4 строки:
- DM-20–DM-25;
- MCP-часть DM-07: результаты инструментов проходят детекторы косвенных инъекций.

Сценарии S5 (опасное действие агента) и S6 (косвенная инъекция) входят в приёмку этапа.

Что есть в коде на 27.10.2026:
- В шлюзе один слушатель приложений (по умолчанию `127.0.0.1:8443`). На нём `/v1/chat/completions`, `/v1/embeddings`, `/guard/v1/check`, `/v1/models`, вход по ключу приложения.
- В ответах модели аргументы `tool_calls` уже проверяются выходными детекторами (DM-13). В потоке вызовы собираются целиком и могут удерживаться до конца проверки (`holdTools`).
- Сообщения `role: tool` в запросе проверяются как вход с источником `tool`. В Check API есть источник `tool`.
- `require_approval` объявлено в `internal/policy/action.go`, его приоритет — между `redact` и `block`. Сохранять такое действие пока нельзя.
- Ослабление версии политики (`versions.Compare` → `Weakening`) требует повторной проверки пароля или кода. Правило `security.weakening` (DM-40) группирует такие изменения за 10 минут.
- Шлюз ходит на сервер только сам, по mTLS: heartbeat, события, пакет. Клиент управляющего канала ждёт ответа не дольше 10 с. Длинных запросов к серверу нет.
- Сетевые клиенты разрешены только в `cmd/aisec-gateway`, `internal/gateway`, `internal/providers`, `internal/notify` (`NET_CLIENT_ALLOWED`).

Ограничения:
- Только стандартная библиотека.
- Каждый разборщик недоверенного ввода — с лимитами и fuzz-тестом.
- `os/exec` в серверных компонентах запрещён.
- Внешние соединения — только к адресам, которые настроил администратор.
- Содержимое — только через модуль событий по режиму хранения.

Ревизия MCP 2026-07-28 заметно поменяла транспорт по сравнению с 2025-11-25:
- нет `initialize` и сессий `Mcp-Session-Id`;
- нет GET-потока и возобновления по `Last-Event-ID`;
- версия и возможности клиента передаются в каждом запросе (`_meta`);
- обязательны заголовки `Mcp-Method` и `Mcp-Name`, они должны совпадать с телом;
- запросы сервера к клиенту заменены результатом `input_required` (MRTR);
- задачи (tasks) вынесены в расширение.

Большинство клиентов на конец 2026 года ещё говорят на 2025-11-25. Прокси должен понимать обе ревизии.

## Решение

### 1. Сущности и реестр (сервер, задача 4.8)

**Агент** принадлежит приложению. В одном приложении может быть несколько агентов. Поля карточки:

| Поле | Что задаёт |
|---|---|
| `slug` (`[a-z0-9-]{1,64}`, уникален в приложении) | идентификатор агента |
| `name`, `description`, `owner` | описание |
| `mcp_servers` | MCP-серверы, к которым агенту можно обращаться |
| `status` | `active` или `disabled` |

Расширение `mcp_servers` — ослабление: повторная проверка и DM-40, как у политики.

**Как шлюз определяет агента:**
1. Ключ приложения можно привязать к агенту (`app_keys.agent_id`). Привязка задаётся при создании ключа и потом не меняется.
2. Если ключ не привязан, агент берётся из заголовка `X-AISec-Agent`. Заголовок должен встречаться один раз, называть агента этого же приложения и укладываться в 64 байта ASCII.
3. Если заголовок не совпадает с привязкой ключа — 403 `agent_mismatch`.
4. Без агента MCP-прокси отвечает 403 `agent_required`. В `/v1/chat/completions` агент необязателен: тогда действуют правила политики вызовов без поля `agents`.

**MCP-сервер** — вышестоящий сервер, зарегистрированный по образцу провайдера. Поля:

| Поле | Что задаёт |
|---|---|
| `slug` | имя в пути прокси |
| `url` | только `https://` |
| доверенные корневые сертификаты | проверка TLS вышестоящего сервера |
| учётные данные | статический `Authorization: Bearer` или один именованный заголовок; хранятся зашифрованными, в шлюз идут секретом пакета (HPKE) |
| `external` | сервер вне контура заказчика, по умолчанию `true`; снимает только администратор безопасности, это ослабление (DM-40) |
| таймауты | ограничены сверху (раздел 6) |
| версии протокола | `2026-07-28`, `2025-11-25` или обе |

Ограничения адреса:
- Адрес проверяется по правилу каналов этапа 3: запрещены loopback, link-local и адреса метаданных облаков. Проверяется и при сохранении, и при каждом подключении после разрешения имени.
- `http://` без TLS разрешает только администратор безопасности, флагом `insecure_http`. Это ослабление (DM-40), в консоли рядом с ним постоянное предупреждение.

**Инструмент** определяется парой (MCP-сервер, `name`). Для вызовов функций в ответах модели вместо сервера стоит `function`: пара (агент, `function/<name>`). Поля записи реестра:

| Поле | Что задаёт |
|---|---|
| дескриптор | `name`, `title`, `description`, `inputSchema`, `outputSchema`, `annotations` — последний увиденный и одобренный |
| `descriptor_hash` | хеш последнего увиденного дескриптора |
| `approved_hash` | хеш одобренного дескриптора |
| `hash_alg` | алгоритм хеша |
| `risk` | `low`, `medium`, `high`, `critical` |
| `status` | состояние, см. ниже |
| `first_seen`, `last_seen` | когда шлюз впервые и в последний раз видел инструмент |
| одобрение | кто одобрил, когда, комментарий |

Состояния (`status`):

| Состояние | Когда |
|---|---|
| `new` | увиден впервые, не одобрен |
| `approved` | одобрен |
| `changed` | хеш увиденного дескриптора отличается от одобренного, DM-25 |
| `suspicious` | детекторы нашли внедрённые инструкции в описании, DM-24 |
| `revoked` | одобрение снято |

**Уровень риска** ставит администратор безопасности при одобрении. Подсказки сервера (`destructiveHint`, `readOnlyHint` и другие) спецификация велит считать недоверенными. Поэтому они могут только **поднять** предлагаемый уровень: `destructiveHint: true` предлагает `high`. Понизить уровень подсказки не могут.

**Хеш описания:**
- Хешируется `"aisec-tool-descriptor-v1\n"` и каноничный JSON дескриптора: ключи по порядку байтов, без пробелов, строки в UTF-8 без экранирования HTML, числа — исходной записью (`json.Number`).
- В хеш не входят `icons` и `_meta`: модель их не видит, а внешние ссылки консоль не загружает.
- Функция хеша — криптопрофиля через `internal/crypto` (SHA-256 в `standard`, Стрибог-256 в `gost`). Алгоритм хранится рядом с хешем.
- Каноничную форму и хеш вычисляют одной функцией `internal/agents.DescriptorHash` и шлюз, и сервер.

**Одобрение:**
- Одобрение привязано к `approved_hash`. Любое изменение дескриптора переводит запись в `changed`. Вызовы блокируются до повторного одобрения (DM-25).
- При повторном одобрении консоль показывает разницу между одобренным и новым дескриптором.
- Каждое одобрение требует повторной проверки пароля или кода, как ослабление политики.
- Одобрение записи в состоянии `suspicious` или `changed` помечается как ослабление (`weakening: true`) и проходит через DM-40.

**Как шлюз сообщает об увиденных инструментах.** Сервер узнаёт о них из `tools/list` через внутреннюю точку `POST /internal/v1/agents/tools:observe`:
- пакет до 256 дескрипторов;
- без повторов по хешу;
- не чаще раза в 10 с на MCP-сервер.

Новый инструмент поднимает оповещение `agents.tool_new` (тип `new`). Переход в `changed` поднимает `agents.tool_changed`: тип `security`, отключить нельзя, DM-25.

**Пакет конфигурации** получает три раздела: `agents`, `mcp_servers` (секреты в HPKE-части) и `agent_tools` (сервер, имя, `approved_hash`, `risk`, `status`). При изменении любого из них растёт ревизия пакета. Пределы:
- 256 агентов;
- 64 MCP-сервера;
- 2 000 инструментов на установку;
- 256 инструментов на MCP-сервер.

### 2. Политика вызовов — часть версии политики (задача 4.9)
Новый раздел `tools` в YAML версии политики (ADR-0016). Он попадает в подписанный пакет вместе с правилами:

```yaml
tools:
  unapproved: block          # не одобрен, changed, suspicious, revoked; block | log
  default: block             # одобрен, но ни одно правило не подходит (DM-20); block | log
  approval_timeout: 10m      # 1m–60m; по истечении — отказ (DM-22)
  limits:                    # DM-23; 0 — без предела, верхние границы зашиты в код
    agent_per_minute: 120    # вызовов на агента
    session_calls: 500       # вызовов на сессию за 24 ч
    repeat: 5                # одинаковых вызовов (инструмент + хеш аргументов) в сессии
    repeat_window: 10m
  rules:
    - id: reports-read
      agents: [report-bot]   # пусто — все агенты приложения
      tool: files/read_*     # сервер/имя; * только в конце имени
      risk: []               # или отбор по уровню: [high, critical]
      action: allow          # allow | log | require_approval | block
      args:                  # подмножество JSON Schema, раздел 3
        type: object
        required: [path]
        properties:
          path: {type: string, maxLength: 512, x-aisec-path-prefix: ["/data/reports/"]}
      rate: {per_minute: 30, per_hour: 600}
      severity: medium
      message: Чтение разрешено только из каталога отчётов
```

**Как вычисляется решение:**
1. Если инструмент не в состоянии `approved` или его хеш не совпадает с одобренным, применяется `unapproved`.
2. Иначе выбираются все правила, подходящие по агенту, имени и риску. Если ни одно не подошло, применяется `default`.
3. По каждому подходящему правилу проверяются `args` и `rate`. Нарушение `args` даёт `block` с угрозой DM-21. Нарушение `rate` или `limits` даёт `block` с угрозой DM-23.
4. Итоговое действие — самое сильное по таблице приоритетов 5.3: `block` > `require_approval` > `log` > `allow`.
5. Таблица и порядок шагов фиксируются тестом, как `TestPriorityTable`.

**Режим `monitor`** (ТЗ 5.3): `block` и `require_approval` только журналируются, вызов проходит. В событии видно, что было бы сделано в `enforce`. Это касается и DM-25: в `monitor` подменённый инструмент не блокируется, но оповещение `agents.tool_changed` поднимается всегда.

**Совместимость:**
- Версия без раздела `tools` (все политики до этапа 4, YAML без раздела) читается как `unapproved: log`, `default: allow`, без лимитов. Поведение старых приложений не меняется.
- Новая политика из консоли получает `unapproved: block`, `default: block`.
- Новый шаблон «Агент: базовая защита»:
  - `unapproved: block`, `default: block`;
  - правило «`risk: [high, critical]` → `require_approval`»;
  - лимиты по умолчанию.

**Ослабление (DM-40).** К причинам из `versions.Compare` добавляются:

| Причина | Когда |
|---|---|
| `tools_unapproved_weakened` | `unapproved` или `default`: `block` → `log` |
| `tool_rule_added` | новое правило с `allow` или `log` — расширение allowlist |
| `tool_action_weakened` | действие правила стало слабее |
| `tool_scope_widened` | шире стали `agents`, шаблон `tool` или `risk` |
| `tool_args_relaxed` | ограничения аргументов ослаблены или изменены так, что сравнение не доказывает усиления |
| `tool_rate_raised` | выросли лимиты `rate` или `limits` |
| `approval_timeout_raised` | вырос таймаут подтверждения |
| `tool_rule_removed` | удалено правило с `block` или `require_approval` |

Правило сравнения консервативное: изменение, усиление которого не доказано, считается ослаблением. Как и сейчас, ослабление требует повторной проверки пароля или кода, а запись аудита получает `weakening` с причинами.

### 3. Ограничения аргументов — своё подмножество JSON Schema (задача 4.9)
Пакет `internal/policy/argschema` без внешних библиотек. Схема разбирается при сохранении версии и при чтении пакета в шлюзе. Незнакомое ключевое слово — ошибка, а не пропуск: пропуск молча ослабил бы проверку.

**Поддерживается:**
- `type`: одно значение или список из `object`, `array`, `string`, `integer`, `number`, `boolean`, `null`;
- `properties`, `required`, `additionalProperties` (только `true` или `false`, по умолчанию `true`, как в JSON Schema);
- `items` (одна схема), `minItems`, `maxItems`;
- `enum` (до 64 скалярных значений), `const`;
- `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum` (числа);
- `minLength`, `maxLength` (в кодовых точках Unicode);
- `pattern`:
  - смысл как в JSON Schema, то есть без привязки к началу и концу строки; в документации советуем `^…$`;
  - синтаксис RE2 из стандартного `regexp`;
  - не длиннее 512 байт и не больше 4 000 инструкций программы, как у словарей `lists`;
- собственные ключевые слова:
  - `x-aisec-path-prefix`: список разрешённых префиксов пути;
  - `x-aisec-domains`: разрешённые домены адресов e-mail и URL; совпадение точное или по суффиксу `.домен`.

**Как проверяется `x-aisec-path-prefix`.** Путь нормализуется по правилам POSIX (`path.Clean`). Затем:
- отказ, если путь не абсолютный;
- отказ, если в нём есть `\`, NUL или `%` (обход через кодирование);
- отказ, если после нормализации путь выходит за префикс;
- префикс сравнивается по границе каталога: `/data/reports/` не пропускает `/data/reports-old/`.

**Не поддерживается** и отвергается при сохранении:
- `$ref`, `$defs`;
- `oneOf`, `anyOf`, `allOf`, `not`, `if`/`then`/`else`;
- `patternProperties`, `dependentSchemas`, `format`;
- `unevaluated*`;
- удалённые схемы.

Причина — Р2: полный JSON Schema 2020-12 означает большой разборщик недоверенного ввода и разрешение ссылок.

**Схему инструмента из `tools/list` (`inputSchema`) шлюз не исполняет.** Её контролирует вышестоящий сервер, то есть при подмене — атакующий. Проверка аргументов по ней — дело самого MCP-сервера. Шлюз применяет только ограничения из политики. `inputSchema` входит в хеш дескриптора (DM-25) и проходит детекторы (DM-24).

**Лимиты схемы:**

| Что | Предел |
|---|---|
| размер схемы одного правила | 16 КиБ |
| глубина вложенности | 8 |
| узлов в схеме | 256 |
| `pattern` в одной политике | 64 |
| `x-aisec-path-prefix` в одной схеме | 32 |

**Лимиты аргументов вызова:**

| Что | Предел |
|---|---|
| размер аргументов | 256 КиБ |
| глубина вложенности | 32 |
| значений | 10 000 |
| длина строки | 64 КиБ |

**Строгий разбор аргументов.** Повторяющиеся ключи, неверный UTF-8, одиночные суррогаты в `\u` и данные после JSON-значения — отказ вызова. Иначе шлюз и MCP-сервер прочли бы один документ по-разному. Целые сравниваются точно. Число, которое нельзя точно представить для проверки `minimum`/`maximum`, — отказ.

**Fuzz-тесты:** `FuzzParseArgSchema` и `FuzzValidateArgs`.

### 4. Лимиты частоты и цепочек (DM-23, задача 4.9)
Счётчики живут в памяти шлюза: на пилоте один шлюз (ADR-0021). Перенос на аренду у сервера — вместе с квотами в задаче 4.29.

Ключи счётчиков:
- (приложение, агент) — `agent_per_minute`;
- (приложение, агент, правило) — `rate`;
- (приложение, агент, сессия) — `session_calls`;
- (приложение, агент, сессия, инструмент, хеш аргументов) — `repeat`, признак зацикливания.

Сессия определяется так, по порядку:
1. `X-AISec-Session` (задача 4.13).
2. Для клиентов 2025-11-25 — HMAC от `Mcp-Session-Id` на ключе псевдонимов установки.
3. Без сессии считаются только лимиты агента и правила.

Память ограничена: не больше 100 000 ключей, вытеснение давно не использованных. При вытеснении счётчик сбрасывается — это fail-open по счётчику. Вытеснение считается метрикой и выводится на «Состоянии системы». Пакет `internal/policy/toolrate` чистый, без сети: его используют и MCP-прокси, и путь `chat`.

### 5. `require_approval` и очередь подтверждений (DM-22, задача 4.10)

**Где ждёт вызов.** Вызов ждёт решения в шлюзе.

MCP, `tools/call`:
- Шлюз отвечает потоком SSE: спецификация разрешает ответить на запрос потоком.
- Пока решения нет, шлюз каждые 15 с пишет комментарий SSE `: aisec-approval-pending`.
- Если клиент передал `progressToken`, шлюз отправляет и `notifications/progress` с текстом «Ожидает подтверждения».
- Закрытие потока клиентом — отмена по спецификации: запрос в очереди закрывается как `cancelled`.

`/v1/chat/completions`, вызовы функций в ответе модели:
- Ответ с `tool_calls` удерживается до решения. Для агентов с правилами `tools` `holdTools` включается всегда.
- Без потока шлюз ничего не отправляет до решения, ожидание — не дольше `min(approval_timeout, 5 мин)`. Клиенту нужен таймаут больше. В документации — значение для SDK OpenAI и для обратного прокси заказчика.
- В потоке уже отправленный текст остаётся у клиента, а `tool_calls` отправляются после одобрения. Пока ждём, пишутся комментарии SSE.
- Отказ или таймаут оформляется так же, как блокировка в конце потока по действующему `response_check`.

**Запрос в очереди.** Шлюз создаёт его на сервере (`POST /internal/v1/approvals`). В запросе:
- ID (UUIDv7), приложение, агент;
- псевдоним пользователя, сессия;
- MCP-сервер, инструмент, `approved_hash`, уровень риска;
- сработавшее правило и сообщение;
- хеш аргументов;
- аргументы.

Как хранятся аргументы:
- Аргументы нужны дежурному для решения (ТЗ 5.10). Поэтому они передаются независимо от режима хранения приложения, но с маскированием ПДн и секретов (`pii.ru`, `secrets`) и не длиннее 16 КиБ.
- На сервере аргументы шифруются ключом данных и удаляются через 30 суток после решения. Метаданные запроса хранятся по сроку событий.
- Полные аргументы показываются при режиме `full` и только с `events.content.read`, с указанием причины. Факт просмотра пишется в аудит, как у событий.

Контекст для дежурного — хронология сессии (последние шаги и вызовы, задача 4.12), если сессия известна.

**Ожидание решения:**
- Шлюз спрашивает решение долгим опросом `GET /internal/v1/approvals/{id}?wait=25s`.
- У этой точки свой клиент: таймаут ответа 35 с, тот же mTLS. Остальной управляющий канал остаётся с 10 с.
- Отмена: `POST /internal/v1/approvals/{id}:cancel`.
- Решение связано с ID запроса, хешем аргументов и `approved_hash`. Шлюз передаёт вышестоящему серверу ровно те аргументы, которые проверил и показал дежурному (раздел 6).

**Пределы:**
- 256 ожидающих запросов на шлюз и 16 на агента. Сверх них — немедленный отказ `approval_queue_full` с событием и оповещением.
- Сервер недоступен при создании запроса — отказ `approval_unavailable`. Подтверждения без сервера не бывает, поэтому режим при отказе приложения здесь не действует.

**Сроки и перезапуск:**
- Срок ожидания — `approval_timeout` из политики, по умолчанию 10 минут. Затем отказ `approval_timeout`.
- Решение после срока — 409.
- В heartbeat шлюз передаёт список ожидающих ID. Если шлюз перезапустился, сервер закрывает пропавшие из списка запросы как `interrupted`.

**Решение в консоли:**
- Право `approvals.decide` есть у `security_admin` и `analyst`. У `system_admin` и у токенов API его нет: подтверждать вызов должен человек.
- Одобрение вызова с риском `critical` требует повторной проверки пароля или кода.
- Отклонение — с необязательным комментарием, он виден в событии.
- Коды аудита: `agent.approval.approve` и `agent.approval.deny`. Таймаут, отмена и прерывание — не действие администратора: они видны в событии вызова.

**Что получает агент при отказе, таймауте или блокировке:**
- В MCP — результат `tools/call` с `isError: true`. Текст — сообщение правила или «Вызов отклонён» / «Вызов не подтверждён вовремя». В `_meta` — `ru.aisec/decision`.
- Это ошибка выполнения инструмента по спецификации: модель видит причину и не повторяет вызов вслепую. Повторы всё равно ловит `repeat`.
- В `chat` — как блокировка ответа сейчас (`policy_violation`).

**Уведомления.** Встроенное правило `agents.approval_requested`:
- получатели по умолчанию — `security_admin` и `analyst`;
- одно уведомление на запрос, без группировки: важна задержка;
- больше 20 запросов за 10 минут объединяются в одно уведомление со списком;
- в канал уходят приложение, агент, инструмент, риск, срок и ссылка на консоль. Аргументы и содержимое — никогда: каналы могут быть внешними.

**Режим `monitor`:** `require_approval` только журналируется (ТЗ 5.3), очередь не создаётся.

### 6. MCP-прокси в шлюзе (задача 4.11)

**Точка входа:**
- `POST /mcp/v1/{server}` на слушателе приложений шлюза, вход по ключу приложения. Агент — по разделу 1.
- `{server}` — slug MCP-сервера из списка агента, иначе 403 `mcp_server_not_allowed`.
- Один путь соответствует одному вышестоящему серверу. Агрегации нескольких серверов в одной точке нет.
- `GET` и `DELETE` → 405. Спецификация 2025-11-25 это разрешает, в 2026-07-28 этих методов нет.

**Транспорт — только Streamable HTTP** (Р2):
- stdio-серверы остаются вне шлюза;
- устаревший HTTP+SSE (2024-11-05) не поддерживается;
- ответ вышестоящего сервера может быть `application/json` или `text/event-stream`, клиенту отдаётся в том же виде.

**Версии протокола:** `2026-07-28` и `2025-11-25`. Шлюз не переводит одну версию в другую: вышестоящий сервер должен поддерживать версию клиента.
- 2026-07-28:
  - заголовок `MCP-Protocol-Version` обязан совпадать с `_meta["io.modelcontextprotocol/protocolVersion"]`;
  - `Mcp-Method` и `Mcp-Name` (с base64-обёрткой `=?base64?…?=`) обязаны совпадать с телом;
  - иначе 400 и ошибка `-32020` (`HeaderMismatch`);
  - неизвестная версия — 400 `UnsupportedProtocolVersionError` со списком поддерживаемых.
- 2025-11-25:
  - `initialize` разрешён; шлюз сверяет предложенную версию и отвечает своей, если версия клиента не поддерживается;
  - `Mcp-Session-Id` пропускается, но привязан к (ключ приложения, MCP-сервер): чужая сессия — 404;
  - таблица сессий в памяти: TTL 24 ч, до 10 000 записей.

**Разбор JSON-RPC.** Пакет `internal/mcp`, без сети. Тело:
- одно сообщение JSON-RPC; пакеты (массивы) — отказ;
- размер — не больше `max-body-bytes` приложения;
- `jsonrpc` равно `"2.0"`;
- `id` — строка до 128 байт или целое без дробной части, не `null`;
- `method` до 128 байт, `params` — объект;
- повторяющиеся ключи, неверный UTF-8 и вложенность глубже 32 — отказ;
- fuzz-тесты: `FuzzParseJSONRPC`, `FuzzParseSSE`, `FuzzToolsListResult`, `FuzzCallToolResult`.

**Разрешённые методы клиента:**

| Ревизия | Методы |
|---|---|
| обе | `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list`, `prompts/get` |
| 2026-07-28 | `server/discover`, `subscriptions/listen` |
| 2025-11-25 | `initialize`, `notifications/initialized`, `ping`, `notifications/cancelled` |

Остальные методы получают `-32601` от шлюза и событие. Это, например, `completion/complete`, `logging/setLevel`, `tasks/*`, а также ответы клиента на запросы сервера.

**Возможности клиента.** Из `initialize.params.capabilities` и `_meta["io.modelcontextprotocol/clientCapabilities"]` шлюз удаляет `sampling`, `elicitation`, `roots`, `tasks` и `extensions`:
- Каждой из этих возможностей нужны свои проверки содержимого. Sampling и roots спецификация 2026-07-28 к тому же объявила устаревшими.
- От сервера к клиенту пропускаются только уведомления `notifications/progress` и `notifications/*/list_changed`, а также ответ с тем же `id`.
- Запросы сервера к клиенту (2025-11-25) и результаты `input_required` (2026-07-28) не передаются клиенту: вместо них — ошибка и событие.
- Возможности добавляются дополнением к ADR.

**Заголовки к вышестоящему серверу.** Шлюз передаёт только:
- `Content-Type`, `Accept`;
- `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`;
- `Mcp-Session-Id` (2025-11-25);
- `traceparent`;
- учётные данные из реестра.

Не передаются `Authorization` клиента (это ключ шлюза; передача токена дальше запрещена и спецификацией авторизации MCP), `Cookie` и `X-AISec-*`.

Тело запроса шлюз собирает заново из проверенного документа, а не пересылает исходные байты. Заголовки `Mcp-Param-*` строятся заново по `x-mcp-header` одобренной `inputSchema`. Так заголовки и тело не расходятся с тем, что проверено.

Заголовок `Origin`:
- есть и не входит в разрешённые источники приложения (по умолчанию пусто) → 403;
- браузерные клиенты по умолчанию не допускаются.

**`tools/list`** (DM-24, DM-25):
1. Каждый дескриптор разбирается с лимитами: до 256 инструментов на страницу, 64 КиБ на дескриптор, `description` до 32 КиБ.
2. Шлюз вычисляет хеш и сверяет его с реестром из пакета.
3. Все строки дескриптора — `title`, `description`, описания и значения `enum`/`default` внутри `inputSchema` — проходят `injection.heuristic` и `unicode.hidden` с источником `tool`. Эта проверка встроенная: она работает и тогда, когда в политике нет входных правил с источником `tool`. Ещё применяются входные правила политики с источником `tool`.
4. В `enforce` клиенту возвращаются только инструменты, которые сейчас разрешены агенту: одобрены, хеш совпадает, нет находок DM-24, подходит правило с действием не `block`. Остальные убираются из списка. Так модель не видит лишних инструментов (принцип наименьших полномочий, LLM06).
5. В `monitor` возвращается всё, находки журналируются.
6. Новые и изменённые дескрипторы уходят на сервер (`tools:observe`).
7. В ответе шлюз ставит `cacheScope: "private"` и `ttlMs` не больше 60 000: список зависит от агента, а отзыв одобрения должен дойти до клиента за минуту.
8. `nextCursor` пропускается без изменений.

**`tools/call`** (DM-20–DM-23, DM-07):
1. Шлюз проверяет инструмент: он в реестре, одобрен, и хеш, увиденный в последнем `tools/list` этого сервера, равен одобренному. Если `tools/list` ещё не видели, шлюз сам запрашивает его у вышестоящего сервера перед первым вызовом.
2. Политика вызовов (раздел 2).
3. Детекторы политики по аргументам:
   - направление `input`, источник `tool_args` — новое значение `detect.Source`;
   - находки ПДн и секретов при `external: true` сервера идут под DM-31 и DM-32;
   - `redact` и `pseudonymize` к аргументам не применяются, потому что сломали бы вызов: действует `block` или запись в журнал; событие показывает, что маскирование аргументов не выполнялось.
4. `require_approval` — раздел 5.
5. Вызов вышестоящего сервера.
6. Результат:
   - `content[].text`, текст встроенных ресурсов и строковые значения `structuredContent` (с путём) проходят детекторы политики для источника `tool` — косвенная инъекция DM-07 (S6), ПДн, секреты;
   - `image` и `audio` обрабатываются по `non_text` политики: этап 5 добавит `aisec-media`, до него — блокировка или отметка «не проверено»;
   - `resource_link` пропускается с отметкой, URI проверяет `output.exfil`.
7. Действия над результатом:
   - `block` заменяет результат на `isError: true` с сообщением;
   - `redact` маскирует строки в `content` и `structuredContent` (JSON собирается заново);
   - `pseudonymize` для результата выполняется как `redact`: обратной подстановки на этом пути нет.

**`resources/read`, `prompts/get`:** результат проверяется как результат инструмента (DM-07).
**`resources/list`, `prompts/list`:** описания проходят встроенную проверку `tools/list`. Реестра и одобрения для ресурсов и промптов в этапе 4 нет.
**`subscriptions/listen`:**
- поток не дольше 1 ч, затем шлюз закрывает его;
- пропускаются только `notifications/*/list_changed` и подтверждение подписки;
- новый список всё равно пройдёт проверку `tools/list`.

**Лимиты и таймауты вышестоящего сервера:**

| Что | Значение |
|---|---|
| соединение | 10 с |
| `tools/list` | 30 с |
| `tools/call` | по умолчанию 120 с, в карточке сервера до 10 мин (без времени ожидания подтверждения) |
| ответ JSON или поток SSE | до 4 МиБ на сообщение, до 1 024 событий SSE на запрос |
| одновременных запросов к серверу | 64 |
| перенаправления | не выполняются |

Каждый исходящий вызов — с контекстом запроса клиента.

**Где код:**
- Сетевой клиент живёт в `internal/gateway` (уже в `NET_CLIENT_ALLOWED`). Новых разрешений сетевых клиентов не нужно.
- Разборщики — в `internal/mcp` без сетевого кода.
- TLS — `*tls.Config` из `internal/crypto`.

### 7. События агентов (ТЗ 5.5)
Два новых типа событий.

**`agent_tool_call`** — вызов инструмента. Источник — `tools/call` через MCP-прокси или `tool_calls` в ответе модели. Поля:
- `path` (`mcp` или `chat`), `request_event_id` для `chat`;
- агент, MCP-сервер, инструмент, `tool_hash`, риск;
- сессия;
- решение и трассировка по правилам `tools`;
- `approval`: ID, состояние (`approved`, `denied`, `timeout`, `cancelled`, `interrupted`, `queue_full`, `unavailable`), кто решил (пользователь консоли), ожидание в миллисекундах, комментарий;
- находки по аргументам и по результату;
- угрозы (DM-07, DM-20–DM-25);
- задержки вышестоящего сервера, размер результата, `isError`;
- аргументы и результат — по режиму хранения приложения (`none`, `masked`, `full`), как содержимое других событий.

**`agent_mcp`** — остальные методы MCP: `tools/list`, `resources/*`, `prompts/*`, `server/discover`, отклонённые методы. Поля: метод, сервер, число инструментов или элементов, находки по описаниям (DM-24), расхождения хеша (DM-25), отклонения протокола (заголовки, версия, метод).

Хронологию сессии (4.12) консоль строит по событиям `gateway_request`, `check`, `agent_tool_call`, `agent_mcp` с одной сессией.

### 9. Права и роли
Новые права (имена из 2–3 частей):

| Право | Безопасности | `security_admin` | `system_admin` | `analyst` | `auditor` | `app_owner` |
|---|---|---|---|---|---|---|
| `agents.read` (агенты, MCP-серверы, инструменты) | нет | да | да | да | да | своих приложений (`own`) |
| `agents.manage` (агенты, MCP-серверы, привязка ключей) | нет | да | да | — | — | — |
| `agents.tools.approve` (одобрение, снятие, риск) | да | да | — | — | — | — |
| `approvals.read` | нет | да | — | да | да | — |
| `approvals.decide` | да* | да | — | да | — | — |

\* У `approvals.decide` признак безопасности означает: не выдаётся `system_admin` и токенам, не входит в «.read» аудитора. Если текущий признак `Security` не допускает выдачу роли `analyst`, задача 4.10 добавляет признак «только человеку» (`HumanOnly`), а не ослабляет `Security`.

Ослабляющие действия в `agents.manage` проходят повторную проверку и DM-40. Это расширение `mcp_servers` агента, снятие `external`, `insecure_http`. При этом `external` и `insecure_http` меняет только администратор безопасности, как признак «внешний» у провайдера.

Политика вызовов — часть политики, поэтому её меняет право `policies.manage`.

Каждое действие пишет аудит: `agent.create|update|delete`, `mcp_server.create|update|delete`, `agent_tool.approve|revoke|risk`, `agent.approval.approve|deny`.

### 10. Поверхность атаки (дополнить `attack-surface.md` в задачах 4.8–4.11)
- **Шлюз:**
  - `POST /mcp/v1/{server}`, `GET` и `DELETE` → 405;
  - заголовки `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`, `Mcp-Param-*`, `Mcp-Session-Id`, `X-AISec-Agent`, `X-AISec-Session`, `Origin`;
  - исходящие соединения к MCP-серверам из реестра.
- **Внутренний API:**
  - `POST /internal/v1/agents/tools:observe`;
  - `POST /internal/v1/approvals`;
  - `GET /internal/v1/approvals/{id}?wait=`;
  - `POST /internal/v1/approvals/{id}:cancel`;
  - поле ожидающих подтверждений в heartbeat.
- **API консоли:**
  - `/api/v1/agents`, `/api/v1/mcp-servers`, `/api/v1/agent-tools` (с `:approve`, `:revoke`);
  - `/api/v1/approvals` (с `:approve`, `:deny`).
- **Пакет конфигурации:** разделы `agents`, `mcp_servers`, `agent_tools`; раздел `tools` в YAML политики.
- **События:** типы `agent_tool_call`, `agent_mcp`.

### 11. Правило обновления версии MCP
Спецификация MCP меняется быстро.
- Новая ревизия MCP добавляется в шлюз дополнением к этому ADR: разбор, тесты совместимости, список разрешённых методов.
- Ревизия, которую спецификация перевела в Removed, удаляется в ближайшем выпуске. Устаревшие (Deprecated) возможности не включаются.
- Сверка версии — при каждой задаче, которая трогает `internal/mcp`, и при закрытии этапа. Результат записывается строкой в журнал этапа.

## Альтернативы
- **stdio-серверы через шлюз** (шлюз запускает процесс MCP-сервера). Отклонено:
  - `os/exec` в серверных компонентах запрещён;
  - шлюз стал бы средой исполнения чужого кода;
  - stdio-сервер живёт рядом с агентом, а не со шлюзом.
- **Отдельный процесс-прокси `aisec-mcp`.** Отложено:
  - пришлось бы дублировать пакет конфигурации, политику, детекторы, события и связь с сервером;
  - шлюз и так сетевой посредник с теми же функциями;
  - вынести можно позже без смены внешнего контракта: путь `/mcp/v1/{server}` останется.
- **Полный JSON Schema библиотекой** (например, `santhosh-tekuri/jsonschema`). Отклонено по Р2: новая зависимость, большой разборщик недоверенного ввода, `$ref` с разрешением ссылок.
- **Проверка аргументов по `inputSchema` сервера.** Отклонено: схему контролирует сервер, а при подмене описания — атакующий.
- **Агрегация нескольких MCP-серверов в одной точке.** Отложено: конфликты имён, переименование инструментов, которое видит модель. Можно добавить отдельной точкой.
- **Передача `Authorization` клиента вышестоящему серверу (OAuth MCP).** Отклонено:
  - спецификация авторизации MCP запрещает передавать токен дальше;
  - ключ шлюза не должен уходить наружу.

  Учётные данные пользователя для MCP-сервера (OAuth на пользователя) — отдельным решением, когда попросит пилот.
- **Подтверждение через расширение `tasks`** (вызов сразу возвращает задачу, клиент опрашивает её). Отложено: это расширение, а не ядро протокола, и клиенты поддерживают его неравномерно. Вернуться, когда расширение устоится — подтверждения дольше 10 минут без удержания соединения.
- **На пути `chat` заменять `require_approval` блокировкой.** Отклонено: ТЗ 5.10 требует подтверждения для высокорисковых вызовов независимо от того, как агент исполняет инструменты. Удержание ответа ограничено 5 минутами.
- **Агент как вид приложения.** Отклонено: у одного сервиса бывает несколько агентов с разными правами, а квоты, бюджеты, ключи и режим хранения — общие для приложения.
- **Блокировать подменённый инструмент и в `monitor`.** Отклонено: это противоречит 5.3. Взамен оповещение DM-25 поднимается всегда.

## Последствия
- Задачи 4.8–4.11 получают модель данных, формат раздела `tools`, пределы и права. Разбиение по файлам и тестам — в `docs/plans/stage-4.md`, раздел «Уточнения задач 4.8–4.12».
- В `internal/gateway` добавляется MCP-клиент. В `NET_CLIENT_ALLOWED` ничего не меняется, а `attack-surface.md` получает новый исходящий поток «шлюз → MCP-серверы».
- Внутренний API получает первую долгую операцию (ожидание подтверждения) со своим таймаутом клиента. Остальной управляющий канал не меняется.
- Политика без раздела `tools` ведёт себя как раньше. Защита агентов включается шаблоном «Агент: базовая защита» или ручным разделом `tools`.
- Подтверждение держит соединение до 10 минут, на пути `chat` до 5 минут. Таймауты клиента и обратного прокси заказчика должны быть больше. Это пишется в руководство администратора (4.31).
- Sampling, elicitation, roots, tasks, OAuth на пользователя и HTTP+SSE не поддерживаются. Если агенту они нужны, он обращается к серверу напрямую, мимо шлюза, и это видно по отсутствию событий. Для контроля такие обращения закрывает сетевой экран заказчика.
- Откат: прокси выключается удалением MCP-серверов из реестра. Раздел `tools` удаляется новой версией политики — это ослабление с повторной проверкой. Миграции реестра обратимы удалением таблиц: на них никто, кроме модуля агентов, не ссылается.

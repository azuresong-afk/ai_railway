# ADR-0003. Инструменты сборочной среды и сборка без интернета

- Статус: принято
- Дата: 29.09.2026
- Связанные разделы ТЗ: 8.2, 8.6, 8.7, 15 («Закрытый контур»); `CLAUDE.md`, «Зависимости»

## Контекст
1. Продукт должен собираться и проверяться без интернета: в закрытом контуре и в сборочной среде, которую проверяет лаборатория (ТЗ, 8.7). При этом часть проверок по природе требует внешних данных: govulncheck — базу уязвимостей Go, npm — реестр пакетов.
2. `CLAUDE.md` запрещает GPL для зависимостей. Основной линтер Go — golangci-lint (вместе с depguard) — распространяется под GPL-3.0, как и GNU Make.
3. Инструменты разработки не входят в поставку, но методика ФСТЭК проверяет и сборочную среду, поэтому их нужно учитывать.

## Решение
1. **Инструменты сборочной среды — не компоненты продукта.** Программы, которые запускаются только при сборке и проверке и не линкуются в продукт и не поставляются заказчику (golangci-lint, GNU Make, govulncheck, sbom-utility), могут иметь лицензию GPL. Запрет GPL из `CLAUDE.md` действует для кода, который попадает в продукт: библиотеки, вендоренные модули, npm-пакеты в составе консоли, образы в поставке. Инструменты учитываются в `docs/cert/components.yaml` с `scope: build` и в SBOM продукта не входят (решения Д1 и Д5 плана этапа 0).
2. **Скрытые загрузки запрещены.** `Makefile` задаёт `GOFLAGS=-mod=vendor` и `GOPROXY=off` без возможности переопределить их окружением; `GOTOOLCHAIN` — только `local` или точная версия. Единственная цель, которая явно ходит в сеть, — `make tools` (установка инструментов по зафиксированным версиям с проверкой по `sum.golang.org`).
3. **Инструменты и toolchain — в сборочном образе.** Образ `golang` по digest с установленными инструментами (задача 0.15). В закрытом контуре образ переносится целиком.
4. **База уязвимостей Go.** `make vuln` использует `GOVULNDB` (по умолчанию `https://vuln.go.dev`). В закрытом контуре — локальный снимок: `make vuln GOVULNDB=file:///<каталог>`, где каталог повторяет структуру базы (`index/`, `ID/`). Снимок переносится на внешнем носителе вместе с датой; снимок старше 7 дней считается устаревшим, это фиксируется в отчёте о сборке. Способ получения снимка проверяется при подготовке сборочного образа (задача 0.15).
5. **npm.** До этапа 6 пакеты ставятся из публичного реестра строго по lock-файлу (`npm ci`) с проверкой хешей `integrity`. К этапу 6 — внутреннее зеркало, отдельным решением вместе с переездом хостинга.
6. **Доказательство.** `make check-offline` (задача 0.15) — `make check` в контейнере без сети (`--network=none`) с локальным снимком базы уязвимостей.

## Альтернативы
- **Без GPL-инструментов** (staticcheck, gosec, errcheck по отдельности и своя проверка импортов вместо depguard) — отклонено: дольше в поддержке, три синтаксиса подавлений, а GNU Make всё равно под GPL.
- **Пропускать govulncheck без сети** — отклонено: проверка уязвимостей не должна молча выключаться; без базы `make vuln` падает.
- **Вендорить исходники инструментов** — отклонено: сотни модулей (у golangci-lint — 223) в дереве продукта без пользы; сборочный образ решает задачу проще.

## Последствия
- `make check` без доступа к базе уязвимостей падает на `make vuln`. Так и должно быть: нужна либо сеть до `vuln.go.dev`, либо локальный снимок.
- В облачной среде разработки, где сетевая политика запрещает `vuln.go.dev`, проверка уязвимостей выполняется в CI; в плане задачи это отмечается явно.
- При обновлении инструмента меняются одновременно: переменная версии в `Makefile`, `components.yaml`, сборочный образ.

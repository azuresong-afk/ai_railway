# ADR-0008. Архивация журнала аудита с подписанной контрольной точкой

- Статус: предложено
- Дата: 21.10.2026
- Связанные разделы ТЗ: 7.4 (РСБ.3, РСБ.4, РСБ.5), 7.2 (УПД.2), 5.16 (DM-43), 10.2; решение Р5 плана этапа 2; ADR-0006, ADR-0007

## Контекст
Журнал аудита (задача 2.4) — таблица только для добавления: роль приложения имеет `SELECT, INSERT`, триггеры запрещают `UPDATE` и `TRUNCATE` всем, а `DELETE` — всем, кроме роли `aisec_audit_archiver`. Записи связаны цепочкой хешей со сплошной нумерацией, удаление начала цепочки проверка видит как `head_missing`.

РСБ.3 задаёт срок хранения (30–3650 дней), а РСБ.4 требует, чтобы срок хранения не нарушал правило «только добавление»: записи старше срока выгружаются в архив с подписанной контрольной точкой и только затем удаляются, отдельной процедурой под отдельной ролью СУБД и только командой `aisec-cli`. Новая часть цепочки начинается от контрольной точки. РСБ.5 требует выгрузку журнала в файл для переноса на внешний носитель.

Ошибки здесь трудно откатить: удалённые записи без проверяемого архива потеряны, а процедура, которая позволяет удалить начало журнала без следа, обесценивает всю цепочку (DM-43).

## Решение
1. **Команды.** `aisec-cli audit archive -keys <каталог> -out <файл> [-before ГГГГ-ММ-ДД]` (РСБ.4), `aisec-cli audit export -out <файл> [-from …] [-to …]` (РСБ.5, без удаления), `aisec-cli audit verify-archive -keys <каталог> <файл>` (проверка архива без БД), `aisec-cli audit verify [-keys <каталог>]` (с `-keys` проверяются и подписи точек). Через интерфейс и API продукта удалить записи нельзя (УПД.2).
2. **Граница.** По умолчанию — срок хранения из `audit_settings` (РСБ.3, по умолчанию 365 дней). `-before` сдвигает её только в прошлое. Архивируется только непрерывное начало цепочки: записи после последней точки до первой записи не старше границы. **Последняя запись журнала не архивируется никогда**: хранимая часть не бывает пустой, и её начало видно по самой цепочке.
3. **Порядок.** Самотест профиля → проверка всей цепочки (`Verifier`; нарушенную цепочку не архивируем, иначе архив узаконил бы подмену) → файл архива `O_CREATE|O_EXCL`, 0600, `fsync` каталога → одна транзакция под `SET LOCAL ROLE aisec_audit_archiver` и рекомендательной блокировкой: проверка прежних точек ключом аудита → чтение записей с повторной проверкой цепочки и запись файла → подпись точки → строка точки, `fsync` файла → `INSERT audit_checkpoints` → `DELETE` архивируемых записей со сверкой числа удалённых строк → запись `audit.archive` в той же транзакции → `COMMIT`. Файл и запись каталога о нём сбрасываются на диск **до** удаления записей. Если точка не подписана или точно не записана, файл удаляется. Если ошибка пришла на `COMMIT`, команда проверяет строку точки, предварительно взяв ту же рекомендательную блокировку (она держится до конца исходной транзакции, и ответ не опередит идущую фиксацию): есть — успех; проверить не удалось — файл **сохраняется** (записи могли быть уже удалены, и архив — их единственная копия), администратор получает инструкцию.
4. **Файл архива** — JSON Lines, строки до 256 КиБ. Первая строка — заголовок: формат `aisec-audit-archive`, версия, организация, алгоритм хеша, предыдущая точка (`prev_seq`, `prev_hash`), диапазон номеров, время. Далее записи в канонической форме, по которой считается хеш цепочки, плюс `hash`. Последняя строка — контрольная точка и подпись. Хеш тела (заголовок и записи) входит в точку, поэтому файл проверяется без БД. Выгрузка (`export`) — тот же формат с типом `aisec-audit-export`, без точки и подписи: цепочка в ней проверяется по хешам записей.
5. **Контрольная точка** — `audit_checkpoints`: номер и хеш последней архивированной записи, предыдущая точка (у первой — 0 и нулевой хеш), число записей (= разности номеров), имя и хеш тела архива, время, алгоритм, подпись, открытый ключ (только для сверки). Подписывается Ed25519 по канонической форме с контекстом `aisec-audit-checkpoint-v1\n`: подпись точки не подходит ни к чему другому. Таблица только для добавления: триггеры запрещают `UPDATE`, `DELETE`, `TRUNCATE` всем.
6. **Ключ подписи аудита** — отдельная пара `audit-signing.key` (0400) и `audit-signing.pub` (0444) в каталоге ключей, PEM `AISEC AUDIT SIGNING KEY` / `AISEC AUDIT SIGNING PUBLIC KEY`. Её создаёт `init`; для установок, где `init` прошёл до этого ADR, — `init -add-audit-key` (только эта пара, нужен каталог установки и ключ данных в БД, запись `system.audit_key`). Ключ пакетов (ADR-0007) не используется: он нужен серверу постоянно, а ключ аудита — только `aisec-cli` при архивации; компрометация одного не позволяет подделать другое. Проверка подписи — всегда ключом из каталога ключей, не из таблицы. **Ротации ключа аудита до этапа 6 нет**: все точки проверяются одним открытым ключом, смена пары сделала бы прежние точки непроверяемыми. Ротация (набор доверенных открытых ключей с отпечатком в точке) — отдельным ADR.
7. **Проверка цепочки после архивации.** `Log` получает точки через `WithCheckpoints`; проверяются связность всех точек (каждая продолжает предыдущую, число записей сходится, алгоритм профиля) и, при наличии открытого ключа, их подписи. Хранимая часть проверяется от последней точки; после точки журнал не бывает пустым (последняя запись не архивируется), пустой — `tail_truncated`. Нарушение последовательности точек или подписи — `checkpoint_invalid` (DM-43). Сервер получает открытый ключ аудита параметром `-audit-signing-pub` (`AISEC_SERVER_AUDIT_SIGNING_PUB`) и проверяет подписи. Параметр обязателен, как только в `audit_checkpoints` есть точки: без него сервер не запускается; новая установка без точек стартует без ключа (с предупреждением), в поставке и стенде разработки параметр задаётся (решение владельца 21.10.2026 по замечанию В5 ревью 2.r1). `aisec-cli audit verify -keys` проверяет подписи всегда. Если архивация зафиксировалась между чтением точки и записей, проверка видит смену точки и проходит заново от новой — ложного `head_missing` нет.
8. **Инварианты в СУБД** (миграция `0005_audit_archive`, функции с фиксированным `search_path`). Триггер `audit_log_link` для пустого журнала требует, чтобы первая запись продолжала последнюю точку, а без точек — начиналась с номера 1 и нулевого `prev_hash`; раньше пустая таблица принимала любую первую запись. Триггер `audit_checkpoints_link` принимает точку, только если она продолжает последнюю, её запись есть в журнале с тем же хешем и алгоритмом, все записи диапазона на месте и после неё журнал продолжается. `audit_log_guard` разрешает архиватору `DELETE` только записей, покрытых точкой. Поэтому даже участник роли архиватора без ключа аудита не удалит записи незаметно: удаление требует точки, точка описывает реальные записи и остаётся в таблице, а её поддельную подпись видит проверка открытым ключом.
9. **Права.** `aisec_audit_archiver` (без входа, `NOLOGIN`): `SELECT, INSERT, DELETE` на `audit_log`, `SELECT, INSERT` на `audit_checkpoints`, `SELECT` на `audit_settings`. Логину, от которого запускается `aisec-cli audit archive`, нужно членство в этой роли; у логина сервера (`aisec_app`) его нет. `aisec_app` — только `SELECT` на `audit_checkpoints`.
10. **Объём.** Удаление — одной транзакцией с таймаутом 10 мин: для журнала до миллионов записей достаточно. Пакетная архивация — отдельным решением, если понадобится.
11. **Опора между архивациями** (дополнение 21.10.2026, замечания В1 и В2 ревью 2.r1). Сервер проверяет цепочку сразу после запуска и раз в `-audit-verify-interval` (по умолчанию час); итог — в «Состоянии системы» (уведомление РСБ.4) и `system.alert`. Подписанная точка появляется только при архивации, а ключа подписи аудита у сервера нет и не должно быть (п. 6), поэтому между архивациями голова цепочки защищается имитовставкой: в строке `audit_verifications` хранятся `head_mac` — HMAC профиля от контекста `aisec-audit-head-v1`, номера и хеша последней проверенной записи — и `mac_key_id`. Ключ выводится из действующего ключа данных (`keyring.Box.MAC`, назначение `audit-head`, ADR-0007 п. 8), который расшифровывается мастер-ключом из файла: владелец таблиц не может подделать имитовставку после переписывания журнала. Опорой служит только строка с верной имитовставкой действующего ключа данных; строки без неё (проверки до миграции `0015`, `aisec-cli audit verify` без `master.key` в каталоге ключей) и строки прежнего ключа данных пропускаются, строка с неверной имитовставкой — нарушение `anchor_forged`.

## Альтернативы
- **Общий ключ с подписью пакетов конфигурации.** Меньше файлов, но ключ пакетов нужен серверу онлайн, и его компрометация позволила бы подделать и историю аудита. Отклонено.
- **Удаление без архива с сохранением только точки.** Проще, но нарушает РСБ.4 («выгружаются в архив») и лишает разбор инцидентов исходных записей. Отклонено.
- **Партиционирование `audit_log` и `DROP PARTITION`.** Быстро на больших объёмах, но обходит построчный триггер, требует прав владельца таблицы и усложняет миграции. Отложено до появления объёмов, при которых одна транзакция не укладывается.
- **Архив в БД (отдельная таблица).** Не решает задачу переноса на внешний носитель (РСБ.5) и не уменьшает объём БД. Отклонено.
- **Подпись всего файла вместо точки.** Точка в БД связывает хранимую часть с архивом; подписанный хеш тела внутри точки даёт и то и другое одной подписью.

## Последствия
- Удаление записей аудита в обход `aisec-cli` возможно только участнику роли `aisec_audit_archiver` и только с точкой, покрывающей реальные записи; без ключа аудита её подпись не проверится (сервер с `-audit-signing-pub`, `audit verify -keys`). Каждая архивация `aisec-cli` оставляет точку и запись `audit.archive`. Владелец таблиц и суперпользователь СУБД могут отключить триггеры — это вне модели (ТЗ 5.16, DM-43): против них — цепочка, подписи и проверка известных записей.
- Администратор хранит файлы архива на внешнем носителе и проверяет их `verify-archive`; `audit-signing.pub` хранится вместе с архивами. Выгрузка (`export`) пишет в заголовок начало хранимой части из того же снимка — цепочка полной выгрузки проверяется вне продукта.
- Сервер подключает точки (`cmd/aisec-server`, новый параметр `-audit-signing-pub`); без них после первой архивации проверка покажет `head_missing`.
- Имитовставка головы (п. 11) не защищает от суперпользователя СУБД, который удалит в обход триггеров все строки `audit_verifications` с имитовставкой: это остаточный риск в `threat-model.md`, опора вне СУБД целиком — выгрузка в syslog на этапе 3. После ротации ключа данных опорой становится первая проверка новым ключом.
- Код: `internal/audit/checkpoint.go`, `archivefile.go`, `archive.go` (`Archive`, `Export`, `VerifyArchive`, `PGCheckpoints`), `internal/audit/verify.go` (`checkpoint_invalid`), `cmd/aisec-cli/audit_archive.go`, `cmd/aisec-cli/init.go` (ключ аудита, `-add-audit-key`), `internal/crypto/keyfile.go` (виды PEM), миграция `0005_audit_archive`, события `audit.archive`, `audit.export`, `system.audit_key`.
- Документы: `docs/cert/security-functions.md` (РСБ.4, РСБ.5), `docs/cert/attack-surface.md` (команды и форматы файлов), `docs/cert/threat-model.md` (DM-43), `docs/cert/fuzzing.md` (`FuzzVerifyArchive`).
- Откат: миграция только добавляет таблицу, триггеры, права и заменяет функцию `audit_log_link`; после первой архивации откат возможен только с сохранением точек, иначе хранимая часть журнала перестанет проверяться.

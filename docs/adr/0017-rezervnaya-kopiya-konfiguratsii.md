# ADR-0017. Резервная копия конфигурации: ключ из парольной фразы, состав и восстановление

- Статус: принято (решения H-Р1–Р3 по поручению владельца, 22.10.2026; п. 7 и 8 — их реализация)
- Дата: 22.10.2026
- Связанные разделы ТЗ: 7.7 (РВ.1), 7.9 (ЗИ.1), 7.5 (РСБ.2), 10.2, 10.4; решения H-Р1–Р3 волны H этапа 2; задача 2.19 этапа 2

## Контекст
РВ.1 требует сохранять конфигурацию в зашифрованный файл и восстанавливать её: политики, приложения, пользователей, роли, настройки и ключ HMAC псевдонимов. Без ключа HMAC псевдонимы после восстановления не совпадут со старыми событиями. Копия нужна прежде всего при потере установки, в том числе мастер-ключа (ADR-0007). Поэтому шифровать её ключом установки нельзя. Ограничения: криптография только в `internal/crypto`, новых зависимостей нет, секреты не попадают в журналы и на диск в открытом виде, триггеры БД запрещают удалять пользователей, приложения, ключи и версии политик. Решения H-Р1–Р3 владелец поручил принять по общепринятой практике (22.10.2026).

## Решение
1. **Ключ копии — из парольной фразы администратора (H-Р1).** `PassphraseKDF` в `internal/crypto` использует Argon2id с параметрами Р3 (`m=65536,t=3,p=2`, ADR-0006). Соль 16 байт и параметры лежат в заголовке файла. При разборе параметров действуют те же границы, что у хешей паролей: подложенный файл не поднимет память выше 64 МиБ. Из 32 байт Argon2id через HKDF-SHA-256 выводятся два ключа AES-256-GCM: ключ содержимого (`aisec-backup-v1|payload`) и ключ секретов (`aisec-backup-v1|secret`). Мастер-ключ установки в копии не участвует. Фраза не короче 16 символов. Её вводят дважды с терминала без отображения или читают из файла с правами ровно 0400. В аргументах фраза не принимается.
2. **Формат файла `aisec-config-backup`, версия 1.** Первая строка — открытый заголовок JSON: формат, версия, профиль, KDF, параметры, соль, алгоритм, время. Дальше идёт шифротекст содержимого с AAD `payload|<строка заголовка>`, поэтому подмена версии, соли или параметров ломает расшифрование. Предел файла — 64 МиБ (предел одного шифрования). Файл пишется во временный файл 0600 в том же каталоге через `os.Root`, затем ставится жёсткой ссылкой под итоговое имя. Существующий файл не перезаписывается.
3. **Проверка при восстановлении** идёт в таком порядке: AEAD, версия формата, строгая схема. Схема — JSON без неизвестных полей и без данных после объекта, с пределами числа объектов, форматом ID, ссылочной целостностью внутри копии, номерами версий политик подряд с 1 и совпадением хеша версии с её текстом. Неверную фразу и подменённый файл не различить: в обоих случаях один отказ, код возврата 3.
4. **Секреты перешифровываются поштучно.** Учётные данные провайдеров, секреты TOTP и ключ HMAC расшифровываются ключом данных и сразу шифруются ключом секретов копии с AAD «вид секрета, ID объекта». Открытый текст затирается. В JSON содержимого лежат только шифротексты, поэтому секретов в открытом виде нет даже в памяти кодировщика JSON. При восстановлении каждый секрет так же поштучно переходит под ключ данных новой установки с AAD места хранения (Р4).
5. **Состав (H-Р2).** Политики со всеми версиями. Приложения с ключами (хеши, сроки, ротация, отзыв). Провайдеры. Пользователи с хешами паролей, историей паролей, вторым фактором и хешами кодов восстановления. Токены API (хеши). Свои роли с разрешениями. Название организации. Настройки входа, аудита, сроков хранения событий и первичной настройки (часовой пояс и режим хранения по умолчанию, H-Р4). Ключ HMAC — из файла `-user-hmac-key`, на сервере его нет. Отказ от ключа задаётся явно флагом `-no-user-hmac-key`. В копию не входят события, журнал аудита (у него своя архивация, ADR-0008), сохранённые фильтры событий, сессии, шлюзы, пакеты конфигурации и ключи установки.
6. **Снимок** снимается одной транзакцией `REPEATABLE READ READ ONLY`. Запись `backup.create` с хешем файла и числом объектов пишется после записи файла. Если запись аудита не удалась, файл удаляется.
7. **Восстановление (H-Р3)** выполняется командой `aisec-cli backup restore` в установку после `migrate` и `init`. Нужна схема БД не старше копии и ключ данных. «Пустая» установка — нет пользователей, своих ролей, токенов API, провайдеров, приложений и политик. В непустую установку восстановление идёт только с флагом `-allow-nonempty`, и оно **добавляет** объекты копии. Совпадение по ID или уникальному имени (логин, slug, префикс ключа) — отказ целиком. Затирать существующие объекты нельзя, это запрещают триггеры неизменяемости. Название организации и настройки копии переносятся только в пустую установку. В непустой установке они не меняются, а в записи «после» стоит `settings_restored: false`. Новые значения настроек пишутся в запись «после». Запись аудита «до» (`stage: started`) фиксируется отдельно. Проверка пустоты и совпадений под рекомендательной блокировкой, вставка и запись «после» (`stage: done`) идут одной транзакцией. Отказы пишутся с `result: denied` (непустая установка, совпадения) или `failure` (неверная копия, ошибка). Неиспользованный токен первичной настройки гасится. Ключи шлюзов и УЦ не восстанавливаются: шлюзы регистрируются заново.
8. **Ввод фразы без отображения** выключает `stty -echo` из состава ОС (`/usr/bin/stty` или `/bin/stty`, не через `PATH`). Используется `os/exec`, это допустимо только в `aisec-cli` (правило depguard `server-exec` его не касается). Отображение возвращается и при SIGINT и SIGTERM. Если stdin не терминал, ввод отклоняется: для автоматизации есть `-passphrase-file`.

## Альтернативы
- Шифровать копию мастер-ключом установки. Отклонено: при потере установки копия бесполезна. В Vault, Bitwarden и restic ключ копии — от пароля или отдельного ключа.
- Отдельный файл-ключ копии вместо фразы. Отклонено для MVP: администратору проще хранить фразу отдельно от файла, а утерянный файл-ключ — та же потеря мастер-ключа.
- Включить события и журнал аудита. Отклонено (H-Р2): копия выросла бы и хранила бы содержимое запросов без сроков хранения.
- Восстановление «поверх» с заменой объектов. Отклонено: триггеры запрещают удалять пользователей, приложения и версии политик (УПД.5, ТЗ 5.3), а их обход ослабил бы защиту. Откат конфигурации на работающей установке — версии политик (ADR-0016).
- `golang.org/x/term` для ввода без отображения. Не выбрано: новая зависимость (и пакет `golang.org/x/sys/unix`) только ради одной команды. Её можно взять позже с согласия владельца, интерфейс команды не изменится.
- Один ключ AES-GCM на содержимое и секреты. Отклонено: отдельный ключ секретов не даёт открыть секрет ключом содержимого и наоборот, а стоит один вызов HKDF.

## Последствия
- `internal/crypto`: метод `Provider.PassphraseKDF` (в профиле `gost` пока `ErrNotImplemented`, этап 6). Новый пакет `internal/backup`. Команды `aisec-cli backup create` и `backup restore`. Миграции нет.
- Копия переносит хеши паролей, секреты TOTP и учётные данные провайдеров. Её стойкость не выше стойкости фразы и хранения файла. Модель угроз: кража файла и подбор фразы (`docs/cert/threat-model.md`).
- Новая настройка попадает в копию только вместе с изменением кода `internal/backup`: поле в `Settings` или новая версия формата с обновлением ADR.
- Восстановление выполняется при остановленном сервере. Рекомендательные блокировки защищают от второго восстановления и от первичной настройки в тот же момент; недавно активная сессия консоли — отказ (Н40 ревью 2.r4).
- Профиль `gost`: копия пишет имя профиля в заголовок, восстановление в установку другого профиля отклоняется.
- Откат: удалить команды и пакет. Данные в БД копия не меняет, восстановление только добавляет строки в новую установку.

## Дополнение: ревью 2.r4 (22.10.2026)
Решения ревьюера приняты по поручению владельца.
- **Отозванное после даты копии (В21).** Действующие токены API восстанавливаются отозванными (`revoke_reason = backup_restore`, без автора, миграция 0023): их выпускают заново, шлюзам они не нужны. Флаг `-keep-api-tokens` оставляет их как в копии и пишется в запись `started`. Ключи приложений и учётные записи восстанавливаются как в копии, иначе она теряет смысл. Поэтому в выводе, в записи `done` (`copy_age_hours`) и в `docs/install/backup.md` есть обязательный шаг: по архиву журнала аудита с даты копии повторить отзывы ключей, деактивации, блокировки и сбросы паролей. Копия старше 7 суток восстанавливается только с `-accept-old-copy`.
- **Проверка правилами сервиса (В22).** До записи `started` объекты копии проверяются так, как их проверил бы сервис этого выпуска: свои роли и токены — по каталогу разрешений и правилу 2.10, текущие версии политик — по каталогу детекторов, приложения — строгим разбором словарей, псевдонимов и квот, правилами API и компиляцией политик по словарям, как у шлюза. Любой отказ — восстановления нет, код 3, перечень объектов.
- **Парольная фраза (Н41).** Для новой копии — не меньше 8 разных символов, не повтор фрагмента, не последовательность, не имя пользователя ОС и не название организации; подсказка — 4–5 случайных слов. Фраза открываемой копии так не проверяется: копии, снятые раньше, восстанавливаются.

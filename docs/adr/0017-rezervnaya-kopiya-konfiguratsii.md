# ADR-0017. Резервная копия конфигурации: ключ из парольной фразы, состав и восстановление

- Статус: принято (решения H-Р1–Р3 по поручению владельца, 22.10.2026; п. 7 и 8 — их реализация; п. 8 изменён 22.10.2026 с согласия владельца на `golang.org/x/term`)
- Дата: 22.10.2026
- Связанные разделы ТЗ: 7.7 (РВ.1), 7.9 (ЗИ.1), 7.5 (РСБ.2), 10.2, 10.4; решения H-Р1–Р3 волны H этапа 2; задача 2.19 этапа 2

## Контекст
РВ.1 требует сохранять конфигурацию в зашифрованный файл и восстанавливать её: политики, приложения, пользователей, роли, настройки и ключ HMAC псевдонимов. Без ключа HMAC псевдонимы после восстановления не совпадут со старыми событиями. Копия нужна прежде всего при потере установки, в том числе мастер-ключа (ADR-0007). Поэтому шифровать её ключом установки нельзя. Ограничения: криптография только в `internal/crypto`, новых зависимостей нет, секреты не попадают в журналы и на диск в открытом виде, триггеры БД запрещают удалять пользователей, приложения, ключи и версии политик. Решения H-Р1–Р3 владелец поручил принять по общепринятой практике (22.10.2026).

## Решение
1. **Ключ копии — из парольной фразы администратора (H-Р1).** `PassphraseKDF` в `internal/crypto` использует Argon2id с параметрами Р3 (`m=65536,t=3,p=2`, ADR-0006). Соль 16 байт и параметры лежат в заголовке файла. При разборе параметров действуют те же границы, что у хешей паролей: подложенный файл не поднимет память выше 64 МиБ. Из 32 байт Argon2id через HKDF-SHA-256 выводятся два ключа AES-256-GCM: ключ содержимого (`aisec-backup-v1|payload`) и ключ секретов (`aisec-backup-v1|secret`). Мастер-ключ установки в копии не участвует. Фраза не короче 16 символов. Её вводят дважды с терминала без отображения или читают из файла с правами ровно 0400. В аргументах фраза не принимается.
2. **Формат файла `aisec-config-backup`, версия 1.** Первая строка — открытый заголовок JSON: формат, версия, профиль, KDF, параметры, соль, алгоритм, время. Дальше идёт шифротекст содержимого с AAD `payload|<строка заголовка>`, поэтому подмена версии, соли или параметров ломает расшифрование. Предел файла — 64 МиБ (предел одного шифрования). Файл пишется во временный файл 0600 в том же каталоге через `os.Root`, затем ставится жёсткой ссылкой под итоговое имя. Существующий файл не перезаписывается.
3. **Проверка при восстановлении** идёт в таком порядке: AEAD, версия формата, строгая схема. Схема — JSON без неизвестных полей и без данных после объекта, с пределами числа объектов, форматом ID, ссылочной целостностью внутри копии, номерами версий политик подряд с 1 и совпадением хеша версии с её текстом. Неверную фразу и подменённый файл не различить: в обоих случаях один отказ, код возврата 3.
4. **Секреты перешифровываются поштучно.** Учётные данные провайдеров, секреты TOTP и ключ HMAC расшифровываются ключом данных и сразу шифруются ключом секретов копии с AAD «вид секрета, ID объекта». Открытый текст затирается. В JSON содержимого лежат только шифротексты, поэтому секретов в открытом виде нет даже в памяти кодировщика JSON. При восстановлении каждый секрет так же поштучно переходит под ключ данных новой установки с AAD места хранения (Р4).
5. **Состав (H-Р2).** Политики со всеми версиями. Приложения с ключами (хеши, сроки, ротация, отзыв). Провайдеры. Пользователи с хешами паролей, историей паролей, вторым фактором и хешами кодов восстановления. Токены API (хеши). Свои роли с разрешениями. Название организации. Настройки входа, аудита, сроков хранения событий и первичной настройки (часовой пояс и режим хранения по умолчанию, H-Р4). Ключ HMAC — из файла `-user-hmac-key`, на сервере его нет. Отказ от ключа задаётся явно флагом `-no-user-hmac-key`. В копию не входят события, журнал аудита (у него своя архивация, ADR-0008), сохранённые фильтры событий, сессии, шлюзы, пакеты конфигурации и ключи установки.
6. **Снимок** снимается одной транзакцией `REPEATABLE READ READ ONLY`. Запись `backup.create` с хешем файла и числом объектов пишется после записи файла. Если запись аудита не удалась, файл удаляется.
7. **Восстановление (H-Р3)** выполняется командой `aisec-cli backup restore` в установку после `migrate` и `init`. Нужна схема БД не старше копии и ключ данных. «Пустая» установка — нет пользователей, своих ролей, токенов API, провайдеров, приложений и политик. В непустую установку восстановление идёт только с флагом `-allow-nonempty`, и оно **добавляет** объекты копии. Совпадение по ID или уникальному имени (логин, slug, префикс ключа) — отказ целиком. Затирать существующие объекты нельзя, это запрещают триггеры неизменяемости. Название организации и настройки копии переносятся только в пустую установку. В непустой установке они не меняются, а в записи «после» стоит `settings_restored: false`. Новые значения настроек пишутся в запись «после». Запись аудита «до» (`stage: started`) фиксируется отдельно. Проверка пустоты и совпадений под рекомендательной блокировкой, вставка и запись «после» (`stage: done`) идут одной транзакцией. Отказы пишутся с `result: denied` (непустая установка, совпадения) или `failure` (неверная копия, ошибка). Неиспользованный токен первичной настройки гасится. Ключи шлюзов и УЦ не восстанавливаются: шлюзы регистрируются заново.
8. **Ввод фразы без отображения** — `term.ReadPassword` из `golang.org/x/term` (BSD-3-Clause, команда Go; зависимость — `golang.org/x/sys/unix`), импорт только в `cmd/aisec-cli`. Согласие владельца — 22.10.2026, запись в `docs/cert/components.yaml`. Внешних процессов нет, `stty` в составе ОС не нужен (образы distroless). Состояние терминала запоминается до ввода и возвращается при SIGINT и SIGTERM. Если stdin не терминал, ввод отклоняется: для автоматизации есть `-passphrase-file`. Остаточный риск: буферы `ReadPassword` растут, и в куче могут остаться незатёртые копии фразы; у фразы из файла этого нет.

## Альтернативы
- Шифровать копию мастер-ключом установки. Отклонено: при потере установки копия бесполезна. В Vault, Bitwarden и restic ключ копии — от пароля или отдельного ключа.
- Отдельный файл-ключ копии вместо фразы. Отклонено для MVP: администратору проще хранить фразу отдельно от файла, а утерянный файл-ключ — та же потеря мастер-ключа.
- Включить события и журнал аудита. Отклонено (H-Р2): копия выросла бы и хранила бы содержимое запросов без сроков хранения.
- Восстановление «поверх» с заменой объектов. Отклонено: триггеры запрещают удалять пользователей, приложения и версии политик (УПД.5, ТЗ 5.3), а их обход ослабил бы защиту. Откат конфигурации на работающей установке — версии политик (ADR-0016).
- `stty -echo` из состава ОС через `os/exec` (первая реализация 2.19, eb632ab). Заменён: внешний процесс в утилите с доступом к ключам и не работает в образах без `stty`.
- Один ключ AES-GCM на содержимое и секреты. Отклонено: отдельный ключ секретов не даёт открыть секрет ключом содержимого и наоборот, а стоит один вызов HKDF.

## Последствия
- `internal/crypto`: метод `Provider.PassphraseKDF` (в профиле `gost` пока `ErrNotImplemented`, этап 6). Новый пакет `internal/backup`. Команды `aisec-cli backup create` и `backup restore`. Миграции нет. Новая зависимость — `golang.org/x/term` v0.47.0 (п. 8), в vendor добавляются `golang.org/x/sys/unix` (и `windows`, `plan9` по тегам сборки).
- Копия переносит хеши паролей, секреты TOTP и учётные данные провайдеров. Её стойкость не выше стойкости фразы и хранения файла. Модель угроз: кража файла и подбор фразы (`docs/cert/threat-model.md`).
- Новая настройка попадает в копию только вместе с изменением кода `internal/backup`: поле в `Settings` или новая версия формата с обновлением ADR.
- Восстановление выполняется при остановленном сервере. Рекомендательные блокировки защищают от второго восстановления и от первичной настройки в тот же момент; недавно активная сессия консоли — отказ (Н40 ревью 2.r4).
- Профиль `gost`: копия пишет имя профиля в заголовок, восстановление в установку другого профиля отклоняется.
- Откат: удалить команды и пакет. Данные в БД копия не меняет, восстановление только добавляет строки в новую установку.

## Дополнение: ревью 2.r4 (22.10.2026)
Решения ревьюера приняты по поручению владельца.
- **Отозванное после даты копии (В21).** Действующие токены API восстанавливаются отозванными (`revoke_reason = backup_restore`, без автора, миграция 0023): их выпускают заново, шлюзам они не нужны. Флаг `-keep-api-tokens` оставляет их как в копии и пишется в запись `started`. Ключи приложений и учётные записи восстанавливаются как в копии, иначе она теряет смысл. Поэтому в выводе, в записи `done` (`copy_age_hours`) и в `docs/install/backup.md` есть обязательный шаг: по архиву журнала аудита с даты копии повторить отзывы ключей, деактивации, блокировки и сбросы паролей. Копия старше 7 суток восстанавливается только с `-accept-old-copy`.
- **Проверка правилами сервиса (В22).** До записи `started` объекты копии проверяются так, как их проверил бы сервис этого выпуска: свои роли и токены — по каталогу разрешений и правилу 2.10, текущие версии политик — по каталогу детекторов, приложения — строгим разбором словарей, псевдонимов и квот, правилами API и компиляцией политик по словарям, как у шлюза. Любой отказ — восстановления нет, код 3, перечень объектов.
- **Парольная фраза (Н41).** Для новой копии — не меньше 8 разных символов, не повтор фрагмента, не последовательность, не имя пользователя ОС и не название организации; подсказка — 4–5 случайных слов. Фраза открываемой копии так не проверяется: копии, снятые раньше, восстанавливаются.

## Дополнение: настройки этапов 3 и 4, формат версии 2 (задача 5.8 этапа 5, 30.10.2026)
- **Версия 2.** `FormatVersion = 2`. В содержимое добавлены необязательные разделы: каналы уведомлений, правила оповещений (свои и параметры встроенных), расписания отчётов, цены моделей, инструкции реагирования, сертификат шлюза, OIDC и LDAP с сопоставлением групп, MCP-серверы, агенты с их MCP-серверами, инструменты, исключения теневого ИИ, лицензии и отметка часов лицензии, ручные отметки соответствия; у приложения — бюджет, эталон системного промпта и доступ к моделям по группам, у ключа — `agent_id`, у пользователя — e-mail, в настройках установки — сроки хранения оповещений, инцидентов и событий теневого ИИ и режим квот. Заголовок, KDF и строки `info` HKDF не менялись (`v1` в них — версия вывода ключей, а не формата). Версия в заголовке (в AAD) и в содержимом должна совпадать; разделы версии 2 в копии версии 1 — отказ схемы.
- **Копии версии 1** читаются и восстанавливаются: команда пишет, что настроек этапов 3 и 4 в копии нет; ключи агентов из такой копии — отозванными, как в 4В38. Образец настоящей копии версии 1 — `cmd/aisec-cli/testdata/config-v1.aisec-backup` (`TestBackupRestoreVersion1OnRealDB`).
- **Секреты разделов** (пароль SMTP и секрет webhook каналов, секрет клиента OIDC, пароль LDAP, учётные данные MCP, закрытый ключ сертификата шлюза, текст эталона промпта) — как учётные данные провайдеров (п. 4): открываются ключом данных с AAD места хранения (`internal/keyring`), сразу запечатываются ключом секретов копии с видом и ID, при восстановлении — ключом данных новой установки.
- **Объекты и настройки.** Объекты (каналы, свои правила, расписания, цены, MCP-серверы, агенты, инструменты, бюджеты, эталоны, доступ по группам) добавляются и в непустую установку с `-allow-nonempty` и проверяются на совпадение по ID и уникальным именам, как объекты этапов 1–2. Настройки (параметры встроенных правил, инструкции, сертификат шлюза, OIDC и LDAP, исключения теневого ИИ, лицензия, отметки соответствия, новые поля настроек установки) переносятся только в пустую установку, как название организации. Встроенное правило обновляется по `builtin_key` с сохранением ID установки (сервер создаёт встроенные правила при запуске).
- **Ссылки.** Объект, ссылающийся на то, чего нет в копии (получатель правила, канал расписания, провайдер цены, приложение агента, MCP-сервер или агент инструмента, роль группы IdP, изменивший настройки IdP пользователь), не восстанавливается: строка в выводе и в записи `backup.restore` (`skipped_objects`, до 20 строк в `skipped`), остальное восстанавливается. Совпадения ищутся по объектам после этого отбора. Исключение теневого ИИ по пользователю без ключа псевдонимов в копии пропускается так же. Порядок записи — по внешним ключам: провайдеры → цены, каналы → расписания, MCP-серверы и приложения → агенты → ключи и инструменты.
- **Ключи агентов (уточнение 4В38).** Ключ с `agent_id` восстанавливается с привязкой, если агент того же приложения есть в копии и не пропущен; иначе — отозванным с `backup_restore`.
- **Лицензия.** Файл лицензии проверяется подписью ключа производителя, как при загрузке (ADR-0026, п. 2). Не прошёл — отказ с кодом 3 (В22), а не пропуск: без лицензии установка вернулась бы в режим пилота незаметно для администратора. Отметка часов — наибольшая из копии и установки (`greatest`; триггер БД не даёт её уменьшить).
- **Проверка правилами сервиса (В22) для разделов версии 2:** свои правила оповещений — `alerting.ParseRuleInput`, издатель OIDC — `oidc.ValidateIssuer`, настройки LDAP — `ldap.ValidateConfig`; остальное — строгой схемой копии и ограничениями CHECK БД. Проверки каналов (`settings`), адресов и признаков MCP-серверов, групп доступа к моделям и соответствия ключа сертификату шлюза в модулях не экспортированы; задача 5.8 пакеты модулей не меняет — это остаточный риск (объект от другого выпуска, который сервис не принял бы), закрывается выносом этих проверок в экспортируемые функции модулей отдельной задачей.
- **Не входят:** события, инциденты, журнал аудита, очереди подтверждений и доставки (данные; полная копия пилота); каталог теневого ИИ и база требований (подписанные служебные базы, загружаются заново; отметки соответствия ссылаются на пункты базы и видны после её загрузки; включение — задача 5.15); ключи установки; файлы вне БД (слушатель syslog теневого ИИ, пакеты моделей `aisec-ml`). Миграция не понадобилась.

## Дополнение: служебные базы и проверки модулей (остатки волны A этапа 5, 30.10.2026)
- **Служебные базы в копии.** Необязательный раздел `service_dbs` содержимого: подписанные файлы текущей и предыдущей версии каждого вида (ADR-0028) с видом, слотом, номером версии и отметкой загрузки. Формат остаётся версии 2: раздел необязательный, копия без него читается как прежде, копия с ним в выпуске до этого дополнения отклоняется строгой схемой (неизвестное поле). Схема копии проверяет вид (`^[a-z0-9_]{1,64}$`), слот (`current`/`previous`) без повторов, номер версии (от 1 до 2^53−1), размер файла (до 4 МиБ, как CHECK `service_dbs`) и то, что у вида с предыдущей версией есть текущая и она новее. Ключей в разделе нет: файлы открыты, их подлинность — подпись производителя.
- **Восстановление по правилам ADR-0028.** Каждый файл проверяется так же, как сохранённая версия при запуске сервера: подпись и заверение встроенным ключом производителя, отзыв, вид, дата выпуска в сроке заверения, разбор содержимого видом этого выпуска; срок заверения на текущее время не проверяется (ADR-0027, п. 3), номер версии в файле совпадает с номером в копии. Сведения (дата, число записей, номер заверения, отпечаток) записываются из проверенного файла, а не из копии. Файл, не прошедший проверку, и вид, неизвестный выпуску, пропускаются строкой отчёта: копия переносит конфигурацию, а базу администратор загрузит заново — отказ всей копии из-за одной базы не нужен (в отличие от лицензии, п. «Лицензия»).
- **Версия установки.** Служебные базы добавляются и в непустую установку (это не настройка: версия только растёт). Если в установке текущая версия вида не ниже новейшей проверенной версии копии — вид пропускается строкой «в установке версия N не ниже версии копии M — пропущена». Если ниже — версия копии становится текущей, текущая установки — предыдущей (как при загрузке). В установке без версий вида записываются обе версии копии. Строки отчёта выводятся под заголовком «Служебные базы:» и пишутся в запись `backup.restore` (`service_dbs_report`). Пустота установки (`Inspect`) служебные базы не учитывает. Запись — в той же транзакции восстановления, с блокировкой строк вида (`FOR UPDATE`). Миграция не понадобилась.
- **Проверки модулей (закрыт остаточный риск В22 версии 2).** Проверки вынесены в экспортируемые функции, которые используют и модули, и `checkSnapshot`: `notify.CheckStoredChannel` (строгий разбор `settings` и расшифрованных ключом копии секретов, все правила сохранения через API, `settings` — ровно те, что записал бы сервер, включая `url_origin` по адресу webhook, `secret_fields` — по заданным секретам), `agents.CheckServer` и `agents.CheckStoredServer` (slug, адрес и правило адресов, `http://` — только с `insecure_http`, заголовок учётных данных, таймаут, версии MCP, корневые сертификаты), `apps.CleanUserAccess` и `apps.CheckStoredUserAccess` (группы доступа к моделям и псевдонимам приложения в каноническом виде, 4В15), `apps.ParseGatewayTLS` и `apps.CheckStoredGatewayTLS` (ключ — пара листу цепочки, имя в SAN, цепочка до корня, отпечаток и срок — как записаны; срок проверяется внутри срока цепочки, как у шлюза: истёкший после снятия копии сертификат — не отказ, о нём сообщает «Состояние системы»), `alerting.CheckStoredRule` (своё правило — как при создании; встроенное — ключ известен выпуску, вид тот же, у системных правил и правил безопасности условие и группировка как у встроенного, поле правила «новое» не меняется). Объект, не прошедший проверку, — отказ всей копии до записи «до» (код 3), как для объектов этапов 1–2.
- **Применимость в расписании отчёта** (миграция 0070, задача 5.12): необязательное поле `applies` расписания (`gis`, `kii`, `ispdn`, `commercial`, только у отчёта `compliance`; нет поля — все пункты базы, как в копии до миграции).

## Дополнение: исправления ревью 5.r1 и реестр ИИ (поток C4 этапа 5, 31.10.2026)
- **Встроенные правила оповещений (5В1).** У системных правил и правил безопасности из копии берутся только ID, получатели (проверка — как в API), версия и отметки изменения; вид, название, описание, включение, важность, условие, группировка и окна — значения встроенного правила этого выпуска (`alerting.StoredBuiltin`, в `Restore` — `RestoreOptions.BuiltinAlertRule`). Через API у таких правил меняются только получатели (`lockedConflict`), поэтому значения из копии нельзя было бы вернуть ни из консоли, ни через API; копия прежнего выпуска теперь не оставляет навсегда устаревшие важность и окна. Выключить такое правило копией не давал и раньше CHECK миграции 0028, но важность, название, условие (до этого — отказ) и окно группировки проходили. `alerting.CheckStoredRule` у таких правил проверяет только получателей. Встроенное правило с ключом, которого нет в выпуске, — `alerting.ErrUnknownBuiltin`: пропуск со строкой отчёта, а не отказ всей копии. Остальные встроенные правила («порог», «новое», «частота», «аномалия», «бюджет») переносятся как в копии: их меняют через API.
- **Проверка настроек только для пустой установки (5Н1).** `checkSnapshot` проверяет встроенные правила, сертификат шлюза, OIDC, LDAP и лицензии, только если установка пустая (признак `Inspect` до проверки): в непустую `Restore` их не пишет (`withoutSettings`), и непереносимая настройка (например, лицензия стенда) копию не отклоняет. Если установка стала пустой между проверкой и транзакцией восстановления, транзакция отказывает: непроверенные настройки не пишутся.
- **Служебные базы при восстановлении (5Н2).** Запись вида — под той же advisory-блокировкой (`pg_advisory_xact_lock` по виду), что загрузка и возврат (`servicedb.PGStore.inTx`): `FOR UPDATE` не блокирует отсутствующие строки. Текущая версия установки, которую вытесняет более новая версия копии, проверяется так же, как версии копии, и становится предыдущей только при успехе; иначе удаляется (строка «версия установки N не прошла проверку — удалена»), предыдущая установки при этом остаётся — как в `PGStore.Save`.

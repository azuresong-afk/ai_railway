# ADR-0013. Ролевая модель консоли

- Статус: предложено
- Дата: 21.10.2026
- Связанные разделы ТЗ: 1.3, 7.3 (УПД.1–3, 6, 8), 7.2 (ИАФ.5, ИАФ.9), 12, 13; задача 2.9 плана этапа 2

## Контекст
ТЗ требует пять предустановленных ролей (1.3), свои роли из набора разрешений (УПД.1), разделение обязанностей (УПД.2), проверку прав на сервере для каждого эндпоинта с тестом на отказ (УПД.3) и проверку на уровне объектов для владельца приложения (УПД.8). До задачи 2.9 права ролей были статической таблицей в `internal/auth/roles.go`, а `users.role` допускал только пять значений.

Модель ролей трудно поменять позже: от неё зависят схема БД, API консоли (2.27), токены API (2.10), приложения владельца (2.11), доступ к содержимому событий (2.16) и обязательность второго фактора (2.8).

## Решение
1. **Одна роль на пользователя.** `users.role` — внешний ключ на `roles (org_id, id)`. Набор прав собирается в своей роли, а не сложением ролей: тогда проверка «права цели входят в права действующего» сводится к сравнению двух наборов.
2. **Каталог разрешений — в коде** (`internal/auth/permissions.go`). У разрешения есть имя `раздел.действие`, описание, группа, признак «управление безопасностью» и признак `Ownable`. Новая задача добавляет разрешение строкой в каталог и в права предустановленных ролей, а в `api/openapi.yaml` указывает его в `x-permission`. Разрешения `session` (свои данные, выход, второй фактор) и `self` (смена своего пароля) в роль не назначаются: их добавляет `SessionGrants` по состоянию сессии. `session` есть у любой сессии, `self` — после второго фактора, права роли — только у полной сессии (`active`).
3. **Права предустановленных ролей — в коде и неизменны.** Они обновляются вместе с продуктом: новая версия может добавить роли администратора безопасности разрешение нового раздела без миграции данных. В БД у предустановленных ролей есть только строки, на которые ссылается `users.role`; триггеры запрещают их менять, удалять и давать им разрешения — даже владельцу таблицы.
4. **ID роли — короткое латинское имя** (`^[a-z][a-z0-9_]{2,47}$`), а не UUID. Предустановленные роли имеют одинаковые ID во всех установках, своя роль получает ID при создании и не переименовывается (меняется только название).
5. **Область разрешения: `all` или `own`** (УПД.8). Маршрут без признака `Scoped` пропускает только `all`. Маршрут со `Scoped` пропускает и `own`, но сам отбирает объекты; чужой объект — 404. Так забытый отбор не открывает чужие объекты.
6. **Права читаются на каждом запросе, без кэша.** Изменение своей роли действует сразу. Смена роли пользователя завершает его сессии: новые права и требование второго фактора действуют со следующего входа.
7. **Разделение обязанностей — в `internal/auth`, не только в обработчиках.** Пользователь не меняет свою роль и роль, которую носит. Он не выдаёт разрешений, которых нет у него самого. Он не управляет учётной записью, чьи права шире его прав: не создаёт её, не сбрасывает ей пароль, не деактивирует, не завершает сессии и не меняет роль. Последнего активного администратора безопасности понизить нельзя. Отказ пишется в аудит с результатом `denied`.
8. **Второй фактор задаётся ролью.** Признак `roles.mfa_required`: у `security_admin` и `system_admin` он включён. Своя роль с любым разрешением на изменение получает его принудительно. Вход (задача 2.8) берёт признак из роли через `Service.RoleRequiresMFA`, вместо отдельной таблицы ролей с обязательным фактором; флаг политики `mfa_required_all` по-прежнему требует фактор от всех.
9. **Матрица «роль × эндпоинт» строится из спецификации.** `x-permission` у каждой защищённой операции, генератор `tools/rbac-matrix` и файл `docs/cert/rbac-matrix.md` с проверкой актуальности. Тест `TestRBACMatrixDenials` перебирает все пары «маршрут × роль».

## Альтернативы
- **Несколько ролей у пользователя.** Гибче, но разделение обязанностей пришлось бы проверять по объединению ролей, а интерфейс показывал бы итоговые права отдельно. Остаётся возможным позже: таблица назначений вместо столбца.
- **Права предустановленных ролей в БД, правка из консоли.** Тогда администратор мог бы дать аудитору право на изменение (нарушение УПД.2), а новые разрешения при обновлении требовали бы миграции данных. Вместо этого — копия предустановленной роли как своя.
- **UUID у ролей.** Соответствует ТЗ 12 для основных сущностей, но ID предустановленных ролей различались бы между установками, а резервная копия и выгрузка ролей (2.19) были бы менее переносимы.
- **Кэш прав в памяти сервера.** Экономит запрос к БД, но изменение роли действовало бы с задержкой, а при нескольких экземплярах сервера — непредсказуемо.

## Последствия
- Каждый новый эндпоинт обязан иметь `x-permission`, иначе падают контрактный тест и тест матрицы. После изменения спецификации или прав ролей нужно выполнить `make rbac-matrix`.
- Своя роль, у которой в БД осталось разрешение, удалённое из каталога, просто не получает его: в правах оно не учитывается.
- Изменение ролей и назначение роли перечитывают действующего пользователя в той же транзакции: роль, статус и наличие `roles.manage` берутся на момент записи. Блокировки берутся в одном порядке — строки пользователей (администраторы безопасности, затем действующий и цель по ID), затем строки ролей. Редкие встречные изменения всё же могут закончиться взаимоблокировкой; PostgreSQL прерывает одну транзакцию, запрос получает 500 и повторяется пользователем. Состояние при этом не меняется.
- Операции над учётными записями (создание, деактивация, завершение сессий) проверяют права действующего и роль цели на момент запроса, а пишут в хранилище задачи 2.7. Остаётся окно: если в эти миллисекунды роль цели расширили или права действующего сократили, операция пройдёт по прежним данным. Для сброса пароля окно закрыто: хранилище сверяет роль цели под блокировкой строки (`PasswordChange.ExpectRole`), иначе временный пароль позволил бы войти под учётной записью, которую только что повысили. Для остальных операций последствия ограничены: деактивацию и завершение сессий администратор безопасности отменяет, а создание учётной записи с ролью сверх прав по-прежнему запрещено проверкой роли.
- Роль приложения может менять `roles.mfa_required` своей роли (права на столбец). Это нужно, чтобы сохранить признак при изменении роли; сам признак вычисляется сервером (`parseRole`) и снять его у роли с правами на изменение через API нельзя.
- Токены API (2.10) получают область в пределах прав роли владельца и проходят ту же матрицу.

## Дополнение: токены API (задача 2.10)
Решения владельца от 21.10.2026.
1. **Токен действует от имени пользователя.** Его права — пересечение области, заданной при выпуске, с текущими правами роли владельца (`auth.TokenGrants`). Отдельной «роли токена» нет: понижение роли сразу сужает токен, деактивация владельца его отключает.
2. **Токену не выдаются функции безопасности (`Security`), свои данные (`self`, `session`) и права на сами токены** (`auth.TokenGrantable`). Управление доступом остаётся за человеком с паролем и вторым фактором; токен не выпускает токены. Новое разрешение без `Security` автоматически становится доступным токену — в `api/openapi.yaml` у его операций нужно указать `bearerToken` (контрактный тест сверяет).
3. **Выпускает только сам пользователь из сессии консоли** (`api_tokens.manage`): у `security_admin` — на все токены, у `system_admin` — на свои (`own`), аудитор только читает. Срок обязателен (до 365 дней), токены не удаляются, отзыв необратим.
4. **Каждый запрос по токену пишется в аудит** (`api_token.used`: метод, шаблон пути, код ответа), а не только последнее использование.
5. **Заголовок `Authorization` исключает cookie.** Запрос с ним проверяется только по токену, без CSRF и без отката на сессию.

Альтернатива — права токена задавать отдельной ролью — отвергнута: токен с ролью шире владельца обходил бы разделение обязанностей.

# ADR-0007. Ключи установки и `aisec-cli init`

- Статус: предложено
- Дата: 20.10.2026
- Связанные разделы ТЗ: 7.9 (ЗИ.1, ЗИ.4), 10.2, 10.4; решения Р4, Р7, Р8 плана этапа 2; ADR-0006

## Контекст
Серверу этапа 2 нужны ключи, которых на этапе 1 не было: шифрование секретов при хранении (ЗИ.1), подпись пакетов конфигурации для шлюзов (Р7), внутренний УЦ для mTLS «шлюз — сервер» (Р8) и одноразовый токен первичной настройки (ЗИ.4: паролей по умолчанию нет). ТЗ 10.4 требует создавать их при установке (`aisec-cli init`) и хранить с ограниченными правами, мастер-ключ — файлом 0400 для пользователя службы. ADR-0006 оставил этому ADR учёт предела AES-GCM (2^32 сообщений на ключ со случайным nonce) и ротацию ключа данных.

Ошибки здесь трудно откатить: потерянный мастер-ключ — потерянные секреты, перезаписанный ключ подписи — шлюзы, которые перестали принимать конфигурацию.

## Решение
1. **Команда.** `aisec-cli init -dir <каталог> [-profile standard]` (профиль `gost` принимается флагом, но до этапа 6 отклоняется самотестом), строка подключения — только `AISEC_DATABASE_URL` (как у `migrate`). Порядок: самотест профиля → каталог существует и закрыт для группы и остальных (`perm & 0o077 == 0`, каталог не создаётся — его владельца задаёт администратор; дальше файлы открываются через `os.Root`, подмена пути не выводит запись за пределы каталога) → ни одного из файлов ключей нет → в БД нет ключа данных организации → все ключи создаются в памяти → файлы пишутся с `O_CREATE|O_EXCL` (существующий файл и символическая ссылка — ошибка), `fsync` файлов и каталога → одна транзакция в БД (ключ данных, хеш токена, запись аудита `system.init`) → однократный вывод токена. Если транзакция точно не зафиксирована, созданные файлы удаляются и токен не показывается. Если ошибка пришла на `COMMIT`, `init` проверяет строку ключа данных: есть — фиксация прошла, работа продолжается; проверить не удалось — файлы **сохраняются** (иначе ключ данных в БД навсегда останется без мастер-ключа), а администратор получает инструкцию. Ошибка вывода токена — ненулевой код возврата и подсказка о повторном выпуске. Файлы принадлежат пользователю, запустившему `init`; передать их пользователю службы (`chown`) — шаг руководства администратора, об этом напоминает вывод (проверка владельца через `syscall` запрещена ADR-0004). **Повторный `init` ничего не перезаписывает** и отказывает с пояснением.
2. **Иерархия (Р4, ЗИ.1).**
   - Мастер-ключ — 32 случайных байта, файл `master.key` (0400). Шифрует только ключи данных.
   - Ключ данных — 32 случайных байта, в БД (`data_keys.wrapped`), зашифрован мастер-ключом AES-256-GCM. AAD — `aisec-aad-v1|data_keys|wrapped|<id строки>` (`crypto.StorageAAD`): шифротекст, перенесённый в другую строку, не расшифруется. Этот же формат AAD обязателен для всех шифротекстов в БД (секреты провайдеров, TOTP, ключ HMAC псевдонимов, содержимое `full`).
   - Открытые копии ключей в памяти затираются после использования (насколько это возможно в Go: копии внутри стандартной библиотеки не контролируются).
3. **Ключ подписи пакетов (Р7)** — seed Ed25519, `bundle-signing.key` (0400); открытый ключ — `bundle-signing.pub` (0444), его получают шлюзы.
4. **Внутренний УЦ (Р8)** — самоподписанный, ECDSA P-256, `ca.key` (PKCS#8, 0400) и `ca.crt` (0444), срок — 825 дней (`MaxCertValidity`). Сертификаты шлюзов и внутреннего API выпускает задача 2.14 через `crypto.LoadCA` (проверяет признак УЦ, самоподпись, P-256, парность ключа); истёкший УЦ не выпускает сертификатов.
5. **Формат файлов ключей** — PEM с одним блоком, тип по назначению (`AISEC MASTER KEY`, `AISEC SIGNING KEY`, `AISEC SIGNING PUBLIC KEY`) и единственным заголовком `Profile`. Разбор строгий (`crypto.DecodeKeyPEM`: файл начинается с блока, один блок, ожидаемый тип, длина ключа, допустимый профиль, до 4 КиБ; `FuzzDecodeKeyPEM`). Ключ другого профиля распознаётся при чтении: смена профиля — перевыпуск ключей (ТЗ 10.2). Читать файлы ключей — только `crypto.ReadKeyFile`, который отказывает при доступе группы или остальных.
6. **Токен первичной настройки (ЗИ.4)** — `aisec_setup_` + 32 случайных байта (base64url). В БД (`setup_tokens`) — только SHA-256 токена, срок 24 часа и отметка `used_at`. Токен печатается один раз, в аудит и логи не попадает. Гасит токен сервер (задача 2.7) условным `UPDATE … SET used_at = now() WHERE used_at IS NULL AND expires_at > now()`; повторный выпуск токена, если срок истёк до настройки, — тоже задача 2.7.
7. **Права СУБД.** Ключи и токены создаёт только `aisec-cli init` под логином владельца схемы. Роль `aisec_app` читает `data_keys` и меняет только счётчик `sealed`, у `setup_tokens` — только `used_at`. Права на столбцы не ограничивают значения, поэтому триггеры `data_keys_guard` и `setup_tokens_guard` (для всех, включая владельца) запрещают уменьшать `sealed`, менять сам ключ, возвращать выведенный ключ, снимать или переставлять отметку `used_at` и менять остальные поля токена.
8. **Предел AES-GCM (ADR-0006).** Рабочий предел — 2^31 шифрований одним ключом данных (запас вдвое к 2^32 по NIST SP 800-38D, 8.3). Счётчик `data_keys.sealed` (`CHECK sealed <= 2^31`). Потребитель ключа резервирует шифрования до самого шифрования: `UPDATE data_keys SET sealed = sealed + $n WHERE id = $1 AND retired_at IS NULL RETURNING sealed` пачками (например, по 4096 на процесс), неиспользованный резерв просто теряется. Отказ `CHECK` означает исчерпание ключа: шифрование останавливается, пишется `system.error` в аудит, нужна ротация. При 2^30 — предупреждение на «Состоянии системы» (задача 2.20). Для содержимого событий в режиме `full`, где поток шифрований большой, задача 2.15 оценивает объём и при необходимости вводит производные ключи по дням (HKDF от ключа данных) — тогда счётчик ведётся на производный ключ. Реализовано в 2.15: содержимое `full` шифруется производным ключом суток UTC — HKDF-SHA-256 (`crypto.Provider.NewKDF`) от ключа данных, контекст `aisec-derived-v1|<назначение>|<id ключа данных>|<ГГГГ-ММ-ДД>`; счётчик — `derived_key_usage (data_key_id, purpose, day)` с тем же пределом 2^31 и резервом по 4096 (миграция `0010_events`).
9. **Ротация (порядок; команда — отдельной задачей).**
   - Ключ данных: новая версия (`version + 1`), прежняя получает `retired_at`; новые шифрования — только действующей версией; перешифрование старых записей — фоновым заданием, после него прежняя версия удаляется. Индекс `data_keys_active` не допускает двух действующих ключей.
   - Мастер-ключ: новый файл, перешифрование всех строк `data_keys` в одной транзакции, затем замена файла; старый файл хранится до проверки резервной копии.
   - Ключ подписи пакетов и УЦ: новый ключ рядом со старым, шлюзы получают новый открытый ключ или корень в пакете, подписанном старым ключом, затем старый выводится. Подробности — руководство администратора и ADR-0009 (задача 2.13).
10. **Резервное копирование.** `master.key` хранится отдельно от резервной копии БД: копия БД без мастер-ключа бесполезна для злоумышленника, а без него не восстановить секреты. Об этом `init` напоминает в выводе.

## Альтернативы
- **Ключ данных в файле рядом с мастер-ключом.** Проще, но ключ данных и мастер-ключ оказываются в одном месте, а ротация ключа данных требует записи в каталог ключей от имени сервера. Отклонено (Р4).
- **Мастер-ключ из переменной окружения или аргумента.** Виден в `/proc/<pid>/environ`, списке процессов и выводе оркестратора. Отклонено.
- **Мастер-ключ в HSM, KMS или СКЗИ.** Правильно для госсектора и КИИ, но требует выбора СКЗИ — этап 6 (ТЗ 10.4). Интерфейс `AEAD` уже позволяет заменить источник ключа без смены схемы БД.
- **Токен в файле, который сервер удаляет после настройки.** Серверу понадобилось бы право записи в каталог ключей. Отклонено.
- **Перезапись при повторном `init` с флагом `-force`.** Одна ошибка оператора уничтожает доступ к секретам. Отклонено: ротация — отдельной командой.
- **Ключ УЦ под мастер-ключом в БД.** Защищает от чтения файла, но УЦ нужен только при выпуске сертификатов шлюзов; файл 0400 соответствует ТЗ 10.4 и проще в аудите лабораторией.

## Последствия
- Код: `cmd/aisec-cli/init.go`, `internal/crypto/keyfile.go` (`EncodeKeyPEM`, `DecodeKeyPEM`, `StorageAAD`), `internal/crypto/pki.go` (`LoadCA`, `KeyPEM`, отказ истёкшего УЦ), `internal/audit/tx.go` (`RecordTx`), событие `system.init` в перечне аудита, миграция `0003_keys`.
- Задачи 2.7 (погашение токена), 2.11 и 2.15 (шифрование под ключом данных с резервом `sealed`), 2.13 (подпись пакетов), 2.14 (выпуск сертификатов), 2.19 (резервная копия конфигурации) опираются на эти файлы и таблицы.
- Команды ротации и повторного выпуска токена ещё нет: до неё ротация — только переустановкой.
- Откат: ключей и данных, зашифрованных ими, пока нет. До задач 2.7 и 2.11 ADR откатывается удалением команды и миграцией, удаляющей таблицы.
- Дополнено ADR-0008 (21.10.2026): `init` создаёт и пару ключей подписи контрольных точек журнала аудита (`audit-signing.key` 0400, `audit-signing.pub` 0444); для установок, где `init` прошёл раньше, — `init -add-audit-key`.

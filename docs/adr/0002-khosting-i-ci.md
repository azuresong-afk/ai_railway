# ADR-0002. Хостинг репозитория, CI и подпись изменений

- Статус: принято
- Дата: 29.09.2026
- Связанные разделы ТЗ: 8.2, 8.7, 8.11, 11.4, 16 (вопросы 1 и 17)

## Контекст
ГОСТ Р 56939-2024 требует управления конфигурацией: защищённая основная ветка, ревью каждого изменения человеком, контроль целостности кода (подписи). Часть кода пишет ИИ-ассистент в облачной среде, где коммиты не подписываются ключом владельца. Сертификационная методика проверяет и сборочную среду.

## Решение
1. **Хостинг** — GitHub, репозиторий `azuresong-afk/ai_railway`, путь Go-модуля `github.com/azuresong-afk/ai_railway`.
2. **CI** — GitHub Actions как тонкая обёртка: вся логика в `Makefile`, workflow только готовит сборочный контейнер и вызывает `make`. Сторонние actions закрепляются по SHA коммита, `permissions` — минимальные (`contents: read`).
3. **Ветки.** `main` защищена: изменения только через pull request с ревью владельца и зелёной проверкой `check`; force-push и удаление запрещены. Ассистент работает в рабочих ветках `claude/*`.
4. **Подпись.** Подписанным является коммит слияния в `main`: владелец сливает pull request локально (`git merge --no-ff -S`) своим ключом (GPG или SSH) и отправляет в `main`. Коммиты ассистента в рабочих ветках не подписаны; это описано в `docs/cert/build-env.md`. Теги релизов подписываются владельцем.
5. **Переезд** на российский хостинг (GitFlic, GitVerse, собственный GitLab и т. п.) — отдельный ADR до этапа 6. Переезд дешёвый, потому что CI — тонкая обёртка над `make`.

## Альтернативы
- **Слияние кнопкой веб-интерфейса.** Коммит подписывается ключом GitHub (web-flow), а не владельца, — это не подтверждает, кто принял изменение.
- **Правило «Require signed commits» в защите ветки.** Требует подписи у всех коммитов в `main`, включая неподписанные коммиты ассистента; совместимо только со squash-слиянием через веб-интерфейс, а тогда подпись снова принадлежит GitHub. Не включается.
- **GitLab CI, GitFlic, GitVerse сейчас.** Репозиторий уже на GitHub, а переезд до пилотов не даёт выигрыша по сертификации.

## Последствия
- Владелец выполняет слияние локально; инструкция — в `docs/cert/build-env.md`.
- История `main` содержит подписанные коммиты слияния, по которым проверяется, кто и когда принял каждое изменение.
- Настройки защиты ветки и разрешённых actions делает владелец вручную (план этапа 0, раздел «Что сделать владельцу руками»).

## Дополнение от 22.10.2026: PostgreSQL в CI
Сквозные тесты этапа 2 (`TestE2EStage2_*`, `TestE2EAuthz_*`, `TestE2EConsole_*`) идут на живой БД и без `AISEC_TEST_DATABASE_URL` пропускаются. Пропущенный тест ничего не проверяет, поэтому в `.github/workflows/check.yml` job `check` получает сервис `postgres:17.6-alpine` (версия из `deploy/compose/dev`) с одноразовой тестовой базой и переменную `AISEC_TEST_DATABASE_URL`. Образ сборки получает её через `make check-docker`: при заданной переменной контейнер запускается с `--network=host -e AISEC_TEST_DATABASE_URL`; без неё (локально, `check-offline`) ничего не меняется. Строки матрицы обнаружения по-прежнему покрываются модульными тестами `TestDM…`; сквозные тесты на БД — дополнительная проверка, и их имена не содержат ID строки (иначе пропуск без БД считался бы провалом `make dm-coverage`).
Сценарий консоли на настоящем сервере (`TestE2EStage2_ConsoleLive`, `web/e2e/live.spec.ts`) в CI пропускается: в сборочном образе нет Node.js и консоль не встроена в бинарник. Он запускается локально и в облаке после `make web-build` и `make build`.

# ADR-0022. Ключ производителя: хранение, подпись выпуска без сети, отпечаток

- Статус: принято (решение Р1 плана этапа 4 подтверждено владельцем 27.10.2026; задача 4.4)
- Дата: 27.10.2026
- Связанные разделы ТЗ: 7.5 (ОЦЛ.1, ОЦЛ.2), 10.2, 10.4, 5.15 (лицензии), 5.11 (служебные базы); функции безопасности ЗИ.2, ЗИ.5, ОБН.1; замечания Н34, Н35 ревью 2.r4; ADR-0012, ADR-0019; следующие ADR-0026 (лицензии), ADR-0027 (теневой ИИ)

## Контекст
ADR-0012 ввёл манифест целостности, подписанный ключом производителя, и встроенный открытый ключ (`-tags aisec_release`). ADR-0019 построил на нём поставку пилота. Закрытого ключа производителя ещё нет. В этапе 3 и раньше было так:
- `make release-dir RELEASE=1 MANIFEST_KEY=…` собирает бинарники и подписывает манифест одной командой. Значит, закрытый ключ лежит на сборочной машине, а у неё есть сеть: зависимости, git, Docker.
- Отпечатка ключа нет. Заказчику не с чем сравнить ключ, которым проверяется поставка.
- При первой установке образы загружаются без проверки (`docker load`). `verify-release.sh` работает только при обновлении, когда уже есть установленная версия.
- Тест `TestReleaseKeyIsNotTestKey` (Н35) запускается только с настоящим ключом, поэтому в `make check` поставочная сборка не проверялась.

Решение Р1: Ed25519; ключ хранится офлайн у владельца (отдельный носитель, копия в сейфе); манифест выпуска подписывается отдельной командой на машине без сети; отпечаток публикуется в руководстве установки и README поставки; тестовый ключ — только для `make images-test`. Тот же ключ или подключ, подписанный им, подписывает лицензии (Р8) и служебные базы (Р9).

## Решение
1. **Алгоритм и формат.**
   - Ed25519 через `Signer`/`Verifier` профиля `standard` из `internal/crypto`.
   - Файлы PEM видов `AISEC MANIFEST SIGNING KEY` (закрытый, 32 байта seed) и `AISEC MANIFEST SIGNING PUBLIC KEY` с заголовком `Profile` (ADR-0012).
   - Подпись манифеста — над `"aisec-integrity-manifest-v1\n"` + байты файла (без изменений).
   - Профиль `gost` (этап 6) получает свою пару ключей производителя ГОСТ Р 34.10-2012 и свой встроенный открытый ключ. Решение — вместе с выбором СКЗИ.
2. **Роль ключа.**
   - Ключ производителя — корневой ключ доверия к продукту. Им напрямую подписывается манифест каждого выпуска: выпусков мало, и подпись офлайн их не задерживает.
   - Лицензии (ADR-0026, 4.26) и служебные базы (каталог теневого ИИ, ADR-0027, 4.22) подписываются **рабочими ключами**. Каждый рабочий ключ заверяет ключ производителя: заявление с назначением (`license`, `service_db`), открытым ключом, сроком и номером. У заявления свой контекст подписи, поэтому подпись манифеста нельзя выдать за заверение или лицензию, и наоборот.
   - Формат заявления определяют ADR-0026 и ADR-0027. Требования этого ADR к нему: контекст `aisec-vendor-subkey-v1`, проверка через `internal/crypto`, отзыв заверения новым выпуском.
   - Встроенный ключ проверки остаётся одним и тем же. Переход на рабочие ключи поэтому не меняет ключ в установленных системах и не требует переходного выпуска.
3. **Хранение.**
   - Закрытый ключ — файл `0400` на зашифрованном носителе: USB-накопитель, LUKS2 с парольной фразой. Копия хранится на втором таком же носителе в сейфе. Парольная фраза хранится отдельно от носителей.
   - Ключа нет в репозитории, CI, облаке, переписке, на сборочной машине и на машинах с сетью.
   - Машина подписи — отдельный ноутбук с шифрованием диска. Сеть на нём отключена: Wi-Fi выключен или снят, кабель не подключён. Другие задачи на нём не выполняются.
   - На машину подписи переносится только манифест, на отдельном носителе (не на носителе с ключом), и с неё уносится только файл подписи. Бинарники продукта на ней не запускаются.
4. **Создание ключа** (владелец, один раз, на машине подписи).
   - Команда: `aisec-manifest-sign gen-key -key /media/vendor-key/vendor-manifest.signkey -pub manifest.pub`. Инструмент собирает `make release-signer`, это статический `tools/manifest`.
   - Команда печатает отпечаток.
   - Открытый ключ владелец коммитит в `internal/integrity/keys/manifest.pub`, отпечаток вносит в руководство установки и README поставки.
5. **Инструмент подписи** (`tools/manifest sign`; `make release-sign MANIFEST_KEY=… [MANIFEST_SHA256=…]`, если на машине подписи есть Go и репозиторий на теге выпуска).
   - Работает только без сети: отказ, если работает хотя бы один сетевой интерфейс, кроме петлевого (`FlagUp` и `FlagRunning`). Это защита от ошибки оператора, а не граница безопасности: root машины её обойдёт. Так же работает `gen-key`; тестовые пары репозитория создаются с `-test`.
   - Отказывает ключам из репозитория (тестовому и имитации) и файлу ключа, доступному группе или остальным.
   - Разбирает манифест тем же строгим правилом, что и проверка (до 4 МиБ, только обычный файл, профиль совпадает).
   - Сверяет SHA-256 манифеста с `-expect-sha256` — значением, которое напечатал `release-dir` на сборочной машине. Без флага подписывает, но напоминает сверить хеш вручную.
   - Не перезаписывает существующую подпись, проверяет готовую подпись открытым ключом.
   - Печатает версию, время сборки, число файлов, SHA-256 манифеста и отпечаток ключа.
   - Инструмент собирается с тега выпуска. Его SHA-256 записывается в журнал выпусков владельца, обновляется только вместе с этим ADR.
6. **Выпуск — три шага.**
   1. Сборочная машина, тег `VERSION`, чистое дерево: `make web-build`, `make check`, `make release-dir RELEASE=1`. Результат — бинарники и манифест **без подписи** в `build/release`, на экране — SHA-256 манифеста. `MANIFEST_KEY` здесь не нужен: `tools/manifest build` больше не принимает `-key`, а `make manifest RELEASE=1` отказывает.
   2. Машина подписи: `aisec-manifest-sign sign -key … -manifest aisec-manifest.json -expect-sha256 …`. Файл `aisec-manifest.json.sig` переносится обратно в `build/release`.
   3. Сборочная машина: `make images RELEASE=1`. Цель проверяет чистое дерево и тег, наличие подписи, `make release-test` с настоящим ключом, `aisec-cli verify` каталога выпуска поставочным `aisec-cli` и печатает отпечаток. Затем — образы, SBOM, `images-verify` (ADR-0019). Каталог выпуска при этом не пересобирается.
7. **Приём только ключа производителя.**
   - Поставочная сборка встраивает `keys/manifest.pub`.
   - `EmbeddedVerifier` отказывает, если встроен ключ из репозитория: тестовый `manifest-test.pub` или имитация `manifest-release-ci.pub`.
   - Имитацию разрешает только тестовый файл с тегом `aisec_release`. Тесты в бинарники не попадают.
   - `make release-test` входит в `make check`. Без `RELEASE=1` он встраивает имитацию ключа производителя через `go test -overlay`: проверяются приём подписи ключом производителя, отказ при подмене манифеста, при подписи тестовым и чужим ключом и при встроенном ключе из репозитория. С `RELEASE=1` встроен настоящий ключ, и `TestReleaseKeyIsNotTestKey` проверяет, что это не ключ из репозитория.
8. **Отпечаток.**
   - Хеш профиля (SHA-256) от 32 байт открытого ключа, шестнадцатеричный, 16 групп по 4 знака через двоеточие (`integrity.Fingerprint`). Не зависит от оформления файла PEM.
   - Печатают отпечаток `tools/manifest gen-key`, `sign`, `fingerprint`, `make release-fingerprint` и `aisec-cli verify -release` (строка «Отпечаток ключа производителя: …»).
   - Где публикуется:
     - руководство установки, раздел 3.1;
     - README поставки (`deploy/compose/pilot/README.md`);
     - письмо производителя заказчику, отдельно от поставки.

     Источник доверия — руководство и письмо. README приходит вместе с поставкой и сам по себе доверия не даёт.
9. **Проверка поставки у заказчика** (`verify-release.sh`, ОБН.1).
   - Администратор записывает отпечаток в `.env` как `AISEC_VENDOR_FINGERPRINT`. Без него скрипт отказывает. Исключение — `AISEC_IMAGE_REPO=aisec-test`: тогда только предупреждение.
   - Обновление: подпись и файлы проверяет `aisec-cli` установленной версии, а скрипт сверяет напечатанный отпечаток с `.env`.
   - Первая установка (`-first`): установленной версии нет. Архив образа `aisec-cli` из поставки проверяется до загрузки, затем загруженный образ проверяет выпуск, и отпечаток сверяется с `.env`. Остальные образы проверяются так же, как при обновлении. При ошибке загруженные образы удаляются.
10. **Плановая смена ключа.** Срока у ключа нет; плановая смена — со сменой профиля или по решению владельца. Порядок:
    - переходный выпуск N подписан старым ключом и встраивает новый ключ как «следующий» (`keys/manifest.next.pub`). `aisec-cli verify -release` принимает им подписанный следующий выпуск, а самопроверка компонентов — нет;
    - выпуск N+1 встраивает и подписан новым ключом;
    - производитель сообщает новый отпечаток письмом, администратор меняет `AISEC_VENDOR_FINGERPRINT` перед проверкой N+1.

    Код «следующего» ключа пишется вместе с первой плановой сменой (сейчас он не нужен).
11. **Компрометация или утрата.**
    - Признаки: носитель утерян вне сейфа, парольная фраза раскрыта, найдена подпись, которой нет в журнале выпусков.
    - Действия производителя:
      - прекратить выпуски;
      - создать новый ключ по п. 4;
      - собрать выпуск с новым ключом;
      - письмом сообщить заказчикам новый отпечаток и дату, после которой подписи старым ключом недействительны;
      - отозвать заверения рабочих ключей (лицензии и базы переподписываются).
    - Действия заказчика:
      - не использовать обычный режим `verify-release.sh`: установленная версия доверяет старому ключу;
      - проверить новый выпуск как первую установку: `-first` с новым отпечатком;
      - сменить `AISEC_VERSION` (данные установки сохраняются);
      - выполнить `aisec-cli verify`.
    - Утрата без компрометации (носитель повреждён): ключ восстанавливается из копии в сейфе. Если утеряны обе копии — порядок как при компрометации, но без отзыва прежних выпусков.

## Альтернативы
- **Подпись на сборочной машине с ключом в файле** (как было). Ключ попадает на машину с сетью и в окружение сборки. Противоречит Р1.
- **Аппаратный токен (PKCS#11, Рутокен, YubiKey).** Ключ нельзя извлечь, это сильнее. Но нужны библиотека PKCS#11 (cgo, новая зависимость) и токен с Ed25519. Вернёмся к этому с профилем `gost` и СКЗИ (этап 6).
- **Мастер-ключ и рабочий ключ выпусков с самого начала.** Нужен формат заверения уже сейчас, а выпусков мало и они подписываются офлайн. Рабочие ключи вводятся там, где подписей много: лицензии и базы (п. 2).
- **GPG, cosign или Sigstore.** Внешние инструменты и форматы вне `internal/crypto`. Sigstore требует сети (журнал прозрачности). Проверка у заказчика зависела бы от сторонних программ.
- **Подпись образов** (Docker Content Trust, Notation). Нужны реестр и сеть. Образы и так побайтно сверяются с подписанным манифестом (ADR-0019).
- **Отпечаток от файла PEM** (`sha256sum manifest.pub`). Зависит от переводов строк и заголовков. Отпечаток от байтов ключа устойчив.
- **Проверка «без сети» только регламентом.** Оставлена как основная мера, но инструмент ещё и проверяет интерфейсы: ошибку оператора (забытый Wi-Fi) он ловит сам.

## Последствия
- Ключ производителя не бывает на машине с сетью. Без него нельзя выпустить поставочную сборку, и подписать её может только тот, у кого есть носитель и парольная фраза.
- Поставка проверяется и при первой установке. Остаточный риск: полностью подменённая поставка с изменённым `aisec-cli`, который печатает ожидаемый отпечаток. Его закрывают канал поставки и письмо производителя (threat-model, подмена выпуска); пакеты с проверкой подписи до установки — этап 6.
- Выпуск — три шага вместо одного. `make manifest RELEASE=1` и `make check RELEASE=1` не поддерживаются: проверки идут без `RELEASE`, поставочные тесты — `make release-test` (входит в `check`).
- Новая переменная `.env` `AISEC_VENDOR_FINGERPRINT`, флаг `verify-release.sh -first`, команды `tools/manifest sign` и `fingerprint`, цели `release-sign`, `release-signer`, `release-fingerprint`, `images-build`. В репозитории — пара-имитация `testdata/integrity/manifest-release-ci.signkey` и `internal/integrity/keys/manifest-release-ci.pub`.
- Владельцу до первой поставки:
  - создать ключ на машине подписи;
  - закоммитить `keys/manifest.pub`;
  - вписать отпечаток в руководство (раздел 3.1) и README поставки;
  - записать SHA-256 инструмента подписи;
  - выполнить замер установки на чистой ВМ (4.3).
- ADR-0012 (п. 5) и ADR-0019 (п. 2) в части подписи заменены этим ADR.
- Откат: вернуть `-key` в `tools/manifest build` и прежние цели `release-dir`/`images`. Ключи и формат манифеста не меняются.

## Дополнение (28.10.2026, ревью 4.r1): проверки в `verify-release.sh` и `make images`
- **`verify-release.sh` не скачивает `aisec-cli` (4В10).** При обновлении подпись нового выпуска проверяет `aisec-cli` из образа установленной версии; `docker run` и `docker create` — с `--pull never`, нет локального образа — отказ с подсказкой про `-first`. Иначе при пустом или неверном `AISEC_VERSION` Docker скачал бы образ из реестра, и проверку выполнил бы не тот код, которому доверяет установка. В `.env.example` `AISEC_VERSION` пуст: значение вписывает установщик.
- **`make images RELEASE=1` — только из каталога, подписанного ключом производителя (4В11).** `aisec-cli verify -manifest` при тестовом ключе только предупреждал. Новая цель `release-signed-check` запускает `aisec-cli` выпуска с `-release` и отказывает, если: сборка с тестовым ключом; отпечаток ключа, которым проверена подпись, не совпадает с отпечатком `VENDOR_PUB` (по умолчанию `internal/integrity/keys/manifest.pub`); версия манифеста не равна `VERSION`. Пока владелец не закоммитил `manifest.pub`, цель отказывает — так и должно быть до первой поставки.

# Среда сборки и разработки

Черновик этапа 0. Описание сборочной среды для проверки по методике ФСТЭК, включая использование ИИ-ассистента (ТЗ, 8.7, 8.11).

## Сборочный образ
Базовый образ Go для сборки: `golang:1.27.3-bookworm@sha256:21ade014faf952365b9ecbd8dbdb87176fbacb82fac9fb132d9f2a7b8cc3f132` (индекс образа для всех архитектур). Происхождение digest: получен 21.10.2026 из mirror.gcr.io — зеркала Docker Hub; сверено, что SHA-256 тела индекса совпадает с digest. Это подтверждает только согласованность самого зеркала; что Docker Hub отдаёт образ по этому digest, подтвердит `make check-docker` в CI (для 1.27.2 это подтвердил запуск https://github.com/azuresong-afk/ai_railway/actions/runs/38058660303). Версия 1.27.3 нужна из-за GO-2026-6809 (crypto/x509). Обновляется вместе с `toolchain` в `go.mod`: выход исправлений безопасности Go — повод обновиться сразу (их находит `make vuln`).

Образы стенда разработки (`deploy/compose/dev/Dockerfile`): сборка в этом образе без сети (`GOFLAGS=-mod=vendor`, `GOPROXY=off`, `GOTOOLCHAIN=local`), запуск в `scratch` — только статический бинарник, без оболочки и пакетов ОС. В контекст сборки попадают только `go.mod`, `go.sum`, `vendor/`, `cmd/`, `internal/` (`Dockerfile.dockerignore`). Контейнеры: файловая система только для чтения, без привилегий (`cap_drop: ALL`, `no-new-privileges`), от UID пользователя, запустившего стенд.

**Сборочный образ** (`deploy/build/Dockerfile`, `make build-image`) — тот же базовый образ плюс golangci-lint, govulncheck и sbom-utility в версиях из `Makefile` (передаются аргументами сборки; другого места с версиями нет). Инструменты ставятся в `/opt/aisec-tools/bin`, кеши — во временном каталоге.
- `make check-docker` — `make check` в сборочном образе от UID пользователя: это проверка «на чистой машине» (критерий приёмки этапа 0).
- `make check-offline VULNDB_DIR=<снимок>` — то же без сети (`--network=none`) с локальной базой уязвимостей: доказательство сборки без интернета (ADR-0003). Снимок базы монтируется снаружи, а не вшивается в образ (так его можно обновлять без пересборки образа) — это отличается от первоначального плана задачи 0.15.

**Перенос в закрытый контур (процедура, ещё не прогонялась):**
1. На машине с интернетом: `make build-image`; `docker save` образа в файл; записать digest образа (`docker image inspect`) в акт переноса.
2. Снимок базы уязвимостей: каталог в формате базы Go (`index/db.json`, `index/modules.json`, `ID/*.json`) — копия содержимого vuln.go.dev на дату снимка. **Способ получения снимка не проверен** (в среде разработки vuln.go.dev недоступен); его нужно проверить при первой подготовке закрытого контура и описать здесь точной командой. Дата снимка записывается в акт; снимок старше 7 дней считается устаревшим (ADR-0003).
3. В контуре: `docker load`, сверка digest с актом, `make check-offline VULNDB_DIR=<снимок>`.
- `make fuzz-long-docker` — ночной длительный фаззинг.

**Лабораторная сборка** (`deploy/build/Dockerfile.lab`, задача 4.32 этапа 4, ADR-0019, дополнение 27.10.2026) — для `deploy/compose/pilot/lab-install.sh`, когда на хосте только Docker. Стадия консоли — `node:22.22.0-bookworm-slim` по digest: `npm ci --ignore-scripts` строго по `web/package-lock.json` (сеть нужна только этой команде, `npm run build` — под `RUN --network=none`; корень прокси с проверкой TLS — секретом сборки `build-ca`, в образы не попадает); стадия Go — тот же образ golang, `make release-dir` под `RUN --network=none` с тестовым ключом манифеста. Контекст сборки ограничен `Dockerfile.lab.dockerignore` (без `.git`, `bin/`, `build/`, `web/node_modules`, `web/dist`). Результат — каталог выпуска и образы `aisec-test`, не для поставки.

Закреплённые версии сверяет `make licenses`: каждый образ в `FROM` файлов `deploy/**/Dockerfile*` (golang, node) — по digest и с той же версией, что в `components.yaml`; каждое действие в `.github/workflows/` — по SHA коммита и с тем же SHA, что в реестре.

## Цели Makefile
Вся логика сборки и проверок — в `Makefile` (ТЗ, 11.4); список — `make help`. `make check` — всё, что нужно для pull request; состав растёт по мере выполнения задач этапа 0, а цели, которые ещё не реализованы, падают с сообщением, а не проходят молча.

Переменные окружения, которые задаёт Makefile:
| Переменная | Значение | Зачем |
|---|---|---|
| `GOFLAGS` | `-mod=vendor`, не переопределяется окружением | Зависимости только из `vendor/` |
| `GOPROXY` | `off`, не переопределяется окружением | Никаких обращений к прокси модулей при сборке и проверках. Исключение — `make tools`, где прокси (`TOOLS_GOPROXY`) задан явно |
| `GOTOOLCHAIN` | `local`; допустимо только `local` или `go1.27.3`, иначе `make` останавливается | Запрет скрытой загрузки toolchain. На машине без Go 1.27 — `GOTOOLCHAIN=go1.27.3` при уже скачанном toolchain |
| `CGO_ENABLED` | `0` | Статические бинарники без cgo. Для `make test` (детектор гонок), `make lint` и `make vet` включается, чтобы проверялись и файлы с cgo |

`make lint` сверяет версию `bin/golangci-lint` с `GOLANGCI_LINT_VERSION`. Пока не все проверки этапа 0 реализованы, `make check` печатает предупреждение со списком недостающих (`PENDING_CHECKS`).

Сборка: `go build -trimpath -tags '$(BUILD_TAGS)' -ldflags '-s -w -buildid= …'`, результат в `build/bin/`.

Манифест целостности (ОЦЛ.1, ADR-0012) создаёт `make manifest` (входит в `make check`): `build/aisec-manifest.json` и подпись `.sig` по бинарникам поставки, `web/dist` и `migrations/`, затем проверка готового манифеста через `build/bin/aisec-cli verify`.
- По умолчанию манифест подписывается тестовым ключом `testdata/integrity/manifest-test.signkey` («не для поставки»), а бинарники встраивают его открытую пару.
- Поставочная сборка (ADR-0022) — три шага, закрытый ключ производителя на сборочную машину не попадает:
  1. `make release-dir RELEASE=1` на теге `VERSION` из чистого дерева: бинарники с тегом `aisec_release` (встраивают открытый ключ производителя `internal/integrity/keys/manifest.pub`) и манифест **без подписи** в `build/release`, на экране — его SHA-256.
  2. На отдельной машине без сети: `tools/manifest sign -key <ключ на отдельном носителе> -manifest aisec-manifest.json -expect-sha256 <хеш шага 1>` (статический инструмент — `make release-signer`; при Go и репозитории на машине подписи — `make release-sign MANIFEST_KEY=… MANIFEST_SHA256=…`). Инструмент отказывает при работающем сетевом интерфейсе, ключе из репозитория, файле ключа с открытыми правами и несовпадении хеша.
  3. `make images RELEASE=1`: проверка подписи поставочным `aisec-cli verify`, `release-test` с настоящим ключом, отпечаток ключа (`make release-fingerprint`), образы, SBOM, `images-verify`.
- `make manifest RELEASE=1` и `make check RELEASE=1` отказывают: проверки идут без `RELEASE`. Без файла открытого ключа поставочная сборка не компилируется.
- `make release-test` входит в `make check`: тесты с тегом `aisec_release`, где вместо `keys/manifest.pub` через `go test -overlay` встроена имитация ключа производителя (`internal/integrity/keys/manifest-release-ci.pub`, закрытая пара — `testdata/integrity/`, поставочная сборка её не принимает).
- Переменные сборки: `RELEASE` (`1` — поставочная сборка), `MANIFEST_KEY` (путь к закрытому ключу производителя, только `release-sign` на машине без сети), `MANIFEST_SHA256` (ожидаемый хеш манифеста для `release-sign`), `VERSION`.

Инструменты разработки ставятся `make tools` в `bin/` по версиям из переменных в начале `Makefile`.

## CI
GitHub Actions — тонкая обёртка над `make` (ADR-0002):
- `.github/workflows/check.yml` — на каждый pull request и push в `main`: `make check-docker`, выгрузка отчётов (SARIF, SBOM, покрытие матрицы) как артефактов на 90 дней. Права токена — только `contents: read`, учётные данные git после получения кода не сохраняются (`persist-credentials: false`).
- `.github/workflows/fuzz-nightly.yml` — каждую ночь `make fuzz-long-docker`; при падении выгружаются найденные входы.
- Сторонние действия закреплены по SHA коммита: `actions/checkout` v7.0.1, `actions/upload-artifact` v7.0.1.
- `make vuln` в CI работает по онлайн-базе vuln.go.dev.

**Настройки репозитория (делает владелец вручную; решение от 05.10.2026):** набор правил (ruleset) для `main`:
- обязательный pull request и обязательная проверка `check` на его последнем коммите;
- запрет force-push и удаления ветки;
- **обход правил разрешён только владельцу** (список bypass — одна учётная запись владельца). Без этого push подписанного коммита слияния в `main` (процедура выше) будет отклонён: правило «только через pull request» не различает слияние кнопкой и локальное. GitHub сам отмечает pull request слитым, когда в `main` попадает его последний коммит;
- обязательного одобрения (approvals) не включать: владелец — единственный ревьюер, а одобрить собственный pull request GitHub не даёт. Ревью владельца подтверждается его подписью на коммите слияния.

В настройках Actions — разрешить только действия, закреплённые по SHA, права `GITHUB_TOKEN` по умолчанию «только чтение», запрет Actions создавать и одобрять pull request.

## Проверка vendor/
Хеш `h1` из `go.sum` — хеш всего дерева модуля, а в `vendor/` Go копирует только нужные пакеты, поэтому по `vendor/` его не пересчитать. Проверка двухуровневая (`tools/vendor-check`, ТЗ, 8.7):
- `make vendor-check` — в составе `make check`, без сети: версии в `vendor/modules.txt` и `go.mod` совпадают, у каждого модуля есть хеши `h1` и `/go.mod h1` в `go.sum`, нет модуля только в одном из файлов, нет директив `replace` в `go.mod` и замен `=>` в `modules.txt`, а SHA-256 каждого файла `vendor/` (в том числе `modules.txt`) совпадает с манифестом `docs/cert/vendor.sha256`. Лишний, пропавший или изменённый файл — ошибка; не обычный файл (ссылка) в `vendor/` — ошибка.
- `make vendor-manifest` — пересчёт манифеста после `go mod vendor`; изменение манифеста проверяет ревью вместе с обновлением зависимости (CLAUDE.md, «Зависимости»).
- `make vendor-verify` — вне `make check`, нужна сеть: сначала проверка без сети, затем `go mod vendor -o <временный каталог>` с пустым кешем модулей (`GOMODCACHE` во временном каталоге) и сравнение с `vendor/`. Модули скачиваются заново, и Go сверяет их с хешами `go.sum`, поэтому отравленный кеш сборочной машины проверку не обманет; `sum.golang.org` опрашивается только для модулей, которых нет в `go.sum`. Пока запускается вручную перед выпуском и после обновления зависимостей там, где есть сеть; в CI её нет — отдельное задание с сетью ждёт решения владельца (`docs/plans/stage-1.md`, «Открытые вопросы»). В закрытом контуре — по зеркалу модулей.

## Сборка без интернета
Решение — [ADR-0003](../adr/0003-sborochnaya-sreda-i-offlain.md).
- Сборка и проверки не обращаются к прокси модулей (`GOPROXY=off`) и берут зависимости только из `vendor/`.
- Инструменты и toolchain — в сборочном образе (задача 0.15).
- База уязвимостей: `make vuln` использует `GOVULNDB`, по умолчанию `https://vuln.go.dev`; в закрытом контуре — `make vuln GOVULNDB=file:///<каталог снимка>`. Без доступа к базе `make vuln` падает, проверка молча не пропускается.
- В облачной среде разработки ИИ-ассистента сетевая политика на 29.09.2026 запрещает `vuln.go.dev` (ответ 403), поэтому там `make vuln` не проходит; проверка уязвимостей выполняется в CI.
- npm: до этапа 6 — публичный реестр строго по lock-файлу, затем внутреннее зеркало.

## Управление изменениями и подпись
Решение — ADR-0002.
- Основная ветка `main` защищена; изменения — только через pull request с ревью владельца и зелёной проверкой `check`.
- ИИ-ассистент работает в рабочих ветках `claude/*`. Его коммиты **не подписаны**: у среды ассистента нет ключа владельца, и давать ей такой ключ нельзя.
- **Подписанным является коммит слияния в `main`.** Владелец сливает pull request локально своим ключом GPG или SSH и отправляет в `main`:
  ```
  git fetch origin
  git switch main && git pull --ff-only
  git merge --no-ff -S origin/<рабочая-ветка>
  git push origin main
  ```
  Слияние кнопкой веб-интерфейса GitHub подписывается ключом GitHub (web-flow), а не владельца, — для этого проекта не используется.
- Правило «Require signed commits» в защите ветки не включается: оно несовместимо с неподписанными коммитами ассистента при обычном слиянии.
- Теги выпусков подписывает владелец (`git tag -s`).

## ИИ-ассистент в разработке
Использование ИИ-ассистента — часть среды разработки (ТЗ, 8.11).
- **Инструмент:** Claude Code (Anthropic) в облачной среде выполнения. Код, документы и вывод команд из репозитория передаются модели за периметр организации.
- **Что не передаётся:** секреты, ключи, данные заказчиков и реальные ПДн. В тестах — только синтетические данные. Правило `deny` в `.claude/settings.json` запрещает инструменту чтения файлов открывать `.env`, `secrets/` и `.dev-keys/`. **Это не техническая изоляция:** через команды оболочки (например, `cat`) файлы прочитать можно, поэтому защита держится на правилах работы ассистента и на том, что реальных секретов в рабочей копии нет (ключи стенда разработки — одноразовые, без доступа к чему-либо).
- **Права ассистента:** работа в рабочей ветке; слияние в `main` — только владельцем. В `.claude/settings.json` подтверждение человека требуется для команд, которые загружают код и данные извне: `go get`, `go install`, `go mod download`, `make tools`, `make build-image`, `docker pull`, `docker build`, `git clone`, `npm install`/`add`, `npx`, `pip install`, `curl`, `wget`, а также для `git push`. Не требуют подтверждения `git fetch` своего репозитория и `go run пакет@версия` — они ограничены сетевой политикой среды (расширено 05.10.2026). Запрет изменения `.dev-keys/` и `secrets/` и чтения `.env*` — там же.
- **Сетевые ограничения среды:** исходящие соединения ассистента идут через прокси с политикой организации. Например, vuln.go.dev на 01.10.2026 запрещён — поэтому проверка уязвимостей выполняется в CI.
- **Какие проверки проходит сгенерированный код:** все те же, что код человека — `make check` в CI (линтеры с самопроверкой правил, SAST с разметкой, тесты, e2e, fuzz-smoke, лицензии, SBOM, govulncheck, покрытие матрицы), сабагент `cert-reviewer` (`.claude/agents/cert-reviewer.md`) после значимых изменений и обязательное ревью владельцем перед слиянием.
- **Правила работы ассистента** — `CLAUDE.md` в корне репозитория; план и статусы задач — `docs/plans/`.

## SBOM
`make sbom` формирует `build/sbom/aisec.cdx.json` в формате CycloneDX 1.6 (ТЗ, 8.6):
- **Состав** читается из собранных бинарников поставки (`debug/buildinfo`), а не из `go.mod`: в SBOM ровно то, что вошло в продукт. Модуль, которого нет в `components.yaml` со `scope: product`, — ошибка.
- **Компоненты:** стандартная библиотека Go (`pkg:golang/stdlib@…`), модули Go (`pkg:golang/<путь>@<версия>`), бинарники как `file` с SHA-256. Граф зависимостей: продукт → бинарники → модули.
- **Хеши модулей:** `h1` из `go.sum` — SHA-256 по дереву файлов модуля, проверяемый по `sum.golang.org`; в `hashes` он записан в шестнадцатеричном виде, а исходное значение — в свойстве `go:module_hash_h1`. При сборке с `-mod=vendor` Go не пишет хеш в сведения о сборке, и `tools/sbom` берёт его из `go.sum` (флаг `-gosum`). **Это заявленный хеш модуля, а не хеш кода из `vendor/`:** сборка сверяет `vendor/modules.txt` только с `go.mod`, содержимое `vendor/` с `go.sum` сверяет лишь `go mod vendor`. Неизменность `vendor/` проверяет `make vendor-check` (манифест `docs/cert/vendor.sha256` и согласованность `modules.txt`, `go.mod`, `go.sum`; без сети) и `make vendor-verify` (повторный `go mod vendor` во временный каталог с пустым кешем модулей и сравнение; нужна сеть, в CI пока нет); см. раздел «Проверка vendor/». Хеши бинарников считаются через `Hasher` из `internal/crypto`.
- **Свойства по методике ФСТЭК:** `GOST:attack_surface`, `GOST:security_function` (`yes`/`no`), `GOST:provided_by` — из `components.yaml`. Формат значений сверяется с приложением 1 методики до этапа 6.
- **Воспроизводимость:** время документа — время последнего коммита (`SOURCE_DATE`), серийный номер (UUID версии 8) выводится из содержимого.
- **Проверка:** `sbom-utility validate` по схеме CycloneDX 1.6 и собственная проверка обязательных полей (`tools/sbom -check`).

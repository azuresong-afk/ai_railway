Сессии до второго фактора ограничены отдельно от полных (тот же предел `session_max_per_user`): вход по одному паролю вытесняет только такие же сессии и не завершает полные. Неверный код (при входе, подключении и перевыпуске кодов) — неудачная попытка ИАФ.4 с общим счётчиком; вход по паролю при подключённом факторе счётчик не сбрасывает (иначе перебор кодов между входами), сбрасывает принятый код. 10 кодов восстановления по 80 бит — показываются один раз, хранятся хешами профиля, гасятся при использовании и перевыпуске (триггер: погашенный код не возвращается). ## Политики (ТЗ, 5.3)
Функция фильтрации входа и выхода (ТЗ, 2.1): по находкам детекторов политика решает, что сделать с запросом и ответом. Статус — частично: модель, схема YAML, таблица приоритетов, режимы, `non_text`, эмбеддинги и шаблоны реализованы в `internal/policy` (задача 1.19); к запросу `POST /v1/chat/completions` политика применяется конвейером шлюза (задача 1.22), к ответу модели — проверкой ответа (задача 1.23); исключения, неизменяемые версии с откатом, песочница и подписанные пакеты — этап 2 (сервер, аудит, `internal/crypto`).

- **Модель.** Политика: `id`, `name`, `version`, `mode` (`monitor`, `enforce`), `non_text`, `response_check`, `block_message`, упорядоченный список `rules`. Правило: `id`, `detector` (ID из реестра детекторов), `directions`, условия `categories` и `sources`, `threshold` (по умолчанию 0,5), `action`, `severity` (`info`–`critical`), `message`. Политика ссылается на детекторы только по ID и не зависит от их пакетов.
- **Строгая проверка.** Неизвестные поля, повторы, значения вне перечислений, порог вне (0, 1] (в том числе `.nan`), текст сообщений с управляющими и скрытыми символами — ошибка; до 256 правил, до 1 МиБ при импорте (`Parse`). `require_approval` отвергается до этапа 4. `pseudonymize` — только для входа: псевдоним в ответе модели восстановить нечем. Политика заказчика компилируется строго: незарегистрированный детектор, неподдерживаемое им направление или категория, которую детектор не выдаёт (опечатка `pii.pasport` иначе дала бы правило, которое молча никогда не срабатывает), — ошибка (`Compile`). Категории детектор сообщает через `detect.Categorizer` (все встроенные; у `lists` — категории списков приложения); правило с `categories` для детектора без списка категорий отвергается.
- **Таблица приоритетов** (менять только вместе с `TestPriorityTable`):

| Приоритет | Действие | Что делает |
|---|---|---|
| 6 | `block` | Блокирует запрос или ответ (`policy_violation`, безопасное сообщение без названий детекторов) |
| 5 | `require_approval` | Этап 4; в политиках этапа 1 отвергается |
| 4 | `redact` | Необратимое маскирование фрагмента |
| 3 | `pseudonymize` | Обратимое: псевдоним в запросе, обратная подстановка в ответе |
| 2 | `log` | Только запись в событие |
| 1 | `allow` | Ничего |

- **Разрешение конфликтов.** Для находки берутся все совпавшие правила (детектор, направление, источник, категория, порог), итог по находке — самое сильное действие; при равенстве — первое правило по списку. Итог решения — самое сильное по всем находкам и `non_text`. Правило не ослабляет другое: `allow` не отменяет `block` (ослабление — только исключением, этап 2). Отдельно запоминается самая сильная защита данных по находке (`redact` или `pseudonymize`), даже если итог — `block`.
- **Режимы.** `enforce` применяет решение целиком. `monitor` применяет только защиту данных во входе к внешнему провайдеру, в том числе когда итог — `block`; `block` только журналируется; для внутреннего провайдера и для ответа модели ничего не применяется. Решение содержит итог «как в `enforce`» и фактически применённые действия. Режим приложения (`policy_mode`) важнее режима политики; пусто — режим политики; незнакомое значение считается `enforce`.
- **Эмбеддинги.** Для `/v1/embeddings` `pseudonymize` выполняется как `redact` с отметкой в решении (ТЗ, 5.1).
- **Нетекстовые части** (`non_text`, DM-14): `allow_unchecked` (по умолчанию) — пропустить с отметкой «содержит непроверенные части»; `allow_inline` — пропустить с отметкой только данные в запросе, ссылки на медиа блокировать (провайдер загружает ссылку сам — SSRF в его контуре); `block` — блокировать любые.
- **Шаблоны.** `base` «Базовая защита» (`monitor`, по умолчанию для приложения без политики — решение Р7), `pii-strict` «ПДн — строго» (`enforce`, `non_text: block`), `external-no-pii` «Внешний провайдер: ПДн не передавать» (`enforce`, `non_text: block`), `monitor-only` «Только мониторинг» (только журнал; ПДн уходят провайдеру как есть — с внешним провайдером шлюз при запуске пишет предупреждение, `GatewayFile.Warnings`). Правила шаблона для детекторов, которых нет в реестре, опускаются: шаблон не зависит от набора встроенных детекторов (сейчас встроены все семь детекторов этапа 1 из шаблонов). В «ПДн — строго» к блокирующим правилам скрытых символов, ПДн и секретов добавлены правила `redact`: в `monitor` скрытые символы, ПДн и секреты к внешнему провайдеру всё равно вырезаются и маскируются (к внутреннему провайдеру `monitor` ничего не применяет). Правило `lists` во всех шаблонах — только `log`: запрещённые темы заказчика блокируются только его собственной политикой.
- **Конфигурация шлюза.** Раздел `policies` файла конфигурации (решение Р2); ID политики заказчика не совпадает с шаблоном; приложение ссылается на политику из `policies` или на шаблон, пусто — `base`. Политика приложения находится через `policy.Resolve` и компилируется при запуске по детекторам приложения (встроенные, `lists` со списками заказчика, `output.exfil` с `exfil_allow_domains`): незарегистрированный детектор в политике заказчика — отказ запуска.
- **Конвейер шлюза** (задача 1.22, `internal/gateway/pipeline.go`, ТЗ, 4.3–4.4):
  - Детекторы политики для входа запускаются по каждому текстовому фрагменту запроса (содержимое, отказы и аргументы `tool_calls` в истории, имена файлов, описания инструментов) параллельно; текстовые части одного сообщения детекторы `injection.*` проверяют ещё и склеенными, как их склеит провайдер, а маскирование находки в склейке переносится на части. Детекторы — параллельно, каждый со своим сроком: 100 мс плюс 2 мс на КиБ текста (расчётная скорость 0,5 МБ/с — в 5 раз ниже наихудшей измеренной), не больше минуты. Срок по длине закрывает обход через срок (`threat-model.md`).
  - Сбой детектора (срок, ошибка, паника, некорректная находка) — по режиму приложения (`fail_mode`): `fail_closed` блокирует (503 `check_unavailable`) в любом режиме политики, в том числе `monitor`: несостоявшаяся проверка не подтверждает, что защита данных не нужна; `fail_open` пропускает. Сбои — в `decision.failures` события, без текста ошибки.
  - Блокировка — 400 `policy_violation` с сообщением правила или политики; какие детекторы сработали, приложение не узнаёт. Квоты и неразрешённая модель отклоняются до детекторов и в `monitor` тоже.
  - Защита данных (с задачи 1.23 — через `internal/pseudonym`): `pseudonymize` заменяет фрагмент псевдонимом `[[ТИП_N]]` из словаря запроса, `redact` — маской `[[ТИП]]`, у `unicode.hidden` (кроме гомоглифов) — вырезает символы (DM-05). Пересекающиеся фрагменты объединяются, `redact` среди них делает объединение необратимым. Ошибка защиты данных — запрос не уходит (500).
  - Событие `gateway_request` — на каждый разобранный запрос: решение (что было бы в `enforce` и что применено), правило, политика и версия, трассировка, находки без значений, категории угроз, задержки, токены, псевдоним пользователя (HMAC, `internal/crypto`), содержимое по режиму хранения; с 1.23 — проверка ответа (`response`: режим, решение, обрыв потока) и счётчики псевдонимизации (`pseudonyms`, без значений). Заголовки `X-AISec-Event-Id` и `X-AISec-Decision` (у ответа без потока и `buffered` — самое сильное из сделанного с запросом и ответом, у потока — только по запросу).
- **Проверка ответа** (задача 1.23, `internal/gateway/response.go`, ТЗ, 4.3, шаг 7; 5.1; 5.3): выходные детекторы политики проверяют `content`, `refusal` и аргументы каждого вызова `tool_calls` (DM-13; находки в аргументах получают строку DM-13, какой бы детектор их ни нашёл); находки ответа — в общем списке события с местом `choices[0].message.…`.
  - Ответ без потока и `response_check: buffered` — собрать целиком, проверить, отдать: `block` — 400 `policy_violation`, сбой при `fail_closed` — 503 `check_unavailable`, `redact` — маска `[[ТИП]]`; маска, которая ломает JSON аргументов вызова (значение стояло числом), блокирует ответ (правило `tool_args_json`). В `buffered` потоке до проверки приложение не получает ничего, проверенный ответ отдаётся частями SSE.
  - `incremental` (по умолчанию, Р7) — текст проверяется окнами: после каждых 512 байт нового текста детекторы проверяют окно из 4 КиБ уже переданного текста и всего непереданного; начало окна сдвигается назад по разметке markdown всего текста (`exfil.Window`: в блоке кода — с начала строки и оградой перед окном, в списке — с начала последнего пункта верхнего уровня, иначе — с начала абзаца, не дальше 8 КиБ; дальше — окно, где `output.exfil` не учитывает код, а его находки в переданном тексте решает итоговая проверка), чтобы код в окне был тем же, что во всём ответе; клиенту уходит проверенный текст, кроме последних 256 байт и недописанного слова (ссылка или значение, которое ещё дописывается, целиком остаётся в непереданном хвосте); слово без пробелов длиннее 4 КиБ отдаётся принудительно; непереданного текста больше 64 КиБ (маскируемая находка всё ещё дописывается) — обрыв (правило `stream_hold_limit`), чтобы работа детекторов оставалась линейной (`TestIncrementalWorkBounded`). Находка с `block` или находка для маскирования, начавшаяся в уже переданном тексте, обрывает поток событием `error` с `policy_violation` и сообщением решения без `[DONE]` (правило `stream_cut`); сбой проверки при `fail_closed` — `check_unavailable`. Находка с `block` или для маскирования целиком в уже переданном тексте, которую нашла только проверка с большим контекстом, тоже обрывает поток (правило `stream_late`, шаг трассировки с детектором и категорией); применённой считается находка, целиком закрытая отданными масками. Повторная причина завершения от провайдера ответ ещё раз не завершает (действует первая). Найденное прежним окном остаётся под маской, даже если следующие проверки его не нашли (сбой при `fail_open`, другой контекст на стыке окон). Сбои детекторов на окнах пишутся в событие без повторов. Вызовы инструментов отдаются целиком в конце, после проверки. В конце — проверка всего ответа (решение в событии). Проверяются тексты и аргументы вызовов; имена функций и идентификаторы вызовов — нет.
  - `monitor`, а также любой `response_check` при режиме политики `monitor` или без выходных правил — части уходят без задержки, ответ проверяется после передачи (синхронно, после `[DONE]`, до закрытия соединения), решение только журналируется (к ответу в `monitor` ничего не применяется, ТЗ, 5.3). Сбой проверки ответа в `monitor` только журналируется: блокировать ответ строже, чем при успешной проверке, незачем.
  - Обратная подстановка выполняется всегда, в том числе в `monitor`: `content` — `Restore` (при `response_format` JSON — `RestoreJSON`), `refusal` — `Restore`, в потоке — `NewStream`/`NewJSONStream`; аргументы всех вызовов ответа — одним `RestoreToolArgs` по массиву JSON из них, чтобы признак адреса в одном вызове запрещал подстановку во всех (аргументы не JSON — без подстановки). Детекторы проверяют ответ с псевдонимами (ПДн, которые вернула подстановка, — данные самого пользователя). Без потока после подстановки `output.exfil` проверяет текст ещё раз; если появилась находка (категория и найденный текст), которой не было в тексте с псевдонимами, или детектор не ответил, подстановка в этом тексте отменяется (`pseudonyms.withheld`). Так ловится и значение внутри изображения, которое было находкой уже с псевдонимом.

## Псевдонимизация (ТЗ, 5.1)
Функция исключения передачи защищаемой информации разработчику модели (ТЗ, 2.1; DM-31). Статус — частично (задачи 1.20, 1.21, 1.23): пакет `internal/pseudonym`, формат и правила — ADR-0005; подключён к конвейеру шлюза в задаче 1.23 (словарь на запрос `chat/completions`, обратная подстановка — «Проверка ответа» выше); в Check API и эмбеддингах `pseudonymize` выполняется как `redact`.

- **Замена.** `NewVault(лимиты, тексты запроса…)` резервирует псевдонимы, которые уже есть в запросе; `Vault.Protect` заменяет фрагменты с действием `pseudonymize` псевдонимом `[[ТИП_N]]`, с `redact` — маркером `[[ТИП]]`; пересекающиеся фрагменты объединяются, `redact` среди них делает объединение необратимым. Одинаковое значение — один псевдоним. Неверные позиции или действие — ошибка, текст не возвращается.
- **Обратная подстановка.** `Vault.Restore` (текст ответа), `RestoreJSON` (`content` при `response_format` JSON), `RestoreToolCalls` (собранные аргументы всех вызовов `tool_calls` одного ответа; `RestoreToolArgs` — для одного вызова) возвращают только значения из словаря этого запроса и принимают ограниченный набор искажений моделью. Не восстанавливаются: искажённые сильнее допустимого, неизвестные номера, псевдонимы там, где значение может стать частью адреса (DM-11): перед псевдонимом признак адреса, а сразу за ним — продолжение адреса или метки домена (`/ @ # %`, латинская буква, цифра, `-`, `_`, точка перед буквой или цифрой); в JSON — вне значения строки и после признака адреса, в том числе без схемы (`@`, `=`, `?q`, `буква.буква`, IPv4, `пример.рф`); в аргументах инструментов — при любом признаке адреса в любом вызове ответа (DM-13). Правило мест — ADR-0005, п. 5. Значение в JSON экранируется; восстановленное значение повторно не разбирается.
- **Потоковая передача.** `Vault.NewStream` (`content`, `refusal`) и `NewJSONStream` (`content` в формате JSON), по одному на текст: хвост части, в котором может начинаться псевдоним, задерживается до следующей части — не больше `MaxPending` (49) байт, остальное отдаётся сразу; `Flush` в конце потока, в том числе при обрыве. Склейка результатов равна подстановке по всему тексту при любом разбиении. Аргументы `tool_calls` в потоке собираются целиком и восстанавливаются вместе с аргументами остальных вызовов ответа.
- **Метрика неудачных подстановок** — `Stats.Failed()`: неизвестный номер (кроме псевдонимов из самого запроса), искажение сильнее допустимого (переведённый тип, потерянные скобки), небезопасное место, превышение объёма; счётчики значений не содержат.
- **Пределы.** До 4096 значений в словаре (сверх — необратимое маскирование), до 4096 разных псевдонимов в резерве из текста запроса (сверх — всё маскируется необратимо), до 4 МиБ значений, вставленных за весь запрос.
- **Словарь** — только в памяти на время запроса; `String`, `GoString`, `LogValue` печатают только число записей; `Clear` удаляет значения; после него `Protect` — ошибка, а подстановка отдаёт текст как есть, не меняя метрик. Режим хранения `full` — только с сервером управления, содержимое шифруется (задача 2.15, раздел «События»).
- **Тесты.** `TestDM31_PseudonymizeRoundTrip`, `TestDM31_ExperimentMockLLM`, `TestExperimentCollisions`, `TestProtectOverlap`, `TestProtectRejects`, `TestReserveExisting`, `TestFallbackToRedact`, `TestRestoreTolerant`, `TestRestoreUnchanged`, `TestRestoreKeepsBackslash`, `TestRestoreNoRecursion`, `TestDM11_RestoreNotInURL`, `TestRestoreJSON`, `TestDM13_RestoreToolArgs`, `TestDM13_RestoreToolCalls`, `TestReserveLimit`, `TestClearDuringStream`, `TestRestoreLimit`, `TestVaultNoLeak`, `FuzzProtectRestore`; поток — `TestStreamSplitEverywhere`, `TestStreamHoldsOnlyCandidate`, `TestDM31_ExperimentMockLLMStream`, `FuzzStream`.

## События (ТЗ, 5.5; задача 2.15)
Приём, хранение и сроки хранения событий шлюзов: `internal/events` (`DecodeBatch`, `Check`, `PGStore`, `Queue`, `Maintain`), `internal/api/events.go`, `internal/gateway/eventsink.go`, миграция `0010_events`, решение Р9.

- **Источник.** `POST /internal/v1/events:batch` — только на внутреннем порту с mTLS (ИАФ.10): шлюз берётся из клиентского сертификата, сверенного с реестром; поля шлюза в теле нет, неизвестные поля — 400. Подменить события другого шлюза нельзя.
- **Разбор.** Пакет до 8 МиБ и 1–500 событий, строгий JSON; событие проверяется `Validate` и `Check`: ID — UUIDv7 строчными, время не старше 7 суток, не дальше 5 минут в будущем и не дальше 5 минут от времени в ID; строки до 256 байт, содержимое до 64 КиБ, находок до 1024, угроз до 64 (`DM-NN`), без U+0000. Неверное событие отклоняется поштучно (код в ответе), неверный пакет — целиком.
- **Идемпотентность.** Ключ секции — время из UUIDv7 события, поэтому повтор события попадает в ту же строку: `ON CONFLICT (id, ts) DO NOTHING`; содержимое пишется только для новых событий.
- **Хранение.** `events` и `event_content` секционированы по суткам UTC (только ядро PostgreSQL); события неизменны: `UPDATE` и `DELETE` запрещены триггером всем, у `aisec_app` — только `SELECT, INSERT`. Содержимое отдельно от метаданных: `none` — нет, `masked` — текст после маскирования шлюзом, `full` — только шифротекст (ЗИ.1). Режим `full` шлюз разрешает только при работе с сервером: в файл JSONL полное содержимое не пишется.
- **Сроки хранения.** Метаданные — 365 суток (30–3650), содержимое — 90 (7–3650, не дольше метаданных), таблица `event_settings`; у сервера нет права её менять. Секции создаёт и удаляет только функции `SECURITY DEFINER` с фиксированным `search_path` (`events_ensure_partitions` — окно ±7 суток, не больше 31; `events_drop_expired` — по настройкам, аргументов срока нет). Задание сервера при запуске и раз в час; удаление секций и запись `events.retention` в аудит — одной транзакцией (РСБ).
- **Отправитель шлюза.** `ServerSink`: таймаут 10 с на попытку, до 3 попыток с паузой 1–2 с и `Retry-After` до 5 с; 400/413/415/422 — пакет не повторяется; сеть, 401, 429, 5xx — пакет остаётся в очереди и повторяется с паузой 1–30 с, новые события копятся (10 000), сверх — отбрасываются со счётчиком; при остановке неотправленное считается отброшенным. Счётчики отброшенных и отклонённых уходят на сервер в каждом пакете (`gateway_event_stats`, «Состояние системы» — задача 2.20; оповещение DM-44 — этап 3).
- **Журналы.** Содержимое событий и текст ошибок СУБД (в нём могли бы быть значения полей) в технический журнал не пишутся: только коды отказа, `SQLSTATE` и имя ограничения.
- **Тесты.** `TestDecodeBatchOK`, `TestDecodeBatchErrors`, `TestCheckRejects`, `TestCheckBoundaries`, `TestHasNUL`, `FuzzDecodeBatch`, `TestEventsBatchAccepts`, `TestEventsBatchErrors`, `FuzzEventsBatchRequest`, `TestServerSinkOverMTLS`, `TestEventsBatchRejectsGatewayInBody`, `TestServerSinkRetries`, `TestServerSinkSplitsLargeBatch`, `TestQueueRetriesLater`, `TestDM44_QueueDropsWhileServerDown`, `TestQueuePermanentFailureNotRetried`, `TestCheckEventsSink`, `TestValidateFull`; на PostgreSQL — `TestPGEventsInsertContent`, `TestPGEventsSwappedCiphertext`, `TestPGEventsAppRights`, `TestPGEventsNoPartition`, `TestPGEventsRetention`.

## Целостность зависимостей (ТЗ, 8.7)
Функция контроля целостности исходных текстов зависимостей. Статус — реализовано для `vendor/` (задача 1.28 этапа 1); контроль целостности установленного продукта — `internal/integrity`, этап 2.
- **Состав и версии.** `make vendor-check` (`tools/vendor-check`): модули и версии в `vendor/modules.txt` и `go.mod` совпадают; у каждого есть хеши модуля и `go.mod` в `go.sum`; модуль не может быть только в одном из файлов; директивы `replace` в `go.mod` и замены `=>` в `modules.txt` запрещены.
- **Файлы.** SHA-256 каждого файла `vendor/` сверяется с манифестом `docs/cert/vendor.sha256`; лишние, пропавшие и изменённые файлы — ошибка. Манифест обновляет только `make vendor-manifest`.
- **Сверка с источником.** `make vendor-verify` (нужна сеть, запускается вручную; в CI пока нет): проверка без сети, затем повторный `go mod vendor` с пустым кешем модулей и сравнение с `vendor/`; скачанные модули сверяет с `go.sum` сам `go`.
- **Ограничения.** Хеш `h1` в SBOM заявленный (`docs/cert/build-env.md`, «SBOM»); `vendor-check` без сети доказывает неизменность относительно манифеста, а не относительно источника; ссылки и не обычные файлы в `vendor/` отвергаются; размер файла ограничен 32 МиБ.
- **Тесты.** `TestVendorCheck` (изменение, добавление, удаление файла, расхождение версий, нет хешей в `go.sum`, модуль только в одном файле, нет или повреждён манифест, путь манифеста вне `vendor/` или с пробелом, `replace` в `go.mod` одиночный и блоком, замена в `modules.txt`), `TestReadLimited`, `FuzzReadManifest`, `FuzzParseGoMod`, `FuzzParseModules`, `FuzzParseGoSum`.

## Политики (ТЗ, 5.3)
Функция фильтрации входа и выхода (ТЗ, 2.1): по находкам детекторов политика решает, что сделать с запросом и ответом. Статус — частично: модель, схема YAML, таблица приоритетов, режимы, `non_text`, эмбеддинги и шаблоны реализованы в `internal/policy` (задача 1.19); к запросу `POST /v1/chat/completions` политика применяется конвейером шлюза (задача 1.22), к ответу модели — проверкой ответа (задача 1.23); исключения, неизменяемые версии с откатом, песочница и подписанные пакеты — этап 2 (сервер, аудит, `internal/crypto`).

- **Модель.** Политика: `id`, `name`, `version`, `mode` (`monitor`, `enforce`), `non_text`, `response_check`, `block_message`, упорядоченный список `rules`. Правило: `id`, `detector` (ID из реестра детекторов), `directions`, условия `categories` и `sources`, `threshold` (по умолчанию 0,5), `action`, `severity` (`info`–`critical`), `message`. Политика ссылается на детекторы только по ID и не зависит от их пакетов.
- **Строгая проверка.** Неизвестные поля, повторы, значения вне перечислений, порог вне (0, 1] (в том числе `.nan`), текст сообщений с управляющими и скрытыми символами — ошибка; до 256 правил, до 1 МиБ при импорте (`Parse`). `require_approval` отвергается до этапа 4. `pseudonymize` — только для входа: псевдоним в ответе модели восстановить нечем. Политика заказчика компилируется строго: незарегистрированный детектор, неподдерживаемое им направление или категория, которую детектор не выдаёт (опечатка `pii.pasport` иначе дала бы правило, которое молча никогда не срабатывает), — ошибка (`Compile`). Категории детектор сообщает через `detect.Categorizer` (все встроенные; у `lists` — категории списков приложения); правило с `categories` для детектора без списка категорий отвергается.
- **Таблица приоритетов** (менять только вместе с `TestPriorityTable`):

| Приоритет | Действие | Что делает |
|---|---|---|

- **Разрешение конфликтов.** Для находки берутся все совпавшие правила (детектор, направление, источник, категория, порог), итог по находке — самое сильное действие; при равенстве — первое правило по списку. Итог решения — самое сильное по всем находкам и `non_text`. Правило не ослабляет другое: `allow` не отменяет `block` (ослабление — только исключением, этап 2). Отдельно запоминается самая сильная защита данных по находке (`redact` или `pseudonymize`), даже если итог — `block`.
- **Режимы.** `enforce` применяет решение целиком. `monitor` применяет только защиту данных во входе к внешнему провайдеру, в том числе когда итог — `block`; `block` только журналируется; для внутреннего провайдера и для ответа модели ничего не применяется. Решение содержит итог «как в `enforce`» и фактически применённые действия. Режим приложения (`policy_mode`) важнее режима политики; пусто — режим политики; незнакомое значение считается `enforce`.
- **Эмбеддинги.** Для `/v1/embeddings` `pseudonymize` выполняется как `redact` с отметкой в решении (ТЗ, 5.1).
- **Нетекстовые части** (`non_text`, DM-14): `allow_unchecked` (по умолчанию в файле YAML; политика, созданная в консоли или через API, по умолчанию получает `allow_inline` — решение 1.19, задача 2.12) — пропустить с отметкой «содержит непроверенные части»; `allow_inline` — пропустить с отметкой только данные в запросе, ссылки на медиа блокировать (провайдер загружает ссылку сам — SSRF в его контуре); `block` — блокировать любые.
- **Шаблоны.** `base` «Базовая защита» (`monitor`, по умолчанию для приложения без политики — решение Р7), `pii-strict` «ПДн — строго» (`enforce`, `non_text: block`), `external-no-pii` «Внешний провайдер: ПДн не передавать» (`enforce`, `non_text: block`), `monitor-only` «Только мониторинг» (только журнал; ПДн уходят провайдеру как есть — с внешним провайдером шлюз при запуске пишет предупреждение, `GatewayFile.Warnings`). Правила шаблона для детекторов, которых нет в реестре, опускаются: шаблон не зависит от набора встроенных детекторов (сейчас встроены все семь детекторов этапа 1 из шаблонов). В «ПДн — строго» к блокирующим правилам скрытых символов, ПДн и секретов добавлены правила `redact`: в `monitor` скрытые символы, ПДн и секреты к внешнему провайдеру всё равно вырезаются и маскируются (к внутреннему провайдеру `monitor` ничего не применяет). Правило `lists` во всех шаблонах — только `log`: запрещённые темы заказчика блокируются только его собственной политикой.
- **Конфигурация шлюза.** Раздел `policies` файла конфигурации (решение Р2); ID политики заказчика не совпадает с шаблоном; приложение ссылается на политику из `policies` или на шаблон, пусто — `base`. Политика приложения находится через `policy.Resolve` и компилируется при запуске по детекторам приложения (встроенные, `lists` со списками заказчика, `output.exfil` с `exfil_allow_domains`): незарегистрированный детектор в политике заказчика — отказ запуска.
- **Конвейер шлюза** (задача 1.22, `internal/gateway/pipeline.go`, ТЗ, 4.3–4.4):
  - Детекторы политики для входа запускаются по каждому текстовому фрагменту запроса (содержимое, отказы и аргументы `tool_calls` в истории, имена файлов, описания инструментов) параллельно; текстовые части одного сообщения детекторы `injection.*` проверяют ещё и склеенными, как их склеит провайдер, а маскирование находки в склейке переносится на части. Детекторы — параллельно, каждый со своим сроком: 100 мс плюс 2 мс на КиБ текста (расчётная скорость 0,5 МБ/с — в 5 раз ниже наихудшей измеренной), не больше минуты. Срок по длине закрывает обход через срок (`threat-model.md`).
  - Сбой детектора (срок, ошибка, паника, некорректная находка) — по режиму приложения (`fail_mode`): `fail_closed` блокирует (503 `check_unavailable`) в любом режиме политики, в том числе `monitor`: несостоявшаяся проверка не подтверждает, что защита данных не нужна; `fail_open` пропускает. Сбои — в `decision.failures` события, без текста ошибки.
  - Блокировка — 400 `policy_violation` с сообщением правила или политики; какие детекторы сработали, приложение не узнаёт. Квоты и неразрешённая модель отклоняются до детекторов и в `monitor` тоже.
  - Защита данных (с задачи 1.23 — через `internal/pseudonym`): `pseudonymize` заменяет фрагмент псевдонимом `[[ТИП_N]]` из словаря запроса, `redact` — маской `[[ТИП]]`, у `unicode.hidden` (кроме гомоглифов) — вырезает символы (DM-05). Пересекающиеся фрагменты объединяются, `redact` среди них делает объединение необратимым. Ошибка защиты данных — запрос не уходит (500).
  - Событие `gateway_request` — на каждый разобранный запрос: решение (что было бы в `enforce` и что применено), правило, политика и версия, трассировка, находки без значений, категории угроз, задержки, токены, псевдоним пользователя (HMAC, `internal/crypto`), содержимое по режиму хранения; с 1.23 — проверка ответа (`response`: режим, решение, обрыв потока) и счётчики псевдонимизации (`pseudonyms`, без значений). Заголовки `X-AISec-Event-Id` и `X-AISec-Decision` (у ответа без потока и `buffered` — самое сильное из сделанного с запросом и ответом, у потока — только по запросу).
- **Проверка ответа** (задача 1.23, `internal/gateway/response.go`, ТЗ, 4.3, шаг 7; 5.1; 5.3): выходные детекторы политики проверяют `content`, `refusal` и аргументы каждого вызова `tool_calls` (DM-13; находки в аргументах получают строку DM-13, какой бы детектор их ни нашёл); находки ответа — в общем списке события с местом `choices[0].message.…`.
  - Ответ без потока и `response_check: buffered` — собрать целиком, проверить, отдать: `block` — 400 `policy_violation`, сбой при `fail_closed` — 503 `check_unavailable`, `redact` — маска `[[ТИП]]`; маска, которая ломает JSON аргументов вызова (значение стояло числом), блокирует ответ (правило `tool_args_json`). В `buffered` потоке до проверки приложение не получает ничего, проверенный ответ отдаётся частями SSE.
  - `incremental` (по умолчанию, Р7) — текст проверяется окнами: после каждых 512 байт нового текста детекторы проверяют окно из 4 КиБ уже переданного текста и всего непереданного; начало окна сдвигается назад по разметке markdown всего текста (`exfil.Window`: в блоке кода — с начала строки и оградой перед окном, в списке — с начала последнего пункта верхнего уровня, иначе — с начала абзаца, не дальше 8 КиБ; дальше — окно, где `output.exfil` не учитывает код, а его находки в переданном тексте решает итоговая проверка), чтобы код в окне был тем же, что во всём ответе; клиенту уходит проверенный текст, кроме последних 256 байт и недописанного слова (ссылка или значение, которое ещё дописывается, целиком остаётся в непереданном хвосте); слово без пробелов длиннее 4 КиБ отдаётся принудительно; непереданного текста больше 64 КиБ (маскируемая находка всё ещё дописывается) — обрыв (правило `stream_hold_limit`), чтобы работа детекторов оставалась линейной (`TestIncrementalWorkBounded`). Находка с `block` или находка для маскирования, начавшаяся в уже переданном тексте, обрывает поток событием `error` с `policy_violation` и сообщением решения без `[DONE]` (правило `stream_cut`); сбой проверки при `fail_closed` — `check_unavailable`. Находка с `block` или для маскирования целиком в уже переданном тексте, которую нашла только проверка с большим контекстом, тоже обрывает поток (правило `stream_late`, шаг трассировки с детектором и категорией); применённой считается находка, целиком закрытая отданными масками. Повторная причина завершения от провайдера ответ ещё раз не завершает (действует первая). Найденное прежним окном остаётся под маской, даже если следующие проверки его не нашли (сбой при `fail_open`, другой контекст на стыке окон). Сбои детекторов на окнах пишутся в событие без повторов. Вызовы инструментов отдаются целиком в конце, после проверки. В конце — проверка всего ответа (решение в событии). Проверяются тексты и аргументы вызовов; имена функций и идентификаторы вызовов — нет.
  - `monitor`, а также любой `response_check` при режиме политики `monitor` или без выходных правил — части уходят без задержки, ответ проверяется после передачи (синхронно, после `[DONE]`, до закрытия соединения), решение только журналируется (к ответу в `monitor` ничего не применяется, ТЗ, 5.3). Сбой проверки ответа в `monitor` только журналируется: блокировать ответ строже, чем при успешной проверке, незачем.
  - Обратная подстановка выполняется всегда, в том числе в `monitor`: `content` — `Restore` (при `response_format` JSON — `RestoreJSON`), `refusal` — `Restore`, в потоке — `NewStream`/`NewJSONStream`; аргументы всех вызовов ответа — одним `RestoreToolArgs` по массиву JSON из них, чтобы признак адреса в одном вызове запрещал подстановку во всех (аргументы не JSON — без подстановки). Детекторы проверяют ответ с псевдонимами (ПДн, которые вернула подстановка, — данные самого пользователя). Без потока после подстановки `output.exfil` проверяет текст ещё раз; если появилась находка (категория и найденный текст), которой не было в тексте с псевдонимами, или детектор не ответил, подстановка в этом тексте отменяется (`pseudonyms.withheld`). Так ловится и значение внутри изображения, которое было находкой уже с псевдонимом.

Расход не меньше жёсткого бюджета (ровно 100 % — исчерпан) — 429 `budget_exceeded` для chat/completions и embeddings с `Retry-After` до начала следующего месяца, правило `budget.hard`, угроза DM-15 в событии; Check API бюджет не тратит. Модель без цены — расход «не определён» (счётчики `unpriced_*`, видны в консоли), запрос не отклоняется. Счётчики процесса нарастающие, сервер хранит максимум по процессу: повтор heartbeat не удваивает расход, после перезапуска шлюз получает прежний расход в первом ответе. Часы или пояс установки назад через границу месяца не обнуляют бюджет: расход «будущего» месяца переносится в текущий, отчёт heartbeat заканчивается текущим месяцем, ответ сервера его не удаляет; сервер сверяет месяц отчёта со своим в поясе установки (допуск — сутки) и расходящийся отчёт не сохраняет, причина — в техническом журнале (3В23 ревью 3.r3). При переполнении месяца (по числу приложений пакета) вытесняются счётчики приложений, которых нет в текущем пакете, с записью в технический журнал. Остаточный риск: до первого ответа сервера после запуска и при недоступности сервера чужой расход не учитывается — шлюз работает автономно (ТЗ 4.2), бюджет может быть превышен на расход, не дошедший до сервера. Ещё остаточные риски: проверка — до запроса, учёт — после ответа, поэтому параллельные запросы в работе превышают бюджет (каждый — до `max_tokens` × цена); расход с последнего heartbeat теряется при аварийном завершении шлюза; при первом запуске чужой расход приходит со вторым heartbeat; запрос без `max_tokens` (и без `max_tokens` в квоте приложения) с неизвестным исходом списывает вход и 4 096 токенов ответа (`unknownOutTokens`, остаток 3В22, задача 4.5; `TestUnknownOutEstimate`) — ответ длиннее оценки, который провайдер успел выставить в счёт, не учитывается, эмбеддинги списывают только вход; запрос, который не ушёл провайдеру (отказ в соединении, ошибка TLS, имя не разрешилось), не списывается: признак «запрос записан» — по `httptrace` `WroteRequest` (замечание ревью исправлений 3.r3); у GigaChat в тот же признак попадает запрос токена OAuth, поэтому сбой после получения токена списывает оценку — бюджет завышается, а не занижается; если часы сервера сами уходят назад через границу месяца, строка «будущего» месяца остаётся на сервере до очистки, а шлюз переносит тот же расход в текущий месяц — чужой расход считается дважды (тоже завышение, не занижение). Снижение или удаление цены уменьшает учитываемый расход — пишется в аудит с `relaxed`. Хранение строк `budget_usage` (процесс × приложение × месяц) пока не ограничено — вопрос в stage-3.md. Тесты: `TestSyncBudgetPrunesOldUsage`, `TestDM15_HardBudgetBlocks`, `TestDM15_CanceledRequestCharged`, `TestBudgetClockBackAcrossMonth`, `TestBudgetTimezoneChangeAcrossMonth`, `TestBudgetEvictsAppsOutsideBundle`, `TestSyncBudgetMonthSkew`, `TestBudgetMonthRolloverInTimezone`, `TestBudgetOthersFromServer`, `TestBudgetUnpricedModel`, `TestBudgetOverflowSaturates`, `TestHeartbeatBudget`, `TestBudgetsViaAPI`, `TestPGBudgetsAndUsage`, `FuzzParseMoney`, `FuzzPriceRequest`.

## Псевдонимизация (ТЗ, 5.1)
Функция исключения передачи защищаемой информации разработчику модели (ТЗ, 2.1; DM-31). Статус — частично (задачи 1.20, 1.21, 1.23): пакет `internal/pseudonym`, формат и правила — ADR-0005; подключён к конвейеру шлюза в задаче 1.23 (словарь на запрос `chat/completions`, обратная подстановка — «Проверка ответа» выше); в Check API и эмбеддингах `pseudonymize` выполняется как `redact`.

- **Замена.** `NewVault(лимиты, тексты запроса…)` резервирует псевдонимы, которые уже есть в запросе; `Vault.Protect` заменяет фрагменты с действием `pseudonymize` псевдонимом `[[ТИП_N]]`, с `redact` — маркером `[[ТИП]]`; пересекающиеся фрагменты объединяются, `redact` среди них делает объединение необратимым. Одинаковое значение — один псевдоним. Неверные позиции или действие — ошибка, текст не возвращается.
- **Обратная подстановка.** `Vault.Restore` (текст ответа), `RestoreJSON` (`content` при `response_format` JSON), `RestoreToolCalls` (собранные аргументы всех вызовов `tool_calls` одного ответа; `RestoreToolArgs` — для одного вызова) возвращают только значения из словаря этого запроса и принимают ограниченный набор искажений моделью. Не восстанавливаются: искажённые сильнее допустимого, неизвестные номера, псевдонимы там, где значение может стать частью адреса (DM-11): перед псевдонимом признак адреса, а сразу за ним — продолжение адреса или метки домена (`/ @ # %`, латинская буква, цифра, `-`, `_`, точка перед буквой или цифрой); в JSON — вне значения строки и после признака адреса, в том числе без схемы (`@`, `=`, `?q`, `буква.буква`, IPv4, `пример.рф`); в аргументах инструментов — при любом признаке адреса в любом вызове ответа (DM-13). Правило мест — ADR-0005, п. 5. Значение в JSON экранируется; восстановленное значение повторно не разбирается.
- **Потоковая передача.** `Vault.NewStream` (`content`, `refusal`) и `NewJSONStream` (`content` в формате JSON), по одному на текст: хвост части, в котором может начинаться псевдоним, задерживается до следующей части — не больше `MaxPending` (49) байт, остальное отдаётся сразу; `Flush` в конце потока, в том числе при обрыве. Склейка результатов равна подстановке по всему тексту при любом разбиении. Аргументы `tool_calls` в потоке собираются целиком и восстанавливаются вместе с аргументами остальных вызовов ответа.
- **Метрика неудачных подстановок** — `Stats.Failed()`: неизвестный номер (кроме псевдонимов из самого запроса), искажение сильнее допустимого (переведённый тип, потерянные скобки), небезопасное место, превышение объёма; счётчики значений не содержат.
- **Пределы.** До 4096 значений в словаре (сверх — необратимое маскирование), до 4096 разных псевдонимов в резерве из текста запроса (сверх — всё маскируется необратимо), до 4 МиБ значений, вставленных за весь запрос.
- **Словарь** — только в памяти на время запроса; `String`, `GoString`, `LogValue` печатают только число записей; `Clear` удаляет значения; после него `Protect` — ошибка, а подстановка отдаёт текст как есть, не меняя метрик. Режим хранения `full` — только с сервером управления, содержимое шифруется (задача 2.15, раздел «События»).
- **Тесты.** `TestDM31_PseudonymizeRoundTrip`, `TestDM31_ExperimentMockLLM`, `TestExperimentCollisions`, `TestProtectOverlap`, `TestProtectRejects`, `TestReserveExisting`, `TestFallbackToRedact`, `TestRestoreTolerant`, `TestRestoreUnchanged`, `TestRestoreKeepsBackslash`, `TestRestoreNoRecursion`, `TestDM11_RestoreNotInURL`, `TestRestoreJSON`, `TestDM13_RestoreToolArgs`, `TestDM13_RestoreToolCalls`, `TestReserveLimit`, `TestClearDuringStream`, `TestRestoreLimit`, `TestVaultNoLeak`, `FuzzProtectRestore`; поток — `TestStreamSplitEverywhere`, `TestStreamHoldsOnlyCandidate`, `TestDM31_ExperimentMockLLMStream`, `FuzzStream`.

## События (ТЗ, 5.5; задача 2.15)
Приём, хранение и сроки хранения событий шлюзов: `internal/events` (`DecodeBatch`, `Check`, `PGStore`, `Queue`, `Maintain`), `internal/api/events.go`, `internal/gateway/eventsink.go`, миграция `0010_events`, решение Р9.

- **Источник.** `POST /internal/v1/events:batch` — только на внутреннем порту с mTLS (ИАФ.10): шлюз берётся из клиентского сертификата, сверенного с реестром; поля шлюза в теле нет, неизвестные поля — 400. Подменить события другого шлюза нельзя.
- **Разбор.** Пакет до 8 МиБ и 1–500 событий, строгий JSON; событие проверяется `Validate` и `Check`: ID — UUIDv7 строчными, время не старше 7 суток, не дальше 5 минут в будущем и не дальше 5 минут от времени в ID; строки до 256 байт, содержимое до 64 КиБ, находок до 1024, угроз до 64 (`DM-NN`), без U+0000, `policy_mode` — только `monitor`/`enforce` у всех типов. Неверное событие отклоняется поштучно (код в ответе), неверный пакет — целиком. Если СУБД отвергла пакет, прошедший проверку, он записывается заново по одному событию в точках сохранения, и отказ (`storage`) получают только отвергнутые события — одно событие не губит пакет (В10 ревью 2.r3a).
- **Идемпотентность.** Ключ секции — время из UUIDv7 события, поэтому повтор события попадает в ту же строку: `ON CONFLICT (id, ts) DO NOTHING`; содержимое пишется только для новых событий.
- **Хранение.** `events` и `event_content` секционированы по суткам UTC (только ядро PostgreSQL); события неизменны: `UPDATE` и `DELETE` запрещены триггером всем, у `aisec_app` — только `SELECT, INSERT`. Содержимое отдельно от метаданных: `none` — нет, `masked` — текст после маскирования шлюзом, `full` — только шифротекст (ЗИ.1) JSON `{request, response}` без HTML-экранирования; если открытый текст не помещается в предел шифротекста 256 КиБ (управляющие символы занимают до 6 байт), запрос и ответ обрезаются по границе символа с «…», событие с находками записывается с отметкой `details.content_truncated`, число обрезанных — в ответе пакета и в технических журналах (В10 ревью 2.r3a). `received_at` ставят часы СУБД, по которым идут агрегаты (Н22). Режим `full` шлюз разрешает только при работе с сервером: в файл JSONL полное содержимое не пишется.
- **Сроки хранения.** Метаданные — 365 суток (30–3650), содержимое — 90 (7–3650, не дольше метаданных), таблица `event_settings`. Меняет администратор с разрешением `events.retention.manage` (`PUT /api/v1/events/settings`, задача 2.16): изменение и запись `events.settings_changed` (до, после, признак сокращения `reduced` — основа правила DM-40 этапа 3) — одной транзакцией; у `aisec_app` право `UPDATE` только на столбцы сроков. Сокращение любого срока необратимо удаляет данные и требует повторной проверки текущим паролем или кодом TOTP, как выпуск токена (В13 ревью 2.r3a, решение владельца): только из сессии консоли, неверное значение — 403 `reauthentication_failed` и неудачная попытка ИАФ.4 в общем счётчике блокировки; увеличение и сохранение тех же сроков — без проверки, удаление по новому сроку — без задержки, при ближайшем запуске задания. Секции создаёт и удаляет только функции `SECURITY DEFINER` с фиксированным `search_path` (`events_ensure_partitions` — окно ±7 суток, не больше 31; `events_drop_expired` — по настройкам, аргументов срока нет). Задание сервера при запуске и раз в час; удаление секций и запись `events.retention` в аудит — одной транзакцией (РСБ).
- **Отправитель шлюза.** `ServerSink`: таймаут 10 с на попытку, до 3 попыток с паузой 1–2 с и `Retry-After` до 5 с; 400/413/415/422 — пакет не повторяется; сеть, 401, 429, 5xx — пакет остаётся в очереди и повторяется с паузой 1–30 с, новые события копятся (10 000), сверх — отбрасываются со счётчиком; при остановке неотправленное считается отброшенным. Счётчики отброшенных и отклонённых уходят на сервер в каждом пакете (`gateway_event_stats`, «Состояние системы» — задача 2.20; оповещение DM-44 — этап 3).
- **Журналы.** Содержимое событий и текст ошибок СУБД (в нём могли бы быть значения полей) в технический журнал не пишутся: только коды отказа, `SQLSTATE` и имя ограничения.

### События в API консоли (задача 2.16)
`internal/events` (`filter.go`, `query.go`, `export.go`, `aggregate.go`), `internal/api/events_console.go`, миграция `0013_events_api`.

- **Права.** `events.read` — список, карточка без содержимого, агрегаты, свои сохранённые фильтры, сроки хранения; `events.export` — выгрузка; `events.content.read` — содержимое (УПД.7); `events.retention.manage` — сроки. - **Фильтры.** Условия через `and` по белому списку полей и операторов (`=`, `!=`, `in`, `not in`); значения только в кавычках, проверка формы у перечислимых полей; строка до 2048 байт, до 20 условий, до 50 значений, значение до 256 байт, без управляющих символов. CSV: UTF-8 с BOM, каждое поле в кавычках; апостроф перед `=`, `+`, `-`, `@` в начале значения и после `,`, `;`, табуляции и переводов строки (через пробелы и кавычки) — защита от формул и при делении строки по «;» в русской локали Excel (В12). Ошибка посреди выгрузки обрывает соединение, чтобы неполный файл не выглядел законченным.
- **Просмотр.** Список и карточка пишут необязательные `events.list` и `events.view` (РСБ.1, отключаются в настройках аудита); сбой такой записи не мешает ответу и попадает в технический журнал.

Фоновое задание раз в минуту с таймаутом 30 с: находит минуты событий, принятых после прошлой отметки, пересчитывает их целиком из `events` и их часы из минутных агрегатов с заменой строк — повторный пересчёт идемпотентен, позднее событие пересчитывает свою минуту заново; один пересчёт за раз (`pg_try_advisory_xact_lock`). Минутные агрегаты хранятся 31 сутки, часовые — как метаданные. Содержимого в агрегатах нет.

## Оповещения (ТЗ, 5.6; задача 3.10, ADR-0020)
`internal/alerting` (`Service`, `PGStore`, `Memory`, `ParseRuleInput`, `Weakening`), `internal/api/alerts.go`, точка вызова `events.WithIngestHook`, миграция `0028_alerts`.

- **Где считаются.** Правила «порог» и «новое» — в транзакции приёма пакета событий по впервые записанным событиям: повтор пакета ничего не добавляет, сбой движка откатывает пакет, шлюз его повторит. Встроенные правила создаются сервером при запуске с записью `alert_rule.create` от имени сервера: `threshold.injection_blocked` (DM-01: `threat = "DM-01" and action = "block"`, группировка по приложению), `new.model`, `new.provider`, `new.risky_user` (DM-34) и правило безопасности `security.recipients_changed`.
- **Дедупликация и подавление.** Не больше одного открытого оповещения на ключ (правило и значения группировки) — частичный уникальный индекс по `open_key`, в том числе при параллельном приёме. Повтор после закрытия в окне подавления (по умолчанию 60 минут, 0–10 080) только увеличивает счётчик `suppressed`; окно группировки (0–1440 минут) открывает новое оповещение после окна. Ссылок на события — не больше 100 на оповещение.
- **Без содержимого.** В оповещение попадают только ID событий и метаданные из столбцов событий; содержимое запросов и ответов не копируется (`TestPGAlertsOnIngest` проверяет отсутствие текста промпта в таблицах оповещений).
- **Жизненный цикл.** `new → in_progress → closed`, допустимо `new → closed`; закрытое не открывается. Смена статуса пишет `alert_history` и `alert.status_changed` в аудит одной транзакцией; принявший в работу становится исполнителем.
- **Права.** `alerts.read`, `alerts.manage`, `alert_rules.read` — аналитик, администратор безопасности, токен API; аудитор — только чтение. `alert_rules.manage` — признак безопасности: только администратор безопасности, не выдаётся токену. У роли `aisec_app` `DELETE` на таблицах оповещений пропускают только триггеры срока хранения (задача 3.11), `UPDATE` — только изменяемых столбцов; `CHECK` не даёт отключить системное правило и правило безопасности даже прямым запросом.
- **Ослабление (DM-40).** Отключение, смена условия или группировки, повышение `min_severity`, понижение серьёзности, увеличение окон, удаление получателя требуют повторной проверки паролем или кодом TOTP и пишутся с `weakening: true`. У встроенных системных правил и правил безопасности меняются только получатели.
- **Получатели.** Роли `security_admin` и `auditor` входят в получатели любого правила и не убираются; изменение списка получателей пишется в аудит (до и после) и порождает оповещение `security.recipients_changed` в той же транзакции.
- **Пределы ввода.** Тело правила до 64 КиБ, условие в JSON до 8 КиБ, фильтр — язык ADR-0015 (до 2048 байт), название до 200 символов, описание и комментарий до 2000, группировка до 4 полей, получателей до 10 ролей и 50 пользователей, правил до 200; SQL только параметризованный (`FuzzParseRuleInput`).
- **Уведомления раздела 7.** Уведомления ИАФ.4, ИАФ.5, УПД.6, РСБ.4, РСБ.5, РСБ.6, ОЦЛ.5, ВРМ.1 — оповещения встроенных системных правил и правил безопасности (задачи 3.11, 3.14, раздел ниже). Каждое новое оповещение ставится в очередь доставки каналов той же транзакцией, что его создаёт (`alerting.PGStore.SetEnqueue(notify.PGStore.EnqueueAlertTx)`, ADR-0020 п. 15): ошибка постановки откатывает приём пакета событий или запись аудита вместе с действием, поэтому оповещения без доставки не бывает. Доставка — очередь `alert_deliveries` (3.13, до 5 попыток, окончательный отказ — DM-44 `system.notify_failed`). Тест покрытия — `TestSection7NotificationsEnqueued` (по одному уведомлению каждого требования в очереди), на PostgreSQL — `TestPGAuditStreamSIEM` (оповещение DM-44 в `alert_deliveries`).
- **Тесты.** `TestDM01_InjectionAlert`, `TestDM34_NewModelAlert`, `TestSuppressionAfterClose`, `TestAlertLifecycle`, `TestAlertEventRefsLimit`, `TestParseRuleInput`, `TestWeakening`, `TestUpdateRule`, `TestRecipientsChecked`, `FuzzParseRuleInput`; API и отказ в доступе — `TestAlertsViaAPI`, `TestAlertRulesViaAPI`, `TestAlertsByAPIToken`; на PostgreSQL — `TestPGAlertsOnIngest`, `TestPGRuleUpdateRaisesRecipientsAlert`, `TestPGIngestHook`.

## Правила фоновой задачи (ТЗ, 5.6, 5.16; задача 3.12, ADR-0020 п. 14)
`internal/alerting` (`frequency.go`, `anomaly.go`, `budget.go`, `periodic.go`, `periodic_pg.go`), `GET /api/v1/alert-rules/{id}/state` в `internal/api/alerts.go`, подключение в `cmd/aisec-server`, миграция `0034_alert_periodic`.

- **Фоновая задача.** Внутри сервера раз в минуту, без cron; один проход — одна транзакция с таймаутом 30 с. Второй экземпляр сервера пропускает проход (`pg_try_advisory_xact_lock`, отметка `alert_job_runs`). Сбой одного правила откатывается до точки сохранения и отмечается в состоянии правила (`warning: evaluation_failed`), остальные правила прохода фиксируются; повтор не удваивает оповещения (`open_key`, `pending`, `alert_seen` в той же транзакции). Отметка прохода старше 5 минут или правило, вычисление которого падает на каждом проходе дольше 5 минут (3Н48 ревью 3.r4, `TestDM44_RuleFailingEveryPass`, `TestPGAlertJob`), — условие `alert_job_stale` в «Состоянии системы» и оповещение `system.alert_job` (DM-44); шаг часов назад проход не останавливает, неверный часовой пояс — `warning: timezone_invalid` (3В17, 3Н36 ревью 3.r2; `TestPeriodicRuleFailureIsolated`, `TestDM44_PeriodicJobStale`, `TestPGPeriodicClockStepBack`).
- **«Частота» (DM-16, DM-36).** N событий за окно по ключу группировки (окно включает текущую минуту). Счётчики по минутам пишутся в транзакции приёма событий (повтор пакета их не увеличивает, события старше окна не считаются), примеры — только ID событий. Неучтённые события (`pending`) обнуляются под блокировкой строк в порядке приёма — ровно прочитанное, без потерь и взаимных блокировок. Смена условия или группировки правила удаляет его счётчики. Встроенные правила: `frequency.probing` (10 событий серьёзности «средняя» и выше за 10 минут от пользователя приложения), `frequency.quota_exceeded` (20 отказов квот за 10 минут).
- **«Аномалия» (DM-17, DM-36).** Последний час против медианы того же часа недели за 2–8 недель по местному времени установки (переход на летнее время учтён), по агрегатам событий. Порог — `factor` × медиана и наименьший объём `min_volume`. Первые 14 суток данных ключа правило молчит, это видно в API (`learning`, `learning_until`). Медленный рост и «отравление» базовой линии не обнаруживаются — остаточный риск в модели угроз. Встроенные правила: `anomaly.activity_spike` (запросы ×3, от 100 за час), `anomaly.extraction_volume` (токены ответа ×3, от 100 000 за час).
- **«Бюджет» (DM-15).** `warn_percent` (по умолчанию 80 %) и 100 % месячного бюджета по учёту расхода задачи 3.18, месяц в часовом поясе установки; одно оповещение на порог в месяц (`budget.monthly`).
- **Без содержимого.** Счётчики, состояние и оповещения содержат только метаданные из столбцов событий, объёмы и ID событий. У роли `aisec_app` в новых таблицах — `UPDATE` только счётчиков и состояния (не ключей и не организации), `DELETE` — только счётчиков (производные данные; фоновая задача удаляет старше суток и часа), состояние не удаляется.
- **Права на состояние.** `GET /api/v1/alert-rules/{id}/state` — `alert_rules.read`; объёмы «аномалии» дополнительно требуют `events.read`, расход «бюджета» — `budgets.read`, иначе ключи скрыты (`keys_hidden`).
- **Ослабление (DM-40).** Отключение, повышение `count`, `factor`, `min_volume`, `warn_percent`, сокращение окна, смена метрики — с повторной проверкой, `weakening: true`.
- **Пределы ввода.** Параметры с диапазонами и проверкой NaN; чужие виду поля отвергаются (`FuzzParseRuleInput`).
- **Тесты.** `TestDM15_BudgetAlerts` (ровно на пороге, смена месяца в Москве), `TestDM16_ProbingSeriesAlert` (ровно 10 за 10 минут), `TestDM17_ExtractionVolumeAnomaly`, `TestDM36_QuotaAlert`, `TestDM36_ActivitySpike` (ровно ×3), `TestAnomalyEmptyHistory`, `TestAnomalyBaselineAcrossDST` (зимнее и летнее время), `TestFrequencyCountsResetOnRuleChange`, `TestFrequencyWindowBoundary`, `TestNewAlertsEnqueued`, `TestParsePeriodicRules`, `TestPeriodicRuleWeakening`, `TestPeriodicRuleService`; API и отказ в доступе — `TestAlertRuleStateViaAPI`, `TestRBACMatrixDenials`; на PostgreSQL — `TestPGPeriodicRules` (сбой посреди прохода, повтор, два экземпляра, дополнение без повторного счёта, очередь доставки, права роли).

## Каналы уведомлений (ТЗ, 5.6, Р4; задача 3.13, ADR-0020 п. 9, 13)
`internal/notify` (`Service`, `Transport`, `PGStore`, `Memory`, `DecodeInput`), `internal/api/notify_channels.go`, `crypto.ClientTLS`, перешифрование в `keyring.Rewrap`, миграция `0033_notify_channels`.

- **Типы.** Почта (`net/smtp`, STARTTLS обязателен: сервер без него — отказ до пароля и письма, AUTH PLAIN только внутри TLS), webhook (`net/http`, только https, тело — общий JSON или формат Mattermost/Rocket.Chat, подпись `AISec-Signature: t=<unix>,v1=<hex>` — MAC криптопрофиля от `t.тело`), syslog (RFC 5424 по TLS, RFC 5425, фрейминг RFC 6587 octet counting, тело JSON или CEF 0).
- **Сеть (ЗИ.2, ЗИ.3).** Адреса задаёт только администратор безопасности; у каждого канала свои корневые сертификаты (`ca_pem`), системное хранилище не используется; прокси из окружения не используется, перенаправления не выполняются; каждая попытка — с контекстом и таймаутом 30 с, ответ получателя читается не больше 64 КиБ.
- **Секреты (ЗИ.1).** Пароль SMTP, адрес и ключ подписи webhook — один шифротекст ключа данных с AAD места хранения; в ответах API и в аудите — только какие секреты заданы или изменены; перешифровываются при ротации ключа данных. Ошибка доставки хранится кодом без текста ответа получателя и адреса.
- **Права и аудит.** `notify_channels.read` — аудитор и администратор безопасности; `notify_channels.manage` (создание, изменение, тестовая отправка) — признак безопасности, не выдаётся токену. Каналы не удаляются; отключение, повышение порога, смена адреса или корней УЦ, удаление адресата — ослабление (DM-40) с повторной проверкой. Коды: `notify_channel.create`, `notify_channel.update`, `notify_channel.test`, `notify.delivery_failed`.
- **Запрещённые адреса (ЗИ.3, 3Н31 ревью 3.r2).** Адрес канала проверяется после разрешения имени при каждом соединении: loopback, link-local, групповые, неуказанные адреса и адреса метаданных облака отклоняются (код `config`); исключения — список сетей администратора сервера `-notify-allowed-networks`. Тестовая отправка обобщает ошибки соединения, TLS и тайм-аут до `unreachable` (`TestChannelAddressRestricted`). Ослабление канала включает также смену ключа подписи, формата syslog и удаление пароля SMTP; в аудите — отпечатки корневых сертификатов (3Н34, 3Н38). Экранирование CEF и Markdown — после очистки управляющих символов, ссылки в Mattermost не активируются (3Н32, 3Н33).
- **Доставка.** Очередь в `alert_deliveries`: 5 попыток с задержкой 30 с, 2, 8 и 10 минут; окончательный отказ — `notify.delivery_failed` и оповещение DM-44. Тестовая отправка — одна попытка, не чаще 5 раз в минуту на канал, строка журнала с `kind: test`. Содержимого запросов в уведомлениях нет; значения, которые мог задать нарушитель, очищаются от управляющих символов и экранируются по формату.
- **Тесты.** Локальные приёмники SMTP, HTTPS и syslog по TLS на 127.0.0.1: `TestEmailDelivery`, `TestEmailNegative`, `TestWebhookDelivery`, `TestSyslogDelivery`, `TestCEFEscaping`, `TestNormalize`, `TestChannelUpdateWeakening`, `TestChannelTestSend`, `TestDispatchRetries`, `TestBackoff`, `FuzzDecodeChannelInput`; API и отказ в доступе — `TestNotifyChannelsAPI`, `TestRBACMatrixDenials`; на PostgreSQL — `TestPGNotifyChannels` (секреты не в открытом виде и не в аудите, DM-44 по отказу, перешифрование при ротации).

## Реагирование на инциденты (ТЗ, 5.7; задача 3.16)
`internal/incidents` (`Service`, `PGStore`, `Memory`, `ParseQuery`, `ParseStatusInput`, справочник категорий), `internal/alerting/incident.go` (правило DM-08 и связь с оповещениями), `internal/api/incidents.go`, миграция `0035_incidents`.

- **Модель.** Инцидент: сквозной номер в организации (без пропусков, счётчик `incident_counters`), название до 300 символов, серьёзность, категория из справочника в коде (9 категорий, каждая строка матрицы 5.16 относится ровно к одной, `docs/taxonomy.md`), источник (`manual`, `alert`, `auto`, `reopen`), ответственный, срок реакции по серьёзности (критическая — 1 ч, высокая — 4 ч, средняя — 24 ч, низкая — 72 ч, информационная — 7 суток; реакция — первый переход в работу или закрытие), этапы реагирования по шаблону ТЗ 5.7 (приём, сбор первичных сведений, локализация, сбор сведений для расследования).
- **Автомат статусов.** `new → in_progress → contained → closed`, закрыть можно из любого незакрытого; назад нельзя; закрытие требует резолюцию (`resolved`, `false_positive`, `risk_accepted`). Закрытый инцидент не меняется и не дополняется даже прямым запросом: триггер `incidents_closed_immutable` отвергает любое `UPDATE` закрытой строки, `incident_child_of_closed` — добавление хронологии, комментариев, ссылок на события и отметку этапов (исключение — запись «открыт заново» в хронологии закрытого). Повторное открытие — новый инцидент со ссылкой `reopened_from` (не больше одного на закрытый). Закрытие инцидента закрывает его незакрытые оповещения (история и `alert.status_changed`).
- **Только добавление.** Хронология, комментарии, ссылки на события: у роли `aisec_app` только `SELECT, INSERT`; правка комментария — новая запись с `replaces` (только автором и только последней версии), исходный текст остаётся. У инцидента `UPDATE` — только изменяемых столбцов, отмеченный этап не снимается (триггер). `DELETE` нет ни на одной таблице.
- **Без содержимого.** В инцидент попадают только ID событий и метаданные оповещений; содержимое запросов и ответов не копируется. Выгрузка карточки (`aisec-incident/1`) — тоже без содержимого, из одного снимка (`REPEATABLE READ READ ONLY`), с записью `data.export` в аудит до выдачи.
- **Создание.** Вручную, из оповещения (повтор из того же оповещения возвращает тот же инцидент, оповещение входит не больше чем в один инцидент) и автоматически: встроенное правило `threshold.canary_leak` (DM-08, канарейка в ответе, сценарий S4) в транзакции приёма событий открывает критический инцидент категории «Утечка системного промпта»; пока его оповещение открыто, новые срабатывания дополняют тот же инцидент (дедупликация по `open_key` оповещения). Окна подавления у правила нет: утечка после закрытия сразу открывает новое оповещение и новый инцидент. Приём событий блокирует только оповещения, строку инцидента не блокирует (внешний ключ берёт `FOR KEY SHARE`, совместимый с `FOR NO KEY UPDATE` консоли); связь уже связанного оповещения читает инцидент без блокировки; редкая встречная блокировка оповещений закрытием и приёмом (40P01) повторяется до трёх раз.
- **Права.** `incidents.read` — аналитик, аудитор, администратор безопасности, токен API; `incidents.manage`, `incidents.export` — аналитик и администратор безопасности, токен API; `incident_categories.manage` (инструкции реагирования по категориям) — признак безопасности: только администратор безопасности, не выдаётся токену. Ответственным назначается только действующий пользователь с `incidents.read`. Каждое действие пишет код аудита: `incident.create`, `incident.status_changed`, `incident.assigned`, `incident.comment_added`, `incident.stage_completed`, `incident.alert_linked`, `incident_category.update`.
- **Защита в СУБД (3Н35 ревью 3.r2, миграция 0044).** Связь оповещения с инцидентом не меняется; с закрытым инцидентом оповещение не связывается и не открывается; у закрытого инцидента к фиксации нет незакрытых оповещений; статус только вперёд, время реакции и локализации неизменно (`TestPGIncidentsAppendOnly`). Автоматические записи хронологии — до предела минус 100, закрытие проходит всегда (3В18, `TestDM08_CloseAtTimelineLimit`).
- **Срок хранения (3Н37 ревью 3.r2, миграция 0045).** Закрытые инциденты — 1095 суток (3 года) по умолчанию, 365–1825 (`GET`/`PUT /api/v1/incident-settings`: чтение `incidents.read`, изменение `incident_categories.manage`); затем фоновое удаление раз в час вместе с хронологией, комментариями, ссылками, этапами и связанными оповещениями, запись `incident.retention`. Незакрытые не удаляются; открытый заново — после следующего. Раньше срока роль сервера не удаляет ничего (триггеры, `42501`). Сокращение — с паролем или кодом TOTP и `weakening` (DM-40), запись `incident.settings_changed` (`TestPGIncidentRetention`, `TestIncidentSettingsViaAPI`). В консоли — вкладка «Срок хранения» экрана «Инциденты» (просмотр по `incidents.read`, изменение по `incident_categories.manage`); в карточке инцидента событие старше срока хранения событий показывается без ссылки, с пометкой «удалено по сроку хранения» (перенесено из этапа 3, задача 4.5; `IncidentsScreen.test.tsx`).
- **Пределы ввода.** Тело до 32 КиБ (комментарий — 64 КиБ, инструкция — 128 КиБ; запас на экранирование `\uXXXX`), комментарий до 4000 символов, резолюция и заметка этапа до 2000, инструкция до 8000; в инциденте до 500 комментариев, 2000 записей хронологии, 1000 ссылок на события, 100 оповещений, сверх — 422 (приём событий пределы проверяет без блокировки инцидента и при параллельных пакетах может их немного превысить; карточка и выгрузка отдают не больше предела); подробности записи хронологии — до 16 КиБ; фильтры списка — значения из перечней (`FuzzParseQuery`, `FuzzStatusInput`); SQL только параметризованный.
- **Тесты.** `TestDM08_CanaryCreatesIncident`, `TestIncidentStatusTransitions`, `TestIncidentCloseRequiresResolution`, `TestIncidentFromAlertRepeatSameIncident`, `TestIncidentTimelineAppendOnly`, `TestIncidentReopen`, `TestIncidentInstructions`, `TestIncidentExport`, `TestTaxonomyIncidentCategories`; API и отказ в доступе — `TestIncidentsViaAPI`, `TestIncidentsCanaryAndExportViaAPI`, `TestIncidentsByAPIToken`; на PostgreSQL — `TestPGIncidentsLifecycle`, `TestPGIncidentsAppendOnly`, `TestPGIncidentsConcurrent`.

## Приложения, ключи и провайдеры (ТЗ, 5.4; задача 2.11)
`internal/apps` (`Service`, `Memory`, `PGStore`), `internal/api` (`providers.go`, `applications.go`), `internal/config/appcheck.go`, миграция `0014_applications`.

- **Права.** `applications.read` (может быть `own`), `applications.manage`, `app_keys.manage` (может быть `own`), `providers.read`, `providers.manage` — у администратора системы; функции безопасности `applications.policy` (политика, режим политики, режим хранения, режим при сбое детекторов `fail_mode`, словари `lists` и домены-исключения DM-11 `exfil_allow_domains` — В15 ревью 2.r3b) и `providers.external` (признак «внешний») — только у администратора безопасности (УПД.2). Без `applications.policy` приложение создаётся с умолчаниями, явно переданные поля защиты — 422; через `PUT` приложения поля защиты не меняются; перевод приложения на провайдера без признака «внешний» — только с `applications.policy` (403). Ослабление защиты (`weakening`: `monitor`, хранение `none` или `full`, `monitor-only`, `fail_open`, новый домен-исключение, удалённый или ослабленный словарь, переход на невнешнего провайдера, снятие признака «внешний») требует повторной проверки текущим паролем или кодом TOTP, как выпуск токена (В8) и сокращение сроков хранения (В13), — Н32 ревью 2.r3b. Смена адресата провайдера (узел `base_url` или `auth_url`, `ca_pem`, `type`) по праву `providers.manage` сбрасывает его учётные данные и возвращает признак «внешний» (`credential_reset`, `external_reset` в `provider.update`): секрет и решение администратора безопасности привязаны к адресу назначения (В14 ревью 2.r3b). Токенам API доступны чтение и управление приложениями, ключами и провайдерами, но не функции безопасности.

Ослабление (`storage` `none` или `full`, перевод политики в `monitor`, снятие признака «внешний») отмечается в записи аудита признаком `weakening` — основа правила DM-40 этапа 3.

### Исключения в политиках и отметки событий (ТЗ 5.3, 5.5; задача 3.22, решение Р8, ADR-0016, дополнение)
`internal/policy/exception.go`, `internal/policy/versions/exceptions.go`, `internal/gateway/pipeline.go` (`fragmentHash`), `internal/events/marks.go`, `internal/api/policy_exceptions.go`, `internal/api/events_marks.go`, миграция `0036_event_marks`.

- **Исключение — часть версии политики.** Раздел `exceptions` YAML версии: детектор и хотя бы одно сужающее условие — шаблон детектора (`pattern`), хеш фрагмента, приложение или псевдоним пользователя; уточнения `category` и `source`; обязательные причина (до 500 символов), автор, время создания и конец срока (до 365 суток, по умолчанию 30; новое или продлённое исключение для канарейки — до 7 суток, по умолчанию 7: 3Н49 ревью 3.r4, `TestExceptionCanaryShortTTL`; сохранённые версии с прежними сроками действуют до истечения, откат к такой версии — ослабление с повторной проверкой); до 1000 исключений. Исключение без сужающего условия отклоняется (детектор не отключается для всех приложений одним исключением), детектор должен быть зарегистрирован; исключение для канарейки (`canary`) — только с хешем фрагмента: по правилу или приложению обнаружение утечки системного промпта (DM-08) не отключается (3Н42 ревью 3.r3). Для `unicode.hidden` такого ограничения нет: невидимые символы бывают законной частью текста приложения (эмодзи с соединителями), а обход ограничен приложением события. Добавление, продление и удаление — новая неизменяемая версия поверх `base_version` (409 при чужой правке), с записью `policy.exception_add|extend|delete` той же транзакцией; изменения попадают к шлюзам в подписанном пакете вместе с политикой, счётчик ревизий конфигурации (3.34) растёт.
- **Ослабление (DM-40).** Добавление, продление и изменение условия — причины `exception_added`, `exception_extended`, `exception_changed` с признаком `weakening`: только из сессии консоли с текущим паролем или кодом TOTP (как прочие ослабления политики, В23 ревью 2.r5), правило DM-40 срабатывает по записи аудита. Удаление и сокращение срока — без проверки. Автора, время создания и срок ставит сервер при любом пути сохранения (API, полная спецификация, загрузка YAML): подставить чужого автора или старую дату, чтобы продлить срок, нельзя; откат возвращает сохранённые сервером значения.
- **Применение на шлюзе.** После детекторов и до решения политики (`Policy.Evaluate`): совпавшая находка не участвует в выборе действия, остальные находки запроса решают как обычно. Действует и в проверке ответа (целиком и по окнам потока). Срок проверяется при каждом запросе по большему из часов шлюза и времени сервера из последнего heartbeat плюс прошедшее с него монотонное время — шлюз с отставшими часами не продлевает исключение (без heartbeat — по часам шлюза); истёкшее исключение не действует без нового пакета, а сервер в пакет истёкшие исключения не кладёт и к сроку ближайшего собирает пакет заново (версия политики та же, 3Н40 ревью 3.r3); консоль показывает его со статусом `expired`. Расхождение часов с сервером больше 30 с — предупреждение в техническом журнале шлюза (отдельного условия «Состояния системы» пока нет). В событии у находки — ID исключения (`exception`) и хеш фрагмента (`fragment`), в трассировке — шаг `exception`; содержимое запроса не добавляется.
- **Хеш фрагмента.** 16 байт HMAC текста находки на ключе псевдонимов пользователей шлюза с отдельным префиксом домена и ID приложения (`internal/crypto`, интерфейс `MAC`; версия домена 2, 3Н41 ревью 3.r3): без ключа короткие ПДн по хешу не подбираются, у одного текста в разных приложениях хеши разные. Сервер отдаёт хеш (карточка события, выгрузка JSON, черновик исключения) только субъекту с `events.content.read` или `policies.manage`: иначе держатель ключа приложения с `events.read` через `/v1/check` проверял бы, встречалось ли значение (телефон, паспорт) в запросах. Исключения по фрагменту, созданные до смены домена, перестают совпадать — их создают заново по новому событию. Шлюз без ключа (`-user-hmac-key`) хешей не считает, исключения по фрагменту у него не срабатывают.
- **Отметки событий.** «Ложное срабатывание» и «подтверждено» с комментарием до 1000 символов (без управляющих символов) — таблица `event_marks`, отдельно от неизменяемого события, одна на событие; смена и снятие — записи `events.mark_set` и `events.mark_removed` той же транзакцией (значение, прежнее значение, длина комментария; текст комментария в аудит не пишется — в нём может оказаться фрагмент запроса). Право `events.mark` — аналитик и администратор безопасности. Отметки видны в карточке, списке и фильтре `mark`; отметки событий, удалённых по сроку хранения, удаляются той же транзакцией, что и секции.
- **Черновик исключения.** Отметка «ложное срабатывание» и `GET /events/{id}/exception-draft` (`events.read`) возвращают условия по находкам, давшим итоговое действие: детектор, категория, шаблон, хеш фрагмента, источник текста находки (`user`, `rag`, `tool`, `output` — шлюз пишет его в находку события; исключение для ответа модели не действует на вход, 3В24 ревью 3.r3) и приложение события (приложение входит всегда), срок 30 суток — без текста запроса. Снятый в диалоге источник — предупреждение «действует на все тексты»; причина по умолчанию — «Ложное срабатывание (событие …)», комментарий отметки в неё не копируется (3В29). Создаёт исключение по черновику только администратор безопасности (`policies.manage`).
- **Входные данные.** Тело запроса исключения до 10 КиБ, строгий JSON (неизвестные поля — 400), поля по белым спискам формы; ID исключения в пути — по форме, иначе 404.
- **Остаточные риски.** Условие `user` опирается на идентификатор, который передаёт приложение (`X-AISec-User`), и защищает не сильнее него; исключение только по шаблону действует во всех приложениях политики; исключение в шаблонной политике невозможно — нужна копия; Check API и песочница пока не помечают находки, пропущенные по исключению, а песочница не применяет исключения по фрагменту (у сервера нет ключа шлюза).
- **Тесты.** `TestExceptionApplied`, `TestExceptionSkipsOnlyItsHit`, `TestExceptionTooBroadRejected`, `TestExceptionValidate`, `TestExceptionMaxCount`, `TestExceptionRoundTrip`, `TestDM40_ExceptionAddIsWeakening`, `TestDM40_ExceptionWeakeningOtherPaths`, `TestExceptionRejects`, `TestExceptionStampedByServer`, `TestExceptionsStatus`, `TestCompareExceptions`, `TestExceptionInputCheck`, `FuzzExceptionInputCheck`, `TestGatewayAppliesException`, `TestGatewayExceptionWithoutFragmentKey`, `TestGatewayExceptionInResponse`, `TestGatewayExceptionByUser`, `TestCleanMark`, `TestMemoryMarks`, `TestPGEventMarks`, `TestPGEventsRetention`, `TestEventMarkAndExceptionViaAPI`, `FuzzExceptionRequest`, `TestRBACMatrixDenials`, e2e `TestE2EStage3_FalsePositiveException`.

### Политика вызовов инструментов агентами (ТЗ, 5.10, 5.16; задача 4.9, ADR-0023, раздел 2)
`internal/policy/tools.go`, `internal/policy/toolcall.go` (`Policy.DecideTool`), `internal/policy/argschema`, `internal/policy/toolrate`, `internal/policy/versions/toolsdiff.go`, `internal/api/policy_tools.go`, шаблон `agent-base`. Применение на шлюзе — задача 4.11.

- **Раздел `tools` версии политики.** Действие для неодобренного, изменённого или подозрительного инструмента (`unapproved`), действие по умолчанию (`default`), срок ожидания подтверждения (1 мин — 1 ч, по умолчанию 10 мин), лимиты (`agent_per_minute`, `session_calls`, `repeat` с окном 1 мин — 24 ч) и до 256 правил: агенты (до 64 slug), шаблон `сервер/имя` с `*` в конце, уровни риска, действие (`allow`, `log`, `require_approval`, `block`), ограничения аргументов, лимит частоты, важность, сообщение. Раздел идёт в подписанный пакет шлюзов внутри YAML версии. Версия без раздела ведёт себя как раньше (`unapproved: log`, `default: allow`); новая политика из консоли получает `block`/`block`.
- **Решение (DM-20, DM-21, DM-23, DM-25).** Инструмент не в состоянии `approved` или с хешем описания, не совпавшим с одобренным, получает действие `unapproved`; одобренный — действия всех подходящих правил или `default`; аргументы вне ограничений правила, нестрогий JSON аргументов, превышение лимитов — `block`. Итог — сильнейшее действие (`block` > `require_approval` > `log` > `allow`); в `monitor` блокировка и подтверждение только записываются. Трассировка решения — правила, угрозы матрицы 5.16 и причины без значений аргументов.
- **Ограничения аргументов (DM-21).** Своё подмножество JSON Schema без внешних библиотек: `type`, `properties`, `required`, `additionalProperties`, `items`, `minItems`/`maxItems`, `enum`, `const`, `minimum`/`maximum` (и исключающие), `minLength`/`maxLength`, `pattern` (только линейный `regexp`, до 512 байт и 4000 инструкций), `x-aisec-path-prefix` (путь должен быть уже нормализованным: сегменты `..`, `.` и `//` — отказ, а не нормализация, потому что ядро разрешает `..` после символических ссылок иначе; обратная косая, `%` и управляющие символы — отказ; сравнение по границе каталога), `x-aisec-domains` (хост URL `http`/`https` без userinfo или домен адреса почты с локальной частью dot-atom без `/`, `:`, `?`, `#`, `%` и скобок; точное совпадение или поддомен). Дробные границы сравниваются с введённым десятичным числом, а не с его двоичным приближением; число в `args` из API, которое нельзя сохранить в YAML точно, — 400. Незнакомое ключевое слово — ошибка схемы, а не пропуск. Пределы схемы: 16 КиБ, вложенность 8, 256 узлов, 64 выражения на политику. Аргументы разбираются строго до всех шагов решения (и у неодобренного инструмента, и в `monitor`): повтор ключа, неверный UTF-8, одиночные суррогаты, данные после документа — отказ; числа хранятся точно (`big.Rat`, порядок до 400); 256 КиБ, вложенность 32, 10 000 значений. Шлюз передаёт серверу MCP ровно разобранные аргументы.
- **Лимиты (DM-23).** Скользящие окна в памяти шлюза (`toolrate`), не больше 100 000 ключей с вытеснением давно не использованных (вытеснение сбрасывает счётчик, число вытеснений считается); части ключа (сессия, имя инструмента) обрезаются до 256 байт. Признак зацикливания — повтор одного вызова с теми же аргументами (хеш аргументов профиля) в сессии.
- **Ослабление (DM-40).** Причины: `tools_unapproved_weakened` (`unapproved` или `default` слабее), `tool_rule_added` (новое правило слабее прежнего `default`), `tool_action_weakened`, `tool_scope_widened`, `tool_scope_narrowed` (сужение правила, без которого вызов может получить более слабое действие), `tool_args_relaxed` (ограничения сняты или изменены), `tool_rate_raised` (лимит выше или снят, окно `repeat` короче), `approval_timeout_raised`, `tool_rule_removed`. Оценка осторожная: пересечение областей правил не вычисляется, поэтому сомнительное изменение считается ослаблением и требует текущего пароля или кода TOTP. Снятие раздела сравнивается с умолчаниями совместимости.
- **Самотест.** Эталонные вызовы `toolVectors` (DM-20, DM-21, DM-22, DM-25, разрешённый вызов) и повтор вызова в сессии со счётчиками (DM-23) прогоняются при запуске шлюза и сервера вместе с детекторами; расхождение решения — провал `decision` проверки `tools.policy` с реакцией `-selftest-action`.
- **Остаточные риски.** Риск инструмента задаёт администратор при одобрении (задача 4.8); политика не видит смысл аргументов сверх схемы; лимиты в памяти одного шлюза и обнуляются при перезапуске и вытеснении.
- **Тесты.** `TestToolsYAMLRoundTrip`, `TestToolsValidation`, `TestToolsCompatWithoutSection`, `TestDM20_ToolNotInAllowlistBlocked`, `TestDM21_ArgsOutsideConstraintsBlocked`, `TestDM23_AgentRateLimit`, `TestDM23_RepeatedCallLoopBlocked`, `TestDM25_ChangedDescriptorBlockedByPolicy`, `TestToolDecisionSteps`, `TestToolMonitorOnlyLogs`, `TestAgentBaseTemplate`, тесты `argschema` (строгий JSON, пределы, вредоносные схемы), `FuzzParseArgSchema`, `FuzzValidateArgs`, тесты `toolrate`, `TestCompareToolsWeakening`, `TestCompareToolsSectionAddedRemoved`, `TestBundlePolicyToolsSection`, `TestDM20_ToolVectorsCoverThreats`, `TestFractionalBoundsExact`, `TestRateKeyBounded`, `TestPolicyToolsViaAPI`.

### Реестр агентов, MCP-серверов и инструментов (ТЗ, 5.10, 5.16; задача 4.8, ADR-0023, раздел 1)
`internal/agents`, `internal/policy/tooldesc`, `internal/api/agents.go`, `internal/api/agents_internal.go`, `internal/policy/bundle/agents.go`, `internal/policy/bundle/build/agents.go`, `internal/alerting/agents.go`, миграция `0054_agents.sql`. Применение реестра на шлюзе (MCP-прокси, проверка хеша при вызове) — задача 4.11.

- **Хеш описания (DM-25).** Одна функция для сервера, шлюза и самотеста — `internal/policy/tooldesc` (пакет без зависимостей сервера): строгий разбор (повтор ключа, неверный UTF-8, данные после документа — отказ), каноническая форма (ключи по порядку байтов, без пробелов, числа исходной записью, без `icons` и `_meta`), хеш криптопрофиля от `"aisec-tool-descriptor-v1\n"` и канонической формы; алгоритм хранится рядом с хешем. Описание до 64 КиБ, вложенность 32, 10 000 значений.
- **Одобрение.** Инструмент `new`, `changed`, `suspicious` или `revoked` до одобрения не вызывается (действие `unapproved` политики вызовов). Одобряет только `agents.tools.approve` (право безопасности: не выдаётся `system_admin` и токенам API; сервис проверяет его и сам, не только маршрут) с повторной проверкой паролем или кодом; запрос несёт хеш показанного описания — изменившееся после показа описание не одобряется (409). Одобрение `changed`, `suspicious` или `revoked` и понижение риска — ослабление (`weakening`, DM-40). Подсказка `destructiveHint` только поднимает предлагаемый риск.
- **Подмена описания (DM-25).** Шлюз сообщает увиденные описания через `tools:observe`; хеш, не совпавший с одобренным, переводит инструмент в `changed` (запись аудита `agent_tool.changed`, оповещение безопасности `agents.tool_changed`, не отключается, поднимается и в `monitor`), в пакете — статус `changed`, вызовы блокируются до повторного одобрения; возврат к одобренному описанию — `restored`. Смена криптопрофиля меняет хеш, поэтому требует повторного одобрения. Подмена одобренного описания — `changed` и оповещение даже при находке детекторов в новом описании (в записи — `suspicious: true`). Признак детекторов шлюза (DM-24) переводит в `suspicious` неодобренный или изменённый инструмент; описание, одобренное после проверки находки, с тем же хешем снова подозрительным не становится. Ограничение СУБД: одобренный инструмент всегда с одобренным хешем, равным увиденному.
- **MCP-серверы.** Адрес — `https://` (`http://` — только флагом `insecure_http` администратора безопасности, ослабление), узел проверяется `internal/netguard` (общее правило с каналами уведомлений: loopback, link-local, адреса метаданных облаков и неопределённые запрещены). Новый сервер — внешний; снять признак может только администратор безопасности (ослабление). Смена схемы, узла или порта адреса либо корневых сертификатов сбрасывает учётные данные и признак «внутренний»: секрет не уходит на новый узел. Учётные данные (до 16 КиБ, `Authorization: Bearer` или один именованный заголовок вне служебных) шифруются ключом данных с AAD `mcp_servers|credential|<id>`, в API не возвращаются (только признак и время), шлюзам идут секретом пакета (HPKE); при ротации ключа данных перешифровываются (`aisec-cli keys rotate-data`). Сервер из списка агента не удаляется.
- **Агенты и ключи.** Агент принадлежит приложению; создание агента со списком MCP-серверов и расширение списка — ослабление с повторной проверкой (новый агент сразу получает одобренные инструменты серверов), токеном API недоступно. Ключ приложения привязывается к агенту только при выпуске (поле `agent_id`, право `agents.manage`), только к агенту своего приложения (составной внешний ключ) и потом не меняется (триггер); агент с привязанным ключом не удаляется.
- **Пакет конфигурации.** Разделы `agents`, `mcp_servers`, `agent_tools` в подписанном содержимом (без описаний инструментов — только имя, одобренный хеш, алгоритм, риск, статус); без агентов разделов нет, байты пакета прежние. Агенты архивных и исключённых из пакета приложений не едут, ключи таких приложений — без привязки; MCP-серверы — только те, что нужны агентам пакета. Пределы: 256 агентов, 64 MCP-сервера, 2 000 инструментов, 256 на сервер или агента.
- **Права и аудит.** `agents.read` (область `own` — агенты, MCP-серверы и инструменты своих приложений), `agents.manage`, `agents.tools.approve`; у каждого эндпоинта — тест отказа. Аудит: `agent.create|update|delete`, `mcp_server.create|update|delete|credentials_set|security_changed`, `agent_tool.approve|revoke|risk`, от шлюза — `agent_tool.discovered|changed|restored|suspicious`; описаний и учётных данных в записях нет, только хеши.
- **Приём от шлюзов.** `tools:observe` — до 256 описаний, не чаще раза в 10 с от одного шлюза на MCP-сервер или агента (429; неудачная запись отметку не оставляет), `agent_id` — UUID, инструменты сверх пределов реестра не принимаются (остаются неизвестными, вызовы — `unapproved`).
- **Самотест.** Эталоны хеша описания (`tools.descriptor`): равенство при эквивалентной записи, известный хеш SHA-256 в профиле `standard`, различие при подмене, отказ при повторе ключа — при запуске шлюза и сервера; провал — `hash` с реакцией `-selftest-action`.

TLS из `internal/crypto` с доверием `ca_pem` сервера, без прокси и перенаправлений; сроки соединения, списка, вызова и потока; до 64 одновременных запросов на сервер.

Правила `agents.tool_blocked` (DM-20, частотное: 3 блокировки за 10 минут по агенту, серверу и инструменту) и `agents.tool_poisoning` (DM-24, безопасности: отравленное описание в `tools/list`, группировка по серверу и инструменту).

### Очередь подтверждений вызовов (ТЗ, 5.10, 5.16; задача 4.10, ADR-0023, раздел 5; DM-22)
`internal/approvals` (`Service`, `PGStore`, `Memory`), миграция `0056_approvals`, `internal/api/approvals.go`, `internal/api/approvals_internal.go`, `internal/alerting/approvals.go`, `internal/gateway/approval.go` (интерфейс `Approver`), `internal/gateway/approvalclient.go`, `internal/gateway/agents.go`, `internal/gateway/chattools.go`, `internal/gateway/response.go`, перешифрование в `keyring.Rewrap`.

- **Удержание вызова.** Действие `require_approval` политики вызовов в режиме `enforce` (DM-22) — вызов не передаётся, пока пользователь консоли его не одобрит. На пути `chat` вызовы функций (`tool_calls`) ответа модели проверяются как инструменты `function/<имя>` агента запроса (агент ключа или `X-AISec-Agent`, ADR-0023, раздел 1; у приложения без агентов заголовок не проверяется); при разделе `tools` в политике вызовы в потоке отдаются только в конце, после решения, а поток держится комментариями SSE `: aisec-approval-pending` каждые 15 с, а срок простоя потока провайдера на время ожидания приостанавливается (`providers.Holder`): одобренный ответ дочитывается до конца. Ответ без потока и поток с `response_check: buffered` удерживаются целиком, без keep-alive (клиенту нужен таймаут больше 5 мин). Срок ожидания — `approval_timeout` политики (1–60 мин); на пути `chat` все вызовы ответа вместе ждут не больше 5 мин (следующему вызову — остаток срока, меньше минуты — отказ по сроку), плюс до 30 с на ответ сервера; общий срок ответа провайдера `response_timeout` (по умолчанию 10 мин) должен быть больше. В `monitor` запрос не создаётся (`TestDM22_ChatMonitorNoApprovalRequest`).
- **Отказ по умолчанию (fail-closed).** Отказ дежурного, истечение срока, сервер недоступен, очередь переполнена, сбой маскирования аргументов, расхождение ответа сервера с отправленным (ID, `args_hash`, `approved_hash`, состояние) — вызов не передаётся: 400 `policy_violation` или обрыв потока с сообщением правила, «Вызов не подтверждён вовремя» или «Вызов не может быть подтверждён: очередь подтверждений недоступна» — без аргументов и комментария дежурного. Шлюз без сервера управления (режим `-config`) такие вызовы отклоняет.
- **Подмена аргументов.** Шлюз передаёт дальше ровно те аргументы, хеш которых (`aisec-tool-args-v1`, хешер криптопрофиля) отправил серверу; одобрение связано с ID запроса и `args_hash`: тело `approve` содержит хеш показанного дежурному запроса (не совпал — 409), ответ сервера с другим хешем шлюз считает отказом. Одобренный хеш описания инструмента в запросе — только если описание из запроса совпало с одобренным в реестре.
- **Аргументы для дежурного.** Шлюз маскирует ПДн и секреты категорией находки (`[pii.email]`) детекторами `pii` и `secrets` независимо от режима хранения приложения; маскированные аргументы длиннее 16 КиБ дежурному не обрезаются, а вызов отклоняется (иначе одобрялось бы невиденное); сервер шифрует их ключом данных с AAD места хранения и удаляет через 30 суток после закрытия (метаданные — по сроку событий). Аргументы видны только в карточке запроса и только пользователю с `approvals.decide`; в списке, уведомлениях, оповещениях, аудите и технических логах их нет (в логах — приложение, агент, инструмент, правило, ID запроса, состояние и время ожидания).
- **Права и аудит.** `approvals.read` — `security_admin`, `analyst`, `auditor` (можно токену API: метаданные без аргументов); `approvals.decide` (признак `security`) — только `security_admin` и `analyst`, не `system_admin` и не токенам API: решает человек, сервер дополнительно проверяет тип субъекта. Одобрение вызова с риском `critical` — с текущим паролем или кодом TOTP. Решение после срока или повторное — 409. Записи `agent.approval.requested`, `agent.approval.queue_full` (субъект — шлюз), `agent.approval.approve`, `agent.approval.deny` (длина комментария `comment_len`, без текста комментария и аргументов: журнал неизменяем). Текст комментария хранится в запросе очереди вместе с метаданными.
- **Пределы.** 256 ожидающих запросов на шлюз и 16 на агента шлюза — на сервере (рекомендательная блокировка шлюза `pg_advisory_xact_lock` в транзакции создания) и на шлюзе (локальные слоты); сверх них 429 `approval_queue_full` и запись аудита не чаще раза в минуту на шлюз, приложение и агента. Тело создания до 104 КиБ (аргументы в JSON-строке), строгий JSON; долгий опрос `wait` — `0s`–`25s`, у шлюза для него свой клиент с таймаутом 35 с, без перенаправлений; ответ сервера до 16 КиБ.
- **Обрыв и перезапуск шлюза.** Клиент закрыл соединение — шлюз отменяет запрос (`cancelled`). Heartbeat шлюза передаёт ID ожидающих запросов (`approvals_pending`, только после ответа сервера `approvals: true`); запросы шлюза, которых нет в списке и которые старше 60 с, закрываются как `interrupted`. Просроченные закрываются как `timeout` фоновой задачей раз в 5 с и при опросе.
- **Оповещения.** Встроенные правила `agents.approval_requested` (каждый запрос; при всплеске — сводное) и `agents.approval_queue_full` — по записям аудита, без аргументов; канал и получатели — по правилам этапа 3.
- **Остаточные риски.** Функции агента на пути `chat` в реестр сами не попадают (наблюдение описаний — путь MCP, задача 4.11): без одобренной функции вызов получает действие `unapproved`. Аргументы, которые детекторы не распознали как ПДн или секрет, дежурный видит как есть. Ожидание держит соединение клиента и слот шлюза до срока. Комментарий дежурного хранится по сроку метаданных (не 30 суток, как аргументы): копировать в него аргументы не следует.
- **Тесты.** `TestDM22_ApprovalTimeoutDenies`, `TestDM22_ApprovedCallForwardedWithSameArgs`, `TestDM22_DeniedCall`, `TestDM22_ClientCancelClosesRequest`, `TestDM22_ApprovalServerUnavailable`, `TestDM22_ApprovalQueueFull`, `TestDM22_ApprovalResponseMismatchDenied`, `TestApprovalChatTimeoutCapped`, `TestHeartbeatApprovalsPending`, `TestDM22_ChatToolCallHeldUntilApproved`, `TestDM22_ChatToolCallDenied`, `TestDM22_ChatToolCallWithoutApprover`, `TestDM22_ChatMonitorNoApprovalRequest`, `TestDM22_ChatStreamApproval`, `TestDM22_ChatStreamApprovalOutlivesIdle`, `TestDM22_ChatApprovalsShareDeadline`, `TestStreamHoldPausesIdle`, `TestApprovalArgsMasked`, `TestChatToolCallBlocked`, `TestChatAgentHeaderMismatch`, `TestAgentsResolve`, тесты `internal/approvals` (`TestDM22_*`: сроки, решение после срока, `critical`, повторное решение, человек, пределы), `TestPGApprovalLifecycle`, `TestPGApprovalQueueLimitConcurrent`, `TestPGApprovalClosedImmutable`, `TestPGApprovalExpireInterruptPurge`, `TestPGApprovalArgsRewrap`, тесты API (`TestDM22_*`: консоль, отказ в доступе `system_admin`, владельцу, аудитору на решение, токену, 409 после срока, прерывание по heartbeat), `TestDM22_ApprovalRequestedAlert`, `TestDM22_ApprovalQueueFullAlert`, `FuzzParseWait`, `FuzzApprovalDecision`, `FuzzApprovalCreate`, `FuzzApprovalsPending`, `TestRBACMatrixDenials`.

Без адреса, деактивированный или потерявший право — пропускается; число пропущенных — в журнале запуска (`report_runs.skipped_no_email`), идентификаторы — в `data.export` (`skipped_users`), адреса — только в `recipients` записи `data.export`, как и адреса канала. `GET /api/v1/report-recipients` адресов не выдаёт. - **Устойчивость рассылки.** Очередь `report_runs` с повторами и блокировкой `SKIP LOCKED`; после простоя сервера отправляется одно догоняющее письмо, а не серия. Окончательный отказ виден в журнале запуска; ошибки — кодами без текста ответа SMTP-сервера. Завершённые запуски хранятся 365 суток и удаляются опросом раз в час (3Н47 ревью 3.r4); факт выгрузки остаётся в журнале аудита.
- **Тесты.** `TestReportsViaAPI`, `TestReportsOwnerScope`, `TestReportsAuditFailure`, `TestReportSchedulesViaAPI`, `TestRBACMatrix`; модульные и fuzz-тесты `internal/reports`; `ReportsScreen.test.tsx`, `e2e/reports.spec.ts`.

## Дашборды, потребление и цены (ТЗ, 5.8; задачи 3.18–3.21)
`internal/events` (`dash.go`, `dash_read.go`), `internal/api/dashboards.go`, `internal/api/budgets.go`, `internal/apps/budgets.go`, миграции `0031_budgets`, `0037_dashboards`, `0046_dash_dirty_hours`.

- **Состав.** Экраны «Обзор», «Угрозы», «ПДн», «Приложение» и «Потребление» (`GET /api/v1/dashboards/{overview,threats,pii,consumption,app/{id},stream}`, право `dashboards.read`) строятся из почасовых агрегатов `dash_*`; поток `stream` присылает снимки по SSE; тик потока проверяет сессию и права, но активностью сессии не считается (задача 4.5). Содержимого запросов и ответов в агрегатах нет: числа, ключи приложений, моделей и детекторов, строки матрицы, псевдонимы пользователей, токены и стоимость.
- **Доступ (УПД.3, УПД.8).** Все маршруты — `dashboards.read`; значение области `own` допускает только `app/{id}` своих приложений, чужое приложение — 404, остальное — 403 с записью `access.denied`. «Лента решений» обзора — это метаданные каждого события, поэтому она только с `events.read` на все объекты, иначе `feed: []` и `feed_hidden: true` (3В27 ревью 3.r3). Цены моделей и бюджеты — отдельные права `model_prices.read`/`manage`, `budgets.read`/`manage`; расход бюджета в консоли и отчётах виден только с `budgets.read`.
- **Аудит (РСБ.1, РСБ.2).** Чтение дашбордов записей не пишет (нет изменения и нет содержимого). Изменения: `model_price.create`, `model_price.update`, `model_price.delete`, `budget.set`, `budget.delete` — в одной транзакции с изменением; снятие или повышение жёсткого бюджета — не ослабление защиты (не DM-40, решение Р7), но запись аудита несёт отметку `relaxed` (`apps.relaxed`).
- **Пределы (ЗИ.6).** Параметры `period`, `from`, `to`, `feed`, `dashboard`, `app_id` — закрытый набор, неизвестные и повторы — 400; интервал до 366 суток; чтение с таймаутом 15 с и общим пределом нагрузки (3В28 ревью 3.r3); потоков не больше 3 на субъекта и 100 на сервер, сверх — 429; права и сессия перепроверяются на каждом тике.
- **Запись.** Агрегаты пополняются хуком в транзакции приёма событий; занятый час или сбой прироста не задерживает приём, а ставит час в `dash_dirty_hours` (3В25), досчёт пересчитывает помеченные часы первыми — отмеченные до начала прохода по часам БД (метки ставятся по `clock_timestamp()`, часы сервера не участвуют). Признак `aggregates_ready` снимают только метки старше трёх периодов досчёта (90 с): свежую метку снимает следующий проход, и «цифры неполные» не мигает при каждом занятом часе (перенесено из этапа 3, задача 4.5; `TestPGDashboardAggregates`, `TestPGDashIngestNotBlockedByBackfill`). Расход бюджета на шлюзе — раздел «Политики» выше (DM-15, `internal/gateway/budget.go`).
- **Тесты.** `TestDashboardsViaAPI`, `TestDashboardPeriods`, `TestDashboardForecast`, `TestDashboardStream`, `TestDashboardStreamBounded`, `TestDashboardCacheShared`, `TestDashboardFeedRequiresEventsRead`, `TestDashboardComputeLimit`, `TestDashTick`, `TestBudgetsViaAPI`, `FuzzPriceRequest`, `TestRBACMatrixDenials`; на PostgreSQL — `TestPGDashboardAggregates`, `TestPGDashboardHugeValues`, `TestPGDashboardSumNoOverflow`, `TestPGDashIngestNotBlockedByBackfill`; консоль — `web/e2e/dashboards.spec.ts` (строгий CSP), `DashboardsScreen.test.tsx`, `UsageScreen.test.tsx`.

## Криптопрофиль (ТЗ, раздел 10)

| Интерфейс | Профиль `standard` | Профиль `gost` |
|---|---|---|
| `Hasher` | SHA-256 | не реализовано (этап 6) |
| `MAC` | HMAC-SHA-256, ключ не короче 32 байт и копируется при создании, проверка за постоянное время; при выводе через `fmt` и `slog` показывается только имя алгоритма, ключ не попадает в логи (`TestMACDoesNotLeakKey`) | не реализовано |

## Целостность зависимостей (ТЗ, 8.7)
Функция контроля целостности исходных текстов зависимостей. Статус — реализовано для `vendor/` (задача 1.28 этапа 1); контроль целостности установленного продукта — `internal/integrity`, этап 2.
- **Состав и версии.** `make vendor-check` (`tools/vendor-check`): модули и версии в `vendor/modules.txt` и `go.mod` совпадают; у каждого есть хеши модуля и `go.mod` в `go.sum`; модуль не может быть только в одном из файлов; директивы `replace` в `go.mod` и замены `=>` в `modules.txt` запрещены.
- **Файлы.** SHA-256 каждого файла `vendor/` сверяется с манифестом `docs/cert/vendor.sha256`; лишние, пропавшие и изменённые файлы — ошибка. Манифест обновляет только `make vendor-manifest`.
- **Сверка с источником.** `make vendor-verify` (нужна сеть, запускается вручную; в CI пока нет): проверка без сети, затем повторный `go mod vendor` с пустым кешем модулей и сравнение с `vendor/`; скачанные модули сверяет с `go.sum` сам `go`.
- **Ограничения.** Хеш `h1` в SBOM заявленный (`docs/cert/build-env.md`, «SBOM»); `vendor-check` без сети доказывает неизменность относительно манифеста, а не относительно источника; ссылки и не обычные файлы в `vendor/` отвергаются; размер файла ограничен 32 МиБ.
- **Тесты.** `TestVendorCheck` (изменение, добавление, удаление файла, расхождение версий, нет хешей в `go.sum`, модуль только в одном файле, нет или повреждён манифест, путь манифеста вне `vendor/` или с пробелом, `replace` в `go.mod` одиночный и блоком, замена в `modules.txt`), `TestReadLimited`, `FuzzReadManifest`, `FuzzParseGoMod`, `FuzzParseModules`, `FuzzParseGoSum`.

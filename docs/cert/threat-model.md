# Модель угроз

Черновик этапа 0. Составляется по Методике оценки угроз безопасности информации ФСТЭК России (2021) с использованием БДУ ФСТЭК, включая раздел «Угрозы безопасности информации систем ИИ»; STRIDE — вспомогательно, по компонентам (ТЗ, 8.9). Обновляется при изменении архитектуры или поверхности атаки.

**Идентификаторы БДУ здесь не приводятся**, пока их нет в `docs/taxonomy.md`: их переносят вручную из официального текста раздела, ничего не придумывая (ТЗ, 5.16). До этого угрозы систем ИИ связаны со строками матрицы обнаружения (`DM-NN`) и кодами OWASP.

Охват черновика: компоненты этапа 0 (шлюз — прозрачный прокси, mock-llm, сборочная среда) и целевая архитектура в общих чертах. Сервер управления, консоль и `aisec-media` детализируются на этапах 2 и 5.

## Объект защиты и активы
Объект защиты — платформа AISec, установленная в контуре заказчика. Она сама является средством защиты, поэтому её компрометация опаснее, чем у обычного приложения: нарушитель получает и данные, и возможность ослабить защиту незаметно.

| Актив | Где | Чем ценен |
|---|---|---|
| Содержимое запросов и ответов LLM (в том числе ПДн, коммерческая тайна) | Шлюз (в памяти), события (с этапа 1–2) | Утечка — штрафы по 152-ФЗ, коммерческий ущерб |
| Ключи API провайдеров | Файл ключа шлюза; с этапа 2 — БД в зашифрованном виде (ЗИ.1) | Расход бюджета, доступ к данным у провайдера |
| Ключи приложений (этап 1) | Хеши в конфигурации или БД | Обход политики, расход квот |
| Политики, исключения, правила оповещений (этапы 1–3) | Сервер, подписанные пакеты в шлюзе | Ослабление защиты без следа |
| Журнал аудита (этап 2) | БД, цепочка хешей | Сокрытие действий нарушителя |
| Закрытые ключи TLS, внутреннего УЦ, подписи пакетов | Файлы с правами 0600 | Подмена компонентов, перехват трафика |
| Целостность бинарников, статики, служебных баз | Файловая система, манифест (этап 2) | Подмена кода средства защиты |
| Исходный код и сборочная среда | Репозиторий, CI, сборочный образ | Внедрение закладки на этапе разработки |

## Границы доверия
Подробно — `docs/architecture.md`. Ключевые:
1. **Приложение → шлюз.** Недоверенные запросы: тела, заголовки, строка запроса. Также косвенно недоверенное содержимое документов RAG и ответов инструментов, которое приложение передаёт в промпт.
2. **Шлюз → провайдер.** Провайдер, особенно внешний, вне контура заказчика: его ответы — недоверенный ввод.
3. **Шлюз ↔ сервер** (этап 2) — mTLS, подписанные пакеты политик.
4. **Пользователь консоли → сервер** (этап 2).
5. **Шлюз → `aisec-media`** (этап 5) — недоверенные медиа, изолированный процесс.
6. **Разработка → поставка:** репозиторий, зависимости, сборочная среда, CI, ИИ-ассистент.

## Нарушители
Категории и возможности — по Методике ФСТЭК; уточняются с лабораторией.

| Нарушитель | Вид | Цели | Возможности |
|---|---|---|---|
| Пользователь ИИ-приложения | Внешний или внутренний | Обойти инструкции модели, получить чужие данные или системный промпт, вывести ПДн | Произвольный текст запроса, многоходовые диалоги, кодирование, медиа |
| Автор недоверенного содержимого (документ RAG, веб-страница, письмо, ответ инструмента) | Внешний | Косвенная инъекция | Текст, который попадёт в контекст модели |
| Владелец или разработчик приложения | Внутренний | Обход политики, расход чужих квот | Ключ приложения, произвольные запросы к шлюзу |
| Внешний провайдер LLM (или нарушитель на его стороне) | Внешний | Получить данные заказчика, вернуть вредоносный ответ | Ответы модели, заголовки и тело HTTP-ответа |
| Нарушитель в сети заказчика | Внутренний | Перехват, подмена, отказ в обслуживании | Доступ к сетевым интерфейсам платформы |
| Администратор платформы (недобросовестный) | Внутренний, привилегированный | Ослабить защиту, скрыть действия, выгрузить содержимое | Права в консоли (ограничены разделением обязанностей, УПД.2) |
| Нарушитель в цепочке поставки | Внешний | Внедрить закладку | Скомпрометированная зависимость, образ, действие CI |

## Угрозы по компонентам (STRIDE)
Этапы 0–1: шлюз с аутентификацией приложений, строгим разбором запроса и ответа и маршрутизацией (задачи 1.4–1.7); детекторов ещё нет. Колонка «Меры» ссылается на реализованное; «план» — где мера появится.

| T | Подделка псевдонима пользователем или документом: `[[PHONE_1]]` в запросе, чтобы спутать значения | Псевдонимы из запроса резервируются и не выдаются (`TestReserveExisting`); подставляются только значения того же запроса |
| D — отказ | Большие тела, медленная передача тела или заголовков | Лимит тела (413), 30 с на тело (408), 10 с на заголовки, лимит заголовков 64 КиБ |
| D | Зависший или медленный провайдер | Таймауты соединения и заголовков ответа, общий срок ответа (10 мин, в том числе чтение тела и поток), простой потока (60 с) — 504 или событие ошибки в потоке |
| D | Текст, рассчитанный на медленную работу детектора (длинные последовательности цифр, много «@», дат, ключевых слов, префиксов ключей, скрытых символов, шаблонов инъекций, вложенных кодировок) | Время детекторов линейно (у `secrets` — O(n log n) по числу находок, у `injection.heuristic` — O(n log n) по числу пар «смена роли + снятие ограничений» в части 64 КиБ), регулярные выражения — только на коротком окне у найденного префикса; память `injection.heuristic` ограничена частью текста, её представлениями и одним сигналом на правило; декодирование в `injection.heuristic` — до двух уровней вложенности и до 1 МиБ на отрезок, двоичные данные отбрасываются по первым 256 байтам, каждое преобразование — не больше одного дополнительного прохода; худший случай — `pii.ru` 15 МБ/с, `secrets` 9,8 МБ/с, `unicode.hidden` 9,9 МБ/с, `injection.heuristic` 5,1 МБ/с на 1 МБ (2,2 МБ/с на 1 МБ base64 от base64). Срок детектора проверяется во всех циклах — после срока детектор останавливается за десятки миллисекунд (`TestDeadline` на 32 МиБ), брошенная реестром горутина не занимает процессор |
| T — обход проверки | Текст, рассчитанный на превышение срока детектора: `injection.heuristic` проверяет 2,4–12 МБ/с, поэтому при сроке около 30 мс текст от 70–450 КБ не успевает проверяться целиком; при `fail_open` запрос прошёл бы без проверки на инъекцию (ревью 1.15–1.16, п. 6) | Превышение срока — сбой детектора (`RunError`), а не «чисто». Мера (задача 1.22): срок детектора растёт с длиной фрагмента — 100 мс плюс 2 мс на КиБ (0,5 МБ/с, в 5 раз ниже наихудшей измеренной скорости), до минуты; текст до 32 МиБ (предел тела) проверяется целиком, а не до срока (`TestDM01_LongTextNotBypassedByDeadline`). Почему не другие меры: проверка только начала и конца оставляет середину; лимит размера проверяемого текста — тот же обход; `fail_closed` только для `injection.*` расходится с ТЗ, 4.4 (сбой — по режиму приложения). Остаточный риск: при перегрузке процессора срок может истечь; тогда действует `fail_mode` приложения — при `fail_open` запрос проходит с отметкой сбоя в событии. Для приложений с внешним провайдером и ПДн рекомендуется `fail_closed`; перегрузку ограничивают квоты (`max_input_bytes`, частота) |
| T — обход проверки | Текст в непроверяемых полях и на стыке фрагментов: инструкция или ПДн в описании инструмента (`tools[].function.description`, до 16 КиБ); инъекция, разрезанная на текстовые части одного сообщения, которые провайдер склеит | Описания инструментов проверяются и маскируются, как сообщения; текстовые части, части `refusal` и `refusal` сообщения `injection.*` проверяет ещё и склеенными — без разделителя и через перевод строки, как склеивают адаптеры GigaChat и YandexGPT; повторы одной находки из склеек в событие не попадают (задача 1.22, решение владельца 20.10.2026, итоговое ревью этапа 1; `TestToolDescriptionsChecked`, `TestDM01_InjectionSplitAcrossParts`, `TestDM01_InjectionSplitAtWordBoundary`). Размер схем входит в квоту `max_input_bytes`; общий срок проверки запроса — 1 мин, оставшиеся фрагменты — сбой по `fail_mode`. Остаточный риск: схемы JSON (`parameters`, `response_format`) не проверяются; инъекция, разнесённая по разным сообщениям, проверяется по сообщениям |
| D | Запрос из тысяч разных псевдонимов (`[A_1][A_2]…`), раздувающий резерв словаря | Резерв — не больше 4096 разных псевдонимов; сверх — резерв не хранится, всё маскируется необратимо (`TestReserveLimit`) |
| D | Ответ из тысяч повторов псевдонима длинного значения | Не больше 4 МиБ вставленных значений за запрос, словарь — до 4096 значений (`TestRestoreLimit`, `TestFallbackToRedact`) |
| D | Поток, который копит буфер обратной подстановки (бесконечный «незавершённый псевдоним») | Задержка — не больше 49 байт: грамматика псевдонима ограничена по длине (`FuzzStream`, `TestStreamHoldsOnlyCandidate`) |
| T | Обход подстановки разрезанием псевдонима между частями потока | Результат не зависит от разбиения: `FuzzStream` сравнивает поток с подстановкой по всему тексту |
| D | Раздутый ответ провайдера | Ответ и поток — до 16 МиБ, строка SSE — до 1 МиБ, событие — до 4 МиБ |
| D | Исчерпание квот и бюджета (denial of wallet) | Лимиты сообщений и `max_tokens` по квоте приложения; без `max_tokens` в запросе подставляется квота (DM-15). Квоты частоты, токенов и размера входа — `Limiter` в `internal/gateway` (задача 1.18), проверяются до детекторов (задача 1.22): отказ 429 `quota_exceeded` и событие; резерв токенов уточняется по `usage` ответа. Бюджеты — этап 3 |
| E — повышение привилегий | Выполнение кода через уязвимость разбора | Go без `unsafe` и cgo, fuzz-тесты обработчиков и разборщиков (`FuzzProxyHandler`, `FuzzParse`, `FuzzReader`, `FuzzAssembler`). На стенде разработки — контейнер `scratch` без оболочки, непривилегированный пользователь, без привилегий. Для поставки — план: ЗИ.5 (контейнеры — этап 3, пакеты — этап 6) |

### Сборочная среда и цепочка поставки
| Угроза | Меры |
|---|---|
| Скомпрометированная зависимость | Минимум зависимостей (ADR-0001), реестр `components.yaml` с хешами файлов лицензий, вендоринг, govulncheck, SBOM из бинарников |
| Скрытая загрузка при сборке | `GOPROXY=off` и `-mod=vendor` без возможности переопределить окружением; `GOTOOLCHAIN` — только `local` или точная версия `go1.27.2`. Сборка без сети (`make check-offline`) подготовлена, но ещё не прогонялась — см. остаточные риски |
| Подмена кода зависимости в `vendor/` (в репозитории, при слиянии, на сборочной машине) | `make vendor-check` (входит в `make check`): любой изменённый, добавленный или удалённый файл `vendor/` не совпадает с манифестом `docs/cert/vendor.sha256`, версии в `vendor/modules.txt`, `go.mod` и `go.sum` обязаны совпасть, у каждого модуля должны быть оба хеша в `go.sum`, директивы `replace` (подмена модуля другим путём) запрещены. Манифест меняется только `make vendor-manifest`, дифф манифеста смотрит ревью. Подмену вместе с манифестом выявляет `make vendor-verify` (повторный `go mod vendor` с пустым кешем модулей: модули скачиваются заново и сверяются с `go.sum`), но она запускается вручную, где есть сеть, а не в CI; до задания CI с сетью подмену вместе с манифестом ловит только ревью диффа. `tools/vendor-check` — Go без зависимостей |
| Подмена базового образа или действия CI | Образы по digest, действия по SHA коммита; `make licenses` требует закрепления у любого `FROM` и `uses:` и сверяет их с реестром. Подлинность самих digest и SHA сверяется при их внесении в реестр (ревью владельцем) |
| Изменение кода в обход ревью | Защищённая `main`, pull request с ревью владельца, подписанный коммит слияния (ADR-0002) |
| Ошибки в коде от ИИ-ассистента | Те же проверки, что для любого кода: линтеры с самопроверкой, SAST с разметкой, тесты, fuzz, `cert-reviewer`, ревью человеком (`build-env.md`) |
| Ослабление проверок ради «зелёной» сборки | `make lint-selftest` ловит ослабленные правила; каждое подавление — с обоснованием (nolintlint) и в перечне `suppressed.md` |

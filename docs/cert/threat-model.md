# Модель угроз

Черновик этапа 0. Составляется по Методике оценки угроз безопасности информации ФСТЭК России (2021) с использованием БДУ ФСТЭК, включая раздел «Угрозы безопасности информации систем ИИ»; STRIDE — вспомогательно, по компонентам (ТЗ, 8.9). Обновляется при изменении архитектуры или поверхности атаки.

**Идентификаторы БДУ здесь не приводятся**, пока их нет в `docs/taxonomy.md`: их переносят вручную из официального текста раздела, ничего не придумывая (ТЗ, 5.16). До этого угрозы систем ИИ связаны со строками матрицы обнаружения (`DM-NN`) и кодами OWASP.

Охват черновика: компоненты этапа 0 (шлюз — прозрачный прокси, mock-llm, сборочная среда) и целевая архитектура в общих чертах. Сервер управления, консоль и `aisec-media` детализируются на этапах 2 и 5.

## Объект защиты и активы
Объект защиты — платформа AISec, установленная в контуре заказчика. Она сама является средством защиты, поэтому её компрометация опаснее, чем у обычного приложения: нарушитель получает и данные, и возможность ослабить защиту незаметно.

| Актив | Где | Чем ценен |
|---|---|---|
| Содержимое запросов и ответов LLM (в том числе ПДн, коммерческая тайна) | Шлюз (в памяти), события (с этапа 1–2) | Утечка — штрафы по 152-ФЗ, коммерческий ущерб |
| Ключи API провайдеров | Файл ключа шлюза; с этапа 2 — БД в зашифрованном виде (ЗИ.1) | Расход бюджета, доступ к данным у провайдера |
| Ключи приложений (этап 1) | Хеши в конфигурации или БД | Обход политики, расход квот |
| Политики, исключения, правила оповещений (этапы 1–3) | Сервер, подписанные пакеты в шлюзе | Ослабление защиты без следа |
| Журнал аудита (этап 2) | БД, цепочка хешей | Сокрытие действий нарушителя |
| Закрытые ключи TLS, внутреннего УЦ, подписи пакетов | Файлы с правами 0600 | Подмена компонентов, перехват трафика |
| Целостность бинарников, статики, служебных баз | Файловая система, манифест (этап 2) | Подмена кода средства защиты |
| Исходный код и сборочная среда | Репозиторий, CI, сборочный образ | Внедрение закладки на этапе разработки |

## Границы доверия
Подробно — `docs/architecture.md`. Ключевые:
1. **Приложение → шлюз.** Недоверенные запросы: тела, заголовки, строка запроса. Также косвенно недоверенное содержимое документов RAG и ответов инструментов, которое приложение передаёт в промпт.
2. **Шлюз → провайдер.** Провайдер, особенно внешний, вне контура заказчика: его ответы — недоверенный ввод.
3. **Шлюз ↔ сервер** (этап 2) — mTLS, подписанные пакеты политик.
4. **Пользователь консоли → сервер** (этап 2).
5. **Шлюз → `aisec-media`** (этап 5) — недоверенные медиа, изолированный процесс.
6. **Разработка → поставка:** репозиторий, зависимости, сборочная среда, CI, ИИ-ассистент.

## Нарушители
Категории и возможности — по Методике ФСТЭК; уточняются с лабораторией.

| Нарушитель | Вид | Цели | Возможности |
|---|---|---|---|
| Пользователь ИИ-приложения | Внешний или внутренний | Обойти инструкции модели, получить чужие данные или системный промпт, вывести ПДн | Произвольный текст запроса, многоходовые диалоги, кодирование, медиа |
| Автор недоверенного содержимого (документ RAG, веб-страница, письмо, ответ инструмента) | Внешний | Косвенная инъекция | Текст, который попадёт в контекст модели |
| Владелец или разработчик приложения | Внутренний | Обход политики, расход чужих квот | Ключ приложения, произвольные запросы к шлюзу |
| Внешний провайдер LLM (или нарушитель на его стороне) | Внешний | Получить данные заказчика, вернуть вредоносный ответ | Ответы модели, заголовки и тело HTTP-ответа |
| Нарушитель в сети заказчика | Внутренний | Перехват, подмена, отказ в обслуживании | Доступ к сетевым интерфейсам платформы |
| Администратор платформы (недобросовестный) | Внутренний, привилегированный | Ослабить защиту, скрыть действия, выгрузить содержимое | Права в консоли (ограничены разделением обязанностей, УПД.2) |
| Нарушитель в цепочке поставки | Внешний | Внедрить закладку | Скомпрометированная зависимость, образ, действие CI |

## Угрозы по компонентам (STRIDE)
Этапы 0–1: шлюз с аутентификацией приложений, строгим разбором запроса и ответа и маршрутизацией (задачи 1.4–1.7); детекторов ещё нет. Колонка «Меры» ссылается на реализованное; «план» — где мера появится.

### Шлюз (`aisec-gateway`)
| STRIDE | Угроза | Меры |
|---|---|---|
| S — подмена | Нарушитель выдаёт себя за приложение | Ключи приложений: SHA-256 и сравнение за постоянное время, отзыв, срок, подсети; ограничение частоты неудач; событие `auth_failure` (ИАФ.8, DM-38) |
| S | Подмена провайдера (MITM на исходящем соединении) | TLS 1.2–1.3, доверие только `ca_file` провайдера, проверка имени; перенаправления не выполняются; переменные `HTTP_PROXY` не используются |
| T — искажение | Внедрение заголовков к провайдеру (подмена `Authorization`, `X-Forwarded-*`) | Заголовки приложения провайдеру не передаются вовсе — их формирует шлюз; ключ провайдера проверяется на управляющие символы |
| T | Обход проверок через строку запроса | Строка запроса провайдеру не передаётся |
| T | Обход проверок через формат запроса: повторные ключи JSON, ключи в другом регистре, поля, которых шлюз не знает (`metadata`, `prediction`, `functions`) | Строгий разбор (неизвестные поля — 400) и пересборка тела из проверенной модели: провайдер получает ровно то, что видели проверки (`internal/chat`, `FuzzParse`, `TestDuplicateKeysCannotSmuggle`) |
| T | Вредоносный или раздутый ответ провайдера: неизвестные поля с текстом (`reasoning_content`, `logprobs`), лишние варианты ответа мимо проверки | Пересборка ответа и каждой части потока; ровно один вариант ответа, иначе 502; `logprobs` в запросе не поддерживается |
| T | SSRF руками провайдера: ссылка на медиа на внутренний адрес его контура (служба метаданных облака, сервисы рядом с vLLM) | Ссылки на медиа — только `https://`, `http:` и прочие схемы — 400. Остаётся `https` на внутренние имена: решает политика `non_text` (задача 1.19) — ссылки можно запретить, оставив только данные в запросе |
| R — отказ от авторства | Нельзя установить, кто отправил запрос | План: события с приложением и пользователем (этап 1), аудит (этап 2) |
| I — раскрытие | Содержимое промптов или ключи в журналах | Журнал без содержимого и секретов; класс ошибки без адреса и строки запроса; тест `TestChatLogsHaveNoSecrets`, проверка в e2e |
| I | Утечка ключа провайдера через ответ об ошибке | При 401/403 тело провайдера заменяется ошибкой шлюза; в тексте других ошибок фрагмент ключа (от 8 символов) — замена текста |
| I | Утечка служебных заголовков и трейлеров провайдера приложению | Ответ собирается заново; заголовки — только `Retry-After` и `X-Ratelimit-*` |
| I | Утечка ключа авторизации или токена GigaChat | Ключ и токен только в памяти шлюза; в журнал не пишутся; фрагменты вырезаются из текстов ошибок провайдера; токен обновляется заранее и после 401 (`TestGigaChatSecretsNotLeaked`) |
| T | Несовпадение формата GigaChat с документацией: параметр молча теряется, ответ неверно переводится | Параметры без аналога — 400 с названием параметра; ответ с неизвестной причиной завершения или лишним вариантом — 502; контрактные тесты на фикстурах. Остаточный риск: фикстуры написаны по документации без настоящей учётной записи (Р8) — проверка до пилота |
| I | Раскрытие настоящих имён моделей за псевдонимами | В ответе — имя, которое запросило приложение (DM-33) |
| I | Передача ПДн провайдеру | Поле `user` внешнему провайдеру не передаётся; имя файла — фрагмент для детекторов. План: детекторы и псевдонимизация (этап 1, DM-31). Не проверяются: `stop` (до 4 строк по 256 байт) и схемы JSON инструментов и формата ответа — их задаёт приложение |
| D — отказ | Большие тела, медленная передача тела или заголовков | Лимит тела (413), 30 с на тело (408), 10 с на заголовки, лимит заголовков 64 КиБ |
| D | Зависший или медленный провайдер | Таймауты соединения и заголовков ответа, общий срок ответа (10 мин, в том числе чтение тела и поток), простой потока (60 с) — 504 или событие ошибки в потоке |
| D | Раздутый ответ провайдера | Ответ и поток — до 16 МиБ, строка SSE — до 1 МиБ, событие — до 4 МиБ |
| D | Исчерпание квот и бюджета (denial of wallet) | Лимиты сообщений и `max_tokens` по квоте приложения; без `max_tokens` в запросе подставляется квота (DM-15). План: квоты частоты и токенов (задача 1.18), бюджеты (этап 3) |
| E — повышение привилегий | Выполнение кода через уязвимость разбора | Go без `unsafe` и cgo, fuzz-тесты обработчиков и разборщиков (`FuzzProxyHandler`, `FuzzParse`, `FuzzReader`, `FuzzAssembler`). На стенде разработки — контейнер `scratch` без оболочки, непривилегированный пользователь, без привилегий. Для поставки — план: ЗИ.5 (контейнеры — этап 3, пакеты — этап 6) |

### mock-llm (только разработка)
В поставку не входит. Угрозы — для стенда разработки: доступен только по TLS, наружу из compose не публикуется, внутренняя сеть без выхода в интернет.

### Сборочная среда и цепочка поставки
| Угроза | Меры |
|---|---|
| Скомпрометированная зависимость | Минимум зависимостей (ADR-0001), реестр `components.yaml` с хешами файлов лицензий, вендоринг, govulncheck, SBOM из бинарников |
| Скрытая загрузка при сборке | `GOPROXY=off` и `-mod=vendor` без возможности переопределить окружением; `GOTOOLCHAIN` — только `local` или точная версия `go1.27.1`. Сборка без сети (`make check-offline`) подготовлена, но ещё не прогонялась — см. остаточные риски |
| Подмена базового образа или действия CI | Образы по digest, действия по SHA коммита; `make licenses` требует закрепления у любого `FROM` и `uses:` и сверяет их с реестром. Подлинность самих digest и SHA сверяется при их внесении в реестр (ревью владельцем) |
| Изменение кода в обход ревью | Защищённая `main`, pull request с ревью владельца, подписанный коммит слияния (ADR-0002) |
| Ошибки в коде от ИИ-ассистента | Те же проверки, что для любого кода: линтеры с самопроверкой, SAST с разметкой, тесты, fuzz, `cert-reviewer`, ревью человеком (`build-env.md`) |
| Ослабление проверок ради «зелёной» сборки | `make lint-selftest` ловит ослабленные правила; каждое подавление — с обоснованием (nolintlint) и в перечне `suppressed.md` |

Вне охвата (ТЗ, 5.16, «Е»): галлюцинации; обращения к моделям в обход шлюза, если приложение не вызывает Check API, и использование ИИ с личных устройств и через мобильный интернет (обращения сотрудников к публичным сервисам через корпоративную сеть видит DM-37); отравление данных у разработчика модели; атаки на приватность модели; состязательные искажения медиа; текст на изображениях, который не распознаёт OCR; документы и видео; уязвимости инфраструктуры заказчика. Это заявляется явно.

## Меры и остаточные риски
Реализованные меры — `docs/cert/security-functions.md`. Остаточные риски этапа 0:

| Риск | Почему остаётся | Когда закрывается |
|---|---|---|
| ~~Шлюз без аутентификации приложений~~ | Закрыто задачей 1.4 этапа 1: ключи приложений, `auth_failure`, ограничение частоты неудач (DM-38) | — |
| Блокировка адреса после неудачных попыток задевает клиентов за тем же NAT | Ограничение по адресу — единственный признак клиента до аутентификации. Действующие ключи проходят и с заблокированного адреса, поэтому страдают только неудачные попытки соседей (например, их запросы получают 429 вместо 401) | Оповещение о блокировке — этап 3 (DM-38); настройка порогов — с сервером управления (этап 2) |
| Таблицу ограничителя можно забить блокировками из множества сетей IPv6 /64 | Память ограничена 65 536 записями | Неудачи сверх таблицы попадают в общий счётчик, который блокируется так же; метрика `Overflowed` — в «Состояние системы» с этапа 2 |
| Событие `rate_limited` может быть отброшено при переполнении очереди событий | Очередь ограничена и не блокирует запросы (ТЗ, 4.4) | Счётчик отброшенных событий и оповещение «ослепление мониторинга» (DM-44) — этап 3 |
| Хеши модулей в SBOM взяты из `go.sum`, содержимое `vendor/` с ними при сборке не сверяется | Сборка с `-mod=vendor` сверяет только `vendor/modules.txt` с `go.mod` | Проверка неизменности `vendor/` — задача 1.28 этапа 1 |
| Нет доверенных обратных прокси: за балансировщиком шлюз видит его адрес, `allowed_cidrs` и ограничение частоты теряют смысл | `X-Forwarded-For` от недоверенного клиента подделывается | Список доверенных прокси — при подготовке к пилоту, отдельным решением |
| Нет проверок содержимого | Детекторов ещё нет | Этап 1 |
| Нет ограничения простоя потока SSE | Появится вместе с потоковой проверкой ответов | Этап 1 |
| Проверка уязвимостей зависимостей не выполняется в среде разработки ИИ-ассистента | Сетевая политика запрещает vuln.go.dev | Выполняется в CI; в закрытом контуре — по снимку базы (ADR-0003) |
| Формат SBOM по методике ФСТЭК не сверен с утилитами ИСП РАН, нет хешей ГОСТ | Утилиты и решение по Стрибогу — позже | До этапа 6 |
| Сборка в сборочном образе и без сети не подтверждена прогоном | В среде разработки ИИ-ассистента нет Docker; способ получения снимка базы уязвимостей не проверен | Первый прогон CI на pull request; `check-offline` — при подготовке закрытого контура |
| Нет запуска от непривилегированного пользователя в поставке (ЗИ.5) | Поставки ещё нет | Этап 3 (контейнеры), этап 6 (пакеты) |

**Аутентификация приложений** (задача 1.4 этапа 1, DM-38):
- Ключ — только в `Authorization: Bearer`, схема без учёта регистра, один заголовок, ключ до 128 символов строго формата `aisec_<8 символов>_<43 символа base64url>`. Ключ в строке запроса и в других заголовках не принимается.
- Срок `expires` (ГГГГ-ММ-ДД): ключ действует до 00:00 UTC этой даты (03:00 МСК), сама дата в срок не входит — так же написано в справке `aisec-cli app-key -expires`.
- Порядок проверок: формат → SHA-256 предъявленного ключа сравнивается с сохранённым за постоянное время (для неизвестного префикса — с заглушкой, чтобы время не выдавало, существует ли префикс) → отзыв → срок → `allowed_cidrs`. Отзыв, срок и адрес проверяются только после совпадения секрета: иначе по причине отказа можно было бы узнать о существовании префикса.
- Адрес клиента — только из TCP-соединения. `X-Forwarded-For`, `X-Real-Ip`, `Forwarded` не учитываются: доверенных обратных прокси перед шлюзом на этапе 1 нет, а иначе клиент подставил бы любой адрес. IPv4 в записи IPv6 приводится к IPv4.
- Отказ — 401 `invalid_api_key` с одинаковым текстом и `WWW-Authenticate: Bearer` при любой причине; причина, адрес и префикс — только в событии `auth_failure` (ключ туда не пишется). Успешный вход событие не создаёт.
- Ограничение частоты неудач: 10 неудач за минуту с одного адреса IPv4 или сети IPv6 /64 — блокировка на 15 минут. Во время блокировки **неудачи** с адреса получают 429 `auth_rate_limited` с `Retry-After` и событий не создают; о начале блокировки — одно событие с причиной `rate_limited` и одна строка в техническом журнале без адреса (адрес — только в событии). **Действующий ключ проходит и с заблокированного адреса:** иначе одно приложение с отозванным ключом в цикле повторов отключало бы соседей за тем же NAT или исходящим адресом; подбор это не облегчает — секрет 256 бит. Таблица адресов — в памяти, до 65 536 записей; при переполнении вытесняются незаблокированные, а если таблица забита блокировками (например, из множества сетей /64 одной сети /48), неудачи новых адресов учитываются в одном общем счётчике, который блокируется по тем же правилам: ограничение и поток событий остаются ограниченными. Неразобранный адрес клиента (у TCP-соединения не бывает) — тоже общий счётчик.

`POST /guard/v1/check` и `POST /v1/embeddings` (задача 1.24; контракт — `api/openapi.yaml`) после аутентификации:
- **Вход и аутентификация.** Тот же ключ приложения (RBAC шлюза: без действующего ключа — 401 `invalid_api_key`, события обработки нет), те же правила `Content-Type`, размера и времени передачи тела (415, 413, 408), только объект JSON. Проверка идёт до обращения к чему-либо внешнему; Check API провайдеру не обращается вовсе.
- **Check API, запрос.** Строгий разбор: поля `direction` (`input` или `output`), `source` (`user`, `rag`, `tool` для входа; `output` для выхода; `image` и `audio` — 400 `unsupported_parameter` до этапа 5), ровно одно из `text` (непустая строка) и `messages` (до `quotas.max_messages` или 256; роли `system`, `developer`, `user`, `assistant`, `tool`; `content` — непустая строка, частей нет), необязательное `user` (до 256 байт). Неизвестное поле, данные после объекта, неверный тип — 400.
- **Check API, ответ.** 200 с решением (`decision` — что сделано, `action` — как в `enforce`, `blocked`), находками детекторов политики (детектор, категория, оценка, байтовые смещения в исходном тексте, место, строка матрицы; находки детекторов маскирования для хранения в ответ не входят) и преобразованным текстом либо сообщениями; найденное значение в ответ не попадает, при блокировке преобразованного текста нет. Сбой проверки при `fail_closed` — 503 `check_unavailable`; при `fail_open` ответ помечается `incomplete`. `pseudonymize` политики выполняется как `redact`. Заголовки `X-AISec-Event-Id` и `X-AISec-Decision` — как у чата.
- **Check API, пределы.** Отдельного предела на `text` нет, кроме размера тела (`max-body-bytes`) и квоты `max_input_bytes`; общий срок проверки — не больше минуты. Направление без правил политики — ответ с `unchecked: true`. Ответы 501 и ошибки разбора событий не создают (как в чате).
- **Check API, событие.** Тип `check`: источник (`user`, `rag`, `tool`, `output`), решение, находки, трассировка; в режиме хранения `masked` содержимое пишется замаскированным (`content.request` для входа, `content.response` для выхода). Квоты: частота и размер входа считаются, токены модели — нет.
- **Эмбеддинги, запрос.** Строгая модель: `model`, `input` (строка или до 256 непустых строк; массивы токенов — 400), `encoding_format` (только `float`), `dimensions` (1–65536), `user`. Тело к провайдеру собирается заново; `encoding_format: float` указывает шлюз. Поле `user` внешнему провайдеру не передаётся.
- **Эмбеддинги, проверка и ответ.** Каждая строка `input` — фрагмент с местом `input[i]` и источником `user`, конвейер как у чата с `endpoint=embeddings`: допустимы `redact` и `block` (блокировка — 400 `policy_violation`). Модель — разрешённая или псевдоним (иначе 404 `model_not_found`, DM-33). Ответ провайдера разбирается и собирается заново: ровно по вектору на строку, индексы по порядку, не больше 65536 чисел в векторе, только числа (base64 — 502 `upstream_bad_response`), неизвестные поля отбрасываются; `model` — имя из запроса. Провайдер без эмбеддингов (GigaChat, YandexGPT на этапе 1) — 501 `embeddings_not_supported`, событие не создаётся. Событие — `gateway_request`, расход токенов — из `usage` ответа.

`POST /v1/chat/completions` после аутентификации:
- **Вход.** Только `Content-Type: application/json` (иначе 415); тело не больше `max-body-bytes` (иначе 413), передано не дольше 30 с (иначе 408) и только объект JSON (иначе 400). Всё это проверяется до обращения к провайдеру.
- **Разбор запроса** (`internal/chat`, задача 1.5). Строгая модель: верхний уровень — только `model`, `messages`, `stream`, `stream_options`, `max_tokens`, `max_completion_tokens`, `temperature`, `top_p`, `n` (только 1), `stop`, `presence_penalty`, `frequency_penalty`, `logit_bias`, `response_format`, `seed`, `tools`, `tool_choice`, `parallel_tool_calls`, `user`, `reasoning_effort`. Любое другое поле — 400 `unsupported_parameter`: в том числе `metadata`, `prediction`, `audio`, `modalities`, устаревшие `functions`/`function_call` — через них текст ушёл бы провайдеру мимо проверок; `logprobs` и `top_logprobs` — в них ответ повторяется по токенам в обход маскирования ответа. Роли — `system`, `developer`, `user`, `assistant`, `tool`; части — `text`, `refusal` (только `assistant`), `image_url`, `input_audio`, `file`, `video_url` (только `user`); неизвестный тип части — 400. Диапазоны чисел, имена функций и идентификаторы — по шаблонам; схемы JSON (`tools[].function.parameters`, `response_format`) — объект до 256 КиБ.
- **Пересборка.** Провайдеру уходит тело, собранное заново из разобранной модели, а не исходные байты. Повторные ключи JSON, ключи в другом регистре и неизвестные поля до провайдера не доходят: провайдер получает ровно то, что видели проверки.
- **Нетекстовые части** (DM-14). Шлюз их не декодирует: знает вид (изображение, аудио, файл, видео), способ передачи (данные `data:…;base64` или ссылка `https://`, у файла — ещё `file_id` провайдера) и длину данных; длина проверяется сразу (по умолчанию до 20 МиБ на часть, иначе 400 `media_too_large`). Ссылку загружает провайдер, поэтому `http:` и другие схемы (`file:`, `ftp:` и т. п.) — 400: иначе через провайдера можно было бы обратиться к внутренним адресам его контура. Обработка по параметру политики `non_text` (в том числе запрет ссылок) — задача 1.19. Имя файла (`file.filename`) — текстовый фрагмент для детекторов.
- **Лимиты** (DM-15): до 256 сообщений (или `quotas.max_messages` приложения), 64 частей и 64 вызовов инструментов в сообщении, 128 инструментов; `max_tokens` — не больше `quotas.max_tokens` приложения (400 `max_tokens_exceeded`).
- **Маршрутизация** (задача 1.7, DM-33). Приложение запроса известно по ключу; провайдер — из его карточки. Модель запроса — разрешённая модель приложения или его псевдоним (заменяется моделью провайдера). Иначе — 404 `model_not_found` до обращения к провайдеру, без перечня разрешённых моделей в ответе; перечень — в `GET /v1/models` с ключом приложения.
- **Описания инструментов** `tools[].function.description` проверяются детекторами политики и маскируются, как текст сообщений (задача 1.22, решение владельца 20.10.2026). **Не проверяется на этапе 1:** схемы JSON (`tools[].function.parameters`, `response_format.json_schema`; передаются провайдеру как есть, в том числе с повторными ключами внутри схемы) — их задаёт приложение, а не пользователь; стоп-последовательности `stop` (до 4 строк по 256 байт).
- **Поле `user`** внешнему провайдеру не передаётся: там часто e-mail или ФИО.
- **Пользователь** (задача 1.22): по `user_from` приложения — заголовок `X-AISec-User` (один, до 256 байт, валидный UTF-8 без управляющих символов, иначе 400 `invalid_user`), поле `user` или никак. В событие и счётчики квот попадает только псевдоним — HMAC идентификатора на ключе `gateway.user_hmac_key_file` (`internal/crypto`), первые 16 байт в hex; без ключа шлюз с `user_from` не header/field не запускается.
- **Конвейер проверки** (задача 1.22, ТЗ, 4.3): модель (DM-33) → квоты (DM-15, DM-36; отказ 429 `quota_exceeded`, `Retry-After`, если повтор возможен) → детекторы политики по каждому текстовому фрагменту, параллельно, со сроком по длине текста → решение политики → псевдонимизация (`[[ТИП_N]]`) и маскирование (`[[ТИП]]`, задача 1.23). Блокировка — 400 `policy_violation` с безопасным сообщением политики без названий детекторов; сбой детектора при `fail_closed` — 503 `check_unavailable`. Каждый разобранный запрос создаёт событие `gateway_request` (ошибки разбора и тела — нет).
- **`max_tokens`:** если у приложения задана квота `quotas.max_tokens`, а в запросе предела нет, шлюз подставляет квоту.
- **Строка запроса** клиента провайдеру не передаётся и в журнал не пишется.
- **Заголовки к провайдеру** формирует шлюз: `Content-Type`, `Accept`, `User-Agent: aisec-gateway`, `Authorization` с ключом провайдера. Заголовки приложения провайдеру не передаются вовсе.
- **Ответ провайдера** разбирается и собирается заново (`internal/chat`): неизвестные поля (например, `reasoning_content`, `logprobs`) приложению не уходят; вариант ответа — ровно один (индекс 0), иначе 502 `upstream_bad_response`; поле `model` — имя, которое запросило приложение. Ответ без потока — до 16 МиБ. Поток SSE (`internal/sse`): строка до 1 МиБ, событие до 4 МиБ, данные потока в сумме до 16 МиБ; каждая часть разбирается, служебные события и комментарии провайдера не передаются; ошибка или обрыв потока — событие `data: {"error": …}` без завершающего `[DONE]`.
- **Проверка ответа** (задача 1.23, ТЗ, 5.1): выходные правила политики проверяют `content`, `refusal` и аргументы `tool_calls`. Ответ без потока и `response_check: buffered` — проверяется целиком до отправки: блокировка — 400 `policy_violation`, сбой при `fail_closed` — 503 `check_unavailable` (в `buffered` вместо потока приходит обычный ответ с ошибкой). `incremental` — текст приходит с задержкой (после каждых 512 байт проверки, без последних 256 байт и недописанного слова), вызовы инструментов — одной частью в конце; блокировка обрывает поток событием `data: {"error": {"code": "policy_violation", …}}` без `[DONE]`. `monitor` (и при режиме политики `monitor`) — части уходят сразу. Псевдонимы запроса в ответе заменяются исходными значениями во всех режимах; в потоке начало возможного псевдонима задерживается не больше чем на 49 байт.
- **Сроки ответа провайдера** (план этапа 1, Р11): общий срок ответа, в том числе чтение тела и весь поток, — `response_timeout` провайдера (по умолчанию 10 мин); пауза между событиями потока — `stream_idle_timeout` (по умолчанию 60 с). Превышение — 504 `upstream_timeout` или событие ошибки в потоке.
- **Заголовки к приложению:** только `Content-Type`, `X-AISec-Event-Id` (ID события) и `X-AISec-Decision` (что сделано с запросом, а у ответа без потока и `buffered` — и с ответом: `allow`, `redact`, `pseudonymize` или `block`; что было бы в `enforce`, видно только в событии) шлюза и `Retry-After`, `X-Ratelimit-*` провайдера (значения до 128 символов без управляющих).
- **GigaChat** (задача 1.8, `internal/providers/gigachat.go`). Шлюз получает токен доступа по ключу авторизации (`POST auth_url`, `Authorization: Basic`, `RqUID` — случайный UUID из криптопрофиля, форма `scope`), кеширует его до истечения (обновляет за минуту до срока; срок вне 0–24 ч считается 30 мин) и передаёт API как `Bearer`; на 401 от API токен обновляется и запрос повторяется один раз. Ключ и токен — только в памяти шлюза: в журнал, приложению и в тексты ошибок не попадают (фрагменты вырезаются). Запрос переводится в формат GigaChat (`developer` → `system`, `tool_calls` → `function_call` с аргументами-объектом, `tool` → `function`, `tools` → `functions`), ответ — обратно (идентификаторы ответа и вызовов — случайные). Параметры без аналога (`stop`, `response_format`, `seed`, `logit_bias`, штрафы, `reasoning_effort`, `tool_choice: required`), нетекстовые части и несколько вызовов в одном сообщении — 400 `unsupported_parameter` до обращения к провайдеру. `temperature: 0` передаётся как 0,001 (GigaChat принимает только больше 0). Форматы — по публичной документации; проверка на настоящей учётной записи — до пилота (Р8).
- **YandexGPT** (задача 1.9, `internal/providers/yandexgpt.go`, Foundation Models API, метод `completion`). Авторизация — API-ключ сервисного аккаунта (`Authorization: Api-Key`), каталог — заголовком `x-folder-id`; модель — `gpt://<folder_id>/<модель из запроса>`, сам каталог приложение не задаёт. IAM-токены не поддерживаются (нужна подпись JWT в `internal/crypto` — отдельная задача). Запрос переводится в формат API (`developer` → `system`, `tool_calls` → `toolCallList` с аргументами-объектом, `tool` → `toolResultList`, `max_tokens` → `maxTokens`), ответ — обратно по статусу альтернативы. Поток — строки JSON (до 16 МиБ каждая) с накопленным текстом: приложению уходит приращение; часть, которая не продолжает предыдущую, данные после финальной части и обрыв без финальной — ошибка потока. Параметры без аналога (`stop`, `response_format`, `seed`, `top_p` ≠ 1, `logit_bias`, штрафы, `reasoning_effort`, `tool_choice` кроме `auto`/`none`, `temperature` > 1), нетекстовые части — 400 `unsupported_parameter`. Ключ в журнал и тексты ошибок не попадает. Форматы — по публичной документации; проверка на учётной записи — до пилота (Р8).
- **Ошибки провайдера.** Код, тип и код ошибки — от провайдера (тип и код — только короткие идентификаторы), текст — до 500 символов без управляющих; если в тексте фрагмент ключа провайдера (от 8 символов), текст заменяется общим. 401 и 403 от провайдера — отказ ключу шлюза, а тело может содержать часть ключа: вместо них 502 `upstream_auth_error` без тела провайдера. Коды 3xx (перенаправления не выполняются) и прочие — 502. Ошибки связи — 502 `upstream_unavailable` или 504 `upstream_timeout` без внутренних подробностей; в журнал — класс ошибки и идентификатор провайдера.
- **Разрыв соединения клиентом** отменяет запрос к провайдеру.

**Исходящие соединения шлюза:** только на `base_url` провайдеров из файла конфигурации и, для GigaChat, на адрес выдачи токена `auth_url` (по умолчанию `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`) — allowlist, ЗИ.3; только `https`; перенаправления не выполняются; переменные `HTTP_PROXY`/`HTTPS_PROXY` не используются; TLS с доверием только корневым сертификатам из `ca_file` провайдера; таймауты на соединение (по умолчанию 10 с) и до заголовков ответа (60 с).

Общие ограничения HTTPS-сервера (`internal/httpserver`): таймаут чтения заголовков 10 с, простой соединения 120 с, заголовки до 64 КиБ, корректное завершение до 30 с. Ответы шлюза содержат `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Strict-Transport-Security`.

## Аргументы командной строки
`aisec-gateway` — у каждого флага есть переменная окружения (раздел ниже); флаг важнее переменной. Неизвестные флаги и лишние аргументы — ошибка запуска. Справка `-h` не печатает значения из окружения.

| Флаг | Назначение | Проверка |
|---|---|---|
| `-config` | Файл конфигурации шлюза: приложения, ключи, провайдеры, файл событий | Обязателен; см. «Файлы». Флаги провайдера этапа 0 (`-upstream-*`, `-forward-headers`) удалены в задаче 1.7 |
| `-listen` | Адрес и порт | `адрес:порт`; по умолчанию `127.0.0.1:8443` |
| `-tls-cert`, `-tls-key` | Сертификат и ключ TLS | Обязательны; обычный файл до 1 МиБ; ключ — права 0600 или 0400 |
| `-max-body-bytes` | Предел тела запроса | 1 КиБ – 32 МиБ, по умолчанию 1 МиБ |
| `-server` | Адрес внутреннего API сервера управления (heartbeat по mTLS, задача 2.14) | Только `https://хост[:порт]` без учётных данных, пути, параметров и фрагмента (`FuzzParseServerURL`); пусто — режим «без сервера». С ним обязательны `-server-ca`, `-client-cert`, `-client-key` |
| `-server-ca` | Корень для проверки сертификата сервера | Обычный файл PEM до 1 МиБ; системное хранилище не используется |
| `-client-cert`, `-client-key` | Сертификат и ключ шлюза из `aisec-gateway register` | Ключ — права 0600 или 0400; за 30 дней до окончания сертификата — предупреждение в журнал |
| `-manifest` | Манифест целостности (задача 2.17) | Путь к файлу; по умолчанию `../aisec-manifest.json` от каталога бинарника; подпись — рядом с суффиксом `.sig`. Нет файла — нарушение, реакция по `-integrity-action` |
| `-integrity-action` | Реакция на нарушение целостности | `alert` (по умолчанию, только журнал) или `stop` (не запускаться; после запуска — штатная остановка) |
| `-integrity-interval` | Период проверки целостности | Длительность Go не меньше `1m`, по умолчанию `1h` |

`aisec-gateway register` — получение сертификата шлюза по токену (задача 2.14): `-console` (адрес консоли, `https://хост:порт`), `-console-ca` (корень для проверки консоли), `-out-dir` (каталог 0700); токен — только из `AISEC_GATEWAY_REGISTRATION_TOKEN`, не из аргументов (их видно в списке процессов), в вывод и журнал не попадает. Ключ и CSR создаются на шлюзе; запрос — `POST /api/v1/gateways/register` с доверием только `-console-ca`, без `HTTP_PROXY`, таймаут 10 с, ответ до 64 КиБ; CN полученного сертификата сверяется с ID шлюза из ответа.

## Переменные окружения
`aisec-gateway`: `AISEC_GATEWAY_CONFIG`, `AISEC_GATEWAY_LISTEN`, `AISEC_GATEWAY_TLS_CERT`, `AISEC_GATEWAY_TLS_KEY`, `AISEC_GATEWAY_MAX_BODY_BYTES`, `AISEC_GATEWAY_MANIFEST`, `AISEC_GATEWAY_INTEGRITY_ACTION`, `AISEC_GATEWAY_INTEGRITY_INTERVAL`, `AISEC_GATEWAY_SERVER`, `AISEC_GATEWAY_SERVER_CA`, `AISEC_GATEWAY_CLIENT_CERT`, `AISEC_GATEWAY_CLIENT_KEY` — те же проверки, что у флагов. `AISEC_GATEWAY_REGISTRATION_TOKEN` — одноразовый токен для `aisec-gateway register` (только окружение). Секреты через переменные окружения не передаются: только пути к файлам.

`aisec-server`: `AISEC_SERVER_LISTEN`, `AISEC_SERVER_TLS_CERT`, `AISEC_SERVER_TLS_KEY` — как флаги `-listen`, `-tls-cert`, `-tls-key` (флаг важнее переменной; сертификат и ключ обязательны, ключ — права 0600 или 0400); `AISEC_SERVER_AUDIT_SIGNING_PUB` — как флаг `-audit-signing-pub`: открытый ключ проверки контрольных точек аудита (`audit-signing.pub`, PEM `AISEC AUDIT SIGNING PUBLIC KEY` до 4 КиБ, ADR-0008); необязателен, без него подписи точек сервер не проверяет. `AISEC_SERVER_KEYS_DIR` — как флаг `-keys-dir`: каталог ключей `aisec-cli init` (обязателен, задача 2.8); сервер читает из него только `master.key` (права 0600 или 0400, до 1 МиБ, PEM `AISEC MASTER KEY` профиля сервера), расшифровывает им действующий ключ данных из `data_keys` и не запускается, если файла нет, права шире, профиль другой или ключ данных не расшифровывается. `AISEC_SERVER_MANIFEST`, `AISEC_SERVER_INTEGRITY_ACTION`, `AISEC_SERVER_INTEGRITY_INTERVAL` — как флаги `-manifest`, `-integrity-action`, `-integrity-interval` с теми же проверками, что у шлюза (задача 2.17); сервер сверяет с манифестом свой исполняемый файл и встроенную статику. `AISEC_SERVER_CA_CERT`, `AISEC_SERVER_CA_KEY` — как `-ca-cert`, `-ca-key`: внутренний УЦ (задаются вместе; без них регистрация шлюзов отвечает 503, а внутренний порт не открывается); `AISEC_SERVER_INTERNAL_LISTEN` — как `-internal-listen` (по умолчанию `127.0.0.1:8445`, не может совпадать с `-listen`); `AISEC_SERVER_INTERNAL_TLS_CERT`, `AISEC_SERVER_INTERNAL_TLS_KEY` — как `-internal-tls-cert`, `-internal-tls-key` (задаются вместе; по умолчанию — сертификат консоли). `AISEC_DATABASE_URL` — строка подключения к PostgreSQL (обязательна; только из окружения, не из аргументов, чтобы пароль не был виден в списке процессов; в журнал не попадает). Неизвестные флаги и лишние аргументы — ошибка запуска.

`aisec-cli`: `AISEC_DATABASE_URL` — строка подключения к PostgreSQL для `migrate`, `init`, `audit verify`, `audit archive`, `audit export` и `gateway token`, `gateway list`, `gateway revoke`, необязательно — для `verify` (запись итога в `integrity_checks` и аудит) (`audit verify-archive` к БД не подключается). Тесты `internal/store`, `internal/audit` и `cmd/aisec-cli` на живой БД читают `AISEC_TEST_DATABASE_URL` (без неё пропускаются); только для разработки.

`aisec-cli` (в поставке): `app-key [-expires ГГГГ-ММ-ДД]` — выпуск ключа приложения. Ключ печатается один раз в стандартный вывод и нигде не сохраняется; для конфигурации — префикс и SHA-256. Перед выпуском — самотест криптопрофиля. `migrate` — применяет встроенные SQL-миграции (`migrations/`) к PostgreSQL одной транзакцией под рекомендательной блокировкой; без аргументов, строка подключения — только из переменной окружения `AISEC_DATABASE_URL` (URL `postgres://…`, до 2048 байт; пароль не попадает в аргументы и сообщения об ошибках). Исходящее соединение — только на настроенный адрес БД; таймауты: соединение 10 с, прогон 5 мин. `audit verify` — проверка цепочки журнала аудита по команде (РСБ.4, DM-43): без аргументов, строка подключения — из `AISEC_DATABASE_URL`; только читает `audit_log` и добавляет итог в `audit_verifications`, `audit_log` и `tech_log`; код возврата 3 — цепочка нарушена, 1 — ошибка выполнения; криптопрофиль — `standard`; «кто» в записи — пользователь ОС; таймауты — 30 с на пачку из 1000 записей, 10 с на запись итога; `-keys КАТАЛОГ` — дополнительно проверить подписи контрольных точек архивации открытым ключом `audit-signing.pub` (ADR-0008), без него проверяется только их связность; подмена или удаление точки — код 3. `init -dir КАТАЛОГ [-profile standard]` — создание ключей установки (ЗИ.1, ЗИ.4, ADR-0007; `-profile gost` до этапа 6 отклоняется): каталог должен существовать и быть закрыт для группы и остальных (иначе отказ), файлы открываются через `os.Root`; создаются `master.key`, `bundle-signing.key`, `ca.key`, `audit-signing.key` (0400) и `bundle-signing.pub`, `ca.crt`, `audit-signing.pub` (0444) с `O_EXCL` — существующие файлы и символические ссылки не перезаписываются, повторный запуск отклоняется и по наличию ключа данных в БД. В БД одной транзакцией: `data_keys` (ключ данных под мастер-ключом), `setup_tokens` (SHA-256 токена первичной настройки, срок 24 ч), запись аудита `system.init` (без ключей и токена); сбой транзакции удаляет созданные файлы, при неизвестном исходе фиксации файлы сохраняются; триггеры запрещают уменьшать счётчик шифрований и повторно гасить токен. В стандартный вывод — только имена файлов, id ключа данных, срок УЦ и однократно токен первичной настройки; ключи не выводятся. Таймаут каждой операции с БД — 30 с. `init -dir КАТАЛОГ -add-audit-key` — только пара ключей аудита для установки, где `init` прошёл до ADR-0008: нужен `master.key` в каталоге и ключ данных в БД, существующий ключ аудита не перезаписывается, запись аудита `system.audit_key`; при её сбое файлы удаляются. Новые форматы файлов: PEM `AISEC MASTER KEY`, `AISEC SIGNING KEY`, `AISEC SIGNING PUBLIC KEY`, `AISEC AUDIT SIGNING KEY`, `AISEC AUDIT SIGNING PUBLIC KEY` с заголовком `Profile`, до 4 КиБ, строгий разбор без данных до и после блока (`FuzzDecodeKeyPEM`); ключ УЦ — PKCS#8 PEM (`FuzzLoadCA`). `audit archive -keys КАТАЛОГ -out ФАЙЛ [-before ГГГГ-ММ-ДД]` — архивация записей старше срока хранения (РСБ.4, ADR-0008): строка подключения — из `AISEC_DATABASE_URL`, логину нужно членство в роли `aisec_audit_archiver`; читает `audit-signing.key` и `audit-signing.pub` (`ReadKeyFile` — отказ при доступе группы или остальных, проверка, что это пара); сначала проверка цепочки (нарушена — код 3, архивации нет); файл архива создаётся `O_EXCL` с правами 0600 и сбрасывается на диск до удаления записей; каталог файла сбрасывается на диск до транзакции; в БД одной транзакцией (таймаут 10 мин) — точка в `audit_checkpoints` (триггер принимает только точку, описывающую реальные записи), `DELETE` из `audit_log`, запись `audit.archive`; нечего архивировать — файл удаляется; сбой — файл удаляется, если точка точно не записана, при неизвестном исходе фиксации сохраняется. В вывод — диапазон номеров, граница и хеш последней записи, ключи не выводятся. `audit export -out ФАЙЛ [-from ГГГГ-ММ-ДД] [-to ГГГГ-ММ-ДД]` — выгрузка журнала (РСБ.5): только чтение одним снимком (в заголовке — начало хранимой части), файл `O_EXCL` 0600, запись `audit.export`; при сбое файл удаляется. `audit verify-archive -keys КАТАЛОГ ФАЙЛ` — проверка архива без БД и сети: читает `audit-signing.pub` и обычный файл до 64 ГиБ (больший — отказ до чтения); код 3 — архив недействителен. Новый формат файла — архив и выгрузка журнала аудита: JSON Lines (`aisec-audit-archive`, `aisec-audit-export`), строка до 256 КиБ, строгий разбор без неизвестных полей, каноническая форма точки и записей, не более 2^40 записей (`FuzzVerifyArchive`). `gateway token -name ИМЯ [-ttl 24h] [-reregister]` (задача 2.14) — одноразовый токен регистрации шлюза: имя 1–64 символа `[a-z0-9._-]`, срок от 1 минуты до 7 суток; токен печатается один раз, в БД — только SHA-256, прежние непогашенные токены шлюза гасятся, запись `gateway.token_issue`; без `-reregister` занятое имя — отказ, для отозванного шлюза — отказ. `gateway list` — шлюзы, состояние, срок сертификата, последний контакт и версия (только чтение). `gateway revoke -name ИМЯ` — отзыв: сертификат перестаёт приниматься сразу, токены гасятся, запись `gateway.revoke`; отзыв окончательный. Команды `gateway` работают под логином владельца схемы: у роли сервера нет прав создавать и отзывать шлюзы. `verify [-manifest ФАЙЛ]` (задача 2.17) — проверка целостности установки по подписанному манифесту без сервера: читает манифест, подпись и все невстроенные файлы манифеста в его каталоге (через `os.Root`), сверяет встроенные миграции и свой исполняемый файл; к сети не обращается, к БД — только с `AISEC_DATABASE_URL`; вывод — пути и виды нарушений, код 3 — целостность нарушена. `version` — версия сборки, без доступа к файлам и сети.

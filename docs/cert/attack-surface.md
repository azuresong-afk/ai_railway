# Поверхность атаки

Черновик этапов 0–1. Все внешние интерфейсы продукта: сетевые (порт, протокол, аутентификация), файловые, аргументы CLI, переменные окружения (ТЗ, раздел 9). Обновляется при любом изменении интерфейсов.

## Сетевые интерфейсы
| Компонент | Адрес по умолчанию | Протокол | Аутентификация | Эндпоинты | Этап |
|---|---|---|---|---|---|
| `aisec-gateway` | `127.0.0.1:8443` | HTTPS (TLS 1.2–1.3; HTTP без TLS отвергается) | `GET /healthz`, `GET /readyz` — без аутентификации (только статус). Маршруты приложений — ключ приложения `Authorization: Bearer aisec_…` (ИАФ.8); шлюз без аутентификации не собирается | `GET /healthz`, `GET /readyz`, `POST /v1/chat/completions` (пока прокси на один upstream без проверок содержимого, в том числе SSE). Прочее — 404 или 405 в формате ошибок OpenAI | 0–1 |

**Аутентификация приложений** (задача 1.4 этапа 1, DM-38):
- Ключ — только в `Authorization: Bearer`, схема без учёта регистра, один заголовок, ключ до 128 символов строго формата `aisec_<8 символов>_<43 символа base64url>`. Ключ в строке запроса и в других заголовках не принимается.
- Порядок проверок: формат → SHA-256 предъявленного ключа сравнивается с сохранённым за постоянное время (для неизвестного префикса — с заглушкой, чтобы время не выдавало, существует ли префикс) → отзыв → срок (`expires` — ключ недействителен с начала этих суток по UTC) → `allowed_cidrs`. Отзыв, срок и адрес проверяются только после совпадения секрета: иначе по причине отказа можно было бы узнать о существовании префикса.
- Адрес клиента — только из TCP-соединения. `X-Forwarded-For`, `X-Real-Ip`, `Forwarded` не учитываются: доверенных обратных прокси перед шлюзом на этапе 1 нет, а иначе клиент подставил бы любой адрес. IPv4 в записи IPv6 приводится к IPv4.
- Отказ — 401 `invalid_api_key` с одинаковым текстом и `WWW-Authenticate: Bearer` при любой причине; причина, адрес и префикс — только в событии `auth_failure` (ключ туда не пишется). Успешный вход событие не создаёт.
- Ограничение частоты неудач: 10 неудач за минуту с одного адреса IPv4 или сети IPv6 /64 — блокировка на 15 минут. Пока адрес заблокирован, его запросы получают 429 `auth_rate_limited` с `Retry-After` до проверки ключа (иначе перебор продолжался бы) и событий не создают; о начале блокировки — одно событие с причиной `rate_limited`. Таблица адресов — в памяти, до 65 536 записей; при переполнении вытесняются незаблокированные. Обратная сторона: клиенты за одним NAT с атакующим тоже блокируются — допустимо, ключи приложений высокоэнтропийные и NAT-соседство с атакующим — нештатная ситуация, видимая по событиям.

`POST /v1/chat/completions` после аутентификации:
- **Вход.** Только `Content-Type: application/json` (иначе 415); тело не больше `max-body-bytes` (иначе 413), передано не дольше 30 с (иначе 408) и только объект JSON (иначе 400). Всё это проверяется до обращения к провайдеру.
- **Строка запроса** клиента провайдеру не передаётся и в журнал не пишется.
- **Заголовки к провайдеру:** только `Content-Type`, `Accept`, `User-Agent`, `X-Request-Id` и перечисленные в `forward-headers`. Клиентские `Authorization`, `Cookie`, `X-Forwarded-*` отбрасываются; ключ провайдера подставляет шлюз.
- **Заголовки к приложению:** только `Content-Type`, `Retry-After`, `X-Request-Id` и `X-Ratelimit-*` провайдера. Трейлеры провайдера не передаются.
- **Ошибки провайдера.** Ответы с ошибкой передаются приложению как есть, кроме 401 и 403: это отказ ключу шлюза, а тело провайдера может содержать часть ключа. Поэтому вместо них — 502 `upstream_auth_error` без тела провайдера. Ошибки связи с провайдером — 502 или 504 без внутренних подробностей; в журнал пишется класс ошибки без адреса и строки запроса.
- **Разрыв соединения клиентом** отменяет запрос к провайдеру.
- **Ещё не ограничено (этап 1):** простой потока SSE между частями и общий срок потокового ответа — сейчас поток живёт, пока его не закроет провайдер или клиент.

**Исходящие соединения шлюза:** только на `upstream-url` (allowlist из одного адреса, ЗИ.3); переменные `HTTP_PROXY`/`HTTPS_PROXY` не используются; TLS с доверием только `upstream-ca`; таймауты на соединение и до заголовков ответа.

Общие ограничения HTTPS-сервера (`internal/httpserver`): таймаут чтения заголовков 10 с, простой соединения 120 с, заголовки до 64 КиБ, корректное завершение до 30 с. Ответы шлюза содержат `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Strict-Transport-Security`.

## Файлы
| Файл | Кто читает или пишет | Защита |
|---|---|---|
| Конфигурация шлюза (YAML, флаг `-config`; пример — `testdata/fixtures/config/gateway.yaml`) | Шлюз читает при запуске | Только обычный файл, недоступный на запись группе и остальным (по нему принимаются решения о доступе). До 4 МиБ, один документ, строгая схема (неизвестные поля — ошибка), проверка ссылок и значений; `gateway.events_file` обязателен; подсети `allowed_cidrs` — в каноническом виде, без записи IPv4-in-IPv6. Секретов нет: ключи провайдеров — путями к файлам, ключи приложений — только префикс и SHA-256. Режим хранения `full` и провайдер без источника доверия отвергаются |
| Файл событий JSONL (этап 1, `gateway.events_file`) | Шлюз дописывает | Права 0600; файл с более широкими правами не используется. Содержимое — только по режиму хранения (`none`, `masked`) |
| Сертификаты и ключи TLS (путь задаёт администратор) | Компоненты читают сертификаты через `crypto.ReadPEMFile`, закрытые ключи — через `crypto.ReadKeyFile` | Только обычный файл, не больше 1 МиБ; проверки выполняются на открытом файле (подмена между проверкой и чтением не помогает). Ключ с доступом для группы или остальных не читается (нужно 0600 или 0400) |
| Каталог ключей стенда разработки (`.dev-keys/`) | `tools/devcerts` пишет: сертификаты, ключ TLS, ключ приложения `app-key`, конфигурацию шлюза `gateway.yaml` | Каталог 0700, ключ TLS и ключ приложения 0600, запись через временный файл; ключ УЦ не сохраняется; каталог в `.gitignore`; правило `deny` в `.claude/settings.json` закрывает его только от инструмента чтения файлов ИИ-ассистента, не от команд оболочки — ключи стенда одноразовые и ни к чему не дают доступа |

## Аргументы командной строки
`aisec-gateway` — у каждого флага есть переменная окружения (раздел ниже); флаг важнее переменной. Неизвестные флаги и лишние аргументы — ошибка запуска. Справка `-h` не печатает значения из окружения.

| Флаг | Назначение | Проверка |
|---|---|---|
| `-config` | Файл конфигурации шлюза: приложения, ключи, файл событий | Обязателен; см. «Файлы» |
| `-listen` | Адрес и порт | `адрес:порт`; по умолчанию `127.0.0.1:8443` |
| `-tls-cert`, `-tls-key` | Сертификат и ключ TLS | Обязательны; обычный файл до 1 МиБ; ключ — права 0600 или 0400 |
| `-upstream-url` | Базовый адрес провайдера | Обязателен; только `https`, без учётных данных, параметров и фрагмента |
| `-upstream-ca` | Корневые сертификаты провайдера | Обязателен; доверие только им, системное хранилище не используется |
| `-upstream-key-file` | Ключ API провайдера | Необязателен; права 0600 или 0400 |
| `-max-body-bytes` | Предел тела запроса | 1 КиБ – 32 МиБ, по умолчанию 1 МиБ |
| `-upstream-connect-timeout`, `-upstream-header-timeout` | Таймауты к провайдеру | Больше 0 и не больше 10 мин; по умолчанию 10 с и 60 с |
| `-forward-headers` | Дополнительные заголовки для провайдера | До 16 имён; `Authorization`, `Cookie`, `Host`, `X-Forwarded-*`, `Accept-Encoding`, `Content-Encoding`, `Expect` и заголовки соединения запрещены |

## Переменные окружения
`aisec-gateway`: `AISEC_GATEWAY_CONFIG`, `AISEC_GATEWAY_LISTEN`, `AISEC_GATEWAY_TLS_CERT`, `AISEC_GATEWAY_TLS_KEY`, `AISEC_GATEWAY_UPSTREAM_URL`, `AISEC_GATEWAY_UPSTREAM_CA`, `AISEC_GATEWAY_UPSTREAM_KEY_FILE`, `AISEC_GATEWAY_MAX_BODY_BYTES`, `AISEC_GATEWAY_UPSTREAM_CONNECT_TIMEOUT`, `AISEC_GATEWAY_UPSTREAM_HEADER_TIMEOUT`, `AISEC_GATEWAY_FORWARD_HEADERS` — те же проверки, что у флагов. Секреты через переменные окружения не передаются: только пути к файлам.

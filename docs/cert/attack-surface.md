# Поверхность атаки

Черновик этапов 0–1. Все внешние интерфейсы продукта: сетевые (порт, протокол, аутентификация), файловые, аргументы CLI, переменные окружения (ТЗ, раздел 9). Обновляется при любом изменении интерфейсов.

## Сетевые интерфейсы
| Компонент | Адрес по умолчанию | Протокол | Аутентификация | Эндпоинты | Этап |
|---|---|---|---|---|---|
| `aisec-gateway` | `127.0.0.1:8443` | HTTPS (TLS 1.2–1.3; HTTP без TLS отвергается) | `GET /healthz`, `GET /readyz` — без аутентификации (только статус). Маршруты приложений — ключ приложения `Authorization: Bearer aisec_…` (ИАФ.8); шлюз без аутентификации не собирается. С `-server` (задача 2.13) до первого исправного пакета конфигурации маршруты приложений и `/readyz` отвечают 503 `config_unavailable` с `Retry-After: 30`, ключи не проверяются; приложение, которое сервер исключил из пакета (часть `unavailable`, В16 ревью 2.r3b), проходит проверку ключа и получает 503 `app_unavailable` на всех маршрутах приложений, у приложения, которого нет в пакете вовсе, — 403 `app_not_configured` | `GET /healthz`, `GET /readyz`, `POST /v1/chat/completions` (в том числе SSE; запрос и ответ проверяются конвейером, в том числе аргументы `tool_calls`), `GET /v1/models` (модели и псевдонимы приложения), `POST /v1/embeddings` (задача 1.24; вход проверяется, ответ — векторы провайдера), `POST /guard/v1/check` (Check API, задача 1.24). Прочее — 404 или 405 в формате ошибок OpenAI; неканонический путь (`//`, `/./`, `/../`, завершающий `/`) — 404, перенаправлений шлюз не выдаёт | 0–1 |
| `aisec-server` | `127.0.0.1:8444` (флаг `-listen`) | HTTPS (TLS 1.2–1.3 из `internal/crypto`; HTTP без TLS отвергается) | `GET`/`HEAD` вне `/api` и `/internal` — статика веб-консоли из `web/dist`, встроенной в бинарник (`index.html` по «/» и файлы `assets/…` по точному пути; без аутентификации, без перечисления каталогов, скрытые файлы и неизвестные пути — 404, остальные методы — 405; заголовки безопасности и строгий CSP как у всех ответов). `GET /healthz`, `GET /readyz` — без аутентификации (только статус; причина сбоя готовности в ответ не попадает). `POST /api/v1/auth/login` — открыт (логин и пароль); `GET`/`POST /api/v1/auth/setup` — открыт (состояние настройки; создание первого администратора только по одноразовому токену из `aisec-cli init` и только пока пользователей нет; необязательные поля `timezone` — имя IANA, до 64 символов, неизвестные имена и имена без «/», кроме `UTC` (`Local`, `posixrules`, `localtime`, `Factory`), отклоняются, база поясов встроена в бинарник, и `retention_mode` — `none`, `masked` или `full`, значения проверяются до погашения токена, задача 2.24b). Остальное — сессия консоли (cookie `__Host-aisec_session`) с проверкой права роли на каждом маршруте; изменяющие запросы сессии — с заголовком `X-CSRF-Token` (значение cookie `__Host-aisec_csrf`, привязано к сессии), без него — 403. Права — по роли пользователя (предустановленной или своей, задача 2.9); разрешение каждого маршрута — `x-permission` в `api/openapi.yaml`, матрица — [`rbac-matrix.md`](rbac-matrix.md); каждый 403 аутентифицированному субъекту пишется в аудит (`access.denied`). Токен API (задача 2.10, ИАФ.9): заголовок `Authorization: Bearer aisec_pat_<8 символов>_<43 символа base64url>` — один заголовок, схема без учёта регистра, до 128 символов, строгий канонический формат; с этим заголовком cookie не проверяется и CSRF не нужен, любой отказ по токену — одинаковый 401 и запись `api_token.auth_failed` (префикс и причина, без секрета); заголовок неверного формата в аудит не пишется (счётчик в техническом журнале), после 10 неудач за минуту с адреса клиента — 15 минут 429 с `Retry-After` без записей, о начале блокировки — одна запись `rate_limited` (В9 ревью 2.r2). Заголовок `Authorization` другой схемы (Basic от прокси) на путь токена не уводит: решает сессия (Н10). Токену доступны только операции, у которых в `api/openapi.yaml` указан `bearerToken`: функции безопасности, свои данные (`self`, `session`) и сами токены — 403; права — пересечение области токена с правами роли владельца. Каждый пропущенный запрос по токену пишет `api_token.used` | Каркас (задача 2.6): `GET /healthz`, `GET /readyz`, `GET /api/v1/system/info` (право `system.read`). Вход и учётные записи (задача 2.7): `GET /api/v1/auth/setup` (`setup_required`), `POST /api/v1/auth/setup` (тело до 8 КиБ: токен `aisec_setup_` + 43 символа base64url, логин, имя, пароль; любой отказ по токену — одинаковый 403), `POST /api/v1/auth/login` (тело до 8 КиБ, только JSON; любой отказ — одинаковый 401), `POST /api/v1/auth/logout`, `GET /api/v1/me` (право `session` — любое состояние сессии), `POST /api/v1/auth/password` (право `self`), `GET`/`PUT /api/v1/auth/policy` (`auth_policy.read`/`.manage`), `GET`/`PUT /api/v1/system/settings` (`system.read`/`settings.manage`; тело до 8 КиБ; часовой пояс показа и режим хранения по умолчанию, `none`/`full` — с паролем или кодом, В26 ревью 2.r5), `GET`/`POST /api/v1/users`, `GET /api/v1/users/{id}` (`users.read`/`.manage`), `POST /api/v1/users/{id}/deactivate`, `/activate`, `/password-reset` (`users.manage`), `GET`/`DELETE /api/v1/users/{id}/sessions` (`sessions.read`/`.manage`; у `DELETE` параметр `revoke_api_tokens` — `true` (по умолчанию) или `false`, иное — 400: отзыв токенов пользователя вместе с сессиями, В8 ревью 2.r2); сброс пароля отзывает и токены API пользователя; назначение уже назначенной роли — 409 (Н13); ответы с временным паролем — только при создании и сбросе. Второй фактор (задача 2.8, ИАФ.5): `POST /api/v1/auth/mfa/setup` (`{"current_password"}` — обязателен из полной сессии, в `mfa_setup` не нужен; ответ — секрет TOTP, ссылка `otpauth://` и матрица QR-кода, один раз), `POST /api/v1/auth/mfa/setup/confirm` (`{"code"}`; ответ — 10 кодов восстановления, один раз), `POST /api/v1/auth/mfa/verify` (ровно одно из `code`, `recovery_code`), `POST /api/v1/auth/mfa/recovery-codes` (`{"code"}`) — право `session`, доступны сессии до второго фактора, состояние проверяет сервис (409 вне своего шага); поля кодов до 64 байт, тело до 8 КиБ; неверный код — 400 и неудачная попытка ИАФ.4. После принятого кода `verify` (и `setup/confirm` из `mfa_setup`) выдаёт новые cookie сессии и CSRF, прежние перестают действовать. `POST /api/v1/users/{id}/mfa/reset` (`users.manage`). Роли (задача 2.9): `GET /api/v1/permissions`, `GET /api/v1/roles`, `GET /api/v1/roles/{id}` (`roles.read`), `POST /api/v1/roles`, `PUT`/`DELETE /api/v1/roles/{id}`, `PUT /api/v1/users/{id}/role` (`roles.manage`; тело до 16 КиБ, ID роли `^[a-z][a-z0-9_]{2,47}$`, разрешения только из каталога, неверный ID в пути — 404); `GET /api/v1/me` отдаёт действующие разрешения. Токены API (задача 2.10): `GET /api/v1/api-tokens`, `GET /api/v1/api-tokens/{id}` (`api_tokens.read`), `POST /api/v1/api-tokens` (`api_tokens.manage`, только сессия с CSRF; тело до 16 КиБ: название, срок 1–365 дней, разрешения и ровно одно из `password` (до 1024 байт) или `code` (до 64 байт) — повторная проверка, неверное значение — 403 `reauthentication_failed` и неудача ИАФ.4 (В8 ревью 2.r2); ответ с самим токеном — один раз, без `Idempotency-Key`), `DELETE /api/v1/api-tokens/{id}` (`api_tokens.manage`; отзыв, не удаление); при области `own` — только свои токены, чужой — 404; неверный ID в пути — 404. После пароля сессия может быть в состоянии `mfa_pending` (5 минут) или `mfa_setup` (15 минут): в них права роли не действуют. Cookie сессии: `__Host-aisec_session` (32 случайных байта base64url, `HttpOnly`, `Secure`, `SameSite=Strict`, `Path=/`, без срока — сессионная; срок контролирует сервер: бездействие 15 минут, не дольше 12 ч) и `__Host-aisec_csrf` (то же без `HttpOnly`). `POST` входа, первичной настройки, второго фактора и смены пароля — строгий предел частоты (10 в минуту с адреса клиента); выход и чтение настроек — по общему правилу. Адрес клиента — адрес соединения; от сетей из `-trusted-proxies` принимается `X-Forwarded-For` (справа налево до первого недоверенного, не дальше 16 адресов), иначе заголовок не учитывается; этот адрес — в аудите, сессиях и ограничителе частоты (замечание В3 ревью 2.r1). Все ошибки — Problem Details (`application/problem+json`, русский `detail`). Неизвестный путь — 404, неверный метод — 405 с `Allow`; неканонический путь под `/api/` и `/internal/` (`//`, `/./`, `/../`, завершающий `/`) — 404 без перенаправления. Тело запроса — до 1 МиБ (маршрут может уменьшить), `Content-Type: application/json`, неизвестные поля отвергаются. Списки — курсорная пагинация (`limit` 1–200, `cursor` до 256 символов, строгий разбор). Создающие запросы — `Idempotency-Key`, кроме `POST /api/v1/users`, `POST /api/v1/api-tokens` и `POST /api/v1/auth/setup`: ответ содержит пароль (временный) или токен API либо создаёт первую учётную запись, и хранилище повторов не должно его запоминать (маршруты с одноразовым секретом помечены `SecretOnce`, маршрутизатор не даёт им `Idempotency-Key`, Н1 ревью 2.r1) — повтор даёт 409 «логин занят» или 403 (1–64 символа `[A-Za-z0-9._-]`, хранится 24 часа, до 10 000 ключей). Ограничение частоты (ЗИ.6) — см. `security-functions.md`. Контроль целостности (задача 2.17): `GET /api/v1/system/integrity` (право `system.read`, последние итоги по компонентам: пути и виды нарушений, без содержимого файлов), `POST /api/v1/system/integrity/verify` (право `integrity.verify` — только у администратора безопасности (задача 2.9); без тела; проверка сериализуется с периодической, предел 2 минуты; при `-integrity-action stop` и нарушении сервер штатно останавливается — проверку по команде может вызвать только обладатель права). «Состояние системы» (задача 2.20): `GET /api/v1/system/status` (право `system.read`, без параметров и тела, только чтение; отвечает версиями, шлюзами, итогами целостности и самотеста, синхронизацией времени, счётчиками отброшенных событий, заполнением журнала аудита, итогом последней проверки цепочки аудита (`audit_chain`), пакетом конфигурации (`bundle`: версия, ETag, полнота, исключённые приложения с причиной, отставшие шлюзы; В16, Н28 ревью 2.r3b) и условиями уведомлений раздела 7 (у ОЦЛ.5 и отставания пакета — список компонентов `components`, В18); тексты ошибок БД в ответ не попадают — недоступный раздел отмечается в `unavailable`; сбор — запросы к БД с таймаутом 3 с и общим пределом 15 с; сервер сам не выходит в сеть: время — `adjtimex(2)` в режиме чтения, без NTP и внешних команд). Пути вне `/api` и `/internal` отдаёт статика веб-консоли (задача 2.21); `/internal/*` на порту консоли — 404. Регистрация шлюзов (задача 2.14): `POST /api/v1/gateways/register` — открыт, тело до 16 КиБ: одноразовый токен `aisec_gwreg_` + 43 символа base64url из `aisec-cli gateway token` и CSR в PEM на ключ ECDSA P-256; неверный CSR — 400 до проверки токена; любой отказ по токену — одинаковый 403; токен неверного формата в аудит не пишется (счётчик в техническом журнале, Н17 ревью 2.r3a); без `-ca-cert` — 503; 10 в минуту с адреса; без `Idempotency-Key` (ответ — выпущенный сертификат). Ответ — время сервера и период heartbeat; при принятом `budget` — `budget: {month, others}`: расход остальных процессов и шлюзов за месяц по приложениям с жёстким бюджетом. `POST /internal/v1/events:batch` (задача 2.15): тело до 8 МиБ, только JSON, 1–500 событий, строгая схема без поля шлюза (шлюз — из сертификата), неизвестные поля — 400; событие: ID — UUIDv7 строчными, время не старше 7 суток и не дальше 5 минут в будущем и от времени в ID, строки до 256 байт, содержимое запроса и ответа до 64 КиБ, находок до 1024 (у находки необязательные `fragment` — 32 шестнадцатеричные цифры — и `exception` — ID исключения по форме, задача 3.22), угроз до 64, без U+0000; необязательный объект `session` (задачи 4.13, 4.14): `id` — 32 hex, `source` — `header` или `fingerprint`, `risk` 0–1, `turns`, для `history.integrity` — `history` (до 64 пар `{message, hash}`), `issued` (до 16 хешей по 32 hex), `history_rule`, `history_action` (`allow`, `log`), `history_severity`; хеши без правила — событие отклоняется; сервер сверяет хеши с `session_replies` (миграция 0053) до записи события и в метаданные события их не пишет; неверное событие отклоняется поштучно (индекс и код в ответе, без текста), в том числе отказ СУБД (код `storage`: пакет записывается заново по одному событию), повтор события по ID не записывается; содержимое `full`, не помещающееся в шифротекст 256 КиБ, обрезается с «…» и отметкой `details.content_truncated` (`truncated` в ответе, В10 ревью 2.r3a); хранилище недоступно — 503 с `Retry-After: 30`, хранилище отвергло счётчики шлюза — 422; общий предел порта — 600 в минуту с адреса. Содержимое событий и тексты ошибок СУБД в технический журнал не пишутся. Прочее — 404/405 Problem Details; маршруты консоли здесь не обслуживаются. `GET /internal/v1/policies/bundle` (задача 2.13): подписанный пакет конфигурации для шлюза из сертификата; обязателен заголовок `AISec-Bundle-Key` — открытый ключ получателя шлюза X25519, ровно 32 байта в base64url без дополнения, один заголовок (иначе 400); `If-None-Match` с ETag применённой версии — 304 без тела и без записи в аудит; пакета ещё нет (ни одна версия не собралась, например содержимое больше предела) — 503 с `Retry-After: 60`; приложение, которое не проходит проверку (политика ссылается на словарь, которого у него нет; провайдер с ошибкой), в версию не входит: его идентификатор, среда и ключи — в части `unavailable` содержимого, остальные приложения получают версию (В16 ревью 2.r3b); готовая версия используется повторно 5 с, сборки идут по одной; ответ — JSON до 8 МиБ, `Cache-Control: no-store`, ETag `"версия"`; учётные данные провайдеров в ответе только шифротекстом HPKE на ключ из заголовка. `POST /internal/v1/policies/bundle/status`: итог применения — тело до 1 КиБ, строгая схема `{result: applied|rejected, version ≥ 0, reason}` (причина — из перечня `too_large`, `format`, `signature`, `gateway_mismatch`, `rollback`, `invalid_content`, `decrypt`, только при `rejected`), неизвестные поля — 400, ответ 204; одинаковые отчёты пишутся в аудит не чаще раза в минуту на шлюз. Ротация (задача 3.3, ADR-0018): заголовок `AISec-Trust-Seq` запроса пакета — номер последнего принятого шлюзом заявления о доверии (один заголовок, целое от 0, до 19 цифр, иначе 400; нет заголовка — прежнее поведение); если он меньше номера сервера, `If-None-Match` не учитывается. В конверте пакета — необязательное поле `trust`: до 8 подписанных заявлений `aisec-trust/1` (каждое до 16 КиБ, подписью пакета не покрыты, проверяются по цепочке от `-bundle-pub` до подписи пакета). Ключ получателя закрепляется за шлюзом; другой ключ в `AISec-Bundle-Key` — 409 `bundle_key_mismatch` (секреты для него не шифруются) и запись `gateway.bundle_key_mismatch` не чаще раза в минуту. Корень сертификата клиента вне заявления о доверии или с истёкшим перекрытием — 401 (`ca_unknown`, `ca_expired` в `gateway.mtls_denied`). Ответ heartbeat — признак `reissue`. `POST /internal/v1/certificate`: перевыпуск сертификата шлюза по CSR (строгая схема `{csr}`, тело до 16 КиБ, CSR — один PEM на ключ ECDSA P-256 с верной подписью, иначе 400; CN — ID шлюза из прежнего сертификата, назначение `clientAuth`); не чаще раза в минуту на шлюз (429 с `Retry-After: 60`); без УЦ — 503; ответ — сертификат PEM и срок; новый сертификат принимается вместе с прежним до первого запроса с ним, затем прежний — нет; аудит `gateway.cert_reissue`. Перевыпуск только при необходимости (3В4 ревью 3.r1): сертификат выдан корнем, который уже не действующий, или до его конца не больше 30 суток; иначе 409 `reissue_not_needed` и `gateway.cert_reissue` с итогом «отказ» (не чаще раза в минуту на шлюз). **Сертификат заказчика для адреса шлюза** (задача 3.27, S1, ТЗ 5.4, решение Р9; `GET`, `PUT`, `DELETE /api/v1/gateway-certificate`, сессия консоли или токен API; `GET` — право `gateway_tls.read`, `PUT` и `DELETE` — `gateway_tls.manage`, только у системного администратора и администратора безопасности):
- **Вход.** `PUT` — JSON `{host, chain_pem, key_pem}`, тело до 160 КиБ, неизвестные поля — 400; `host` — DNS-имя (латиница, цифры, «-», без «*») или IP-адрес без зоны, приводится к нижнему регистру. Цепочка — новый входной формат: только блоки PEM `CERTIFICATE` без данных вне блоков, до 64 КиБ и 10 сертификатов, ключи RSA 2048–8192 бит или ECDSA P-256/P-384 (P-521 — только у УЦ). Ключ — ровно один блок PEM без заголовков и пароля (`PRIVATE KEY`, `RSA PRIVATE KEY`, `EC PRIVATE KEY`), до 16 КиБ, RSA от 2048 бит или ECDSA P-256/P-384. Разбор и проверка — только `internal/crypto` (`ParseServerCert`, fuzz-тест `FuzzParseServerCert`).
- **Проверки до сохранения.** Ключ подходит к сертификату шлюза; имя `host` есть в SAN (CN не учитывается); каждый сертификат цепочки действует сейчас; цепочка доходит до самоподписанного корня из загруженных файлов (системное хранилище не используется), назначение `serverAuth`; лишних сертификатов вне пути нет; если у листа задан `keyUsage`, в нём есть `digitalSignature`; имена владельца и издателя до 2048 символов, серийный номер до 32 байт, имён и адресов до 1000, каноническая цепочка до 64 КиБ. Одиночный самоподписанный сертификат принимается (корень — он сам). Отказ — 400 с причинами по-русски в `errors[]`; без ключа данных — 503.
- **Хранение.** Одна запись на установку (`gateway_tls`, миграция 0039): цепочка в каноническом порядке «шлюз → корень» и сведения о ней открыто, ключ — PKCS#8, зашифрованный ключом данных с AAD `gateway_tls`/`key`/ID организации (ЗИ.1); при `keys rotate-data` перешифровывается. В ответах API — только сведения о сертификате и признак `key_set`; в журнале аудита (`gateway_tls.set`, `gateway_tls.delete`) — имя, отпечаток, кому и кем выдан, срок, без PEM.
- **Передача шлюзам.** Новое поле пакета конфигурации `gateway_tls` (`host`, `chain_pem`, `fingerprint`, `not_after`) в подписанном содержимом и элемент секретов `{"tls_key": …}` в части, зашифрованной HPKE на ключ получателя каждого шлюза; ключ — ровно при наличии раздела. Истёкший сертификат в пакет не попадает. Шлюз повторяет все проверки, сверяет отпечаток и переключает TLS адреса приложений без перезапуска (новые соединения — новая пара); неверный раздел — отказ всего пакета (`invalid_content`), шлюз остаётся на прежних пакете и сертификате; сертификат, истёкший по часам шлюза, — возврат к своему `-tls-cert`; ещё не действующий — в пределах 5 минут допуска часов включается сразу, иначе шлюз на своём сертификате и раз в минуту проверяет раздел снова, переключаясь без перезапуска, когда тот начнёт действовать (новый пакет отменяет ожидание; 3Н43 ревью 3.r3). Отпечаток действующей пары в heartbeat пока не передаётся. Срок проверяется при применении пакета: если сертификат истекает, пока шлюз без связи с сервером, шлюз отдаёт истёкший сертификат до следующего пакета (сервер к сроку собирает пакет без раздела). Шлюз прежней версии пакет с разделом отклоняет: обновлять шлюзы до загрузки сертификата.

**Эталон системного промпта приложения** (задача 4.14, DM-26; `GET`, `PUT`, `DELETE /api/v1/applications/{id}/prompt-baseline`, только сессия консоли, право `applications.policy` — администратор безопасности; отказ — 403 и тест на каждый метод):
- **Вход.** `PUT` — JSON `{text?, mode, password?, code?}`, тело до 1 МиБ, неизвестные поля — 400; `text` — до 128 КиБ, валидный UTF-8, не пустой, без управляющих символов кроме табуляции и переводов строк; `mode` — `block`, `alert` или `off`. `DELETE` — необязательное тело `{password?, code?}` до 8 КиБ. Понижение режима и снятие действующего эталона без пароля или кода — 400 с полем `password`, неверный пароль — 403 `reauthentication_failed`.
- **Хранение и передача.** Текст — только зашифрованным ключом данных (`prompt_baselines`, миграция 0052; AAD места хранения), в журналы и аудит не пишется (в аудите — хеш и размер); `GET` возвращает текст только с правом `applications.policy`. Шлюзам — новый раздел подписанного пакета конфигурации `prompt_baselines`: `[{app, hash, mode}]` (хеш — 64 hex, режим `alert` или `block`; неизвестное приложение, повтор или неверное значение — пакет отклоняется).

**Дашборды консоли** (задача 3.19; `GET /api/v1/dashboards/{overview,threats,pii,consumption,app/{id},stream}`, сессия консоли или токен API, право `dashboards.read`, значение области `own` допускает только `app/{id}` своих приложений):
- **Вход.** Только `GET`; query — закрытый набор `period` (`15m`, `1h`, `24h`, `7d`, `30d`), `from`/`to` (RFC 3339; начало раньше конца, не больше 366 суток; часовой шаг до 31 суток, дальше суточный), `feed=all` (только `overview`), для потока ещё `dashboard` и `app_id`. Неизвестный параметр, повтор, неверное значение — 400; чужое приложение владельцу — 404; без права на все объекты — 403 с записью `access.denied`.
- **Данные.** Почасовые агрегаты (`dash_*`, миграция 0037) без содержимого запросов и ответов: числа, ключи приложений, моделей, детекторов, строк матрицы, псевдонимы пользователей, подразделение, токены и стоимость; «лента решений» — метаданные каждого события (то есть просмотр событий без содержимого), поэтому отдаётся только субъекту с `events.read` на все объекты, иначе `feed: []` и `feed_hidden: true` (администратор системы, владелец приложения; признак входит в ключ кэша снимков, 3В27 ревью 3.r3); карточка с содержимым открывается отдельным запросом событий со своими правами. Короткие периоды (до двух часов) читаются из таблицы событий поминутно. Чтение — с таймаутом 15 с, параметризованным SQL, ограничение «топ» — 50 строк; ряды «Угроз» и «ПДн» отбираются по ключам топа в SQL, суммы ограничены 4e18. Нагрузка (3В28 ревью 3.r3): не больше 2 вычислений снимков на сервер (сверх — 503 с `Retry-After: 5`), одинаковые запросы ждут одно вычисление, свой пул из 2 соединений (поиск и выгрузка событий его не делят). Поток SSE (`GET /api/v1/dashboards/stream`, 3 на субъекта, 100 на сервер): у каждой записи срок 10 с (клиент, переставший читать, освобождает место), предельный срок потока — 1 ч (клиент переподключается с новой проверкой прав), при остановке сервера потоки закрываются сразу (3Н44 ревью 3.r3).
- **Поток SSE** (`stream`, `text/event-stream`): снимок каждые 3 с (период длиннее суток — раз в минуту, длиннее 31 суток — раз в 5 минут), при неизменных данных — комментарий-пинг; права и сессия перепроверяются на каждом тике (отозванная сессия или права закрывают поток); не больше 3 потоков на пользователя или токен и 100 на сервер, сверх — 429. Поток держит соединение открытым, поэтому он продлевает активность сессии (известное свойство, открытый вопрос в `docs/plans/stage-3.md`). Снимки одинаковых запросов общие (кэш на шаг потока, не меньше 2 с, 256 записей; произвольный период — в ключе до минуты).
- **Запись.** Агрегаты пополняются в транзакции приёма событий (хук `events`); пересчёт — под исключительной блокировкой каждого пересчитываемого часа, хук её не ждёт: занятый час или сбой прироста — строка в `dash_dirty_hours` (миграция 0046), пакет принимается сразу, досчёт пересчитывает помеченные часы первыми (3В25 ревью 3.r3); часть досчёта — не больше 6 ч и 100 000 событий, после таймаута — вдвое меньше и пауза прохода; сервер пишет только в свои таблицы под ролью `aisec_app`, отдельных новых портов и файлов нет. `GET /api/v1/alerts` принимает `from` и `to` (RFC 3339, период по времени последнего срабатывания).

**Аутентификация приложений** (задача 1.4 этапа 1, DM-38):
- Ключ — только в `Authorization: Bearer`, схема без учёта регистра, один заголовок, ключ до 128 символов строго формата `aisec_<8 символов>_<43 символа base64url>`. Ключ в строке запроса и в других заголовках не принимается.
- Срок `expires` (ГГГГ-ММ-ДД): ключ действует до 00:00 UTC этой даты (03:00 МСК), сама дата в срок не входит — так же написано в справке `aisec-cli app-key -expires`.
- В режиме с сервером (`-server`) пакет конфигурации несёт, кроме действующих ключей, неистёкшие ключи, отозванные за последние 30 суток (не больше 32 последних на приложение), с полем `revoked: true` (Д-E2E-1, DM-38): шлюз отказывает им с причиной `revoked`, и сервер поднимает оповещение `security.gateway_auth`; позже такой ключ выпадает из пакета и отказ идёт с причиной `invalid`. Без отозванных ключей поле не пишется и байты пакета прежние; шлюз прежней версии (строгий разбор) пакет с полем `revoked` отклоняет — обновлять шлюзы раньше сервера.
- Порядок проверок: формат → SHA-256 предъявленного ключа сравнивается с сохранённым за постоянное время (для неизвестного префикса — с заглушкой, чтобы время не выдавало, существует ли префикс) → отзыв → срок → `allowed_cidrs`. Отзыв, срок и адрес проверяются только после совпадения секрета: иначе по причине отказа можно было бы узнать о существовании префикса.
- Адрес клиента — только из TCP-соединения. `X-Forwarded-For`, `X-Real-Ip`, `Forwarded` не учитываются: доверенных обратных прокси перед шлюзом на этапе 1 нет, а иначе клиент подставил бы любой адрес. IPv4 в записи IPv6 приводится к IPv4.
- Отказ — 401 `invalid_api_key` с одинаковым текстом и `WWW-Authenticate: Bearer` при любой причине; причина, адрес и префикс — только в событии `auth_failure` (ключ туда не пишется). Успешный вход событие не создаёт.
- Ограничение частоты неудач: 10 неудач за минуту с одного адреса IPv4 или сети IPv6 /64 — блокировка на 15 минут. Во время блокировки **неудачи** с адреса получают 429 `auth_rate_limited` с `Retry-After` и событий не создают; о начале блокировки — одно событие с причиной `rate_limited` и одна строка в техническом журнале без адреса (адрес — только в событии). **Действующий ключ проходит и с заблокированного адреса:** иначе одно приложение с отозванным ключом в цикле повторов отключало бы соседей за тем же NAT или исходящим адресом; подбор это не облегчает — секрет 256 бит. Таблица адресов — в памяти, до 65 536 записей; при переполнении вытесняются незаблокированные, а если таблица забита блокировками (например, из множества сетей /64 одной сети /48), неудачи новых адресов учитываются в одном общем счётчике, который блокируется по тем же правилам: ограничение и поток событий остаются ограниченными. Неразобранный адрес клиента (у TCP-соединения не бывает) — тоже общий счётчик.

`POST /guard/v1/check` и `POST /v1/embeddings` (задача 1.24; контракт — `api/openapi.yaml`) после аутентификации:
- **Вход и аутентификация.** Тот же ключ приложения (RBAC шлюза: без действующего ключа — 401 `invalid_api_key`, события обработки нет), те же правила `Content-Type`, размера и времени передачи тела (415, 413, 408), только объект JSON. Проверка идёт до обращения к чему-либо внешнему; Check API провайдеру не обращается вовсе.
- **Check API, запрос.** Строгий разбор: поля `direction` (`input` или `output`), `source` (`user`, `rag`, `tool` для входа; `output` для выхода; `image` и `audio` — 400 `unsupported_parameter` до этапа 5), ровно одно из `text` (непустая строка) и `messages` (до `quotas.max_messages` или 256; роли `system`, `developer`, `user`, `assistant`, `tool`; `content` — непустая строка, частей нет), необязательное `user` (до 256 байт). Неизвестное поле, данные после объекта, неверный тип — 400.
- **Check API, ответ.** 200 с решением (`decision` — что сделано, `action` — как в `enforce`, `blocked`), находками детекторов политики (детектор, категория, оценка, байтовые смещения в исходном тексте, место, строка матрицы; находки детекторов маскирования для хранения в ответ не входят) и преобразованным текстом либо сообщениями; найденное значение в ответ не попадает, при блокировке преобразованного текста нет. Сбой проверки при `fail_closed` — 503 `check_unavailable`; при `fail_open` ответ помечается `incomplete`. `pseudonymize` политики выполняется как `redact`. Заголовки `X-AISec-Event-Id` и `X-AISec-Decision` — как у чата.
- **Check API, пределы.** Отдельного предела на `text` нет, кроме размера тела (`max-body-bytes`) и квоты `max_input_bytes`; общий срок проверки — не больше минуты. Направление без правил политики — ответ с `unchecked: true`. Ответы 501 и ошибки разбора событий не создают (как в чате).
- **Check API, событие.** Тип `check`: источник (`user`, `rag`, `tool`, `output`), решение, находки, трассировка; в режиме хранения `masked` содержимое пишется замаскированным (`content.request` для входа, `content.response` для выхода). Квоты: частота и размер входа считаются, токены модели — нет.
- **Эмбеддинги, запрос.** Строгая модель: `model`, `input` (строка или до 256 непустых строк; массивы токенов — 400), `encoding_format` (только `float`), `dimensions` (1–65536), `user`. Тело к провайдеру собирается заново; `encoding_format: float` указывает шлюз. Поле `user` внешнему провайдеру не передаётся.
- **Эмбеддинги, проверка и ответ.** Каждая строка `input` — фрагмент с местом `input[i]` и источником `user`, конвейер как у чата с `endpoint=embeddings`: допустимы `redact` и `block` (блокировка — 400 `policy_violation`). Модель — разрешённая или псевдоним (иначе 404 `model_not_found`, DM-33). Ответ провайдера разбирается и собирается заново: ровно по вектору на строку, индексы по порядку, не больше 65536 чисел в векторе, только числа (base64 — 502 `upstream_bad_response`), неизвестные поля отбрасываются; `model` — имя из запроса. Провайдер без эмбеддингов (GigaChat, YandexGPT на этапе 1) — 501 `embeddings_not_supported`, событие не создаётся. Событие — `gateway_request`, расход токенов — из `usage` ответа.

`POST /v1/chat/completions` после аутентификации:
- **Вход.** Только `Content-Type: application/json` (иначе 415); тело не больше `max-body-bytes` (иначе 413), передано не дольше 30 с (иначе 408) и только объект JSON (иначе 400). Всё это проверяется до обращения к провайдеру.
- **Разбор запроса** (`internal/chat`, задача 1.5). Строгая модель: верхний уровень — только `model`, `messages`, `stream`, `stream_options`, `max_tokens`, `max_completion_tokens`, `temperature`, `top_p`, `n` (только 1), `stop`, `presence_penalty`, `frequency_penalty`, `logit_bias`, `response_format`, `seed`, `tools`, `tool_choice`, `parallel_tool_calls`, `user`, `reasoning_effort`. Любое другое поле — 400 `unsupported_parameter`: в том числе `metadata`, `prediction`, `audio`, `modalities`, устаревшие `functions`/`function_call` — через них текст ушёл бы провайдеру мимо проверок; `logprobs` и `top_logprobs` — в них ответ повторяется по токенам в обход маскирования ответа. Роли — `system`, `developer`, `user`, `assistant`, `tool`; части — `text`, `refusal` (только `assistant`), `image_url`, `input_audio`, `file`, `video_url` (только `user`); неизвестный тип части — 400. Диапазоны чисел, имена функций и идентификаторы — по шаблонам; схемы JSON (`tools[].function.parameters`, `response_format`) — объект до 256 КиБ.
- **Пересборка.** Провайдеру уходит тело, собранное заново из разобранной модели, а не исходные байты. Повторные ключи JSON, ключи в другом регистре и неизвестные поля до провайдера не доходят: провайдер получает ровно то, что видели проверки.
- **Нетекстовые части** (DM-14). Шлюз их не декодирует: знает вид (изображение, аудио, файл, видео), способ передачи (данные `data:…;base64` или ссылка `https://`, у файла — ещё `file_id` провайдера) и длину данных; длина проверяется сразу (по умолчанию до 20 МиБ на часть, иначе 400 `media_too_large`). Ссылку загружает провайдер, поэтому `http:` и другие схемы (`file:`, `ftp:` и т. п.) — 400: иначе через провайдера можно было бы обратиться к внутренним адресам его контура. Обработка по параметру политики `non_text` (в том числе запрет ссылок) — задача 1.19. Имя файла (`file.filename`) — текстовый фрагмент для детекторов.
- **Лимиты** (DM-15): до 256 сообщений (или `quotas.max_messages` приложения), 64 частей и 64 вызовов инструментов в сообщении, 128 инструментов; `max_tokens` — не больше `quotas.max_tokens` приложения (400 `max_tokens_exceeded`).
- **Маршрутизация** (задача 1.7, DM-33). Приложение запроса известно по ключу; провайдер — из его карточки. Модель запроса — разрешённая модель приложения или его псевдоним (заменяется моделью провайдера). Иначе — 404 `model_not_found` до обращения к провайдеру, без перечня разрешённых моделей в ответе; перечень — в `GET /v1/models` с ключом приложения.
- **Описания инструментов** `tools[].function.description` проверяются детекторами политики и маскируются, как текст сообщений (задача 1.22, решение владельца 20.10.2026). **Не проверяется на этапе 1:** схемы JSON (`tools[].function.parameters`, `response_format.json_schema`; передаются провайдеру как есть, в том числе с повторными ключами внутри схемы) — их задаёт приложение, а не пользователь; стоп-последовательности `stop` (до 4 строк по 256 байт).
- **Поле `user`** внешнему провайдеру не передаётся: там часто e-mail или ФИО.
- **Пользователь** (задача 1.22): по `user_from` приложения — заголовок `X-AISec-User` (один, до 256 байт, валидный UTF-8 без управляющих символов, иначе 400 `invalid_user`), поле `user` или никак. В событие и счётчики квот попадает только псевдоним — HMAC идентификатора на ключе `gateway.user_hmac_key_file` (`internal/crypto`), первые 16 байт в hex; без ключа шлюз с `user_from` не header/field не запускается.
- **Сессия** (задачи 4.13, 4.14 этапа 4, DM-06, DM-03): необязательный заголовок `X-AISec-Session` — один, до 128 байт, только `[A-Za-z0-9._:-]`, иначе 400 `invalid_session` с постоянным текстом без эха значения; без заголовка — отпечаток начала диалога (до 8 сообщений до первой реплики пользователя и псевдоним пользователя). Провайдеру заголовок не передаётся; в событие и состояние шлюза попадает только псевдоним — HMAC на ключе псевдонимов с разделителем назначения и ID приложения, 32 hex. Состояние `session.risk` — в памяти шлюза, до 100 000 сессий, срок 24 ч, вытеснение самых старых: заголовок с новыми значениями не увеличивает память сверх предела.
- **Агент и вызовы функций** (задача 4.10 этапа 4, ADR-0023, разделы 1 и 5, DM-22): у приложения с агентами — необязательный заголовок `X-AISec-Agent` (один, до 64 байт, slug агента), не совпавший с агентом ключа или не называющий агента приложения — 403 `agent_mismatch`, отключённый агент — 403 `agent_disabled`, текст постоянный, без эха значения; приложение без агентов заголовок не проверяет. Провайдеру заголовок не передаётся. При разделе `tools` в политике вызовы функций (`tool_calls`) ответа модели проверяются политикой вызовов; `require_approval` удерживает ответ до решения дежурного (все вызовы ответа вместе — не дольше 5 мин и до 30 с на ответ сервера), поток держится комментариями SSE `: aisec-approval-pending` каждые 15 с (при `response_check: buffered` и без потока — без keep-alive), вызовы отдаются только после решения; отказ — 400 `policy_violation` или обрыв потока с сообщением правила.
- **Эталон системного промпта** (задача 4.14, DM-26): начальные сообщения `system`/`developer` сравниваются по хешу нормализованного текста с хешем из пакета конфигурации; расхождение — находка, при режиме `block` — 400 `policy_violation`, как у правил политики.
- **Конвейер проверки** (задача 1.22, ТЗ, 4.3): модель (DM-33) → жёсткий бюджет приложения (DM-15, задача 3.18; только chat/completions и embeddings: расход месяца в часовом поясе установки — свой процесса и остальных из ответа heartbeat — не меньше бюджета → 429 `budget_exceeded` с `Retry-After` до начала следующего месяца, правило `budget.hard` в событии, до провайдера не доходит; модель без цены — расход «не определён», запрос не отклоняется) → квоты (DM-15, DM-36; отказ 429 `quota_exceeded`, `Retry-After`, если повтор возможен) → детекторы политики по каждому текстовому фрагменту, параллельно, со сроком по длине текста → решение политики → псевдонимизация (`[[ТИП_N]]`) и маскирование (`[[ТИП]]`, задача 1.23). Блокировка — 400 `policy_violation` с безопасным сообщением политики без названий детекторов; сбой детектора при `fail_closed` — 503 `check_unavailable`. Каждый разобранный запрос создаёт событие `gateway_request` (ошибки разбора и тела — нет).
- **`max_tokens`:** если у приложения задана квота `quotas.max_tokens`, а в запросе предела нет, шлюз подставляет квоту.
- **Строка запроса** клиента провайдеру не передаётся и в журнал не пишется.
- **Заголовки к провайдеру** формирует шлюз: `Content-Type`, `Accept`, `User-Agent: aisec-gateway`, `Authorization` с ключом провайдера. Заголовки приложения провайдеру не передаются вовсе.
- **Ответ провайдера** разбирается и собирается заново (`internal/chat`): неизвестные поля (например, `reasoning_content`, `logprobs`) приложению не уходят; вариант ответа — ровно один (индекс 0), иначе 502 `upstream_bad_response`; поле `model` — имя, которое запросило приложение. Ответ без потока — до 16 МиБ. Поток SSE (`internal/sse`): строка до 1 МиБ, событие до 4 МиБ, данные потока в сумме до 16 МиБ; каждая часть разбирается, служебные события и комментарии провайдера не передаются; ошибка или обрыв потока — событие `data: {"error": …}` без завершающего `[DONE]`.
- **Проверка ответа** (задача 1.23, ТЗ, 5.1): выходные правила политики проверяют `content`, `refusal` и аргументы `tool_calls`. Ответ без потока и `response_check: buffered` — проверяется целиком до отправки: блокировка — 400 `policy_violation`, сбой при `fail_closed` — 503 `check_unavailable` (в `buffered` вместо потока приходит обычный ответ с ошибкой). `incremental` — текст приходит с задержкой (после каждых 512 байт проверки, без последних 256 байт и недописанного слова), вызовы инструментов — одной частью в конце; блокировка обрывает поток событием `data: {"error": {"code": "policy_violation", …}}` без `[DONE]`. `monitor` (и при режиме политики `monitor`) — части уходят сразу. Псевдонимы запроса в ответе заменяются исходными значениями во всех режимах; в потоке начало возможного псевдонима задерживается не больше чем на 49 байт.
- **Сроки ответа провайдера** (план этапа 1, Р11): общий срок ответа, в том числе чтение тела и весь поток, — `response_timeout` провайдера (по умолчанию 10 мин); пауза между событиями потока — `stream_idle_timeout` (по умолчанию 60 с). Превышение — 504 `upstream_timeout` или событие ошибки в потоке.
- **Заголовки к приложению:** только `Content-Type`, `X-AISec-Event-Id` (ID события) и `X-AISec-Decision` (что сделано с запросом, а у ответа без потока и `buffered` — и с ответом: `allow`, `redact`, `pseudonymize` или `block`; что было бы в `enforce`, видно только в событии) шлюза и `Retry-After`, `X-Ratelimit-*` провайдера (значения до 128 символов без управляющих).
- **GigaChat** (задача 1.8, `internal/providers/gigachat.go`). Шлюз получает токен доступа по ключу авторизации (`POST auth_url`, `Authorization: Basic`, `RqUID` — случайный UUID из криптопрофиля, форма `scope`), кеширует его до истечения (обновляет за минуту до срока; срок вне 0–24 ч считается 30 мин) и передаёт API как `Bearer`; на 401 от API токен обновляется и запрос повторяется один раз. Ключ и токен — только в памяти шлюза: в журнал, приложению и в тексты ошибок не попадают (фрагменты вырезаются). Запрос переводится в формат GigaChat (`developer` → `system`, `tool_calls` → `function_call` с аргументами-объектом, `tool` → `function`, `tools` → `functions`), ответ — обратно (идентификаторы ответа и вызовов — случайные). Параметры без аналога (`stop`, `response_format`, `seed`, `logit_bias`, штрафы, `reasoning_effort`, `tool_choice: required`), нетекстовые части и несколько вызовов в одном сообщении — 400 `unsupported_parameter` до обращения к провайдеру. `temperature: 0` передаётся как 0,001 (GigaChat принимает только больше 0). Форматы — по публичной документации; проверка на настоящей учётной записи — до пилота (Р8).
- **YandexGPT** (задача 1.9, `internal/providers/yandexgpt.go`, Foundation Models API, метод `completion`). Авторизация — API-ключ сервисного аккаунта (`Authorization: Api-Key`), каталог — заголовком `x-folder-id`; модель — `gpt://<folder_id>/<модель из запроса>`, сам каталог приложение не задаёт. IAM-токены не поддерживаются (нужна подпись JWT в `internal/crypto` — отдельная задача). Запрос переводится в формат API (`developer` → `system`, `tool_calls` → `toolCallList` с аргументами-объектом, `tool` → `toolResultList`, `max_tokens` → `maxTokens`), ответ — обратно по статусу альтернативы. Поток — строки JSON (до 16 МиБ каждая) с накопленным текстом: приложению уходит приращение; часть, которая не продолжает предыдущую, данные после финальной части и обрыв без финальной — ошибка потока. Параметры без аналога (`stop`, `response_format`, `seed`, `top_p` ≠ 1, `logit_bias`, штрафы, `reasoning_effort`, `tool_choice` кроме `auto`/`none`, `temperature` > 1), нетекстовые части — 400 `unsupported_parameter`. Ключ в журнал и тексты ошибок не попадает. Форматы — по публичной документации; проверка на учётной записи — до пилота (Р8).
- **Ошибки провайдера.** Код, тип и код ошибки — от провайдера (тип и код — только короткие идентификаторы), текст — до 500 символов без управляющих; если в тексте фрагмент ключа провайдера (от 8 символов), текст заменяется общим. 401 и 403 от провайдера — отказ ключу шлюза, а тело может содержать часть ключа: вместо них 502 `upstream_auth_error` без тела провайдера. Коды 3xx (перенаправления не выполняются) и прочие — 502. Ошибки связи — 502 `upstream_unavailable` или 504 `upstream_timeout` без внутренних подробностей; в журнал — класс ошибки и идентификатор провайдера.
- **Разрыв соединения клиентом** отменяет запрос к провайдеру.

**Исходящие соединения шлюза:** только на `base_url` провайдеров из файла конфигурации и, для GigaChat, на адрес выдачи токена `auth_url` (по умолчанию `https://ngw.devices.sberbank.ru:9443/api/v2/oauth`) — allowlist, ЗИ.3; только `https`; перенаправления не выполняются; переменные `HTTP_PROXY`/`HTTPS_PROXY` не используются; TLS с доверием только корневым сертификатам из `ca_file` провайдера; таймауты на соединение (по умолчанию 10 с) и до заголовков ответа (60 с). С `-server` — ещё внутренний API сервера управления (heartbeat, при остановке — heartbeat `stopping` не дольше 3 с; пакеты событий и пакеты конфигурации — опрос раз в 30 с, пауза при ошибках до 5 мин, таймаут получения пакета 60 с, ответ до 8 МиБ) по mTLS с доверием только `-server-ca`, без прокси, таймаут 10 с на попытку; пакет событий — до 3 попыток, затем очередь в памяти (10 000 событий) с повтором через 1–30 с, сверх — отброс со счётчиком.

**Исходящие соединения сервера управления — каналы уведомлений** (задача 3.13, Р4, ADR-0020 п. 9 и 13; `internal/notify` в `NET_CLIENT_ALLOWED`): только на узлы и адреса, которые администратор безопасности задал в канале (ЗИ.3); других исходящих соединений сервер, кроме PostgreSQL, не открывает. Почта — SMTP на `host:port` (по умолчанию 587), STARTTLS обязателен: без него — отказ до передачи пароля и письма; AUTH PLAIN только внутри TLS. Webhook — `POST` только по `https://`, перенаправления не выполняются (3xx — ошибка), тело ответа читается не больше 64 КиБ, заголовки ответа — до 64 КиБ, HTTP/1.1 без повторного использования соединения; заголовок `AISec-Signature: t=<unix>,v1=<hex>` (MAC профиля от `t.тело`). Syslog — TCP с TLS (RFC 5425) на `host:port` (по умолчанию 6514), одна запись RFC 5424 с фреймингом octet counting на соединение. Для всех: доверие только корневым сертификатам `ca_pem` канала (системное хранилище не используется), проверка имени узла, `*tls.Config` из `internal/crypto`; переменные `HTTP_PROXY`/`HTTPS_PROXY` не используются; срок одной попытки — 30 с (соединение, TLS, обмен); до 5 попыток с задержкой 30 с, 2, 8, 10 минут; содержимого запросов и секретов в уведомлениях нет. **Запрещённые адреса** (3Н31 ревью 3.r2): имя узла канала разрешает сервер при каждом соединении, и соединение идёт только на проверенный адрес, поэтому подмена записи DNS не обходит проверку; хотя бы один запрещённый адрес в ответе — отказ: loopback, link-local (в том числе 169.254.169.254), групповые и неуказанные адреса и адреса метаданных облака (`fd00:ec2::254`, `100.100.100.200`; IPv4 в NAT64 `64:ff9b::/96` проверяется как IPv4) отклоняются с кодом `config` до соединения. Исключения задаёт администратор сервера флагом `-notify-allowed-networks` (переменная `AISEC_SERVER_NOTIFY_ALLOWED_NETWORKS`): сети CIDR через запятую, по умолчанию пусто. Ответ тестовой отправки обобщает отказ соединения, тайм-аут, ошибку TLS и записи до кода `unreachable`, чтобы канал не служил сканером портов внутренней сети. Обоснование размещения клиента в сервере: каналы — функция сервера управления (ТЗ 5.6), шлюз ничего не отправляет во внешние системы, кроме провайдеров LLM. **Передача журнала аудита в SIEM** (задача 3.14, РСБ.6, ADR-0020 п. 15): каналы syslog и webhook с подпиской `audit_stream` получают записи журнала аудита в канонической форме с хешем (подробности — как записаны, без секретов и содержимого запросов). Syslog — до 200 записей RFC 5424 (MSGID `audit`, одна запись — до ~20 КиБ, приёмник должен принимать сообщения от 64 КиБ) по одному соединению TLS; webhook — подписанный `POST` до 1 МиБ (`{"type":"audit","records":[{"record","hash"}…]}`). Проход раз в 10 секунд, срок одной попытки — 30 с, повторы без окончательного отказа с задержкой до 10 минут; адрес и корневые сертификаты — те же, что задал администратор в канале.

**Вход в консоль через внешний IdP по OpenID Connect** (задача 4.17, ТЗ 5.14, ИАФ.7, ADR-0025; `internal/auth/oidc`, `internal/auth/idp.go`, `internal/auth/oidc_login.go`, `internal/api/oidc.go`, миграция 0051):
- **Открытые эндпоинты.** `GET /api/v1/auth/oidc` — только признак и название кнопки «Войти через …». `GET /api/v1/auth/oidc/start` — переход браузера: создаёт одноразовый вход (в БД — только хеш 32 случайных байт, не больше 10000 незавершённых на организацию, срок 10 минут), выдаёт cookie `__Host-aisec_oidc` (HttpOnly, Secure, SameSite=Lax, Path=/, Max-Age 600) и отвечает 303 на `authorization_endpoint` IdP с `state`, `nonce` и PKCE S256 (`code_challenge`); значения выводятся из cookie хешем профиля с разными метками и в БД не хранятся. `GET /api/v1/auth/oidc/callback` — адрес возврата: cookie до 64 байт, строка запроса до 8 КиБ, используются только `state`, `code`, `error`; вход гасится до проверок (`DELETE … RETURNING`, повтор и параллельный возврат не проходят), `state` сверяется за постоянное время, код меняется на токены, ID-токен проверяется, cookie входа удаляется всегда. Успех — cookie сессии (как при входе по паролю, SameSite=Strict) и 303 на `/`; любой отказ — 303 на `/?oidc=denied|failed|unavailable`, причина только в журнале аудита (`auth.login_failed`, `method: oidc`), текст ошибки IdP наружу и в журналы не попадает (в аудит — код `error`, если он из безопасного набора символов). Отдельное ограничение частоты для `/api/v1/auth/oidc/` — 20 GET в минуту с адреса.
- **Настройки.** `GET /api/v1/auth/idp` (`auth_idp.read`), `PUT` и `DELETE /api/v1/auth/idp` (`auth_idp.manage`, право безопасности — только администратор безопасности); `PUT` — тело до 128 КиБ, неизвестные поля — 400; изменение и удаление всегда требуют повторной проверки паролем или кодом TOTP локальной учётной записи (внешняя — 403). Поля: `issuer` (https, без учётных данных, параметров и фрагмента, до 512 символов), `client_id` (печатные ASCII до 256), `client_secret` (печатные ASCII до 1024; пустой — оставить прежний, но при смене `issuer` или `ca_pem` обязателен; хранится шифротекстом под ключом данных, AAD `oidc_settings|client_secret|<org_id>`, в ответах и журналах не показывается, перешифровывается `aisec-cli keys rotate-data`), `console_url` (https, без пути — из него строится `redirect_uri`; заголовок Host запроса не используется), `ca_pem` (корни TLS IdP до 64 КиБ; системные корни не используются), `scopes`, `groups_claim`, `required_acr`, `required_amr` (до 16 значений), до 200 строк «группа → роль». Сохранение завершает сессии внешних пользователей; при `enabled` сервер сначала проверяет IdP (discovery и JWKS).
- **Исходящие соединения сервера к IdP** (единственный сетевой клиент вне шлюза и каналов уведомлений; `NET_CLIENT_ALLOWED` дополнен только пакетом `internal/auth/oidc`): только к узлу `issuer` из настроек — discovery `<issuer>/.well-known/openid-configuration` (поле `issuer` совпадает точно, `authorization_endpoint`, `token_endpoint`, `jwks_uri` — https на том же узле и порту), JWKS и обмен кода (`client_secret_basic`, `grant_type=authorization_code`, `code` до 2048 байт, `code_verifier`). TLS из `internal/crypto` с корнями из настроек; без прокси, без перенаправлений, без keep-alive; каждый запрос — с контекстом и таймаутом 10 с; ответ до 64 КиБ, `Content-Type: application/json`. Адреса после разрешения имени проверяются: loopback, link-local (в том числе метаданные облака 169.254.169.254), multicast, неуказанный адрес, метаданные облака fd00:ec2::254 и 100.100.100.200 запрещены, адрес IPv4 внутри NAT64 (`64:ff9b::/96`) проверяется по тем же правилам; частные сети разрешены (IdP заказчика обычно в них); соединение идёт на проверенный адрес. Метаданные кешируются на час; JWKS перечитывается при неизвестном `kid` не чаще раза в минуту; запросы к IdP идут по одному (ожидание прерывается контекстом запроса), сетевой отказ или таймаут кешируется на 5 с, чтобы недоступный IdP не занимал обработчики.
- **Формат ID-токена** (`internal/crypto/jwt.go`, разбор — только в профиле `standard`; в `gost` вход через IdP недоступен): компактный JWS до 16 КиБ, ровно три части base64url без заполнения, заголовок и утверждения — JSON-объекты до 8 КиБ без повторяющихся ключей, глубина до 16; `alg` — RS256 (модуль 2048–8192 бит), ES256 (P-256, подпись r‖s 64 байта) или EdDSA (Ed25519), тип ключа совпадает с `alg`; `none`, HS*, PS*, `crit`, `typ` кроме `JWT` отвергаются. JWKS до 64 КиБ и 32 ключей; ключи `use` ≠ `sig`, `oct` и неизвестных типов пропускаются, неверный ключ или повтор `kid` отвергают весь набор. Утверждения: `iss` — точное совпадение, `aud` содержит `client_id` (при нескольких — `azp` равен `client_id`), `exp` с допуском 60 с, `iat` не старше 10 минут и не из будущего, `nbf`, `nonce` (сравнение за постоянное время), `sub` 1–255 байт без управляющих символов; группы — до 256 строк до 256 байт, `amr` — до 32 значений.

**Вход в консоль через каталог LDAP** (задача 4.16, ТЗ 5.14, ИАФ.7, ADR-0025, раздел 2; `internal/auth/ldap`, `internal/auth/ldap_settings.go`, `internal/auth/ldap_login.go`, `internal/api/ldap.go`, миграция 0055):
- **Вход.** Новых открытых эндпоинтов нет: пользователь каталога входит обычной формой `POST /api/v1/auth/login`. Если локальной учётной записи с этим логином нет (или запись — из каталога) и вход через каталог включён, сервер проверяет пароль в каталоге; локальная запись с тем же логином всегда имеет приоритет. Логин — по правилам формы входа, пароль 1–1024 байт; пустой пароль отклоняется до обращения к каталогу. Отказы каталога наружу — обычное «Неверный логин или пароль» (401), причина — в аудите (`auth.login_failed`, `method: ldap`, причины `wrong_password`, `unknown_login`, `ldap_ambiguous`, `ldap_identity`, `ldap_unavailable`, `group_conflict`, `no_role`, `deactivated`). Путь каталога тоже проверяет пароль с фиктивным хешем Argon2id (время ответа не меньше локального). Неверные пароли каталога не увеличивают счётчик блокировки консоли (блокирует сам каталог по своей политике), ограничение частоты формы входа действует как прежде; второй фактор консоли — как у локальных записей.
- **Настройки.** `GET /api/v1/auth/ldap` (`auth_idp.read`), `PUT` и `DELETE /api/v1/auth/ldap` (`auth_idp.manage`, только администратор безопасности); `PUT` — тело до 128 КиБ, неизвестные поля — 400; изменение и удаление требуют повторной проверки паролем или кодом TOTP локальной учётной записи (внешняя — 403). Поля: `url` (`ldaps://узел[:порт]` или `ldap://узел[:порт]` только со StartTLS, без DN и параметров, до 512 символов), `ca_pem` (корни TLS каталога до 64 КиБ; системные корни не используются), `bind_dn`, `user_base_dn`, `group_base_dn` (DN до 1024 символов, разбор по RFC 4514), `bind_password` (до 1024 символов без управляющих; пустой — оставить прежний, но при смене `url`, `ca_pem` или `bind_dn` обязателен — 400; шифротекст под ключом данных, AAD `ldap_settings|bind_password|<org_id>`, в ответах, аудите и журналах не показывается, перешифровывается `aisec-cli keys rotate-data`), `user_filter` (фильтр RFC 4515 до 512 символов с `{login}` только в позиции значения), `id_attribute` (`entryUUID`, `ipaUniqueID`, `nsUniqueId`, `objectGUID`), `display_attribute`, `group_mode` (`member_of`, `member`, `ad_nested`), до 200 строк «DN группы → роль». При `enabled` сервер сначала проверяет каталог (TLS, bind сервисной записи, наличие веток); сохранение и удаление завершают сессии пользователей каталога (`ldap_changed`).
- **Исходящие соединения сервера к каталогу** (`NET_CLIENT_ALLOWED` дополнен пакетом `internal/auth/ldap`; библиотека `go-ldap/ldap/v3` разрешена линтером только в нём): только к узлу и порту из `url`. `*tls.Config` из `internal/crypto` с корнями из настроек и проверкой имени узла; LDAPS — рукопожатие `ClientTLS` из `internal/crypto`, для `ldap://` — StartTLS до любого bind (рукопожатие выполняет библиотека через `crypto/tls` с той же конфигурацией), отказ StartTLS — отказ входа. Адрес проверяется после разрешения имени по правилам, общим с IdP (loopback, link-local, multicast, неуказанный, метаданные облака запрещены, NAT64 разворачивается), соединение идёт на проверенный адрес. На каждый вход — два соединения: сервисная запись ищет пользователя (область — поддерево `user_base_dn`, не больше 2 записей) и его группы (не больше 1000), затем отдельный simple bind DN пользователя с его паролем. NTLM, DIGEST-MD5, SASL, анонимный и неаутентифицированный bind запрещены линтером (forbidigo), как и функции `ldap.Dial*` и отладка соединения. Каждая операция — с контекстом и сроком 10 с, ответ читается не больше 1 МиБ на соединение, пакет BER — до 2 МиБ, одновременно не больше 16 проверок (остальные — отказ «каталог недоступен»).
- **Формат ответов каталога.** Разбор BER — библиотекой `go-asn1-ber`; из записей берутся только запрошенные атрибуты: идентификатор (UUID-строка или `objectGUID` 16 байт, приводится к hex), отображаемое имя (до 1024 байт, без управляющих символов), DN групп. Наши разборщики фильтров, DN и идентификаторов покрыты `FuzzUserFilter`, `FuzzGroupFilter`, `FuzzEntryID`, `FuzzSameDN`.
- **Хранение.** Таблицы `ldap_settings` и `ldap_group_roles`, источник учётной записи `ldap` (`users.auth_source`), причина отзыва сессий `ldap_changed` (миграция 0055). Настройки каталога в резервную копию пока не входят.

**E-mail учётной записи** (задача 4.6, `internal/auth`, `internal/api/users.go`, миграция `0057_user_email.sql`): необязательное поле `email` у пользователя (до 254 символов, `net/mail` без отображаемого имени, одна «@», без пробелов и управляющих символов — защита от подмены заголовков письма; проверочное письмо не отправляется). `PUT /api/v1/users/{id}/email` — право `users.manage`, роль записи не сильнее роли вызывающего (УПД.2, иначе 403 и запись `user.email_set` с отказом); `PUT /api/v1/me/email` — право `self`, меняется только своя запись (идентификатор из сессии), токеном API не вызывается; тело не больше 16 КиБ, пустая строка убирает адрес. Поле выдаётся в `GET /api/v1/users`, `/users/{id}` и `/me` (читателям `users.read`). Адрес — персональные данные: в журнал аудита пишется только факт изменения (`user.email_set`: `self`, `cleared`, `changed`), в технические журналы адрес не попадает.

**Отчёты и рассылка** (задачи 3.24 и 3.25, ТЗ 5.8, S10, решения Р5 и Р6; `internal/reports`, `internal/api/reports.go`, сессия консоли или токен API):
- `GET /api/v1/reports/{kind}` (`summary`, `incidents`, `pilot`; параметры `format` — `html`, `csv`, `xlsx`, `delimiter` — `semicolon` (по умолчанию) или `comma`, только с `format=csv` (задача 4.6; иное значение — 400), `from`, `to`, `app`; неизвестный или повторный параметр — 422). Право `reports.read`; владелец приложения (`ScopeOwn`) получает только сводный отчёт по своему приложению, чужое — 404. Период — дни в часовом поясе установки, не длиннее 366 суток; без `from` и `to` — последние 30 суток, одна дата без другой — 400 (3Н46 ревью 3.r4). Отчёт строится из агрегатов и отметок: содержимого запросов и ответов в нём нет. Запись `data.export` — до выдачи данных, не записалась — 503; не больше одной выгрузки на пользователя и двух на сервер (429). CSV: UTF-8 с BOM, разделитель «;» или «,» (значение из белого списка, в файл попадает один байт `;` или `,`), все поля в кавычках, защита от формул (`events.CSVCell`) при обоих разделителях. XLSX собирает сам сервер (`archive/zip`, `encoding/xml`): текстовые и числовые ячейки, без формул, макросов, внешних связей и картинок. HTML — страница без скриптов и внешних ресурсов с политикой `default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'self'`; консоль показывает её в `iframe sandbox=""`.
- `GET`, `POST /api/v1/report-schedules`, `GET`, `PUT`, `DELETE /api/v1/report-schedules/{id}`, `GET /api/v1/report-schedules/{id}/runs`. Права `reports.schedules.read` и `reports.schedules.manage` (только `security_admin` и `system_admin`); тело не больше 16 КиБ; не больше 50 расписаний; изменение — по версии (409 при расхождении). `GET /api/v1/report-channels` (`reports.schedules.manage`, 3Н46 ревью 3.r4) — включённые почтовые каналы с получателями, только ID и название: администратор системы выбирает канал без права `notify_channels.read`, адреса и настройки сервера ему не видны. Задача 4.6: в теле расписания необязательное поле `recipient_user_ids` (до 20 UUID пользователей без повторов); `GET /api/v1/report-recipients` (`reports.schedules.manage`) — активные пользователи с `reports.read` на все объекты и с правами на разделы отчёта не уже, чем у вызывающего: ID, логин, имя и признак `has_email`, адреса не выдаются.
- Исходящая почта: встроенный планировщик сервера (раз в минуту) ставит рассылку в очередь `report_runs`; письмо с отчётом во вложении уходит через почтовый канал `internal/notify` на получателей канала и адрес SMTP, заданные администратором и на адреса пользователей консоли из расписания (задача 4.6: берутся из учётной записи в момент отправки; деактивированные, без права на отчёты и без адреса пропускаются, число пропущенных — в журнале запуска, адрес в журнал доставки не пишется; других адресов нет; общий предел — 40 получателей). До 5 попыток с задержкой 30 с · 4^(n−1), не больше 10 минут; в журнале запуска — код ошибки без текста ответа сервера. Новых портов, переменных окружения и аргументов нет. Миграции `0041_report_schedules.sql`, `0058_report_user_recipients.sql`.

**Реестр агентов, MCP-серверов и инструментов** (задача 4.8, ADR-0023, раздел 1; `internal/agents`, `internal/api/agents.go`, сессия консоли или токен API; контракт — `api/openapi.yaml`, права — `docs/cert/rbac-matrix.md`):
- **Эндпоинты.** `GET`, `POST /api/v1/agents`, `GET`, `PUT`, `DELETE /api/v1/agents/{id}`; `GET`, `POST /api/v1/mcp-servers`, `GET`, `PUT`, `DELETE /api/v1/mcp-servers/{id}`, `PUT /api/v1/mcp-servers/{id}/credentials`, `PUT /api/v1/mcp-servers/{id}/security`; `GET /api/v1/agent-tools`, `GET /api/v1/agent-tools/{id}`, `POST /api/v1/agent-tools/{id}/approve`, `POST /api/v1/agent-tools/{id}/revoke`, `PUT /api/v1/agent-tools/{id}/risk` (суффикс через «/», а не «:» из ADR: маршрутизатор `net/http` не разбирает `{id}:approve`). Права: `agents.read` (область `own`), `agents.manage`, `agents.tools.approve` (безопасности: `security`, `approve`, `revoke`, `risk` — без токенов API). В `POST /api/v1/applications/{id}/keys` — новое поле `agent_id` (право `agents.manage`, иначе 403; агент чужого приложения — 400).
- **Вход.** Строгий JSON (неизвестные поля — 400), тела до 8 КиБ, у MCP-сервера — до 528 КиБ (корневые сертификаты до 256 КиБ), учётные данные — до 16 КиБ (тело до 65 КиБ). `slug` — `[a-z0-9-]{1,64}`, у MCP-сервера `function` занят; адрес — `https://` (или `http://` после флага `insecure_http`), до 2048 байт, без учётных данных, строки запроса и фрагмента, узел — по правилу `internal/netguard`; имя заголовка учётных данных — token RFC 9110 до 64 байт, кроме служебных (`Host`, `Content-*`, `Mcp-*`, `X-AISec-*`, `Proxy-*`, `X-Forwarded-*`, `Sec-*` и др.); версии протокола — `2026-07-28`, `2025-11-25`. Одобрение — `{risk, hash, comment, password|code}`, хеш — 64 шестнадцатеричных символа показанного описания.
- **Выход.** Учётные данные не возвращаются (`credential_set`, `credential_set_at`); описание инструмента — каноническая форма JSON как данные (консоль показывает текстом, ссылки из `icons` не загружает: их в канонической форме нет).
- **Внутренний API шлюзов.** `POST /internal/v1/agents/tools:observe` (mTLS, право `gateway.internal`): `{server, agent_id, tools: [{descriptor, suspicious}]}`, тело до 8 МиБ, до 256 описаний по 64 КиБ (строгий разбор, повтор ключа — 400), не чаще раза в 10 с от одного шлюза на MCP-сервер или агента (429 с `Retry-After`), `agent_id` не UUID — 400, неизвестный сервер или агент — 404.
- **Очередь подтверждений** (задача 4.10, ADR-0023, раздел 5, DM-22; `internal/approvals`, `internal/api/approvals.go`, миграция 0056): `GET /api/v1/approvals` (фильтры `state`, `application`, `agent`, курсор), `GET /api/v1/approvals/{id}`, `POST /api/v1/approvals/{id}/approve`, `POST /api/v1/approvals/{id}/deny`. Права `approvals.read` и `approvals.decide` (`security`: только сессия консоли `security_admin` и `analyst`, не токены API). Тело решения до 8 КиБ, строгий JSON: для одобрения — `args_hash` (хеш показанного запроса, иначе 409), комментарий до 500 символов без управляющих символов, для риска `critical` — `password` или `code`. Аргументы (маскированные, до 16 КиБ) — только в карточке и только с `approvals.decide`. Внутренний API шлюзов (mTLS, `gateway.internal`): `POST /internal/v1/approvals` (тело до 104 КиБ, строгий JSON, 256 ожидающих на шлюз и 16 на агента, сверх — 429 `approval_queue_full`), долгий опрос `GET /internal/v1/approvals/{id}?wait=Ns` (`0s`–`25s`, соединение держится до 25 с; чужой ID — 404), `POST /internal/v1/approvals/{id}/cancel` (суффикс через «/», как у реестра); поле heartbeat `approvals_pending` (до 256 ID, шлюз шлёт после ответа `approvals: true`). Исходящих соединений шлюза не добавилось: опрос идёт на адрес `-server` своим клиентом с таймаутом 35 с.
- **Пакет конфигурации.** Новые разделы подписанного содержимого `agents` (ID, приложение, slug, статус, MCP-серверы), `mcp_servers` (slug, адрес, корневые сертификаты, имя заголовка, `external`, `insecure_http`, срок вызова, версии, время смены учётных данных), `agent_tools` (сервер или `function` с агентом, имя, одобренный хеш, алгоритм, риск, статус; описаний нет); у ключа приложения — поле `agent`. Учётные данные MCP-серверов — элементы секретов `{"mcp", "credential"}` под HPKE. Строгий разбор и пределы (256 агентов, 64 сервера, 2 000 инструментов). Без агентов разделов нет, байты пакета прежние; шлюз прежней версии пакет с разделами отклоняет (строгий разбор) — шлюзы обновляются раньше сервера.
- **Хранение.** Таблицы `mcp_servers`, `agents`, `agent_servers`, `agent_tools`, столбец `app_keys.agent_id` (миграция 0054); учётные данные — шифротекст на ключе данных; триггеры неизменности ID, slug и сведений о создании; роль `aisec_app` — `SELECT`, `INSERT`, `UPDATE`, `DELETE`.

Общие ограничения HTTPS-сервера (`internal/httpserver`): таймаут чтения заголовков 10 с, простой соединения 120 с, заголовки до 64 КиБ, корректное завершение до 30 с. Ответы шлюза содержат `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Strict-Transport-Security`.

## Аргументы командной строки
`aisec-gateway` — у каждого флага есть переменная окружения (раздел ниже); флаг важнее переменной. Неизвестные флаги и лишние аргументы — ошибка запуска. Справка `-h` не печатает значения из окружения.

| Флаг | Назначение | Проверка |
|---|---|---|
| `-config` | Файл конфигурации шлюза: приложения, ключи, провайдеры, файл событий | Обязателен без `-server`; с `-server` запрещён (конфигурация приходит пакетом, задача 2.13); см. «Файлы». Флаги провайдера этапа 0 (`-upstream-*`, `-forward-headers`) удалены в задаче 1.7 |
| `-listen` | Адрес и порт | `адрес:порт`; по умолчанию `127.0.0.1:8443` |
| `-tls-cert`, `-tls-key` | Сертификат и ключ TLS | Обязательны; обычный файл до 1 МиБ; ключ — права 0600 или 0400 |
| `-max-body-bytes` | Предел тела запроса | 1 КиБ – 32 МиБ, по умолчанию 1 МиБ |
| `-server` | Адрес внутреннего API сервера управления (heartbeat по mTLS, задача 2.14; события, задача 2.15) | Только `https://хост[:порт]` без учётных данных, пути, параметров и фрагмента (`FuzzParseServerURL`); пусто — режим «без сервера». С ним обязательны `-server-ca`, `-client-cert`, `-client-key`, `-bundle-pub`, `-state-dir` и запрещён `-config` |
| `-server-ca` | Корень для проверки сертификата сервера | Обычный файл PEM до 1 МиБ; системное хранилище не используется |
| `-client-cert`, `-client-key` | Сертификат и ключ шлюза из `aisec-gateway register` | Ключ — права 0600 или 0400; за 30 дней до окончания сертификата — предупреждение в журнал |
| `-bundle-pub` | Ключи проверки подписи пакетов конфигурации (задача 2.13) | Только с `-server`; один или два пути через запятую (второй — на время ротации ключа подписи), пустой элемент — ошибка |
| `-state-dir` | Каталог состояния: ключ получателя и последний пакет (задача 2.13); заявления о доверии `trust.json` и перевыпущенный сертификат `client.pem` (задача 3.3) | Только с `-server`; каталог 0700 (см. «Файлы») |
| `-user-hmac-key` | Ключ псевдонимов пользователей в режиме с сервером | Только с `-server`; права 0600 или 0400; приложение с `user_from` без ключа — пакет отклоняется (`invalid_content`) |
| `-manifest` | Манифест целостности (задача 2.17) | Путь к файлу; по умолчанию `../aisec-manifest.json` от каталога бинарника; подпись — рядом с суффиксом `.sig`. Нет файла — нарушение, реакция по `-integrity-action` |
| `-integrity-action` | Реакция на нарушение целостности | `alert` (по умолчанию, только журнал) или `stop` (не запускаться; после запуска — штатная остановка) |
| `-integrity-interval` | Период проверки целостности | Длительность Go не меньше `1m`, по умолчанию `1h` |
| `-selftest-action` | Реакция на провал самотеста детекторов при запуске (задача 2.18) | `alert` (по умолчанию, только журнал) или `stop` (не запускаться); провал криптопрофиля останавливает запуск при любом значении |

`aisec-gateway register` — получение сертификата шлюза по токену (задача 2.14): `-console` (адрес консоли, `https://хост:порт`), `-console-ca` (корень для проверки консоли), `-out-dir` (каталог 0700); токен — только из `AISEC_GATEWAY_REGISTRATION_TOKEN`, не из аргументов (их видно в списке процессов), в вывод и журнал не попадает. Ключ и CSR создаются на шлюзе; запрос — `POST /api/v1/gateways/register` с доверием только `-console-ca`, без `HTTP_PROXY`, таймаут 10 с, ответ до 64 КиБ; CN полученного сертификата сверяется с ID шлюза из ответа. `-state-dir` (необязательный, задача 3.3) — каталог состояния 0700: ключ получателя создаётся в нём (или читается) и передаётся серверу в поле `bundle_key` для закрепления (Н27).

`aisec-cli keys` (задачи 3.2–3.3, ADR-0018) — под логином владельца схемы, рекомендательная блокировка `aisec-keys`: `status [-dir]` (версии ключа данных и счётчики строк; с `-dir` — цепочка доверия и ключ аудита, проверенные от файлов-якорей; ключей и секретов в выводе нет); `rotate-master -dir`; `rotate-data -dir [-resume] [-batch 1–10000] [-settle 0–1h]`; `rotate-signing -dir [-overlap 0–2160h]`; `rotate-ca -dir [-overlap 0–2160h]`; `rotate-audit -dir`. `-dir` — каталог ключей 0700 (иначе отказ); лишние аргументы — отказ. Каждая ротация пишет запись аудита (`keys.*`).

`aisec-cli tls init -out КАТАЛОГ -hosts ИМЯ,АДРЕС,… [-days 1–825, по умолчанию 365]` (задача 4.32 этапа 4) — сертификаты TLS консоли и шлюза для установки без корпоративного УЦ; БД и сеть не нужны. `-hosts` — до 8 КиБ, через запятую, каждое имя — DNS-имя (латиница, цифры, «-», без «*») или IP-адрес без зоны (`NormalizeHost`, `FuzzParseTLSHosts`), повторы убираются, не больше 32. `-out` — существующий каталог 0700 (через `os.Root`); пять файлов (`ca.crt`, `console.crt`, `gateway.crt` — 0444; `console.key`, `gateway.key` — 0400) создаются с `O_EXCL`, существующие не перезаписываются, при ошибке созданные удаляются. УЦ и ключи — ECDSA P-256 (`internal/crypto`); закрытый ключ УЦ только в памяти и не сохраняется. В вывод — имена файлов, срок, имена и отпечаток SHA-256 корня; ключей нет. Запись в журнал аудита не делается: команда работает до создания установки и без БД (как `verify -release`).

`aisec-ml` (задача 4.18, ADR-0024): `-socket` (абсолютный путь не длиннее 100 байт, по умолчанию `/run/aisec-ml/aisec-ml.sock`), `-models` (каталог пакета моделей, абсолютный путь, по умолчанию `/opt/aisec/models`), `-max-conns` (1–1024, по умолчанию 64), `-workers` (0–256, 0 — число процессоров), `-queue-wait` (1 мс – 1 с, по умолчанию 20 мс), `-max-model-bytes` (1 МиБ – 16 ГиБ, по умолчанию 1 ГиБ), `-ort-lib` (библиотека ONNX Runtime, абсолютный путь без «..», по умолчанию `/opt/aisec/lib/libonnxruntime.so.1.31.0`; хеш файла сверяется со встроенным при сборке до загрузки, библиотека загружается по дескриптору проверенного файла). Неизвестные флаги и лишние аргументы — ошибка запуска (код 2). Сборка без тега `aisec_onnx` не запускается: исполнителя моделей в ней нет.

## Переменные окружения
`aisec-gateway`: `AISEC_GATEWAY_CONFIG`, `AISEC_GATEWAY_LISTEN`, `AISEC_GATEWAY_TLS_CERT`, `AISEC_GATEWAY_TLS_KEY`, `AISEC_GATEWAY_MAX_BODY_BYTES`, `AISEC_GATEWAY_MANIFEST`, `AISEC_GATEWAY_INTEGRITY_ACTION`, `AISEC_GATEWAY_INTEGRITY_INTERVAL`, `AISEC_GATEWAY_SELFTEST_ACTION`, `AISEC_GATEWAY_SERVER`, `AISEC_GATEWAY_SERVER_CA`, `AISEC_GATEWAY_CLIENT_CERT`, `AISEC_GATEWAY_CLIENT_KEY`, `AISEC_GATEWAY_BUNDLE_PUB`, `AISEC_GATEWAY_STATE_DIR`, `AISEC_GATEWAY_USER_HMAC_KEY` — те же проверки, что у флагов. `AISEC_GATEWAY_REGISTRATION_TOKEN` — одноразовый токен для `aisec-gateway register` (только окружение). Секреты через переменные окружения не передаются: только пути к файлам.

`aisec-server`: `AISEC_SERVER_LISTEN`, `AISEC_SERVER_TLS_CERT`, `AISEC_SERVER_TLS_KEY` — как флаги `-listen`, `-tls-cert`, `-tls-key` (флаг важнее переменной; сертификат и ключ обязательны, ключ — права 0600 или 0400); `AISEC_SERVER_AUDIT_SIGNING_PUB` — как флаг `-audit-signing-pub`: открытый ключ проверки контрольных точек аудита (`audit-signing.pub`, PEM `AISEC AUDIT SIGNING PUBLIC KEY` до 4 КиБ, ADR-0008); обязателен, если в `audit_checkpoints` есть точки (иначе сервер не запускается); новая установка без точек запускается без него с предупреждением в техжурнале (решение владельца по В5 ревью 2.r1). `AISEC_SERVER_AUDIT_VERIFY_INTERVAL` — как `-audit-verify-interval`: период проверки цепочки журнала аудита (длительность Go не меньше `1m`, по умолчанию `1h`; первая проверка — сразу после запуска). `AISEC_SERVER_TRUSTED_PROXIES` — как `-trusted-proxies`: сети доверенных обратных прокси через запятую (адрес или CIDR, до 64; `/0`, зона интерфейса и `::ffff:` — ошибка запуска; по умолчанию пусто — `X-Forwarded-For` не учитывается). `AISEC_SERVER_KEYS_DIR` — как флаг `-keys-dir`: каталог ключей `aisec-cli init` (обязателен, задача 2.8); сервер читает из него `master.key` (из ключа данных выводится и ключ имитовставки головы цепочки аудита) (права 0600 или 0400, до 1 МиБ, PEM `AISEC MASTER KEY` профиля сервера), расшифровывает им действующий ключ данных из `data_keys` и не запускается, если файла нет, права шире, профиль другой или ключ данных не расшифровывается; при открытом внутреннем порту — ещё `bundle-signing.key` (подпись пакетов конфигурации, задача 2.13). `AISEC_SERVER_MANIFEST`, `AISEC_SERVER_INTEGRITY_ACTION`, `AISEC_SERVER_INTEGRITY_INTERVAL` — как флаги `-manifest`, `-integrity-action`, `-integrity-interval` с теми же проверками, что у шлюза (задача 2.17); сервер сверяет с манифестом свой исполняемый файл и встроенную статику. `AISEC_SERVER_CA_CERT`, `AISEC_SERVER_CA_KEY` — как `-ca-cert`, `-ca-key`: внутренний УЦ (задаются вместе; без них регистрация шлюзов отвечает 503, а внутренний порт не открывается); `AISEC_SERVER_INTERNAL_LISTEN` — как `-internal-listen` (по умолчанию `127.0.0.1:8445`, не может совпадать с `-listen`); `AISEC_SERVER_INTERNAL_TLS_CERT`, `AISEC_SERVER_INTERNAL_TLS_KEY` — как `-internal-tls-cert`, `-internal-tls-key` (задаются вместе; по умолчанию — сертификат консоли). Флага `-timezone` и `AISEC_SERVER_TIMEZONE` нет (удалены по H-Р10, В26 ревью 2.r5): часовой пояс показа — только в настройках установки (`GET`/`PUT /api/v1/system/settings`); неизвестный флаг — ошибка запуска. `AISEC_SERVER_AUDIT_STORAGE_LIMIT` — как `-audit-storage-limit`: предел размера журнала аудита в байтах для расчёта заполнения (целое не меньше 1 МиБ, по умолчанию 20 ГиБ); `AISEC_SERVER_AUDIT_STORAGE_WARN_PERCENT` — как `-audit-storage-warn-percent`: порог предупреждения, 1–100 (по умолчанию 80, РСБ.5). Значения только для расчёта и показа, на доступ и хранение не влияют. `AISEC_DATABASE_URL` — строка подключения к PostgreSQL (обязательна; только из окружения, не из аргументов, чтобы пароль не был виден в списке процессов; в журнал не попадает). Сервер открывает по ней два пула: основной на 10 соединений и пул чтения событий консолью на 4 соединения со `statement_timeout` 130 с (В11 ревью 2.r3a), всего до 14 соединений. Неизвестные флаги и лишние аргументы — ошибка запуска.

`aisec-cli`: `AISEC_DATABASE_URL` — строка подключения к PostgreSQL для `migrate`, `init`, `keys …`, `audit verify`, `audit archive`, `audit export`, `gateway token`, `gateway list`, `gateway revoke` и `user unlock`, `user reset-password`, `user reset-mfa`, `backup create`, `backup restore`, необязательно — для `verify` (запись итога в `integrity_checks` и аудит) (`audit verify-archive` к БД не подключается). Тесты `internal/store`, `internal/audit` и `cmd/aisec-cli` на живой БД читают `AISEC_TEST_DATABASE_URL` (без неё пропускаются); только для разработки.

`aisec-ml`: `AISEC_ML_SOCKET`, `AISEC_ML_MODELS`, `AISEC_ML_MAX_CONNS`, `AISEC_ML_WORKERS`, `AISEC_ML_QUEUE_WAIT`, `AISEC_ML_MAX_MODEL_BYTES`, `AISEC_ML_ORT_LIB` — как флаги (флаг важнее). Процесс сам выставляет `ORT_DISABLE_TELEMETRY=1` до инициализации ONNX Runtime. В compose пилота — `AISEC_ML_MEM_LIMIT` (лимит памяти контейнера, по умолчанию `2g`).

## Установка пилота в docker compose (задача 3.5, ADR-0019)
Файлы — `deploy/compose/pilot/`. Образы — `deploy/build/Dockerfile.release`. Правила проверяет `tools/imagecheck`: compose — в `make test`, образы — в `make images-verify` и в CI.

**Образы** `aisec-server`, `aisec-gateway`, `aisec-cli` собраны на `scratch`. Внутри только `/opt/aisec/bin/<компонент>` (в `aisec-cli` — все бинарники выпуска), `/opt/aisec/aisec-manifest.json` и подпись к нему. Владелец файлов — root, `USER 65534:65534`, оболочки и пакетов ОС нет. `EXPOSE`: 8444 и 8445 у сервера, 8443 у шлюза, у `aisec-cli` портов нет. Метка `ru.aisec.build-kind` — `release` или `test`. Образы `aisec-test/…:ВЕРСИЯ-test` собраны с тестовым ключом манифеста и не поставляются. Формат поставки — архивы `docker save` (`images/*.tar`) рядом с каталогом выпуска: `aisec-manifest.json`, `.sig`, `bin/`.

**Сеть.**
| Сервис | Опубликован на хосте | Сети compose | Исходящие |
|---|---|---|---|
| `aisec-server` | `${AISEC_CONSOLE_BIND:-127.0.0.1}:${AISEC_CONSOLE_PORT:-8444}` → 8444 (консоль и API) | `db`, `control` (псевдоним `${AISEC_CONSOLE_HOST}`), `console` | PostgreSQL; SMTP, syslog и webhook — только из настроек администратора. Мост `console` выход наружу не закрывает: ограничение — в коде (ЗИ.2, repocheck), руководство рекомендует правило `DOCKER-USER` |
| `aisec-server`, внутренний порт 8445 | не публикуется | `control` (внутренняя) | — |
| `aisec-gateway` | `${AISEC_GATEWAY_BIND:-127.0.0.1}:${AISEC_GATEWAY_PORT:-8443}` → 8443 | `control`, `gateway` | сервер (`https://${AISEC_CONSOLE_HOST}:8445`, mTLS), провайдеры LLM из пакета конфигурации |
| `postgres` | не публикуется | `db` (внутренняя) | нет |
| `aisec-cli` | не публикуется; запускается только `docker compose run` | `db` (внутренняя) | только PostgreSQL |
| `aisec-ml` (профиль `ml`, по умолчанию не запускается; задача 4.18, ADR-0024) | не публикуется | нет: `network_mode: none` | нет; единственный канал — Unix-сокет в томе `${AISEC_DATA_DIR}/ml/run` |

Связь сервера и `aisec-cli` с PostgreSQL идёт во внутренней сети одного хоста без TLS (`sslmode=disable`). Для своей СУБД заказчика — `AISEC_SERVER_DB_URL` и `AISEC_OWNER_DB_URL` с `sslmode=verify-full`.

**Запуск.** У всех сервисов `read_only`, `cap_drop: [ALL]`, `no-new-privileges:true`, `pids_limit` и `mem_limit`. Пользователи хоста: `aisec` (сервер, `aisec-cli`), `aisec-gw` (шлюз), `aisec-db` (PostgreSQL); UID и GID берутся из обязательных переменных. `tmpfs` есть только у PostgreSQL (`/tmp`, `/var/run/postgresql`) и `aisec-cli` (`/tmp`, 16 МБ). Healthcheck — только у PostgreSQL: `pg_isready -h 127.0.0.1`.

**Тома и секреты** (`AISEC_DATA_DIR`, по умолчанию `/srv/aisec`):
| Путь на хосте | В контейнере | Кто | Защита |
|---|---|---|---|
| `keys/` | `/etc/aisec/keys` | `aisec-cli` — запись (`init`), сервер — только чтение | каталог 0700 `aisec`; файлы `aisec-cli init` 0400 и 0444 |
| `gateway/reg/`, `gateway/state/` | `/var/lib/aisec-gateway/reg`, `…/state` (два тома) | шлюз | каталоги 0700 `aisec-gw` в каталоге `gateway/` (root, 0755, не монтируется) |
| `backups/` | `/var/lib/aisec/backups` | `aisec-cli backup` | каталог 0700 `aisec` |
| `pg/` | `/var/lib/postgresql/data` | PostgreSQL | каталог 0700 `aisec-db` |
| `secrets/console.crt`, `console.key` | `/run/secrets/console-tls-*` | сервер | владелец `aisec`, ключ 0600 или 0400 |
| `secrets/gateway.crt`, `gateway.key` | `/run/secrets/gateway-tls-*` | шлюз | владелец `aisec-gw`, ключ 0600 или 0400 |
| `secrets/console-ca.crt` | `/run/secrets/console-ca` | шлюз (`-server-ca`, `register -console-ca`) | 0644 |
| `secrets/gateway-bundle-anchor.pub` (копия `keys/bundle-signing.pub` после `init`, 3В6 ревью 3.r1) | `/run/secrets/gateway-bundle-anchor` | шлюз (`-bundle-pub`) | root, 0644 |
| `secrets/db-postgres-password`, `db-owner-password`, `db-server-password` | `/run/secrets/…` | PostgreSQL: `POSTGRES_PASSWORD_FILE` и `initdb/10-aisec-roles.sql` | владелец `aisec-db`, 0400 |
| `secrets/db-owner.pgpass`, `db-server.pgpass` | `/run/secrets/db-*-pgpass` | `aisec-cli`, сервер: параметр `passfile` строки подключения pgx | владелец `aisec`, 0400, формат `*:*:*:роль:пароль` |
| `deploy/compose/pilot/initdb/` | `/docker-entrypoint-initdb.d` (только чтение) | PostgreSQL, один раз на пустом каталоге данных | роли `aisec_owner` (владелец схемы, член `aisec_audit_archiver`), `aisec_server` (член `aisec_app`); пароли в журнал СУБД не пишутся |

**Переменные `.env`** (секретов нет): `AISEC_VERSION`, `AISEC_IMAGE_REPO`, `AISEC_POSTGRES_IMAGE` (только реестр, digest закреплён в `compose.yaml`), `AISEC_DATA_DIR`, `AISEC_UID`/`AISEC_GID`, `AISEC_GW_UID`/`AISEC_GW_GID`, `AISEC_DB_UID`/`AISEC_DB_GID`, `AISEC_CONSOLE_HOST`, `AISEC_CONSOLE_BIND`, `AISEC_CONSOLE_PORT`, `AISEC_GATEWAY_BIND`, `AISEC_GATEWAY_PORT`, `AISEC_TRUSTED_PROXIES` (→ `AISEC_SERVER_TRUSTED_PROXIES`), `AISEC_INTEGRITY_ACTION` (→ `AISEC_SERVER_INTEGRITY_ACTION`), `AISEC_VENDOR_FINGERPRINT` (отпечаток ключа производителя из руководства, читает только `verify-release.sh`; ADR-0022), `COMPOSE_PROFILES` (`db`), `AISEC_SERVER_DB_URL`, `AISEC_OWNER_DB_URL` (своя СУБД; пароль только в passfile). Внутри контейнеров `AISEC_DATABASE_URL` передаётся без пароля. pgx читает и стандартную переменную `PGPASSFILE`, но compose её не задаёт.

**Скрипты на хосте** (POSIX sh, вне контейнеров):
- `prepare-host.sh` — от root. Создаёт пользователей без входа, каталоги, пароли ролей БД из `/dev/urandom` (64 шестнадцатеричных символа, не выводятся), записывает UID и GID в `.env` (0644). Повторный запуск ничего не перезаписывает, восстанавливает недостающий passfile из сохранённого пароля и отказывается работать, если каталог данных — символьная ссылка или существующий пользователь `aisec*` — root или с входом в систему. Владельца и права закрытых ключей TLS проверяет и сообщает о расхождении. Если якоря шлюза `secrets/gateway-bundle-anchor.pub` нет, а `keys/bundle-signing.pub` есть, копирует его (чтение от имени `aisec` через `runuser`, до 8 КиБ, проверка заголовка PEM; 0644 root); существующий якорь не перезаписывает (3В6 ревью 3.r1).
- `backup.sh КАТАЛОГ` — полная копия установки (РВ.2, задача 3.8), от root. Каталог копий — абсолютный путь вне `AISEC_DATA_DIR`, не символьная ссылка; он и все каталоги над ним принадлежат root и закрыты для записи группе и остальным (у каталогов выше — допускается бит sticky), иначе отказ. `AISEC_DATA_DIR` — из `.env` (без кавычек и CR), отказ, если в окружении задано другое значение. Копия — новый подкаталог `aisec-<время UTC>` (0700, файлы 0600): `files.tar` (`keys/`, `secrets/`, `gateway/reg/`, `gateway/state/` с именами владельцев; при «файл изменился» — до трёх попыток), `env` (копия `.env`), `db.dump` (`pg_dump -Fc` владельцем схемы `aisec_owner` внутри контейнера `postgres`; пароль — во временном passfile в tmpfs контейнера, не в окружении и не в аргументах), `SHA256SUMS`. Оглавление `db.dump` проверяется `pg_restore -l` до переименования. Копия не шифруется: `files.tar` (мастер-ключ) и `db.dump` хранятся раздельно (руководство администратора, раздел 12.1).
- `restore.sh КАТАЛОГ_КОПИИ` — восстановление копии в пустую установку, от root. Входные данные недоверенные. Путь — абсолютный; файлы копии — обычные, копируются (`cp -P`) во временный каталог root 0700, все проверки и распаковка — только с этой копии. `SHA256SUMS` — ровно файлы копии, `sha256sum --strict`; `AISEC_CONSOLE_HOST` и `COMPOSE_PROFILES` файла `env` совпадают с `.env`; в `files.tar` — только обычные файлы и каталоги (`tar -tv`), без битов setuid, setgid, sticky и записи для группы и остальных, пути только внутри `keys/`, `secrets/`, `gateway/reg/`, `gateway/state/` из символов `[A-Za-z0-9._-]`, без «..». Отказ, если в `keys/` или `pg/` уже есть файлы, сервисы запущены или `AISEC_DATA_DIR` окружения расходится с `.env`. Распаковка с владельцами по именам, затем `chown` каталогов ключей (`aisec`) и шлюза (`aisec-gw`); `pg_restore --exit-on-error --single-transaction` владельцем схемы (passfile как у `backup.sh`); `aisec-cli migrate`, `restore-finish -copy-dir <имя каталога копии>` (отзыв сессий и токенов API копии, погашение токенов регистрации шлюзов и первичной настройки, запись `system.restored`) и `audit verify -keys`. Отказы проверяет `TestE2EPilotScripts_*`.
- `lab-install.sh --host АДРЕС… [--console-name ИМЯ] [--bind АДРЕС] [--mirror РЕЕСТР] [--build-ca ФАЙЛ] [--no-build]` (задача 4.32 этапа 4) — установка для лаборатории и стенда одной командой, от root, **не для поставки**: образы с тестовым ключом манифеста (`aisec-test`). Аргументы проверяются до сборки по набору символов (`--host` — латиница, цифры, `.:,-` и пробел; `--console-name` — только DNS-имя с непустыми метками без «-» по краям, не IP-адрес: по нему шлюз находит сервер в сети Docker; `--bind`, `--mirror` — латиница, цифры, `.:/_-`); разбор `--host` — с `set -f`; полностью имена для сертификата проверяет `aisec-cli tls init`. Сборка — `deploy/build/Dockerfile.lab` (ниже, «Компоненты вне поставки»), каталог выпуска — временный вне репозитория (`mktemp -d` в `TMPDIR` или `/var/tmp`, удаляется при любом выходе), затем образы из него без сети, как `make images-docker`, и `aisec-cli verify` собранного выпуска. Дальше — шаги `install-pilot.md`, разделы 3–4: `prepare-host.sh`; `.env` (`AISEC_IMAGE_REPO`, `AISEC_VERSION`, `AISEC_CONSOLE_HOST`, `AISEC_*_BIND` — `--bind` или `0.0.0.0` в новом `.env`, в прежнем без `--bind` не меняются, `AISEC_POSTGRES_IMAGE` при `--mirror`); если все пять сертификатов уже есть, а `AISEC_CONSOLE_HOST` в `.env` другой — отказ до записи `.env` (сертификаты выпущены на прежнее имя); сертификаты — только если в `secrets/` нет ни одного из пяти файлов: `tls init` от `aisec` во временный каталог 0700 в `AISEC_DATA_DIR` (удаляется при любом выходе), после команды каталог возвращается root, каждый файл проверяется (обычный, без символьных и жёстких ссылок — `find -type f -links 1`), раскладка `install` с владельцами и правами шага 3.4, копия корня `AISEC_DATA_DIR/ca.crt` (0644 root); отпечаток SHA-256 корня повторяется в итоговой сводке; `migrate`, `init` (если нет `keys/master.key`), сервер, регистрация шлюза `gw-1` (если нет `gateway/reg/gateway.crt`): токен на 30 минут из вывода `gateway token` — в переменной окружения процесса, не в аргументах и не в выводе; запуск. Повторный запуск готовые шаги пропускает.
- `verify-release.sh [-first] КАТАЛОГ` — проверка поставки при первой установке (`-first`) и выпуска перед обновлением (ОБН.1, ADR-0022). Входные данные недоверенные: каталог выпуска и архивы `images/*.tar`. Без `AISEC_VENDOR_FINGERPRINT` в `.env` отказ (кроме `AISEC_IMAGE_REPO=aisec-test` — предупреждение); значение — только шестнадцатеричные цифры и двоеточия. Порядок:
  - выпуск копируется во временный каталог (владелец — запускающий, запись только ему); манифест, подпись, `bin/` и архивы образов по символьной ссылке отвергаются; дальше скрипт работает только с копией (3Н6 ревью 3.r1);
  - `aisec-cli` установленной версии без сети, только для чтения, без capabilities, от 65534 проверяет подпись и файлы копии: `verify -release /release` (монтирование `--mount …,readonly`); выпуск, собранный раньше установленного, отвергается. С `-first` установленной версии нет: архив `images/aisec-cli.tar` проверяется так же, как остальные (ниже), загружается, и проверку выполняет он сам с `-allow-older`; образ с этим тегом, уже загруженный, — отказ;
  - отпечаток ключа, которым проверена подпись (строка `aisec-cli`), сравнивается с `AISEC_VENDOR_FINGERPRINT`; расхождение или отсутствие строки — отказ;
  - бинарник каждого образа обязан быть в проверенном манифесте;
  - до `docker load` в архиве проверяются записи (только метаданные OCI и блобы, без обратной косой черты) и имена: ровно один образ `${AISEC_IMAGE_REPO}/<компонент>:<версия из проверенного манифеста>`, отличной от установленной;
  - после загрузки — точные настройки образа (`docker image inspect`) и полный список файлов (`docker export | tar -tv`) без символьных ссылок; затем `docker cp` и побайтная сверка (`cmp`) бинарников, манифеста и подписи;
  - при любом расхождении загруженные образы удаляются (`docker rmi`). Контейнеры нового выпуска не запускаются.

`aisec-cli` (в поставке): `app-key [-expires ГГГГ-ММ-ДД]` — выпуск ключа приложения. Ключ печатается один раз в стандартный вывод и нигде не сохраняется; для конфигурации — префикс и SHA-256. Перед выпуском — самотест криптопрофиля. `migrate` — применяет встроенные SQL-миграции (`migrations/`) к PostgreSQL одной транзакцией под рекомендательной блокировкой; без аргументов, строка подключения — только из переменной окружения `AISEC_DATABASE_URL` (URL `postgres://…`, до 2048 байт; пароль не попадает в аргументы и сообщения об ошибках). Исходящее соединение — только на настроенный адрес БД; таймауты: соединение 10 с, прогон 5 мин. `audit verify` — проверка цепочки журнала аудита по команде (РСБ.4, DM-43): без аргументов, строка подключения — из `AISEC_DATABASE_URL`; только читает `audit_log` и добавляет итог в `audit_verifications`, `audit_log` и `tech_log`; код возврата 3 — цепочка нарушена, 1 — ошибка выполнения; криптопрофиль — `standard`; «кто» в записи — пользователь ОС; таймауты — 30 с на пачку из 1000 записей, 10 с на запись итога; `-keys КАТАЛОГ` — дополнительно проверить подписи контрольных точек архивации открытым ключом `audit-signing.pub` (ADR-0008), без него проверяется только их связность; подмена или удаление точки — код 3. `init -dir КАТАЛОГ [-profile standard]` — создание ключей установки (ЗИ.1, ЗИ.4, ADR-0007; `-profile gost` до этапа 6 отклоняется): каталог должен существовать и быть закрыт для группы и остальных (иначе отказ), файлы открываются через `os.Root`; создаются `master.key`, `bundle-signing.key`, `ca.key`, `audit-signing.key` (0400) и `bundle-signing.pub`, `ca.crt`, `audit-signing.pub` (0444) с `O_EXCL` — существующие файлы и символические ссылки не перезаписываются, повторный запуск отклоняется и по наличию ключа данных в БД. В БД одной транзакцией: `data_keys` (ключ данных под мастер-ключом), `setup_tokens` (SHA-256 токена первичной настройки, срок 24 ч), запись аудита `system.init` (без ключей и токена); сбой транзакции удаляет созданные файлы, при неизвестном исходе фиксации файлы сохраняются; триггеры запрещают уменьшать счётчик шифрований и повторно гасить токен. В стандартный вывод — только имена файлов, id ключа данных, срок УЦ и однократно токен первичной настройки; ключи не выводятся. Таймаут каждой операции с БД — 30 с. `init -dir КАТАЛОГ -add-audit-key` — только пара ключей аудита для установки, где `init` прошёл до ADR-0008: нужен `master.key` в каталоге и ключ данных в БД, существующий ключ аудита не перезаписывается, запись аудита `system.audit_key`; при её сбое файлы удаляются. `init -reissue-setup-token` (только с `AISEC_DATABASE_URL`, без `-dir`) — новый токен первичной настройки вместо утерянного или истёкшего, только пока в организации нет пользователей (под блокировкой первичной настройки): прежние непогашенные токены гасятся, новый печатается один раз, в БД — только хеш, запись аудита `system.setup_token_reissued` (H-Р13 ревью 2.r5). Новые форматы файлов: PEM `AISEC MASTER KEY`, `AISEC SIGNING KEY`, `AISEC SIGNING PUBLIC KEY`, `AISEC AUDIT SIGNING KEY`, `AISEC AUDIT SIGNING PUBLIC KEY` с заголовком `Profile`, до 4 КиБ, строгий разбор без данных до и после блока (`FuzzDecodeKeyPEM`); ключ УЦ — PKCS#8 PEM (`FuzzLoadCA`). `audit archive -keys КАТАЛОГ -out ФАЙЛ [-before ГГГГ-ММ-ДД]` — архивация записей старше срока хранения (РСБ.4, ADR-0008): строка подключения — из `AISEC_DATABASE_URL`, логину нужно членство в роли `aisec_audit_archiver`; читает `audit-signing.key` и `audit-signing.pub` (`ReadKeyFile` — отказ при доступе группы или остальных, проверка, что это пара); сначала проверка цепочки (нарушена — код 3, архивации нет); файл архива создаётся `O_EXCL` с правами 0600 и сбрасывается на диск до удаления записей; каталог файла сбрасывается на диск до транзакции; в БД одной транзакцией (таймаут 10 мин) — точка в `audit_checkpoints` (триггер принимает только точку, описывающую реальные записи), `DELETE` из `audit_log`, запись `audit.archive`; нечего архивировать — файл удаляется; сбой — файл удаляется, если точка точно не записана, при неизвестном исходе фиксации сохраняется. В вывод — диапазон номеров, граница и хеш последней записи, ключи не выводятся. `audit export -out ФАЙЛ [-from ГГГГ-ММ-ДД] [-to ГГГГ-ММ-ДД]` — выгрузка журнала (РСБ.5): только чтение одним снимком (в заголовке — начало хранимой части), файл `O_EXCL` 0600, запись `audit.export`; при сбое файл удаляется. `audit verify-archive -keys КАТАЛОГ ФАЙЛ` — проверка архива без БД и сети: читает `audit-signing.pub` и обычный файл до 64 ГиБ (больший — отказ до чтения); код 3 — архив недействителен. Новый формат файла — архив и выгрузка журнала аудита: JSON Lines (`aisec-audit-archive`, `aisec-audit-export`), строка до 256 КиБ, строгий разбор без неизвестных полей, каноническая форма точки и записей, не более 2^40 записей (`FuzzVerifyArchive`). `gateway token -name ИМЯ [-ttl 24h] [-reregister]` (задача 2.14) — одноразовый токен регистрации шлюза: имя 1–64 символа `[a-z0-9._-]`, срок от 1 минуты до 7 суток; токен печатается один раз, в БД — только SHA-256, прежние непогашенные токены шлюза гасятся, запись `gateway.token_issue`; без `-reregister` занятое имя — отказ, для отозванного шлюза — отказ. `gateway list` — шлюзы, состояние, срок сертификата, последний контакт и версия (только чтение). `gateway revoke -name ИМЯ` — отзыв: сертификат перестаёт приниматься сразу, токены гасятся, запись `gateway.revoke`; отзыв окончательный. Команды `gateway` работают под логином владельца схемы: у роли сервера нет прав создавать и отзывать шлюзы. `user unlock -login ЛОГИН`, `user reset-password -login ЛОГИН`, `user reset-mfa -login ЛОГИН` (В7 ревью 2.r2) — аварийные действия с учётной записью консоли, когда в консоли это сделать некому (единственный администратор безопасности заблокирован или потерял фактор): права консоли не проверяются — команды требуют локального доступа к БД; снятие блокировки (деактивированная запись — отказ), временный пароль (печатается один раз; сессии завершаются, токены API отзываются), удаление второго фактора с завершением сессий; записи `auth.unlocked`, `user.password_reset`, `auth.mfa_reset` от пользователя ОС с логином СУБД (`db_user`). `verify [-manifest ФАЙЛ] [-accept-rollback [-gateway ИМЯ]]` (задача 2.17) — проверка целостности установки по подписанному манифесту без сервера: читает манифест, подпись и все невстроенные файлы манифеста в его каталоге (через `os.Root`), сверяет встроенные миграции и свой исполняемый файл. `verify -release КАТАЛОГ [-allow-older]` (задача 3.5, ОБН.1) — проверка нового выпуска до обновления: манифест (до 4 МиБ) и подпись — только обычные файлы, не ссылки; все невстроенные файлы манифеста читаются через `os.Root` (ссылка на последнем элементе — нарушение, выход за корень невозможен); подпись — ключом, встроенным в установленный `aisec-cli`. Ещё читает подписанный манифест своей установки (`../aisec-manifest.json` от `bin/`): выпуск, собранный раньше, — откат, принимается только с `-allow-older`. Себя и встроенные наборы не сверяет, к БД не обращается, с `-manifest`, `-accept-rollback`, `-gateway` не сочетается; к сети не обращается, к БД — только с `AISEC_DATABASE_URL`; вывод — пути и виды нарушений, код 3 — целостность нарушена, в том числе манифест старше последней успешной проверки (`manifest_rollback`, В20 ревью 2.r4). `-accept-rollback` (нужен `AISEC_DATABASE_URL`) — принять намеренный откат: успешная проверка пишется с признаком принятия и `integrity.rollback_accepted`; нарушение файлов так не принимается. `-gateway ИМЯ` (только с `-accept-rollback`) — принять откат шлюза по его heartbeat, файлы на этом хосте не проверяются. `backup create -keys КАТАЛОГ -out ФАЙЛ (-user-hmac-key ФАЙЛ | -no-user-hmac-key) [-passphrase-file ФАЙЛ]` и `backup restore -keys КАТАЛОГ -in ФАЙЛ [-user-hmac-key-out ФАЙЛ] [-passphrase-file ФАЙЛ] [-allow-nonempty] [-keep-api-tokens] [-accept-old-copy]` (задача 2.19, ADR-0017) — резервная копия конфигурации и восстановление в новую установку после `init`: парольная фраза только с терминала без отображения (`golang.org/x/term`, без внешних процессов; stdin не терминал — отказ) или из файла с правами ровно 0400 (одна строка, до 4 КиБ), в аргументах не принимается, не короче 16 символов (для новой копии — ещё не меньше 8 разных символов, не повтор, не последовательность, не имя пользователя ОС и не название организации, Н41 ревью 2.r4); лишние аргументы — ошибка; файл копии не перезаписывается; непустая установка без `-allow-nonempty` и совпадения объектов — отказ (`denied` в аудите), с флагом объекты только добавляются, настройки установки не меняются; копия другой организации — отказ; неверная фраза или подменённый файл — код 3; объекты, которые сервис этого выпуска не принял бы (роли, токены, политики, приложения), — код 3 с перечнем до записи (В22); действующие токены API восстанавливаются отозванными, `-keep-api-tokens` — как в копии; копия старше 7 суток — только с `-accept-old-copy` (В21); сессия консоли с активностью за последние 5 минут — отказ (Н40); без `-confirm` — отказ до подключения к БД (3Н53 ревью 3.r4): строка подключения — из `AISEC_DATABASE_URL` (в compose — владелец схемы); одной транзакцией (таймаут 2 мин) под блокировкой восстановления завершает все незавершённые сессии консоли и отзывает все действующие токены API организации с причиной `backup_restore`, гасит все непогашенные токены регистрации шлюзов и токен первичной настройки (3В21 ревью 3.r3: копия возвращает их непогашенными), пишет `system.restored` с числом погашенных от пользователя ОС; к сети и файлам не обращается. `version` — версия сборки, без доступа к файлам и сети.

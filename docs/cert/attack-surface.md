# Поверхность атаки

Черновик этапов 0–1. Все внешние интерфейсы продукта: сетевые (порт, протокол, аутентификация), файловые, аргументы CLI, переменные окружения (ТЗ, раздел 9). Обновляется при любом изменении интерфейсов.

## Сетевые интерфейсы
| Компонент | Адрес по умолчанию | Протокол | Аутентификация | Эндпоинты | Этап |
|---|---|---|---|---|---|
| `aisec-gateway` | `127.0.0.1:8443` | HTTPS (TLS 1.2–1.3; HTTP без TLS отвергается) | `GET /healthz`, `GET /readyz` — без аутентификации (только статус). Маршруты приложений — ключ приложения `Authorization: Bearer aisec_…` (ИАФ.8); шлюз без аутентификации не собирается | `GET /healthz`, `GET /readyz`, `POST /v1/chat/completions` (в том числе SSE; проверок содержимого пока нет), `GET /v1/models` (модели и псевдонимы приложения). Прочее — 404 или 405 в формате ошибок OpenAI | 0–1 |

**Аутентификация приложений** (задача 1.4 этапа 1, DM-38):
- Ключ — только в `Authorization: Bearer`, схема без учёта регистра, один заголовок, ключ до 128 символов строго формата `aisec_<8 символов>_<43 символа base64url>`. Ключ в строке запроса и в других заголовках не принимается.
- Срок `expires` (ГГГГ-ММ-ДД): ключ действует до 00:00 UTC этой даты (03:00 МСК), сама дата в срок не входит — так же написано в справке `aisec-cli app-key -expires`.
- Порядок проверок: формат → SHA-256 предъявленного ключа сравнивается с сохранённым за постоянное время (для неизвестного префикса — с заглушкой, чтобы время не выдавало, существует ли префикс) → отзыв → срок → `allowed_cidrs`. Отзыв, срок и адрес проверяются только после совпадения секрета: иначе по причине отказа можно было бы узнать о существовании префикса.
- Адрес клиента — только из TCP-соединения. `X-Forwarded-For`, `X-Real-Ip`, `Forwarded` не учитываются: доверенных обратных прокси перед шлюзом на этапе 1 нет, а иначе клиент подставил бы любой адрес. IPv4 в записи IPv6 приводится к IPv4.
- Отказ — 401 `invalid_api_key` с одинаковым текстом и `WWW-Authenticate: Bearer` при любой причине; причина, адрес и префикс — только в событии `auth_failure` (ключ туда не пишется). Успешный вход событие не создаёт.
- Ограничение частоты неудач: 10 неудач за минуту с одного адреса IPv4 или сети IPv6 /64 — блокировка на 15 минут. Во время блокировки **неудачи** с адреса получают 429 `auth_rate_limited` с `Retry-After` и событий не создают; о начале блокировки — одно событие с причиной `rate_limited` и одна строка в техническом журнале без адреса (адрес — только в событии). **Действующий ключ проходит и с заблокированного адреса:** иначе одно приложение с отозванным ключом в цикле повторов отключало бы соседей за тем же NAT или исходящим адресом; подбор это не облегчает — секрет 256 бит. Таблица адресов — в памяти, до 65 536 записей; при переполнении вытесняются незаблокированные, а если таблица забита блокировками (например, из множества сетей /64 одной сети /48), неудачи новых адресов учитываются в одном общем счётчике, который блокируется по тем же правилам: ограничение и поток событий остаются ограниченными. Неразобранный адрес клиента (у TCP-соединения не бывает) — тоже общий счётчик.

`POST /v1/chat/completions` после аутентификации:
- **Вход.** Только `Content-Type: application/json` (иначе 415); тело не больше `max-body-bytes` (иначе 413), передано не дольше 30 с (иначе 408) и только объект JSON (иначе 400). Всё это проверяется до обращения к провайдеру.
- **Разбор запроса** (`internal/chat`, задача 1.5). Строгая модель: верхний уровень — только `model`, `messages`, `stream`, `stream_options`, `max_tokens`, `max_completion_tokens`, `temperature`, `top_p`, `n` (только 1), `stop`, `presence_penalty`, `frequency_penalty`, `logit_bias`, `response_format`, `seed`, `tools`, `tool_choice`, `parallel_tool_calls`, `user`, `reasoning_effort`. Любое другое поле — 400 `unsupported_parameter`: в том числе `metadata`, `prediction`, `audio`, `modalities`, устаревшие `functions`/`function_call` — через них текст ушёл бы провайдеру мимо проверок; `logprobs` и `top_logprobs` — в них ответ повторяется по токенам в обход маскирования ответа. Роли — `system`, `developer`, `user`, `assistant`, `tool`; части — `text`, `refusal` (только `assistant`), `image_url`, `input_audio`, `file`, `video_url` (только `user`); неизвестный тип части — 400. Диапазоны чисел, имена функций и идентификаторы — по шаблонам; схемы JSON (`tools[].function.parameters`, `response_format`) — объект до 256 КиБ.
- **Пересборка.** Провайдеру уходит тело, собранное заново из разобранной модели, а не исходные байты. Повторные ключи JSON, ключи в другом регистре и неизвестные поля до провайдера не доходят: провайдер получает ровно то, что видели проверки.
- **Нетекстовые части** (DM-14). Шлюз их не декодирует: знает вид (изображение, аудио, файл, видео), способ передачи (данные `data:…;base64` или ссылка `http(s)://`, у файла — ещё `file_id` провайдера) и длину данных; длина проверяется сразу (по умолчанию до 20 МиБ на часть, иначе 400 `media_too_large`). Другие схемы адресов (`file:`, `ftp:` и т. п.) — 400. Обработка по параметру политики `non_text` — задача 1.19.
- **Лимиты** (DM-15): до 256 сообщений (или `quotas.max_messages` приложения), 64 частей и 64 вызовов инструментов в сообщении, 128 инструментов; `max_tokens` — не больше `quotas.max_tokens` приложения (400 `max_tokens_exceeded`).
- **Маршрутизация** (задача 1.7, DM-33). Приложение запроса известно по ключу; провайдер — из его карточки. Модель запроса — разрешённая модель приложения или его псевдоним (заменяется моделью провайдера). Иначе — 404 `model_not_found` до обращения к провайдеру, без перечня разрешённых моделей в ответе; перечень — в `GET /v1/models` с ключом приложения.
- **Не проверяется на этапе 1:** описания инструментов и схемы JSON — их задаёт приложение, а не пользователь.
- **Строка запроса** клиента провайдеру не передаётся и в журнал не пишется.
- **Заголовки к провайдеру** формирует шлюз: `Content-Type`, `Accept`, `User-Agent: aisec-gateway`, `Authorization` с ключом провайдера. Заголовки приложения провайдеру не передаются вовсе.
- **Ответ провайдера** разбирается и собирается заново (`internal/chat`): неизвестные поля (например, `reasoning_content`, `logprobs`) приложению не уходят. Ответ без потока — до 16 МиБ; иначе 502 `upstream_bad_response`. Поток SSE (`internal/sse`): строка до 1 МиБ, событие до 4 МиБ, суммарный текст до 16 МиБ; каждая часть разбирается и отправляется приложению сразу, служебные события и комментарии провайдера не передаются; ошибка или обрыв потока — событие `data: {"error": …}` без завершающего `[DONE]`.
- **Заголовки к приложению:** только `Content-Type` шлюза и `Retry-After`, `X-Ratelimit-*` провайдера (значения до 128 символов без управляющих).
- **Ошибки провайдера.** Код, тип и код ошибки — от провайдера (тип и код — только короткие идентификаторы), текст — до 500 символов без управляющих. 401 и 403 от провайдера — отказ ключу шлюза, а тело может содержать часть ключа: вместо них 502 `upstream_auth_error` без тела провайдера. Коды 3xx (перенаправления не выполняются) и прочие — 502. Ошибки связи — 502 `upstream_unavailable` или 504 `upstream_timeout` без внутренних подробностей; в журнал — класс ошибки и идентификатор провайдера.
- **Разрыв соединения клиентом** отменяет запрос к провайдеру.
- **Ещё не ограничено (этап 1):** простой потока SSE между частями и общий срок потокового ответа — сейчас поток живёт, пока его не закроет провайдер или клиент.

**Исходящие соединения шлюза:** только на `base_url` провайдеров из файла конфигурации (allowlist, ЗИ.3), только `https`; перенаправления не выполняются; переменные `HTTP_PROXY`/`HTTPS_PROXY` не используются; TLS с доверием только корневым сертификатам из `ca_file` провайдера; таймауты на соединение (по умолчанию 10 с) и до заголовков ответа (60 с).

Общие ограничения HTTPS-сервера (`internal/httpserver`): таймаут чтения заголовков 10 с, простой соединения 120 с, заголовки до 64 КиБ, корректное завершение до 30 с. Ответы шлюза содержат `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, `Strict-Transport-Security`.

## Файлы
| Файл | Кто читает или пишет | Защита |
|---|---|---|
| Конфигурация шлюза (YAML, флаг `-config`; пример — `testdata/fixtures/config/gateway.yaml`) | Шлюз читает при запуске | Только обычный файл, недоступный на запись группе и остальным, в каталоге без записи для группы и остальных (кроме каталога с битом sticky): по нему принимаются решения о доступе. Владелец файла не проверяется (нужен `syscall`, запрещённый в серверных компонентах, ADR-0004) — задаётся при установке. До 4 МиБ, один документ, строгая схема (неизвестные поля — ошибка), проверка ссылок и значений; `gateway.events_file` обязателен; подсети `allowed_cidrs` — в каноническом виде, без записи IPv4-in-IPv6. Секретов нет: ключи провайдеров — путями к файлам, ключи приложений — только префикс и SHA-256. Режим хранения `full` отвергается. У провайдера `base_url` — `https` с версией API (`https://llm.example/v1`), `ca_file` обязателен; `system_roots` не поддерживается — доверие системному хранилищу только явным путём к его файлу в `ca_file`. Типы `gigachat` и `yandexgpt` до задач 1.8 и 1.9 — ошибка запуска |
| Файл событий JSONL (этап 1, `gateway.events_file`) | Шлюз дописывает | Права 0600; файл с более широкими правами не используется. Содержимое — только по режиму хранения (`none`, `masked`) |
| Сертификаты и ключи TLS (путь задаёт администратор) | Компоненты читают сертификаты через `crypto.ReadPEMFile`, закрытые ключи — через `crypto.ReadKeyFile` | Только обычный файл, не больше 1 МиБ; проверки выполняются на открытом файле (подмена между проверкой и чтением не помогает). Ключ с доступом для группы или остальных не читается (нужно 0600 или 0400) |
| Каталог ключей стенда разработки (`.dev-keys/`) | `tools/devcerts` пишет: сертификаты, ключ TLS, ключ приложения `app-key`, конфигурацию шлюза `gateway.yaml` | Каталог 0700, ключ TLS и ключ приложения 0600, запись через временный файл; ключ УЦ не сохраняется; каталог в `.gitignore`; правило `deny` в `.claude/settings.json` закрывает его только от инструмента чтения файлов ИИ-ассистента, не от команд оболочки — ключи стенда одноразовые и ни к чему не дают доступа |

## Аргументы командной строки
`aisec-gateway` — у каждого флага есть переменная окружения (раздел ниже); флаг важнее переменной. Неизвестные флаги и лишние аргументы — ошибка запуска. Справка `-h` не печатает значения из окружения.

| Флаг | Назначение | Проверка |
|---|---|---|
| `-config` | Файл конфигурации шлюза: приложения, ключи, провайдеры, файл событий | Обязателен; см. «Файлы». Флаги провайдера этапа 0 (`-upstream-*`, `-forward-headers`) удалены в задаче 1.7 |
| `-listen` | Адрес и порт | `адрес:порт`; по умолчанию `127.0.0.1:8443` |
| `-tls-cert`, `-tls-key` | Сертификат и ключ TLS | Обязательны; обычный файл до 1 МиБ; ключ — права 0600 или 0400 |
| `-max-body-bytes` | Предел тела запроса | 1 КиБ – 32 МиБ, по умолчанию 1 МиБ |

## Переменные окружения
`aisec-gateway`: `AISEC_GATEWAY_CONFIG`, `AISEC_GATEWAY_LISTEN`, `AISEC_GATEWAY_TLS_CERT`, `AISEC_GATEWAY_TLS_KEY`, `AISEC_GATEWAY_MAX_BODY_BYTES` — те же проверки, что у флагов. Секреты через переменные окружения не передаются: только пути к файлам.

`aisec-cli` (в поставке): `app-key [-expires ГГГГ-ММ-ДД]` — выпуск ключа приложения. Ключ печатается один раз в стандартный вывод и нигде не сохраняется; для конфигурации — префикс и SHA-256. Перед выпуском — самотест криптопрофиля.

## Цель и критерии приёмки (ТЗ, 14)
- Все функции раздела 7 с меткой MVP реализованы и описаны в `docs/cert/security-functions.md`. Уведомления ИАФ.4, УПД.6, РСБ.5, ОЦЛ.5, ВРМ.1 пишут запись в журнал аудита и выводятся на «Состояние системы»; доставка по каналам — этап 3.
- Матрица «роль × эндпоинт» покрыта тестами на отказ.
- Подмена бинарника или пакета политик обнаруживается.
- Строки DM-39, DM-42, DM-43 (в части обнаружения) покрыты e2e-тестами.
- Интерфейс работает при строгом CSP (e2e).
- `make dm-coverage` при `STAGE=2` без проблем: 21 строка этапа 1 и DM-39, DM-42, DM-43.

## Состояние кода на 20.10.2026
- Есть: шлюз этапа 1 с локальным YAML (Р2 этапа 1), `internal/crypto` (`Hasher`, `MAC`, `Random`, TLS, самотест, заглушка `gost`), `internal/auth` (ключи приложений, `auth_failure`, ограничение частоты), события с приёмником JSONL, `aisec-cli app-key`.
- Только заготовки (`doc.go`): `internal/audit`, `internal/integrity`, `internal/store`, `internal/api`; `cmd/aisec-server` печатает «не реализован»; `web/` — README. В `go.mod` одна зависимость — `go.yaml.in/yaml/v3`.
- В `internal/crypto` нет `PasswordHasher`, `AEAD`, `Signer`/`Verifier` (ТЗ 10.2) — с них начинается этап.

## Риски
- Объём больше этапа 1 (около 28 дней); экраны — главный кандидат на перенос.
- Radix UI может не работать при строгом CSP без inline-стилей (Р13) — тогда замена примитивов или ADR об исключении.
- Сборка фронтенда без сети: в облачной среде npm может быть недоступен так же, как vuln.go.dev; проверять `make check` в CI.
- Права СУБД «только добавление» проверяются только на настоящем PostgreSQL: тесты аудита требуют БД в CI.
- В облаке не проходят `make lint`, `make sast`, `make vuln` (этап 1) — до решения об инструментах они проверяются только в CI.

## Открытые вопросы
### Ревью 2.r1 (2.2–2.6): замечания для P4
Исправлено 21.10.2026 (поток F1): В1–В5, Н1, Н3 (допуск 0600 зафиксирован в ADR-0007), Н4, Н6, Н9; Н2 отмечено в ADR-0007 (перенос УЦ за `Provider` — этап 6). Н5 и Н8 исправлены вместе с ревью 2.r2 (Н8 оказался не пренебрежимым: при пуле из одного соединения первая запись в пустой журнал зависала до таймаута). Остаётся Н7 — нужен нагрузочный тест этапа.

Важные:
- **В1. Сервер не проверяет цепочку аудита периодически** (2.4; `cmd/aisec-server/main.go:107`). `audit.Verifier.Run` нигде не запускается: в сервере нет ни проверки при запуске, ни раз в час, хотя `security-functions.md` (РСБ.4) это заявляет, а ТЗ 7.4 требует периодической проверки в MVP. Сценарий: нарушитель с правами владельца таблиц правит запись — до ручного `aisec-cli audit verify` нарушение никто не видит, в «Состоянии системы» его нет; проверка по «известным записям из памяти процесса» в сервере не работает вовсе. Исправление: запускать `NewVerifier(auditLog).Run(ctx, DefaultVerifyInterval, …)` (флаг `-audit-verify-interval`), итог — в `sysstatus` (нарушение — уведомление РСБ.4 в «Состоянии системы» и `system.alert`), тест на запуск; сверить `security-functions.md`.
- **В2. Между архивациями у цепочки нет опоры вне БД** (2.4, 2.5; `internal/audit/chain.go`, `verify.go:155`). Хеш цепочки без ключа, подписанная точка появляется только при архивации (срок хранения по умолчанию 365 дней). Владелец таблиц или суперпользователь СУБД отключает триггеры, переписывает журнал и `audit_verifications` и пересчитывает цепочку — после перезапуска сервера `rewritten` не обнаружится. `threat-model.md` (остаточные риски) считает это закрытым задачей 2.5, но 2.5 закрывает только удаление начала журнала. Исправление (на выбор): хранить в `audit_verifications` имитовставку головы цепочки ключом, выведенным из ключа данных (`keyring`, назначение `audit-head`), и проверять её при запуске; либо периодическая подписанная точка без удаления записей. Минимум — честно описать остаточный риск в `threat-model.md`.
- **В3. Ограничение частоты и адрес клиента не учитывают прокси и NAT** (2.6; `internal/api/ratelimit.go:30`, `:140`). Правило `/api/v1/auth/` — 10 запросов в минуту на адрес — общее для `GET /auth/setup`, входа, выхода, второго фактора, смены пароля и настроек входа; клиент определяется только по `RemoteAddr`. За обратным прокси или TLS-шлюзом ГОСТ (ТЗ 10.3 требует работы за ним со списком доверенных прокси) все пользователи — один адрес: консоль офиса упирается в 429, а нарушитель за тем же NAT блокирует вход администраторам; в аудит (`access.denied`, вход) пишется адрес прокси, а не клиента (РСБ.1 «откуда»). Исправление: строгий предел только для `POST` входа, первичной настройки и проверки второго фактора, остальное — по общему правилу; флаг списка доверенных прокси с разбором `X-Forwarded-For` справа налево; общая функция адреса клиента для ограничителя и аудита; тесты; `attack-surface.md`.
- **В4. Фильтр секретов отклоняет запись аудита из-за значения, которое задал пользователь** (2.4; `internal/audit/record.go:359`). `secretValue` отвергает всю запись, если строковое значение начинается с `bearer `/`basic ` или похоже на URL с паролем. В подробности попадает свободный текст: причина просмотра содержимого (`events.content_read`) и другие свободные строки. Сценарий: причина «Bearer-токен утёк, разбор» — запись аудита не создаётся, просмотр содержимого отвечает 503; обязательное событие не пишется (РСБ.2), хотя для полей субъекта выбран принцип «нормализовать, а не отклонять». Исправление: для значений заменять подозрительную строку на «[скрыто]» и записывать событие; отказ оставить только для ключей (ошибка программиста); тест с такой причиной.
- **В5. Без `-audit-signing-pub` сервер принимает точку с любой подписью** (2.5; `cmd/aisec-server/main.go:97`). Участник роли `aisec_audit_archiver` без ключа аудита вставляет точку с мусорной подписью, триггеры её пропускают (они проверяют связность, а не подпись), записи удаляются — сервер видит только связность, нарушение заметит лишь ручной `audit verify -keys`. Параметр необязателен и в `make dev` не задан. Исправление: если в `audit_checkpoints` есть точки, а ключа нет — отказ запуска (или хотя бы состояние «подписи не проверяются» в «Состоянии системы» и запись в техжурнал); в поставке (2.19) и `make dev` — задавать параметр. **Решение владельца 21.10.2026: обязателен** — если в `audit_checkpoints` есть точки, а `-audit-signing-pub` не задан, сервер не запускается; новая установка без точек стартует без ключа; в поставке и `make dev` ключ задаётся. Закрывает и вопрос 2.19 об обязательности параметра.

Незначительные:
- Н1 (2.6, `idempotency.go`). Ответы с `Idempotency-Key` хранятся в памяти 24 ч целиком; маршруту, который показывает секрет один раз (токен API, коды восстановления, секрет TOTP), признак `Idempotent` давать нельзя — закрепить проверкой в `Router.add` или тестом.
- Н2 (2.3, `internal/crypto/pki.go:43`). УЦ и выпуск сертификатов (`NewCA`, `IssueServer`, `LoadCA`, `mtls.go`) не входят в `Provider` и берут `crypto/rand` напрямую — для профиля `gost` (этап 6) их нужно перенести за интерфейс; отметить в ADR-0006/0007.
- Н3 (2.3, `internal/crypto/tls.go:104`). `ReadKeyFile` принимает 0600, а ТЗ 10.4 и ADR-0007 требуют 0400 для мастер-ключа — либо требовать 0400 в `keyring`, либо зафиксировать допуск в ADR-0007.

Важные:
- **В10. Одно событие может погубить пакет до 500 событий, в том числе по воле пользователя LLM-приложения** (2.15; `internal/events/pgstore.go:267`, `migrations/0010_events.sql:59`, `internal/api/events.go:77`, `internal/gateway/eventsink.go:121`). В режиме `full` содержимое шифруется как `json.Marshal(Content)`, а `encoding/json` экранирует `<`, `>`, `&` и управляющие символы в 6 байт (`<`). `Check` проверяет только длину текста (до 64 КиБ на запрос и ответ), а ограничение `sealed` — 256 КиБ: 64 КиБ символов `<` дают 393 КиБ (проверено). СУБД отвергает вставку, транзакция пакета откатывается, сервер отвечает 422 на весь пакет, шлюз считает его окончательным отказом и отбрасывает все события пакета. Сценарий: пользователь приложения шлёт промпт из 64 КиБ `<<<…` (или просит модель повторить такой текст) — вместе с ним пропадают события его же атак и чужие события того же пакета; в «Состоянии системы» остаётся только счётчик `rejected`. Это расходится с решением владельца по 2.15 «поштучный отказ в пакете». Тот же путь у `policy_mode` события `auth_failure`: `Validate` его не проверяет, а ограничение столбца — `monitor`/`enforce` (`internal/events/event.go:214`, `0010_events.sql:26`). Исправление: размер шифротекста проверять в `Check`/`contentArgs` и отказывать в одном событии (`limits`), либо поднять предел `sealed` до худшего случая (6 × 2 × 65 552 + накладные) и кодировать без HTML-экранирования (`json.Encoder.SetEscapeHTML(false)`); `policy_mode` проверять для всех типов; в `Check` сверить все `CHECK` таблиц `events` и `event_content`; тест с 64 КиБ `<` в `full` и с `auth_failure` с чужим `policy_mode` — пакет принят, отказ только в одном событии.
- **В11. Чтение и выгрузка событий занимают все соединения с СУБД** (2.16; `cmd/aisec-server/main.go:41`, `internal/api/events_console.go:400`, `internal/events/query.go:223`). У сервера один пул из 10 соединений на всё: вход, журнал аудита, приём событий шлюзов, консоль. Выгрузка держит соединение и курсор, пока клиент читает ответ (до `ExportTimeout` = 2 мин), список с фильтром `detector` по 31 суткам — до 10 с; ограничений на одновременные запросы нет, общий предел — 600 запросов в минуту с адреса. Защита CSV от формул обходится разделителем «;» русской локали** (2.16; `internal/events/export.go:72`). `CSVCell` проверяет только первый символ ячейки, а `encoding/csv` берёт в кавычки лишь поля с запятой, кавычкой или переводом строки. - Н22 (2.16, `internal/events/aggregate.go:257`, `internal/api/events.go:51`). `received_at` ставится часами сервера приложения, а отметка агрегатов сдвигается по `now()` СУБД с отставанием 1 мин: при расхождении часов хостов больше ~45 с события попадают в уже пройденное окно и в агрегаты не входят никогда. - Н23 (2.15, 2.16, `internal/keyring/keyring.go:314`). Кэш производных ключей общий для шифрования и чтения: просмотр содержимого за 8 разных суток сбрасывает кэш вместе с ключом текущих суток, и следующее шифрование резервирует новую пачку 4096 (счётчик `derived_key_usage` растёт без шифрований). Для чтения выводить ключ без кэша и без резерва.

### Ждут решения владельца
- Задача 2.16: аудитор по праву `events.read` создаёт и удаляет свои сохранённые фильтры (личные настройки, на данные не влияют); владелец приложения не видит события до 2.11 (отбор по своим приложениям, УПД.8); фильтр по `detector` разбирает `details` каждой строки и на длинных периодах медленный; кнопка «Показать содержимое» — в 2.26.
- Задача 2.26: (1) подсветки находок в тексте запроса и ответа нет: `EventContent` — одна строка, а позиции находок в `details.findings` относятся к отдельному фрагменту (`location`, например `messages[0].content`) исходного, не замаскированного текста; без сегментов и смещений от сервера подсветка вводила бы в заблуждение, поэтому показан список находок. Нужно поле сегментов в ответе 2.16 или в `details`. (2) Сортировка по колонкам и изменение ширины колонок не сделаны: API отдаёт только порядок «новые сверху», курсор держит пару (ts, id). (3) Кнопки «Ложное срабатывание», «Подтверждено», «Создать исключение» и связанные оповещения и инцидент появятся с оповещениями, инцидентами и исключениями (этап 3). (4) Изображения и аудио в карточке — этап 5. (5) Глобальный поиск в шапке каркаса остаётся отключённым. (6) Период — пресеты до 30 суток; произвольные даты и диапазон до 31 суток — отдельной задачей.
- Задача 2.27: (1) журнал аудита в консоли не показан: в `api/openapi.yaml` нет операций чтения журнала (`GET /audit`, право `audit.read`) и проверки цепочки по кнопке (`POST /audit/verify`, DM-43); на «Состоянии системы» выводится только итог фоновой проверки (`audit_chain`). Нужна серверная часть в `internal/audit` и `internal/api` (через план) и вкладка в «Администрировании». (2) Часовой пояс показа задаёт только флаг сервера `-timezone`, записи через API нет: в «Администрировании» он описан текстом, поле ввода появится после `PUT` настроек времени. Режим хранения содержимого (`full`/`masked`/`off`) тоже настройка шлюза, не сервера; редактируются только сроки хранения (`events/settings`). (3) Снятие и выдача токенов других пользователей из консоли — по `api_tokens.manage` с областью `all`; отдельного экрана «все токены организации» нет, это та же вкладка. (4) Пользователи грузятся целиком (страницы по 200, до 50 страниц): для организаций с тысячами учётных записей нужны поиск и серверная пагинация.
- Задача 2.20: счётчики отброшенных событий идут с последнего запуска шлюза (при перезапуске шлюза счётчик обнуляется, история не копится) — нужна ли накопительная сумма, решить в 2.26 (экран «События»). Предел журнала аудита по умолчанию 20 ГиБ и порог 80% — настройки, подходящие значения подберёт эксплуатация. Уведомления ИАФ.4 и УПД.6 в «Состоянии системы» считаются по записям `auth.locked` и `access.denied` за 24 часа и не дублируются в `system.alert`. Состояние времени `unknown` (ОС без `adjtimex` или ошибка вызова) уведомления не поднимает. Исключение из правила `syscall` (ADR-0014) — на ревью.

- Задача 2.21: Дополнительные dev-пакеты сверх перечня ТЗ 11.2: `@eslint/js`, `globals`, `@testing-library/jest-dom`, `@types/*`, `jsdom`, `@vitejs/plugin-react`, `@tailwindcss/vite`. В сборочный образ нужны Node.js ≥ 22.12 и кэш npm (иначе `web-check`, `web-e2e` в CI не выполняются).

## Цель и критерии приёмки (ТЗ, 14)
- Все функции раздела 7 с меткой MVP реализованы и описаны в `docs/cert/security-functions.md`. Уведомления ИАФ.4, УПД.6, РСБ.5, ОЦЛ.5, ВРМ.1 пишут запись в журнал аудита и выводятся на «Состояние системы»; доставка по каналам — этап 3.
- Матрица «роль × эндпоинт» покрыта тестами на отказ.
- Подмена бинарника или пакета политик обнаруживается.
- Строки DM-39, DM-42, DM-43 (в части обнаружения) покрыты e2e-тестами.
- Интерфейс работает при строгом CSP (e2e).
- `make dm-coverage` при `STAGE=2` без проблем: 21 строка этапа 1 и DM-39, DM-42, DM-43.

## Состояние кода на 20.10.2026
- Есть: шлюз этапа 1 с локальным YAML (Р2 этапа 1), `internal/crypto` (`Hasher`, `MAC`, `Random`, TLS, самотест, заглушка `gost`), `internal/auth` (ключи приложений, `auth_failure`, ограничение частоты), события с приёмником JSONL, `aisec-cli app-key`.
- Только заготовки (`doc.go`): `internal/audit`, `internal/integrity`, `internal/store`, `internal/api`; `cmd/aisec-server` печатает «не реализован»; `web/` — README. В `go.mod` одна зависимость — `go.yaml.in/yaml/v3`.
- В `internal/crypto` нет `PasswordHasher`, `AEAD`, `Signer`/`Verifier` (ТЗ 10.2) — с них начинается этап.

## Риски
- Объём больше этапа 1 (около 28 дней); экраны — главный кандидат на перенос.
- Radix UI может не работать при строгом CSP без inline-стилей (Р13) — тогда замена примитивов или ADR об исключении.
- Сборка фронтенда без сети: в облачной среде npm может быть недоступен так же, как vuln.go.dev; проверять `make check` в CI.
- Права СУБД «только добавление» проверяются только на настоящем PostgreSQL: тесты аудита требуют БД в CI.
- В облаке не проходят `make lint`, `make sast`, `make vuln` (этап 1) — до решения об инструментах они проверяются только в CI.

## Открытые вопросы
### Ревью 2.r1 (2.2–2.6): замечания для P4
Исправлено 21.10.2026 (поток F1): В1–В5, Н1, Н3 (допуск 0600 зафиксирован в ADR-0007), Н4, Н6, Н9; Н2 отмечено в ADR-0007 (перенос УЦ за `Provider` — этап 6). Н5 и Н8 исправлены вместе с ревью 2.r2 (Н8 оказался не пренебрежимым: при пуле из одного соединения первая запись в пустой журнал зависала до таймаута). Остаётся Н7 — нужен нагрузочный тест этапа.

Важные:
- **В1. Сервер не проверяет цепочку аудита периодически** (2.4; `cmd/aisec-server/main.go:107`). `audit.Verifier.Run` нигде не запускается: в сервере нет ни проверки при запуске, ни раз в час, хотя `security-functions.md` (РСБ.4) это заявляет, а ТЗ 7.4 требует периодической проверки в MVP. Сценарий: нарушитель с правами владельца таблиц правит запись — до ручного `aisec-cli audit verify` нарушение никто не видит, в «Состоянии системы» его нет; проверка по «известным записям из памяти процесса» в сервере не работает вовсе. Исправление: запускать `NewVerifier(auditLog).Run(ctx, DefaultVerifyInterval, …)` (флаг `-audit-verify-interval`), итог — в `sysstatus` (нарушение — уведомление РСБ.4 в «Состоянии системы» и `system.alert`), тест на запуск; сверить `security-functions.md`.
- **В2. Между архивациями у цепочки нет опоры вне БД** (2.4, 2.5; `internal/audit/chain.go`, `verify.go:155`). Хеш цепочки без ключа, подписанная точка появляется только при архивации (срок хранения по умолчанию 365 дней). Владелец таблиц или суперпользователь СУБД отключает триггеры, переписывает журнал и `audit_verifications` и пересчитывает цепочку — после перезапуска сервера `rewritten` не обнаружится. `threat-model.md` (остаточные риски) считает это закрытым задачей 2.5, но 2.5 закрывает только удаление начала журнала. Исправление (на выбор): хранить в `audit_verifications` имитовставку головы цепочки ключом, выведенным из ключа данных (`keyring`, назначение `audit-head`), и проверять её при запуске; либо периодическая подписанная точка без удаления записей. Минимум — честно описать остаточный риск в `threat-model.md`.
- **В3. Ограничение частоты и адрес клиента не учитывают прокси и NAT** (2.6; `internal/api/ratelimit.go:30`, `:140`). Правило `/api/v1/auth/` — 10 запросов в минуту на адрес — общее для `GET /auth/setup`, входа, выхода, второго фактора, смены пароля и настроек входа; клиент определяется только по `RemoteAddr`. За обратным прокси или TLS-шлюзом ГОСТ (ТЗ 10.3 требует работы за ним со списком доверенных прокси) все пользователи — один адрес: консоль офиса упирается в 429, а нарушитель за тем же NAT блокирует вход администраторам; в аудит (`access.denied`, вход) пишется адрес прокси, а не клиента (РСБ.1 «откуда»). Исправление: строгий предел только для `POST` входа, первичной настройки и проверки второго фактора, остальное — по общему правилу; флаг списка доверенных прокси с разбором `X-Forwarded-For` справа налево; общая функция адреса клиента для ограничителя и аудита; тесты; `attack-surface.md`.
- **В4. Фильтр секретов отклоняет запись аудита из-за значения, которое задал пользователь** (2.4; `internal/audit/record.go:359`). `secretValue` отвергает всю запись, если строковое значение начинается с `bearer `/`basic ` или похоже на URL с паролем. В подробности попадает свободный текст: причина просмотра содержимого (`events.content_read`) и другие свободные строки. Сценарий: причина «Bearer-токен утёк, разбор» — запись аудита не создаётся, просмотр содержимого отвечает 503; обязательное событие не пишется (РСБ.2), хотя для полей субъекта выбран принцип «нормализовать, а не отклонять». Исправление: для значений заменять подозрительную строку на «[скрыто]» и записывать событие; отказ оставить только для ключей (ошибка программиста); тест с такой причиной.
- **В5. Без `-audit-signing-pub` сервер принимает точку с любой подписью** (2.5; `cmd/aisec-server/main.go:97`). Участник роли `aisec_audit_archiver` без ключа аудита вставляет точку с мусорной подписью, триггеры её пропускают (они проверяют связность, а не подпись), записи удаляются — сервер видит только связность, нарушение заметит лишь ручной `audit verify -keys`. Параметр необязателен и в `make dev` не задан. Исправление: если в `audit_checkpoints` есть точки, а ключа нет — отказ запуска (или хотя бы состояние «подписи не проверяются» в «Состоянии системы» и запись в техжурнал); в поставке (2.19) и `make dev` — задавать параметр. **Решение владельца 21.10.2026: обязателен** — если в `audit_checkpoints` есть точки, а `-audit-signing-pub` не задан, сервер не запускается; новая установка без точек стартует без ключа; в поставке и `make dev` ключ задаётся. Закрывает и вопрос 2.19 об обязательности параметра.

Незначительные:
- Н1 (2.6, `idempotency.go`). Ответы с `Idempotency-Key` хранятся в памяти 24 ч целиком; маршруту, который показывает секрет один раз (токен API, коды восстановления, секрет TOTP), признак `Idempotent` давать нельзя — закрепить проверкой в `Router.add` или тестом.
- Н2 (2.3, `internal/crypto/pki.go:43`). УЦ и выпуск сертификатов (`NewCA`, `IssueServer`, `LoadCA`, `mtls.go`) не входят в `Provider` и берут `crypto/rand` напрямую — для профиля `gost` (этап 6) их нужно перенести за интерфейс; отметить в ADR-0006/0007.
- Н3 (2.3, `internal/crypto/tls.go:104`). `ReadKeyFile` принимает 0600, а ТЗ 10.4 и ADR-0007 требуют 0400 для мастер-ключа — либо требовать 0400 в `keyring`, либо зафиксировать допуск в ADR-0007.
- Н4 (2.3, `cmd/aisec-cli/init.go`). PEM-копии мастер-ключа, ключей подписи и ключа УЦ (`files[].data`) после записи не затираются — `clear` для закрытых файлов после `writeKeyFiles`.
- Н5 (2.3, 2.5, `cmd/aisec-cli/audit.go:106`). Записи `system.init`, `audit.archive`, `audit.export`, `audit.chain_*` от CLI содержат только пользователя ОС; логин СУБД (`session_user`), под которым выполнено действие, не пишется — добавить в подробности (РСБ.1 «кто»).
- Н6 (2.5, `cmd/aisec-cli/audit_archive.go:133`). Если ошибка пришла на `COMMIT`, а точка записана, команда завершается успешно без итога — вывести, что архивировано и куда.
- Н7 (2.4, `internal/audit/log.go`). Каждая запись берёт одну глобальную рекомендательную блокировку и отдельно читает `audit_settings`; с `api_token.used` на каждый запрос это узкое место — измерить в нагрузочном тесте этапа и при необходимости кэшировать настройки.
- Н8 (2.4, `internal/audit/log.go:192`). Для пустого журнала `head` получает точку через пул, а не через транзакцию: второе соединение при удержании блокировки цепочки — читать точку в той же транзакции.
- Н9 (ADR-0014, `internal/sysstatus/clock_linux.go`). Решение приемлемо: вызов только на чтение, исключение узкое, линтер не ослаблен — ADR можно перевести в «принято». Оговорка: `syscall.Timex.Esterror` на 32-битных Linux (386, arm) имеет тип `int32`, и файл там не соберётся — либо приведение `int64(tx.Esterror)`, либо записать в ADR, что поддерживаются только amd64 и arm64.

### Ревью 2.r2 (2.7–2.10): замечания для P4
Исправлено 21.10.2026 (поток F1): В6–В9, Н10, Н13, Н14, Н15, Н16. Н11 оговорено в ADR-0013 (доп. п. 4) и `threat-model.md` — запись `api_token.used` до обработчика ждёт нагрузочного теста (Н7). Остаётся Н12 — новая сессия при выходе из `password_change` меняет хранилище и клиент шире 1–2 строк; риск низкий: в `password_change` права роли не действуют, а токены сессии уже защищены `HttpOnly`/CSRF.

Нумерация продолжает ревью 2.r1. Пересечение с В3 из 2.r1 (общий предел 10 запросов в минуту на все `/api/v1/auth/`-маршруты, адрес клиента за прокси и NAT) здесь не повторено: те же исправления закрывают и маршруты второго фактора.

Важные:
- **В6. Изменение своей роли сразу даёт права на изменение без второго фактора** (2.8, 2.9; `internal/auth/rbac.go:380`, `rbac_pg.go:299`, `roles.go:17`). `UpdateRole` не завершает сессии пользователей роли, а `SessionGrants` даёт права роли любой сессии `active`, не проверяя, прошла ли она второй фактор. Сценарий: у своей роли только права `.read`, второй фактор ей не обязателен, пользователи вошли по паролю. Администратор добавляет роли `users.manage` или `events.content.read` (признак `mfa_required` включается принудительно), и открытые сессии роли до 12 ч работают с правами безопасности без фактора; укравший пароль такого пользователя получает их сразу. В `threat-model.md` остаточный риск описан как «обязательность фактора действует со следующего входа», без учёта расширения прав. Исправление: хранить в сессии признак пройденного фактора и при обязательном факторе (роль или `mfa_required_all`) без признака давать только `session`, переводя сессию в `mfa_setup`; либо в транзакции `UpdateRole` завершать сессии пользователей роли, если `mfa_required` включился или добавились права на изменение. Тест; ADR-0013 п. 6, `threat-model.md`.
- **В7. Единственного администратора безопасности можно заблокировать без возможности восстановления** (2.7–2.9; `internal/auth/service.go:273`, `pgstore_mfa.go:236`, `admin.go:101`, `policy.go:73`). Снять блокировку, сбросить пароль или фактор может только тот, чьи права покрывают права цели (`canManage`): для `security_admin` — другой `security_admin`; себе нельзя (`ErrSelf`); аварийной команды в `aisec-cli` нет. Сценарий: нарушитель, знающий логин, раз в 15 минут вводит 5 неверных паролей (предел 10 в минуту с адреса это пропускает), и администратор не входит, пока идёт атака; при `lockout_minutes = 0` блокировка бессрочна, и снять её некому. Знающий пароль вводит 5 неверных кодов TOTP — блокировка завершает и полные сессии администратора. Потеря устройства и кодов восстановления единственным администратором — тот же тупик. Обновить `threat-model.md` и `security-functions.md`.
- **В8. Токен API выпускается без повторной проверки и переживает реакцию на компрометацию** (2.10; `internal/auth/apitoken.go:239`, `service.go:429`, `admin.go:150`, `admin.go:183`, `pgstore_mfa.go:268`). - **В9. Запрос без аутентификации пишет запись в журнал аудита** (2.10; `internal/api/bearer.go:43`, `internal/auth/apitoken.go:304`). Важные:
- **В10. Одно событие может погубить пакет до 500 событий, в том числе по воле пользователя LLM-приложения** (2.15; `internal/events/pgstore.go:267`, `migrations/0010_events.sql:59`, `internal/api/events.go:77`, `internal/gateway/eventsink.go:121`). В режиме `full` содержимое шифруется как `json.Marshal(Content)`, а `encoding/json` экранирует `<`, `>`, `&` и управляющие символы в 6 байт (`<`). `Check` проверяет только длину текста (до 64 КиБ на запрос и ответ), а ограничение `sealed` — 256 КиБ: 64 КиБ символов `<` дают 393 КиБ (проверено). СУБД отвергает вставку, транзакция пакета откатывается, сервер отвечает 422 на весь пакет, шлюз считает его окончательным отказом и отбрасывает все события пакета. Сценарий: пользователь приложения шлёт промпт из 64 КиБ `<<<…` (или просит модель повторить такой текст) — вместе с ним пропадают события его же атак и чужие события того же пакета; в «Состоянии системы» остаётся только счётчик `rejected`. Исправление: размер шифротекста проверять в `Check`/`contentArgs` и отказывать в одном событии (`limits`), либо поднять предел `sealed` до худшего случая (6 × 2 × 65 552 + накладные) и кодировать без HTML-экранирования (`json.Encoder.SetEscapeHTML(false)`); `policy_mode` проверять для всех типов; в `Check` сверить все `CHECK` таблиц `events` и `event_content`; тест с 64 КиБ `<` в `full` и с `auth_failure` с чужим `policy_mode` — пакет принят, отказ только в одном событии.

- **В12. Защита CSV от формул обходится разделителем «;» русской локали** (2.16; `internal/events/export.go:72`). `CSVCell` проверяет только первый символ ячейки, а `encoding/csv` берёт в кавычки лишь поля с запятой, кавычкой или переводом строки. Поле `model` задаёт клиент приложения в теле запроса к шлюзу, то есть нарушитель снаружи. Исправление: брать в кавычки каждое поле (свой писатель или замена `encoding/csv`) и добавлять апостроф перед значением, у которого после любого из «,», «;», табуляции стоит символ `= + - @`; при желании — BOM UTF-8, чтобы кириллица в Excel открывалась без перекодировки. Важные:
- **В14. Смена адреса провайдера сохраняет признак «невнешний» и учётные данные** (2.11; `internal/apps/providers.go:153`, `internal/auth/permissions.go:113`). `providers.manage` — не право безопасности: оно есть у администратора системы и у токенов. `UpdateProvider` меняет `base_url`, `auth_url`, `ca_pem` и `type`, а `External` и сохранённые учётные данные оставляет. Сценарий: администратор безопасности снял признак «внешний» у GigaChat в контуре заказчика (с причиной, DM-40). Администратор системы или токен с `providers.manage` ставит внешний `base_url` и свой корневой сертификат. В `monitor` ПДн уходят без маскирования, шлюз отправляет туда учётные данные провайдера в `Authorization`, хотя сам этот субъект их прочитать не может. В аудите при этом обычный `provider.update` без `weakening`. **Решение:** если меняется узел (схема, хост, порт) `base_url` или `auth_url`, `ca_pem` или `type`, то (1) у провайдера с `external = false` признак сам возвращается в `true`, и в той же записи аудита появляется `external_reset: true`; (2) учётные данные сбрасываются (`credential = NULL`), их задают заново. Так секрет привязан к адресу назначения. Тесты: смена адреса у невнешнего провайдера даёт `external = true` и `credential_set = false`; смена имени или таймаутов ничего не сбрасывает. **Исправлено** (H4, 9f3c991).
- **В15. Поля приложения, ослабляющие защиту, меняются без `applications.policy` и без отметки `weakening`** (2.11; `internal/apps/applications.go:179`, `:249`, `:143`; `internal/api/applications.go:119`). Право `applications.manage` (у администратора системы и у токенов) через `POST`/`PUT /api/v1/applications` даёт четыре изменения. (а) `fail_mode: fail_open`: при сбое детекторов запрос уходит к модели без проверки. (б) Новые домены в `exfil_allow_domains`: это исключение для DM-11, а ТЗ 5.16 (DM-40) относит к ослаблению «новое или продлённое исключение». (в) Удаление слов и выражений из `lists`: правила `lists.*` перестают срабатывать. (г) Переключение приложения на провайдера с `external = false`: маскирование в `monitor` выключается. `application.update` пишется без `weakening`. Так обходится разделение УПД.2, ради которого заведено `applications.policy`. **Решение:** `fail_mode`, `exfil_allow_domains` и `lists` перенести в поля защиты (`PUT /api/v1/applications/{id}/protection`, право `applications.policy`). При создании без этого права действуют только умолчания, явные значения дают 422, как сейчас с `policy`. Смена провайдера с внешнего на невнешний разрешена только с `applications.policy` (иначе 403) и пишется с `weakening = true`. `weakening()` дополнить: `fail_closed → fail_open`, новые домены exfil, удалённые слова, выражения или списки, провайдер стал невнешним. Изменение контракта согласовать с экраном «Приложения» (2.25): поля переходят в шаг администратора безопасности. **Исправлено** (H4, c050d5f).
- **В16. Один неверный объект останавливает доставку в шлюзы всех изменений, в том числе отзыва ключей** (2.13; `internal/policy/bundle/build/build.go:116`, `:189`; ADR-0009, п. 1). Сборка работает по принципу «всё или ничего». Если содержимое не прошло проверку, шлюзам бессрочно выдаётся последняя корректная версия. Причины: в политике есть правило `lists.X`, а словаря `X` нет хотя бы у одного приложения с этой политикой (сохранение такое принимает, проверка только при сборке); содержимое больше 4 МиБ (`MaxSize/2`), а это пять приложений со словарями по 1 МиБ (`appMaxBody`) или ключи из Н24; у приложения не найден провайдер. Сценарий: администратор безопасности добавил в общую политику правило `lists.secret`, а у одного из 40 приложений словаря нет. Потом скомпрометированный ключ отозван, приложение отправлено в архив. Шлюзы продолжают принимать этот ключ (ИАФ.8), пока кто-нибудь не найдёт неудачный `bundle.build` в журнале аудита. В «Состоянии системы» этого не видно. **Решение:** (1) приложение, не прошедшее проверку, исключается из пакета, его маршруты на шлюзе отвечают 503 (`fail closed`), а остальное собирается и доставляется. Целиком пакет не собирается только при сбое уровня пакета (размер). В `bundle.build` пишется список исключённых приложений с причинами. (2) Проверка при сохранении: `PUT` политики и `PUT` приложения отвечают 422, если изменение ломает сборку для приложений, которые её используют (тот же `gateway.CheckApplications`); суммарный размер словарей тоже проверяется в API. (3) Условие «Пакет конфигурации собран не полностью» (ОЦЛ.3) в «Состоянии системы» с записью `system.alert` при смене. **Исправлено** (H4, d7619ce): исключённое приложение остаётся в части `unavailable` с ключами, шлюз отвечает по нему 503 `app_unavailable`; проверка при сохранении — кодом сборки (`build.CheckApplication`, `CheckPolicy`); миграция 0020.
- **В17. Журнал аудита читается через основной пул без предела параллельности** (2.4a; `internal/api/auditlog.go:218`, `internal/audit/query.go:123`, `cmd/aisec-server/main.go:49`). Решение В11 (отдельный пул чтения, предел одновременных запросов) на новый эндпоинт не перенесено. В условии `(ts >= $2 AND ts < $3 OR NOT isfinite(ts))` с `ORDER BY seq DESC LIMIT` диапазон по индексу `(org_id, ts)` не применим из-за `OR`. Выборка за давний период или по редкому `object_id` проходит журнал назад по `seq` до таймаута 10 с, а журнал может занимать до 20 ГиБ (РСБ.5). Сценарий: токен с `audit.read` (токенам это разрешено) шлёт 10 параллельных запросов за период полугодовой давности. Все 10 соединений основного пула заняты по 10 с, и так раз за разом. Вход, запись аудита (а с ней любое действие администратора и `api_token.used`) и приём событий ждут соединения. **Решение:** `audit.Log.List` читает через пул чтения (по образцу `events.WithReadDB`, `statement_timeout` 10 с); одновременно не больше 2 выборок на субъект и 4 на сервер, сверх этого — 429. Запрос переписать: диапазон `ts >= $2 AND ts < $3` по индексу и `ORDER BY ts DESC, seq DESC` с курсором `(ts, seq)` (в курсоре время уже есть). Записи с бесконечным `ts` — отдельной частью `UNION ALL` по частичному индексу `WHERE NOT isfinite(ts)` (новая миграция). **Исправлено** (H4, 8f3c3b7; миграция 0021, пул чтения журнала — 4 соединения, `statement_timeout` 12 с при сроке выборки 10 с).
- **В18. Уведомление ОЦЛ.5 одно на все компоненты: второе нарушение целостности не попадает в журнал** (2.20; `internal/sysstatus/service.go:268`, `:399`). Условие `integrity` — одно логическое значение на сервер и все шлюзы, а `Transition` пишет `system.alert` только при его смене. В записи `raised` нет ни компонента, ни причины. Нарушение целостности конкретного компонента не регистрируется (ОЦЛ.5, РСБ.1). **Решение:** условие по компоненту — код `integrity:server` или `integrity:gateway:<id>` (строка `system_alert_state` по коду, без миграции, если код — текст до 128 символов). В `details` — компонент, источник (самотест или целостность), причина и число нарушений. В «Состоянии системы» уведомление ОЦЛ.5 остаётся одной строкой со списком компонентов. **Исправлено** (H4, d7619ce; миграция 0020 расширяет CHECK кодов условий из 0011 и 0015: он перечислял коды).

Важные:
- **В19. В режиме с сервером конфигурация шлюза не на контроле целостности, хотя от неё зависит доверие к пакету** (2.17, ОЦЛ.3; `cmd/aisec-gateway/main.go:287`). Шлюз ставит под наблюдение (`Watch`) только файл `-config`, а с `-server` этот флаг запрещён (2.13). Поэтому у шлюза с сервером не контролируется ни один файл: ни `-bundle-pub` (корень доверия пакетов конфигурации), ни `-server-ca`, ни `-user-hmac-key`. Сценарий: нарушитель с правом записи на хосте шлюза подменяет `bundle-signing.pub` своим ключом и кладёт в `-state-dir` свой подписанный пакет: все приложения в `monitor` и `fail_open`, без правил. После перезапуска шлюз принимает этот пакет, а пакеты сервера отвергает как неверно подписанные. Проверка целостности при этом «в порядке» (бинарник не менялся). В «Состоянии системы» видно только отставание пакета (условие H4 по ETag), а не нарушение целостности; ещё след — записи `bundle.rejected`. **Решение:** (1) у шлюза в `Watch` идут файлы `-bundle-pub`, `-server-ca` и `-user-hmac-key`; у сервера — `-audit-signing-pub`, `-ca-cert` и `bundle-signing.pub` из `-keys-dir`. Сертификаты TLS не включать: их меняют при продлении. Эталон — хеш тех байтов, которые компонент прочитал при запуске (это же закрывает Н37). (2) В heartbeat шлюз передаёт отпечатки (хеш профиля) открытых ключей из `-bundle-pub`; сервер сверяет их со своим `bundle-signing.pub` (текущим и следующим при ротации). Несовпадение — нарушение целостности этого шлюза в условии ОЦЛ.5 по компоненту (как в В18). Отставание по ETag (H4) остаётся как есть. Обновить `api/internal-openapi.yaml`, `attack-surface.md`, `threat-model.md`. Тесты: подмена `-bundle-pub` после запуска даёт `changed`; чужой отпечаток в heartbeat поднимает ОЦЛ.5 для этого шлюза.
- **В20. Откат на старую подписанную версию не обнаруживается** (2.17, DM-42; `internal/integrity/check.go:205`, `internal/integrity/pgstore.go:84`). Манифест проверяется только на подпись и совпадение файлов. Ничто не мешает поставить вместо текущего выпуска более старый, тоже подписанный ключом производителя: бинарники вместе с их манифестом. Сценарий: в выпуске N исправлена уязвимость шлюза. Нарушитель с правом записи возвращает на хост выпуск N−1 вместе с его манифестом и подписью. Все проверки при запуске, по таймеру и через `aisec-cli verify` проходят, в `integrity_checks` меняется только `manifest_version`, уведомления нет. **Решение:** (1) `Result` получает `ManifestCreated` (поле `created` манифеста — время коммита, оно упорядочено, в отличие от `git describe`); в `integrity_checks` новый столбец `manifest_created` (следующая свободная миграция). (2) Сервер и `aisec-cli verify` с БД сравнивают `created` с максимумом по успешным проверкам этого компонента. Если меньше — итог `manifest_rollback`, это нарушение с обычной реакцией `-integrity-action`. (3) Намеренный откат — `aisec-cli verify -accept-rollback`: запись `integrity.rollback_accepted` в аудит с обеими версиями, после неё максимум сбрасывается до текущего. (4) Шлюз передаёт `manifest_version` и `manifest_created` в heartbeat. Сервер хранит максимум по шлюзу в `gateways` и при уменьшении поднимает ОЦЛ.5 для этого шлюза. Тест: проверка манифестом с более ранним `created` даёт `manifest_rollback`, после `-accept-rollback` — `ok`.
- **В21. Восстановление возвращает в силу то, что отозвали после даты копии** (2.19; `internal/backup/pg.go:724`, `cmd/aisec-cli/backup.go:271`). Токены API, ключи приложений, состояние и пароли учётных записей восстанавливаются такими, какими были на момент копии. Сценарий: в понедельник утёк токен API администратора системы, его отозвали, сотрудника уволили (деактивация), пароль администратора безопасности сменили после фишинга. В пятницу установку восстанавливают из копии воскресенья: токен снова действует, уволенный входит, старый пароль подходит. Запись `backup.restore` об этом не предупреждает, `docs/install/backup.md` тоже. **Решение:** (1) токены API восстанавливаются отозванными: `revoked_at = now()`, `revoke_reason = 'backup_restore'`, их выпускают заново (токены не нужны для работы шлюзов). Флаг `-keep-api-tokens` оставляет их как в копии и пишется в запись `started`. (2) Ключи приложений и учётные записи восстанавливаются как есть, иначе копия теряет смысл. В выводе, в записи `done` (`copy_age_hours`) и в `docs/install/backup.md` — обязательный шаг: по архиву журнала аудита (`aisec-cli audit export` с даты копии) повторить отзывы ключей, деактивации и сбросы паролей, сделанные после неё. (3) Если копия старше 7 суток, восстановление требует флаг `-accept-old-copy`. Тесты: токен из копии после восстановления отклоняется; с `-keep-api-tokens` принимается.
- **В22. Восстановление не проверяет объекты правилами сервиса: копия от другого выпуска ломает пакет шлюзов** (2.19; `internal/backup/snapshot.go:498`, `internal/backup/pg.go:531`). Политики сверяются только по хешу текста, а содержимое не проверяется. Версия спецификации не сверяется с каталогом детекторов текущего выпуска. `lists`, `aliases`, `quotas` и `exfil_allow_domains` приложений идут в БД как есть (`json.RawMessage`). Разрешения своих ролей и токенов не сверяются с каталогом `internal/auth` и правилом 2.10 (токенам нельзя права безопасности). Копию от более старого выпуска восстановление допускает (`st.SchemaVersion >= snap.SchemaVersion`). Сценарий: копию выпуска N−1 восстанавливают на выпуске N, где переименована категория детектора или ужесточён разбор словарей. Восстановление проходит, а сборка пакета падает (В16): шлюзы остаются без конфигурации, причина видна только в `bundle.build`. Так же в БД попадает токен с правом, которое API выдать не дал бы. **Решение:** перед записью «до» прогнать проверки сервиса: `versions` — разбор и `Validate` каждой текущей версии по `builtin.All()`; `gateway.CheckApplications` для приложений с их политиками и словарями; проверку разрешений ролей и токенов по каталогу и правилу 2.10. Любая ошибка — отказ целиком до записи, с перечнем объектов (код 3, `stage: refused`, `reason: invalid`). Тест: копия с правилом на несуществующую категорию и с токеном с `audit.verify` отклоняется, в БД ничего не меняется.

Незначительные:
- Н33 (2.18, `cmd/aisec-server/main.go:92`). Самотест сервера проверяет только криптопрофиль: «детекторов у сервера нет». С 2.12 сервер выполняет детекторы в песочнице политик (`gateway.Sandbox`), и по её итогам администратор безопасности принимает политики. Нужно передать `builtin.All()` в самотест сервера (реакция по детекторам — `alert`, итог — в `selftest.result`).
- Н34 (2.17; `internal/sysstatus/service.go:205`, `internal/gateway/reports.go:43`). Признак `test_signed` виден только в списке проверок сервера. Шлюз его в heartbeat не передаёт, условия в «Состоянии системы» он не поднимает. Закрытый тестовый ключ лежит в репозитории, а ключа производителя пока нет. Поэтому пилот на сборке без `RELEASE=1` имеет контроль целостности только для вида: подписать свой манифест может любой, у кого есть репозиторий. Нужно: `test_signed` в `CheckReport` шлюза, условие-предупреждение «Сборка не для поставки (тестовый ключ манифеста)» в «Состоянии системы», пилотный пакет (E3) — только с `RELEASE=1`.
- Н35 (2.17; `internal/integrity/key_release.go`, `tools/manifest/main.go:132`). Ничто не мешает тестовому ключу попасть в поставочную сборку: если в `keys/manifest.pub` по ошибке скопирован `manifest-test.pub`, сборка с `aisec_release` примет манифест, подписанный ключом из репозитория. Нужно: тест под тегом `aisec_release` (встроенный ключ не равен тестовому) и отказ `tools/manifest build -key`, если открытый ключ равен тестовому.
- Н36 (2.17, `internal/integrity/monitor.go:152`). Если итог проверки по команде (`POST /api/v1/system/integrity/verify`) не сохранён в `integrity_checks` и журнал, ответ всё равно 200. Это действие администратора без записи аудита. При ошибке `Record` для ручной проверки нужно отвечать 503, итог остаётся в техническом журнале (как предлагает Н30).
- Н37 (2.17; `cmd/aisec-gateway/main.go:80`, `internal/integrity/check.go:151`, `:243`). Сверяется не то, что работает. Эталон файла конфигурации снимается повторным чтением после `LoadGatewayFile`, и изменение между этими чтениями не видно. Исполняемый файл открывается по пути `os.Executable()`: после замены файла переименованием проверка сверяет новый файл на диске, а процесс работает со старым. Нужно: эталон — хеш прочитанных байтов, на Linux исполняемый файл читать через `/proc/self/exe`.
- Н38 (2.17, ОЦЛ.2; `internal/api/integrity.go:34`). По команде из консоли проверяется только сервер. Шлюз проверяется при запуске и раз в час, а итог `aisec-cli verify` на хосте шлюза без доступа к БД в журнал не попадает. Нужно: признак `verify_requested` в ответе на heartbeat, шлюз выполняет проверку и присылает итог; кнопка в консоли запрашивает проверку всех действующих компонентов.

- Н40 (2.19; `cmd/aisec-cli/backup.go:331`, `internal/auth/pgstore.go:266`). Восстановление и первичная настройка берут разные рекомендательные блокировки. Остановку сервера (ADR-0017) никто не проверяет. Если сервер работает, а токен `init` ещё действует, первичная настройка может пройти между проверкой пустоты и вставкой: в установке окажется и восстановленный, и новый администратор безопасности. - Н41 (2.19, `internal/backup/format.go:74`). Фраза проверяется только по длине: `aaaaaaaaaaaaaaaa` и `1234567890123456` проходят, а подбор по украденному файлу идёт без ограничений (остаточный риск в `threat-model.md`). - Н42 (2.24b, `internal/auth/setup.go:138`). Выбор `full` или `none` при первичной настройке пишется в `setup.completed` без `weakening`, хотя для приложений такое хранение считается ослаблением (Н32, DM-40). Пока сервер значение не читает, это незаметно. Когда новые приложения начнут получать его по умолчанию, ослабление пройдёт без отметки. Нужно: `weakening: true` в `setup.completed` при `retention_mode` ≠ `masked`; `application.create` с режимом по умолчанию `full` — тоже с `weakening`.
- Н43 (2.24b, `internal/auth/setup.go:65`). Допустимость часового пояса зависит от tzdata хоста (`time.LoadLocation`). В образе без `/usr/share/zoneinfo` (scratch, как `deploy/compose/dev/Dockerfile`) любой пояс, кроме `UTC`, даёт 422, в том числе умолчание консоли Europe/Moscow: первичная настройка не проходит. Кроме того, принимаются имена не из IANA (`posixrules`, `localtime`, `Factory`). Нужно: `import _ "time/tzdata"` в `cmd/aisec-server` (стандартная библиотека, около 450 КиБ) и отказ для имён без «/», кроме `UTC`.

(2) Восстановление в непустую установку только добавляет объекты, замену запрещают триггеры неизменяемости; откат на работающей установке — версии политик. (3) Отказы до подключения к БД (нет файла, неверные флаги, фраза короче 16 символов) в журнал аудита не пишутся — это проверка ввода, записи некуда писать. (4) Ручная проверка: ввод фразы с терминала, восстановление на новой установке при остановленном сервере, повторная регистрация шлюзов с файлом ключа псевдонимов. (5) Профиль `gost` копию не поддерживает (этап 6).
- TOTP в «Яндекс Ключе» не проверен: консоль выдаёт стандартный TOTP (RFC 6238, SHA-1, 6 цифр, 30 с), Google Authenticator и независимая проверка кодом прошли. Владелец проверит Яндекс Ключ вручную; при сбое — ввод секрета вручную или параметры otpauth (`internal/auth/mfa.go`).

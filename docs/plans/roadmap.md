# Дорожная карта работы в проекте

Работа ведётся сессиями Claude Code внутри одного проекта, подключённого к репозиторию. Одна сессия — один шаг этой карты. Состояние хранится только в репозитории: статусы в `docs/plans/stage-<N>.md`, раздел «Открытые вопросы» и журнал там же, история — в git. Промпты для каждого шага — в `docs/PROMPTS.md`, раздел «Работа в проекте».

## Настройка проекта (один раз, человек)
1. Создать проект и подключить репозиторий `azuresong-afk/ai_railway`.
2. В окружении проекта задать переменную `GOTOOLCHAIN=go1.27.3`: в образе установлен Go 1.24.
3. В инструкции проекта вставить текст «Инструкции проекта» из `docs/PROMPTS.md`. `CLAUDE.md` загружается из репозитория сам, копировать его не нужно.
4. Каждую сессию начинать с промпта P1 «Статус» (Haiku): он показывает, что делать дальше, ничего не меняя.

## Выбор модели
| Модель | Когда |
|---|---|
| Opus | Безопасность и сложные решения: `internal/auth`, `crypto`, `audit`, `integrity`, конвейер шлюза, политики, псевдонимизация, детекторы и разборщики недоверенного ввода, ADR, планирование этапа, ревью `cert-reviewer` (наследует модель сессии), закрытие этапа |
| Sonnet | Обычный код без влияния на безопасность, mock-сервисы, e2e, экраны по дизайн-системе, корпуса, метрики, документы |
| Haiku | Только чтение: статус, проверка, не выполнена ли задача, сверка документов со списком DoD |

Модель переключается командой `/model` в начале сессии; в репозиторий модель не записывается. Если шаг затронул код из строки Opus, а выполнялся на Sonnet, — ревью на Opus обязательно.

## Защита от повторного выполнения
Источник истины — таблица задач в плане этапа и история git. Правила одинаковы для всех промптов, поэтому повторный запуск промпта безопасен: на выполненной задаче сессия только сообщает статус.

1. **Статусы:**
   - `не начата`;
   - `в работе (ДД.ММ.ГГГГ)`;
   - `готова`;
   - `заблокирована (причина)`.
2. **Метка в коммите.** Тема коммита задачи заканчивается меткой `(задача <N> этапа <M>)`, исправлений по ревью — `(ревью <N>–<K> этапа <M>)`. По метке коммит находится командой `git log --oneline --grep "задача <N> этапа <M>"`.
3. **Проверка перед началом.** `git pull --ff-only`, затем статус в плане и поиск метки в git.
   - Статус `готова` или метка найдена — ничего не менять, ответить «уже выполнено: <коммит>» и предложить следующий шаг.
   - `в работе` — остановиться и спросить владельца: возможно, задачу ведёт другая сессия.
   - `заблокирована` — сообщить причину.
4. **Взятие задачи.** Сначала только статус `в работе (…)`, коммит `docs: задача <N> этапа <M> — в работе` и push. Если push отклонён, другая сессия успела раньше: `git pull --ff-only`, проверить снова, при занятой задаче — остановиться.
5. **Завершение.** В коммите задачи — статус `готова` и строка журнала. Незавершённая сессия оставляет статус `в работе` и запись в «Открытых вопросах»: что сделано и что осталось.
6. **Зависание.** Если `в работе` дольше двух дней без новых коммитов по задаче, следующая сессия не продолжает её сама, а спрашивает владельца.

## Документация — часть готовности
Задача не готова, пока не обновлено всё, что она затронула. В отчёте сессии — список обновлённых документов; если документ не нужен, сказать почему.
- Всегда:
  - статус и журнал в плане этапа;
  - «Открытые вопросы».
- Если затронуто:
  - `docs/detectors.md` — таблица, раздел детектора, бенчмарки;
  - `docs/cert/attack-surface.md` — интерфейсы, порты, переменные окружения, CLI;
  - `docs/cert/security-functions.md`;
  - `docs/cert/threat-model.md`;
  - `docs/cert/fuzzing.md`;
  - `docs/cert/components.yaml`;
  - `api/openapi.yaml`;
  - ADR в `docs/adr/`;
  - README;
  - строки матрицы обнаружения (ТЗ, 5.16) и ID строки в именах тестов.
- Проверки: `make docs-check` — в каждой сессии; `make check` — один раз перед коммитом задачи.

На что обратить внимание при планировании (ТЗ, 14):
- **Этап 2.** Сервер управления и функции безопасности: auth, crypto, audit, integrity — всё на Opus, только через план и ADR. Экраны веб-консоли — Sonnet после дизайн-системы.
- **Этап 3.** Пилотная версия: установка, документация для заказчика — Sonnet; оповещения и инциденты — Opus.
  - Проверка адаптеров GigaChat и YandexGPT на реальных учётных записях (Р8 этапа 1) — после задачи установки пилота в docker compose, на собранной установке (решение владельца 22.10.2026). В плане этапа 3 — отдельная задача сразу после установки.
- **Этап 4.** ML-детекторы и выбор способа интеграции ONNX — ADR на Opus; агенты и MCP — Opus.
- **Этап 5.** Изолированный `aisec-media`, RAG, тестирование устойчивости — Opus; корпуса — Sonnet.
- **Этап 6.** Документы для сертификации: пишет Sonnet, сверку с требованиями и ревью делает Opus.

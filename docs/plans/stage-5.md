## Риски
- Качество OCR на русском и на бледном тексте неизвестно до эксперимента; если ни один движок не даёт приемлемого CER на 4 vCPU — изображения остаются под `non_text`, а DM-45/DM-46 переносятся (решение владельца).
- Нативный код OCR (Tesseract и Leptonica) расширяет поверхность атаки и объём заимствований для сертификации — поэтому рекомендация Р8 в пользу ONNX через уже согласованный ORT.
- Изоляция `aisec-media` средствами контейнера зависит от среды заказчика (seccomp, cgroups v2); для установки без Docker (этап 6) — systemd-юниты с теми же ограничениями.
- `judge.llm` зависит от модели заказчика: задержка, стоимость и устойчивость самого оценщика к инъекциям; по умолчанию — асинхронно, чтобы не замедлять трафик.
- Тестирование устойчивости — исходящий трафик из продукта; ошибка в allowlist превращает сервер в инструмент атаки на чужие адреса: allowlist, запрет внутренних адресов и аудит запусков обязательны, ревью 5.r3.
- Задачи владельца (5.1–5.6) — на критическом пути к первому пилоту, а не к закрытию этапа 5: их задержка сдвигает пилот.
- Объём этапа (7–11 недель) — самый большой; при нехватке времени первыми переносятся `media_sanitize` (5.45), экраны тестирования устойчивости (5.34) и автоматическое пополнение реестра по трафику (часть 5.17).

**Важные**
- **5В1 (5.8, остатки волны A). Восстановление копии переносит у встроенных правил безопасности и системных включение, важность, название, окно подавления и группировку без проверки — а API их потом не меняет.** `internal/alerting/stored.go:38-46` (`CheckStoredRule` для `Locked(b.Kind)` сверяет только условие, группировку и получателей), `internal/backup/pg_sections.go:550-560` (`writeAlertRules` пишет `enabled`, `severity`, `name`, `description`, `suppress_minutes`, `group_minutes` из копии), `internal/alerting/service.go:309-315` (`lockedConflict`: у правил безопасности и системных через API меняются только получатели), `internal/alerting/service.go:462-489` (`EnsureBuiltins` существующие строки не трогает). Сценарий: администратор системы, который снимает копии и знает пароль, расшифровывает файл, ставит `enabled: false` правилам `agents.tool_poisoning` (DM-24), `agents.tool_changed` (DM-25), `security.recipients_changed` и `security.shadow_ai_alias_probe`, шифрует заново и восстанавливает в новую установку. Проверка проходит, оповещений безопасности нет, и вернуть их нельзя ни из консоли, ни через API: это разделение обязанностей, которое API соблюдает. Тот же путь без злого умысла: копия прежнего выпуска, если в новом выпуске у встроенного правила безопасности изменились важность или окно подавления, навсегда оставляет старые значения. Попутно: встроенное правило с ключом, которого нет в выпуске, отклоняет всю копию (`stored.go:31-33`), и копию выпуска, где правило ещё было, нельзя восстановить. Исправление: для `Locked` из копии берутся только получатели (проверка — `parseRecipients`), остальные поля — значения встроенного правила этого выпуска (в `writeAlertRules` — `UPDATE … SET recipients, updated_at, updated_by`); либо `CheckStoredRule` требует равенства `Enabled`, `Severity`, `Name`, `Description`, `SuppressMinutes` и `GroupMinutes` встроенному. Неизвестный выпуску `builtin_key` — пропуск со строкой отчёта (`resolve`), а не отказ. Тесты: копия с выключенным правилом безопасности — после восстановления правило включено (или отказ с именем поля); копия с неизвестным `builtin_key` восстанавливается со строкой о пропуске. — **исправить в C4**

**Незначительные**
- 5Н1 (5.8): `cmd/aisec-cli/backup_check.go:158-194` проверяет сертификат шлюза, OIDC, LDAP, лицензии и встроенные правила и тогда, когда установка не пустая и `Restore` эти настройки не пишет (`withoutSettings`). Копия, у которой не проходит непереносимая настройка (например, лицензия чужим ключом из стенда), отклоняется целиком, хотя ничего из неё не записалось бы. - 5Н2 (5.8, 5.15): `internal/backup/pg_sections.go:804-813` — при восстановлении в установку с более старой версией текущая установки становится предыдущей без повторной проверки. Загрузка так не делает: `keep` в `PGStore.Save` (`internal/servicedb/pgstore.go:150-163`) не переносит в предыдущую версию, не прошедшую проверку, потому что откат должен вести на проверенную базу. Кроме того, `writeServiceDB` (`:783`) не берёт advisory-блокировку вида (`pg_advisory_xact_lock`, как `PGStore.inTx`): `FOR UPDATE` не блокирует отсутствующие строки. - 5Н3 (5.15): возврат предыдущей версии (`POST /api/v1/shadow-ai/catalog/rollback`, `POST /api/v1/compliance/base/rollback`) доступен токенам API. Возврат — единственная операция, которая понижает версию базы без нового подписанного файла: украденный токен импорта откатывает каталог, и новые ИИ-сервисы перестают распознаваться. Исправление: возврат только в сессии консоли, отказ токену 403 (по образцу `license.manage`); тест на отказ; строка в `attack-surface.md`. — **исправить в C4**
- 5Н4 (5.9): `internal/gateway/control.go:397` — признаки возможностей сервера (`limits`, а с этапа 4 и `quota_leases`, `approvals`) обновляются только при успешном ответе. Если сервер откатили на прежний выпуск без перезапуска шлюза, шлюз продолжает слать `limits`, строгий разбор (`internal/api/body.go:23`) отвечает 400 на каждый heartbeat, и шлюз до перезапуска выглядит недоступным, а отчёты самотеста и целостности не доходят.

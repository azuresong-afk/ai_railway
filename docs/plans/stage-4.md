# План этапа 4. Расширение защиты

ТЗ версии 0.6, раздел 14, этап 4, и разделы, на которые он ссылается: 1.4 (S5–S7, S11), 4.3, 5.1 (сессии, группы, JWT), 5.2, 5.3 (`require_approval`), 5.4 (эталон системного промпта), 5.9–5.11, 5.15, 5.16, 7 (ИАФ.7, УПД.9), 8.12. Статусы: `не начата`, `в работе`, `готова`, `заблокирована`.

**Статус плана: подтверждён** владельцем 27.10.2026 (составлен 26.10.2026 потоком F2b при закрытии этапа 3). Решения Р1–Р12 приняты; новые библиотеки (раздел ниже) — по-прежнему отдельным согласием владельца в своей задаче. По Р1 на старте — файл ключа на зашифрованном носителе и подпись на машине без сети; переход на мастер-ключ с рабочими ключами (выпуски, лицензии, базы) — при 4.26, решение в ADR-0022.

## Цель и критерии приёмки (ТЗ, 14)
- Сценарии S5 (опасное действие агента), S6 (косвенная инъекция), S7 (подготовка к аттестации) и S11 (теневой ИИ) проходят как e2e-тесты.
- Строки матрицы 5.16 с этапом 4 и части «ML — 4», «NER — 4», «MCP — 4», «группы — 4» покрыты тестами: `make dm-coverage` при `STAGE=4` без проблем.
- Метрики ML-детекторов на корпусе лучше эвристик на согласованную величину ([Решение] Р4: величина).

Дополнительно, до первого пилота (решение владельца 26.10.2026 при закрытии этапа 3): проверка GigaChat и YandexGPT на реальных учётных записях (3.6), ручные проверки `docs/pilot/manual-checks.md`, замер установки по руководству на чистой ВМ (≤ 1 ч), выпускная сборка с ключом производителя (Н34, Н35), остаток замечаний этапа 3 (раздел «Перенесено в этап 4» в `stage-3.md`).

## Состояние кода на 26.10.2026
- Этап 3 закрыт с пометкой 27.10.2026: ротация пяти ключей, поставка пилота в docker compose (образы на scratch, резервная копия и восстановление, `restore-finish`), оповещения (все типы MVP, DM-38–DM-44), каналы (почта, webhook, syslog/CEF), передача аудита в SIEM, инциденты, отметки ложных срабатываний и исключения в политиках, цены, бюджеты и дашборды, отчёты и рассылка, сертификат заказчика для адреса шлюза, демо-данные, DAST в CI, e2e `STAGE=3`.
- Только заготовки (`doc.go`): `internal/compliance` (5.9), `internal/media` (этап 5).
- Действие `require_approval` в движке политик не реализовано; агентов, MCP, сессий (`X-AISec-Session`), эталона системного промпта, групп пользователей, LDAP/OIDC, ML-детекторов, теневого ИИ и лицензий нет.
- Отозванные ключи приложений 30 суток идут в пакет с `revoked: true` (Д-E2E-1, поток 3-F1c): формат пакета изменён — при обновлении шлюзы обновляются раньше сервера (старый шлюз отвергает пакет с новым полем и остаётся на прежнем).
- Квоты и бюджеты — в памяти одного шлюза; ADR-0021 (аренда лимита у сервера) принят в части выбора, реализация — здесь (4.29).
- Сетевые клиенты разрешены только в `cmd/aisec-gateway`, `internal/gateway`, `internal/providers`, `internal/notify` (`NET_CLIENT_ALLOWED`); LDAP, OIDC (JWKS) и MCP-прокси добавляются туда отдельным решением.
- Миграции заняты до 0046, ADR — до 0021.

| Р1 | [Решение] Ключ производителя: Ed25519, хранится офлайн у владельца (отдельный носитель, копия в сейфе), подпись манифеста выпускной сборки — отдельной командой на машине без сети; отпечаток публикуется в руководстве установки и в README поставки; тестовый ключ остаётся только для `make images-test`. | Р3 | [Решение] ML-детекторы: отдельный процесс `aisec-ml` на localhost шлюза (Unix-сокет), ONNX Runtime через cgo только в нём; шлюз и сервер остаются без cgo; при недоступности `aisec-ml` — эвристики и событие `ml_unavailable` (fail-open для ML, политика решает остальное). | Р4 | [Решение] Порог «лучше эвристик»: на размеченном корпусе RU/EN — полнота выше не меньше чем на 10 п. п. при доле ложных срабатываний не выше, чем у эвристики; задержка p95 `aisec-ml` ≤ 30 мс на 2 000 токенов на 4 vCPU | ТЗ 14 требует «согласованную величину» | ADR-0024 |
| Р5 | [Решение] LDAP: библиотека `github.com/go-ldap/ldap/v3` (MIT) после согласия владельца — свой разборщик BER хуже по рискам; только LDAPS или StartTLS, проверка сертификата, сервисная учётная запись только для поиска. OIDC: код авторизации с PKCE, проверка ID-токена своей реализацией поверх `internal/crypto` (RS256, ES256, EdDSA; JWKS только с настроенного издателя, кэш с ограничением) без `go-oidc`/`go-jose`. Второй фактор: при OIDC — делегируется IdP (`amr`/`acr`), при LDAP — свой TOTP сохраняется. Сопоставление групп с ролями — явная таблица, одна роль на пользователя (решение 2.9) | ТЗ 5.14, 7 (ИАФ.7); меньше зависимостей в `internal/auth` | ADR-0025 |
| Р6 | [Решение] Доступ к моделям по группам (УПД.9, DM-33) и проверка JWT пользователя в шлюзе: шлюз проверяет JWT корпоративного IdP по JWKS из пакета конфигурации (сервер забирает JWKS и кладёт в подписанный пакет, шлюз сам в IdP не ходит); группы — из утверждения, заданного в карточке приложения; без JWT — прежний `X-AISec-User` по настройке приложения | ТЗ 4.3, 5.1; шлюз не получает нового исходящего соединения | ADR-0025 |

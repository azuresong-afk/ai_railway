# Установка пилота на виртуальной машине (docker compose)

Руководство для того, кто ставит AISec на ВМ заказчика: от чистой ВМ до первого приложения, которое ходит в модель через шлюз. Цель — **не дольше часа** (таблица в разделе 2). Устройство поставки и обоснования — в [ADR-0019](../adr/0019-postavka-pilota.md), чек-лист пилота — в [docs/pilot/checklist.md](../pilot/checklist.md). Работу консоли описывает [руководство администратора](admin-guide.md).

> **Образы с тестовым ключом манифеста (`aisec-test/…:ВЕРСИЯ-test`) заказчику не передаются.** Их собирает CI для проверки. Поставочные образы `aisec/…` подписаны ключом производителя (`make images`, `RELEASE=1`, [ADR-0022](../adr/0022-klyuch-proizvoditelya.md)), их подлинность проверяется по отпечатку ключа (раздел 3, шаг 1). Если консоль или `aisec-cli verify` пишут «сборка с тестовым ключом манифеста», это тестовая сборка.

В составе установки: сервер управления с веб-консолью (`aisec-server`), один шлюз (`aisec-gateway`), PostgreSQL и служебная `aisec-cli`. Один шлюз на пилот — это решение, а не ограничение ВМ: квоты считаются в памяти шлюза (раздел 7 руководства администратора, ADR-0021).

## Лаборатория: установка одной командой
Для своего стенда, где не хочется ставить Go и Node.js, есть `deploy/compose/pilot/lab-install.sh`. Он сам проходит разделы 3 и 4 до первичной настройки. **Не для заказчика:** образы собираются с тестовым ключом манифеста (`aisec-test/…:ВЕРСИЯ-test`), консоль и `aisec-cli verify` это показывают.

**Что нужно.** ВМ из раздела 1. Docker Engine 24 или новее с плагинами Compose 2.20 или новее и buildx (пакеты `docker-ce`, `docker-compose-plugin`, `docker-buildx-plugin`). Доступ в интернет к Docker Hub (или его зеркалу) и к `registry.npmjs.org` — только на время сборки. Исходники: `git clone` репозитория или его архив.

```
cd deploy/compose/pilot
sudo ./lab-install.sh --host 192.168.1.50
```

`--host` — адрес или имя ВМ, по которому вы открываете консоль и по которому приложения обращаются к шлюзу; можно указать несколько раз или через запятую. Первая сборка занимает 5–15 минут, следующие быстрее.

Скрипт по шагам: собирает образы в Docker (`deploy/build/Dockerfile.lab`) и проверяет их целостность; выполняет `prepare-host.sh` и заполняет `.env`; готовит сертификаты консоли и шлюза (варианты ниже); создаёт ключи установки; запускает сервер, регистрирует шлюз `gw-1` и запускает всё. В конце выводит адрес консоли, адрес шлюза, путь к корню УЦ `/srv/aisec/ca.crt` и **токен первичной настройки** (показывается один раз, действует 24 часа).

**Сертификаты: два варианта.** Выбираются первым запуском; источник записывается в `.env` (`AISEC_TLS_SOURCE`), и повторный запуск с другим источником скрипт не примет (как перейти — ниже).

| | Собственный УЦ установки (по умолчанию) | УЦ заказчика (`--tls-dir`) |
|---|---|---|
| Когда | своего УЦ нет: стенд, демонстрация, пилот без ИТ-службы | у организации есть УЦ, и браузеры и приложения ему уже доверяют |
| Что делает скрипт | `aisec-cli tls init`: одноразовый УЦ и сертификаты консоли и шлюза на имя консоли и все `--host`, срок 365 суток; закрытый ключ УЦ не сохраняется | проверяет готовые сертификаты (`aisec-cli tls check`) и только после этого кладёт их в `/srv/aisec/secrets` |
| Что добавить в доверенные | корень установки `/srv/aisec/ca.crt` — у каждого администратора (браузер) и каждого приложения; отпечаток SHA-256 — в выводе скрипта | ничего, если корень УЦ заказчика уже в доверенных у администраторов и приложений; иначе — его (`/srv/aisec/ca.crt` — копия) |

Пример с собственным УЦ установки:
```
sudo ./lab-install.sh --host 192.168.1.50 --host lab.example.ru
```

Пример с УЦ заказчика:
```
sudo install -d -o root -g root -m 0700 /root/aisec-tls
# положите туда пять файлов (см. ниже), затем:
sudo ./lab-install.sh --host aisec.corp.example.ru --host 10.20.30.40 --tls-dir /root/aisec-tls
```
Каталог `--tls-dir` — абсолютный путь, владелец root, без записи для группы и остальных, и каталоги на пути к нему тоже принадлежат root (подойдёт `/root/aisec-tls`, не подойдёт каталог в домашнем каталоге обычного пользователя); файлы — обычные, без символьных и жёстких ссылок, каждый не больше 64 КиБ (ключ — 16 КиБ, права `0600`):

| Файл | Что в нём |
|---|---|
| `console.crt` | первым — сертификат консоли, за ним промежуточные сертификаты УЦ (корень можно не класть) |
| `console.key` | закрытый ключ консоли без пароля, один ключ в файле: RSA от 2048 бит или ECDSA P-256/P-384 |
| `gateway.crt`, `gateway.key` | то же для шлюза (адрес для приложений) |
| `ca.crt` | ровно один корневой (самоподписанный) сертификат УЦ, выпустившего оба сертификата |

Требования к сертификатам (их и проверяет `tls check`): назначение `serverAuth`, срок действия идёт (меньше 30 суток до конца — предупреждение), цепочка строится до корня из `ca.crt`. В SAN **обоих** сертификатов — каждое имя и адрес из `--host` (IP-адрес — в поле IP Address, не DNS); в SAN сертификата консоли — ещё и имя консоли внутри установки: по нему шлюз находит сервер. Имя консоли по умолчанию — первое DNS-имя из `--host` (в примере `aisec.corp.example.ru`), а если в `--host` только адреса — `aisec-console`; другое — `--console-name`. Зашифрованный ключ выгрузите без пароля на защищённой машине: `openssl pkey -in key.pem -out console.key`.

Дальше:
1. Собственный УЦ установки: добавьте `/srv/aisec/ca.crt` в доверенные корневые сертификаты и сверьте отпечаток SHA-256 с выводом скрипта (на ВМ его показывает и `openssl x509 -noout -fingerprint -sha256 -in /srv/aisec/ca.crt`). УЦ заказчика: добавьте его корень туда, где его ещё нет:
   - Windows (Chrome, Edge): двойной щелчок по файлу → «Установить сертификат» → «Текущий пользователь» → «Поместить все сертификаты в следующее хранилище» → «Доверенные корневые центры сертификации»;
   - Linux: `cp ca.crt /usr/local/share/ca-certificates/aisec-lab.crt && update-ca-certificates`;
   - Firefox: «Настройки» → «Приватность и защита» → «Сертификаты» → «Просмотр сертификатов» → «Центры сертификации» → «Импортировать»;
   - приложения: `curl --cacert ca.crt`, в Python — `SSL_CERT_FILE=ca.crt` или параметр `verify`.
2. Первичная настройка в консоли — раздел 4, шаг 5.
3. Провайдер LLM — раздел 5, первое приложение — раздел 6.

| Параметр | Когда нужен |
|---|---|
| `--tls-dir КАТАЛОГ` | сертификаты УЦ заказчика вместо собственного УЦ установки (выше) |
| `--bind АДРЕС` | порты 8444 и 8443 только на одном интерфейсе; по умолчанию `0.0.0.0` — на всех, а при повторном запуске — адрес из `.env` |
| `--console-name ИМЯ` | своё имя консоли внутри установки (`AISEC_CONSOLE_HOST`); по умолчанию — первое имя из `--host`, а если там только адреса — `aisec-console` |
| `--mirror РЕЕСТР` | Docker Hub отвечает 429 или закрыт: зеркало для базовых образов и PostgreSQL, например `mirror.gcr.io/library` (digest не меняется) |
| `--build-ca ФАЙЛ` | выход в интернет через прокси с проверкой TLS: корневой сертификат прокси для `npm` при сборке консоли; в образы не попадает |
| `--no-build` | не собирать, взять образы прошлого запуска (`AISEC_IMAGE_REPO` и `AISEC_VERSION` из `.env`) |

Повторный запуск пересобирает образы из текущих исходников и обновляет установку; ключи, регистрацию шлюза и адрес интерфейса (без `--bind`) не трогает. Сертификаты он тоже не меняет, но проверяет `tls check` с текущими `--host` и именем консоли: истёкший сертификат или новый `--host`, которого нет в сертификатах, остановят запуск. Другое имя консоли скрипт не примет — шлюз не узнал бы консоль — и подскажет `--console-name` с прежним именем. Установку с `--tls-dir` запускайте повторно с тем же `--tls-dir`: без него или с другими файлами скрипт откажет.

Чтобы заменить сертификаты (новые имена, истекает срок — у собственного УЦ установки по умолчанию через год — или переход с одного варианта на другой), удалите из `/srv/aisec/secrets` пять файлов `console.crt`, `console.key`, `console-ca.crt`, `gateway.crt`, `gateway.key` и запустите скрипт снова — без `--tls-dir` для собственного УЦ установки или с `--tls-dir` для УЦ заказчика. Скрипт положит новые сертификаты и пересоздаст контейнеры сервера и шлюза. Новый корень (`/srv/aisec/ca.crt`) добавьте в доверенные, прежний корень установки из доверенных удалите.

**Переход с собственного УЦ установки на УЦ заказчика без переустановки** (лаборатория стала пилотом). Два сертификата меняются по-разному:
- *Сертификат шлюза для приложений* можно заменить без перезапуска: загрузите сертификат УЦ заказчика в консоли, «Приложения» → «Подключить приложение» → шаг «Адрес шлюза» (раздел 7 [руководства администратора](admin-guide.md)). Файл `gateway.crt` остаётся запасным: шлюз вернётся к нему, если сертификат из консоли истечёт.
- *Сертификат консоли* сервер читает из файлов при запуске, загрузки через консоль для него нет. Его и корень, которому доверяет шлюз (`console-ca.crt`), меняют файлами с перезапуском сервера и шлюза. В лаборатории — удалить пять файлов и запустить `lab-install.sh --tls-dir` (выше). В установке без скрипта — шаг 3.4 «Замена сертификатов».

## 1. Что нужно

**ВМ.** Linux x86-64, 4 vCPU, 8 ГБ памяти, 40 ГБ диска (без учёта событий и копий). Время синхронизировано по [инструкции](../install/time-sync.md): без этого не работают коды TOTP, сроки ключей и сертификатов.

**Программы на ВМ.** Docker Engine 24 или новее (от root, rootless не поддерживается), Docker Compose 2.20 или новее. Проверка:
```
docker version --format '{{.Server.Version}}'
docker compose version
```

**Что приносите с собой.**
- Каталог выпуска: `aisec-manifest.json`, `aisec-manifest.json.sig`, `bin/`, `images/aisec-server.tar`, `images/aisec-gateway.tar`, `images/aisec-cli.tar` и каталог `deploy/compose/pilot`.
- **Отпечаток ключа производителя** — из этого руководства (раздел 3.1) или из письма производителя, полученного отдельно от поставки. Отпечаток в README поставки для сверки не годится: его подменил бы тот, кто подменил поставку.
- Образ PostgreSQL `postgres:17.11-alpine3.24` с тем digest, что в `compose.yaml`: из Docker Hub или из реестра организации. Продукт его не распространяет. Если Docker Hub отвечает 429 (лимит на анонимные загрузки), возьмите образ из реестра организации или зеркала и задайте `AISEC_POSTGRES_IMAGE` в `.env`; digest от реестра не зависит.
- Сертификаты TLS от корпоративного УЦ (если его нет — их выпустит `aisec-cli tls init`, шаг 3.4):
  - консоль — с именем, по которому её открывают администраторы, например `aisec.example.ru`;
  - шлюз — с именем, по которому к нему обращаются приложения, например `ai-gw.example.ru` (можно один сертификат с обоими именами);
  - корневой сертификат этого УЦ.
- Учётные данные провайдера LLM: ключ API облачного провайдера или адрес и CA локальной модели (раздел 5).

**Имена и порты.** Имена консоли и шлюза должны разрешаться в адрес ВМ у администраторов и у приложений (DNS или `/etc/hosts`).

| Порт | Кто | Куда открыть |
|---|---|---|
| 8444/tcp | консоль (HTTPS) | администраторам; адрес — `AISEC_CONSOLE_BIND` |
| 8443/tcp | шлюз (HTTPS, OpenAI-совместимый API) | приложениям; адрес — `AISEC_GATEWAY_BIND` |
| 8445/tcp | внутренний порт сервера для шлюза | **не публикуется**, только сеть Docker |
| исходящие | шлюз → провайдеры LLM, заданные в консоли; сервер → SMTP, syslog, webhook, если вы их настроили | больше никуда |

PostgreSQL и `aisec-cli` подключены только к внутренним сетям Docker. Если почта, syslog и webhook не нужны, закройте исходящие соединения сервера правилом в цепочке `DOCKER-USER` межсетевого экрана хоста. Правила `ufw`/`firewalld` публикацию портов Docker не ограничивают — используйте `DOCKER-USER` или адреса в `AISEC_*_BIND`.

## 2. Время по шагам

Часы запускаются, когда на ВМ уже стоят Docker и Compose, выпуск скопирован на ВМ, а сертификаты выпущены. Часы останавливаются, когда запрос приложения прошёл через шлюз и событие видно в консоли (раздел 6, п. 4). Выпуск сертификатов и заявки на доступ к сети в зачёт не идут — их закладывают заранее ([чек-лист](../pilot/checklist.md), «Подготовка»).

| Шаг | Раздел | Ориентир |
|---|---|---|
| Проверка поставки и загрузка образов, `prepare-host.sh`, `.env`, сертификаты | 3 | 10 мин |
| PostgreSQL, миграции, ключи установки | 4, шаги 1–3 | 7 мин |
| Сервер и первичная настройка в консоли, TOTP | 4, шаги 4–5 | 10 мин |
| Регистрация шлюза, запуск | 4, шаги 6–7 | 8 мин |
| Провайдер и первое приложение | 5, 6 | 15 мин |
| Проверка | 6 | 5 мин |
| **Итого** | | **55 мин** |

Фактическое время по шагам записывайте в чек-лист пилота; замер на чистой ВМ — [ручные проверки](../pilot/manual-checks.md), п. 3.

## 3. Подготовка хоста
Команды выполняются от root (`sudo -i`) в каталоге `deploy/compose/pilot`, если не сказано иное.

1. Проверьте поставку и загрузите образы (ОБН.1, [ADR-0022](../adr/0022-klyuch-proizvoditelya.md)):
   ```
   cp .env.example .env        # если .env ещё нет
   # в .env: AISEC_VENDOR_FINGERPRINT=<отпечаток ключа производителя>
   ./verify-release.sh -first /путь/к/выпуску
   ```
   Отпечаток ключа производителя: **публикуется с первым поставочным выпуском**. Это 16 групп по 4 шестнадцатеричных знака через двоеточие; сверьте его с письмом производителя. Скрипт проверяет архив образа `aisec-cli`, загружает его, проверяет им подпись манифеста и все файлы выпуска и сверяет отпечаток ключа подписи с `AISEC_VENDOR_FINGERPRINT`. Затем он проверяет и загружает остальные образы так же, как при обновлении (раздел 8). При любом расхождении загруженные образы удаляются. Продолжайте только после строки «Выпуск проверен» и задайте `AISEC_VERSION` из неё.
   PostgreSQL: `docker pull postgres:17.11-alpine3.24@sha256:…` — digest возьмите из `compose.yaml`.
2. Выполните `./prepare-host.sh`. Скрипт:
   - создаёт системных пользователей `aisec` (сервер и `aisec-cli`), `aisec-gw` (шлюз) и `aisec-db` (PostgreSQL) без входа в систему и отказывается работать, если такое имя уже занято root или пользователем со входом;
   - создаёт каталоги в `AISEC_DATA_DIR` (по умолчанию `/srv/aisec`) с правами `0700`;
   - генерирует пароли ролей БД (в вывод они не попадают);
   - записывает UID и GID пользователей в `.env`; если `.env` не было, создаёт его из `.env.example`.

   В конце он перечисляет сертификаты, которых ещё нет. Скрипт можно запускать повторно: существующие пользователи и пароли не меняются.
3. Заполните `.env` (секретов в нём нет):

   | Переменная | Что задать |
   |---|---|
   | `AISEC_VERSION` | версия выпуска — тег образов |
   | `AISEC_IMAGE_REPO` | `aisec` (поставочные образы) или реестр заказчика |
   | `AISEC_VENDOR_FINGERPRINT` | отпечаток ключа производителя (шаг 1); по нему `verify-release.sh` проверяет каждый выпуск |
   | `AISEC_CONSOLE_HOST` | имя из сертификата консоли |
   | `AISEC_CONSOLE_BIND`, `AISEC_GATEWAY_BIND` | адреса интерфейсов ВМ. По умолчанию `127.0.0.1`: консоль и шлюз доступны только с самой ВМ, для администраторов и приложений укажите адрес ВМ |
   | `AISEC_CONSOLE_PORT`, `AISEC_GATEWAY_PORT` | при необходимости другие порты (8444 и 8443) |
   | `AISEC_POSTGRES_IMAGE` | только если PostgreSQL берётся из своего реестра |
   | `AISEC_TRUSTED_PROXIES` | сети балансировщика перед консолью, если он есть |
   | `AISEC_INTEGRITY_ACTION` | `alert` (по умолчанию) или `stop` — остановка сервера при нарушении целостности |

   Остальные переменные (`AISEC_DATA_DIR`, UID и GID) оставьте как есть.
4. Положите сертификаты (при другом `AISEC_DATA_DIR` подставьте свой каталог):
   ```
   install -o aisec    -g aisec    -m 0644 console.crt  /srv/aisec/secrets/console.crt
   install -o aisec    -g aisec    -m 0600 console.key  /srv/aisec/secrets/console.key
   install -o root     -g root     -m 0644 ca.crt       /srv/aisec/secrets/console-ca.crt
   install -o aisec-gw -g aisec-gw -m 0644 gateway.crt  /srv/aisec/secrets/gateway.crt
   install -o aisec-gw -g aisec-gw -m 0600 gateway.key  /srv/aisec/secrets/gateway.key
   ```
   `console.crt` и `gateway.crt` — цепочки до корня (сертификат, затем промежуточные). Повторный `./prepare-host.sh` покажет, чего ещё не хватает; он же проверяет владельца и права закрытых ключей.

   **Проверьте сертификаты до первого запуска** (`aisec-cli tls check`): цепочка до корня из `ca.crt`, срок (меньше 30 суток — предупреждение), имя консоли и адреса в SAN, назначение `serverAuth`, ключ подходит к сертификату, стойкость ключа, ключ без пароля. Каталог проверки читает пользователь `aisec`, но изменить файлы не может:
   ```
   install -d -o root -g aisec -m 0750 /srv/aisec/tls-check
   install -o root -g aisec -m 0440 console.crt console.key gateway.crt gateway.key ca.crt /srv/aisec/tls-check/
   docker compose run --rm --no-deps -v /srv/aisec/tls-check:/in:ro aisec-cli tls check -dir /in \
     -hosts АДРЕС_ВМ,ИМЯ_ДЛЯ_ПРИЛОЖЕНИЙ -console-name AISEC_CONSOLE_HOST
   rm -rf /srv/aisec/tls-check
   ```
   Итог — по пунктам, с причиной каждой ошибки; при ошибке код выхода 1 — исправьте сертификаты и не запускайте установку. Все имена из `-hosts` должны быть в обоих сертификатах; если приложения обращаются к шлюзу по своему имени, а консоль открывают по другому, проверьте сертификат шлюза отдельно или загрузите его в консоли (раздел 7 руководства администратора).

   Корпоративного УЦ нет — выпустите сертификаты от собственного УЦ установки. Его закрытый ключ не сохраняется, поэтому выпустить им что-то ещё нельзя; корень `ca.crt` добавьте в доверенные у администраторов и приложений:
   ```
   install -d -o aisec -g aisec -m 0700 /srv/aisec/tls-new
   docker compose run --rm --no-deps -v /srv/aisec/tls-new:/out aisec-cli tls init -out /out \
     -hosts AISEC_CONSOLE_HOST,AISEC_GATEWAY_HOST,АДРЕС_ВМ
   ```
   Затем верните каталог root, чтобы `aisec` уже не мог подменить файлы, выполните команды `install` выше из каталога `/srv/aisec/tls-new` (корень — его `ca.crt`) и удалите каталог:
   ```
   chown root:root /srv/aisec/tls-new
   cd /srv/aisec/tls-new && ls -l    # пять обычных файлов, без ссылок
   rm -rf /srv/aisec/tls-new         # после install
   ```
   Срок — 365 суток (`-days`, до 825). Отпечаток корня для сверки при импорте — в выводе `tls init` или `openssl x509 -noout -fingerprint -sha256 -in ca.crt`.

   **Замена сертификатов** (истекает срок, переход с собственного УЦ установки на УЦ заказчика). Проверьте новые файлы `tls check` (выше), затем остановите сервер и шлюз, положите файлы командами `install` выше и пересоздайте контейнеры:
   ```
   docker compose stop aisec-gateway aisec-server
   # команды install из начала шага
   docker compose up -d --force-recreate aisec-server aisec-gateway
   ```
   Шлюз сверяет `console-ca.crt` с прочитанным при запуске (контроль целостности), поэтому меняйте его только при остановленном шлюзе. Регистрацию шлюза повторять не нужно: его клиентский сертификат выпускает внутренний УЦ платформы. Шлюзам на других хостах передайте новый корень (`-server-ca`) так же — с остановкой. Новый корень добавьте в доверенные у администраторов и приложений; сертификат шлюза для приложений можно вместо этого загрузить в консоли без перезапуска (раздел 7 руководства администратора).

## 4. Первый запуск
Каталог — `deploy/compose/pilot`, пользователь — root или член группы `docker`.

1. Запустите БД: `docker compose up -d postgres`. При первом запуске создаются роли `aisec_owner` (владелец схемы) и `aisec_server` (вход сервера, не владелец таблиц) и база `aisec`. Подождите, пока `docker compose ps postgres` покажет `healthy` (до минуты).
2. Миграции: `docker compose run --rm aisec-cli migrate`. Ожидаемый вывод: `применено миграций: N`.
3. Ключи установки: `docker compose run --rm aisec-cli init -dir /etc/aisec/keys`. Вывод — список созданных файлов с правами, срок сертификата внутреннего УЦ и **токен первичной настройки**. Он показывается один раз и действует 24 часа; сохраните его. Ключи лежат в `/srv/aisec/keys` и принадлежат пользователю `aisec` — менять владельца не нужно. Сделайте отдельную копию `master.key` (без него ключ данных в БД не расшифровать) и храните её не вместе с копией БД.
   Затем ещё раз выполните `./prepare-host.sh`: он положит якорь шлюза `/srv/aisec/secrets/gateway-bundle-anchor.pub` — копию `keys/bundle-signing.pub`, по которой шлюз проверяет пакеты конфигурации. Это отдельный файл: при компрометации ключа подписи меняется только он ([руководство администратора](admin-guide.md), раздел 14).
   Потеряли токен или он просрочен — до первичной настройки: `docker compose run --rm aisec-cli init -reissue-setup-token`.
4. Запустите сервер: `docker compose up -d aisec-server`. Откройте `https://AISEC_CONSOLE_HOST:8444` (имя из `.env`; корневой сертификат УЦ должен быть доверенным в браузере). При `AISEC_CONSOLE_BIND=127.0.0.1` консоль открывается только с самой ВМ; для администраторов укажите адрес ВМ в `.env` и выполните `docker compose up -d aisec-server` ещё раз.
5. Первичная настройка в консоли ([руководство администратора](admin-guide.md), разделы 3–4). Поля: «Токен настройки», «Логин», «Имя в интерфейсе», «Пароль» (от 12 символов, три класса символов), «Часовой пояс» (по умолчанию `Europe/Moscow`) и «Хранение содержимого по умолчанию» (по умолчанию «Маскированное»: на пилоте менять не нужно). Затем подключите второй фактор: отсканируйте QR-код приложением-аутентификатором, введите код и **сохраните 10 кодов восстановления** — они показываются один раз. Первый пользователь получает роль «Администратор безопасности».
6. Зарегистрируйте шлюз. Токен вводится без отображения и не попадает в историю оболочки:
   ```
   docker compose run --rm aisec-cli gateway token -name gw-1 -ttl 1h
   read -rs AISEC_GATEWAY_REGISTRATION_TOKEN && export AISEC_GATEWAY_REGISTRATION_TOKEN
   docker compose run --rm --no-deps -e AISEC_GATEWAY_REGISTRATION_TOKEN \
     aisec-gateway register -console https://AISEC_CONSOLE_HOST:8444 -console-ca /run/secrets/console-ca \
     -out-dir /var/lib/aisec-gateway/reg -state-dir /var/lib/aisec-gateway/state
   unset AISEC_GATEWAY_REGISTRATION_TOKEN
   ```
   Вместо `AISEC_CONSOLE_HOST` подставьте то же имя, что в `.env`. Токен одноразовый, срок — от 1 минуты до 168 часов. После команды `gateway token` вставьте токен в приглашение `read` (ввод не отображается) и нажмите Enter. С `-state-dir` шлюз создаёт ключ для учётных данных провайдеров, и сервер сразу его закрепляет: другой ключ он не примет.
7. Запустите всё: `docker compose up -d`. Шлюз получит подписанный пакет конфигурации, после чего `GET https://AISEC_GATEWAY_HOST:8443/readyz` отвечает `{"status":"ok"}`. Пока пакета нет, `/healthz` отвечает, а `/readyz` и маршруты приложений — 503. Проверка с ВМ:
   ```
   curl --cacert ca.crt https://AISEC_GATEWAY_HOST:8443/readyz
   ```
   Здесь `ca.crt` — корневой сертификат корпоративного УЦ, `AISEC_GATEWAY_HOST` — имя из сертификата шлюза. Если `AISEC_GATEWAY_BIND=127.0.0.1`, добавьте к `curl` флаг `--resolve AISEC_GATEWAY_HOST:8443:127.0.0.1`.

Целостность установки: `docker compose run --rm aisec-cli verify` сверяет все файлы выпуска с подписанным манифестом, код возврата 3 означает нарушение. Состояние компонентов и шлюзов — экран «Состояние системы» и `docker compose run --rm aisec-cli gateway list`.

## 5. Провайдер LLM
Экран «Провайдеры» → «Создать». Требуется право управлять провайдерами (роль «Администратор системы» или «Администратор безопасности»).

**Облачный или внешний провайдер с OpenAI-совместимым API** (тип «OpenAI-совместимый»).
1. «Название» — понятное имя, «ID провайдера» подставится сам и потом не меняется.
2. «Адрес API» — только `https`, с версией API, без параметров и учётных данных: например `https://llm.example.ru/v1`. Путь метода (`/chat/completions`) шлюз добавит сам.
3. «Корневые сертификаты провайдера (PEM)» — вставьте корень УЦ, выпустившего сертификат провайдера. Системное хранилище сертификатов шлюз не использует: доверие только к этим сертификатам, поэтому поле нужно заполнить и для облачного провайдера.
4. Сохраните, затем «Учётные данные» → вставьте ключ API. Значение шифруется и больше нигде не показывается.

**GigaChat и YandexGPT** — типы «GigaChat» и «YandexGPT». Для GigaChat дополнительно «Адрес выдачи токена» и «Область (scope)», для YandexGPT — «Идентификатор каталога». Учётные данные — как в личном кабинете провайдера.

**Локальная модель** (vLLM, Ollama, llama.cpp-сервер и другие с OpenAI-совместимым `/v1/chat/completions`) подключается тем же типом «OpenAI-совместимый». Что важно:
- адрес должен быть `https`: поставьте перед моделью обратный прокси с TLS и корпоративным сертификатом либо включите TLS в самом сервере модели;
- корень УЦ, выпустившего сертификат модели, вставьте в «Корневые сертификаты провайдера (PEM)»;
- шлюз должен достигать адрес модели из сети `gateway`. Контейнер не видит `127.0.0.1` хоста: укажите адрес или имя хоста модели в сети;
- если модели не нужен ключ, в «Учётных данных» всё равно задайте любое значение (например, `local`): без значения шлюз не отправит запросы. Шлюз передаст его как `Authorization: Bearer …`, сервер модели его проигнорирует;
- новый провайдер считается **внешним** (данные к нему маскируются и в режиме «Мониторинг»). Для локальной модели в контуре заказчика признак можно снять кнопкой «Признак «внешний»»: нужны причина и пароль или код TOTP, действие пишется в журнал аудита и вызывает оповещение (DM-40). На первом показе безопаснее оставить «внешний» и снять признак после согласования с ИБ заказчика.

Сообщение «У провайдеров без учётных данных шлюз не сможет отправлять запросы» исчезнет, когда значения заданы.

## 6. Первое приложение и проверка
1. «Приложения» → «Подключить приложение». Мастер: «Приложение» (название, ID, среда), «Провайдер и политика» (провайдер, разрешённые модели, политика «Базовая защита», режим «Как в политике» — по умолчанию мониторинг), «Адрес шлюза» (сертификат заказчика, если нужен; шаг можно пропустить) и «Ключ» (название, срок в сутках, подсети).
2. Ключ вида `aisec_…` показывается **один раз**. Передайте его команде приложения защищённым каналом, не через чат и таблицы. Мастер показывает пример запроса.
3. В приложении замените `base_url` на адрес шлюза (`https://AISEC_GATEWAY_HOST:8443/v1`) и ключ провайдера на ключ приложения. Остальной код не меняется. Проверка из командной строки:
   ```
   read -rs AISEC_KEY && export AISEC_KEY
   curl --cacert ca.crt https://AISEC_GATEWAY_HOST:8443/v1/chat/completions \
     -H "Authorization: Bearer $AISEC_KEY" -H "Content-Type: application/json" \
     -d '{"model":"МОДЕЛЬ","messages":[{"role":"user","content":"Привет"}]}'
   ```
   `МОДЕЛЬ` — одна из разрешённых моделей приложения. Ответ — обычный ответ модели.
4. Откройте «События»: запрос должен появиться в течение нескольких секунд, с решением шлюза и приложением. Это конец замера времени установки.
5. Проверьте защиту: отправьте запрос с синтетическим номером телефона `+7 300 763-88-13`. В режиме мониторинга к внешнему провайдеру уйдёт замаскированный текст, в событии будет находка `pii`. Сценарии показа заказчику — [чек-лист пилота](../pilot/checklist.md), раздел «Сценарии».

Сертификат заказчика для адреса шлюза. Шлюз отвечает приложениям сертификатом из `secrets/gateway.crt` (шаг 3.4). Если там уже корпоративный сертификат с нужным именем, приложениям ничего доверять дополнительно не нужно. Заменить сертификат без перезапуска можно в консоли — шаг «Адрес шлюза» мастера: выпустите в УЦ организации сертификат на имя адреса шлюза (в SAN, назначение `serverAuth`, RSA от 2048 бит или ECDSA P-256/P-384) и загрузите цепочку до корня и ключ без пароля ([руководство администратора](admin-guide.md), раздел 7). Шлюз переключится с очередным пакетом конфигурации. За 30 и 7 суток до конца срока придёт оповещение. Этот сертификат в резервную копию не входит.

## 7. Резервная копия и восстановление
Полная копия установки (БД, ключи, сертификаты, состояние шлюза) — `./backup.sh КАТАЛОГ` от root при работающей установке. `КАТАЛОГ` — абсолютный путь вне `AISEC_DATA_DIR`; он и все каталоги над ним принадлежат root. Скрипт создаёт в нём подкаталог `aisec-ГГГГММДДTччммссZ`. Восстановление в пустую установку — `./restore.sh КАТАЛОГ_КОПИИ`. Скрипт заканчивается `aisec-cli restore-finish`: все сессии консоли завершаются, токены API отзываются, пользователи входят заново. Порядок, правила хранения и проверка после восстановления — [руководство администратора](admin-guide.md), раздел 12. Сделайте одну копию сразу после установки и проверьте восстановление на тестовой ВМ.

## 8. Обновление
1. Получите каталог нового выпуска и проверьте его: `./verify-release.sh /путь/к/выпуску`. Скрипт работает с копией выпуска во временном каталоге (`TMPDIR`, нужно место размером с выпуск). Выпуск старше установленного он отвергает. Подпись и файлы проверяет `aisec-cli` **установленной** версии, отпечаток её ключа сверяется с `AISEC_VENDOR_FINGERPRINT`. Затем скрипт проверяет состав архивов образов, загружает их, сверяет настройки и полный список файлов каждого образа и побайтно сравнивает бинарники с проверенными. При расхождении загруженные образы удаляются. Устанавливать выпуск можно только после строки «Выпуск проверен».
2. Сделайте полную копию установки: `./backup.sh /var/backups/aisec`. При откате схемы она понадобится.
3. Укажите новую `AISEC_VERSION` в `.env`, затем:
   ```
   docker compose stop aisec-gateway aisec-server
   docker compose run --rm aisec-cli migrate
   docker compose up -d
   ```
4. Откат: вернуть прежнюю `AISEC_VERSION` и принять откат командой `docker compose run --rm aisec-cli verify -accept-rollback`, для шлюза — с `-gateway gw-1`. Запись о принятии попадает в журнал аудита. Миграции назад не откатываются: при откате схемы восстановите копию из шага 2 в пустую установку (`restore.sh`).

## 9. Частые ошибки

| Симптом | Причина и что сделать |
|---|---|
| `prepare-host.sh: запустите от root` | запущен не от root: `sudo ./prepare-host.sh` |
| `у пользователя aisec есть вход в систему` | имя занято обычным пользователем: удалите его или задайте оболочку `nologin` |
| `required variable … запустите prepare-host.sh` | в `.env` нет UID/GID: выполните `./prepare-host.sh` |
| `задайте AISEC_VERSION` (или `AISEC_DATA_DIR`, `AISEC_CONSOLE_HOST`) | переменная не задана в `.env` |
| загрузка PostgreSQL: `toomanyrequests` (429) | лимит Docker Hub: образ из реестра организации, `AISEC_POSTGRES_IMAGE` |
| `init`: «файл уже существует», «ключ данных уже создан» или «нужно 0700» | ключи уже созданы либо каталог создан не `prepare-host.sh`. `init` ничего не перезаписывает; для потерянного токена используйте `init -reissue-setup-token`, для новой установки очистите `keys/` и БД |
| сервер не стартует, в логе имя файла | неверные права или владелец файла сертификата/ключа: повторите шаг 3.4 и запустите `./prepare-host.sh` |
| браузер: сертификат не доверен | корень корпоративного УЦ не установлен в браузере или имя в адресной строке не совпадает с `AISEC_CONSOLE_HOST` |
| `register`: токен не принят или «токен уже погашен» | токен одноразовый и ограничен по сроку: выпустите новый `gateway token -name gw-1 -ttl 1h`. Если шлюз уже зарегистрирован (или регистрация прервалась после погашения токена) — `gateway token -name gw-1 -reregister`. В каталогах `reg/` и `state/` не должно быть чужих файлов, права каталогов — `0700` |
| `/readyz` отвечает 503 | шлюз ещё не получил пакет: подождите минуту, проверьте `docker compose logs aisec-gateway` и экран «Состояние системы» |
| запрос приложения: 401 `invalid_api_key` | ключ приложения не принят: неверный, отозван, просрочен или запрос не из разрешённой подсети |
| запрос приложения: 502 `upstream_unavailable` или `upstream_auth_error`, 504 `upstream_timeout` | провайдер недоступен из сети `gateway`, не доверяется его сертификат или он отклонил учётные данные: проверьте «Адрес API», корни провайдера и «Учётные данные» |
| после запроса в «Событиях» пусто | событие приходит с задержкой в несколько секунд; проверьте фильтры и период |
| `verify`: целостность нарушена, код 3 | файл выпуска изменён: переустановите образы из проверенного выпуска, не игнорируйте |
| `verify-release.sh`: «в .env нет AISEC_VENDOR_FINGERPRINT» | задайте отпечаток ключа производителя из раздела 3.1 или письма производителя |
| `verify-release.sh`: «подпись проверена ключом с отпечатком …, а в руководстве …» | выпуск подписан не ключом производителя или в `.env` опечатка: сверьте отпечаток по письму производителя; выпуск не устанавливайте, сообщите производителю |

Логи — `docker compose logs --tail 100 СЕРВИС` (`aisec-server`, `aisec-gateway`, `postgres`). Секреты и содержимое запросов в технические логи не попадают.

## 10. Своя СУБД
Задайте `COMPOSE_PROFILES=` (пусто), создайте роли и базу так же, как в `initdb/10-aisec-roles.sql`, и задайте в `.env` строки `AISEC_SERVER_DB_URL` и `AISEC_OWNER_DB_URL` с `sslmode=verify-full`. Пароли кладите только в passfile `secrets/db-server.pgpass` и `secrets/db-owner.pgpass` (формат `*:*:*:роль:пароль`, владелец `aisec`, права `0400`). Корень УЦ СУБД подключите дополнительным секретом.

## 11. Ротация ключей
Команды выполняются в каталоге `deploy/compose/pilot`. Новые файлы сразу принадлежат пользователю `aisec`, менять владельца не нужно. Когда что менять и что делать при компрометации, описано в [руководстве администратора](admin-guide.md), раздел 14.
```
docker compose run --rm aisec-cli keys status -dir /etc/aisec/keys
docker compose run --rm aisec-cli keys rotate-master -dir /etc/aisec/keys
docker compose run --rm aisec-cli keys rotate-data -dir /etc/aisec/keys
docker compose run --rm aisec-cli keys rotate-signing -dir /etc/aisec/keys    # затем: docker compose restart aisec-server
docker compose run --rm aisec-cli keys rotate-ca -dir /etc/aisec/keys         # затем: docker compose restart aisec-server
docker compose run --rm aisec-cli keys rotate-audit -dir /etc/aisec/keys      # затем: docker compose restart aisec-server
```
Якорь шлюза `/srv/aisec/secrets/gateway-bundle-anchor.pub` при плановой ротации не меняется: шлюз узнаёт о новом ключе подписи из пакета.

## 12. Где что лежит
| Путь на хосте | Владелец | Что |
|---|---|---|
| `/srv/aisec/keys` | `aisec`, `0700` | ключи `aisec-cli init` (мастер-ключ, УЦ шлюзов, ключи подписи) |
| `/srv/aisec/secrets` | `root`, `0700` | сертификаты TLS, пароли и passfile ролей БД, якорь шлюза `gateway-bundle-anchor.pub` (`0644`) |
| `/srv/aisec/pg` | `aisec-db`, `0700` | данные PostgreSQL |
| `/srv/aisec/gateway` | `root`, `0755` | каталоги шлюза: `reg/` (сертификат шлюза) и `state/` (последний пакет, ключ секретов пакета, заявления о доверии `trust.json`, перевыпущенный сертификат `client.pem`), оба `aisec-gw`, `0700` |
| `/srv/aisec/backups` | `aisec`, `0700` | резервные копии `aisec-cli backup` (`/var/lib/aisec/backups` в контейнере) |

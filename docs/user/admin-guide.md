# Руководство администратора (черновик)

Черновик этапа 2 (задача 2.29, ТЗ 7.7). Описывает то, что работает в версии этапа 2: установка на одном хосте, первичная настройка, пользователи и роли, приложения и провайдеры, политики, шлюзы, события, журнал аудита, проверка целостности, резервная копия. Оповещения по каналам, инциденты, обновления из консоли и внешний источник ключей появятся в следующих этапах; в тексте это отмечено.

Термины — по [словарю](../glossary.md): шлюз, приложение, провайдер, политика, событие, оповещение.

## 1. Что нужно для установки
- Linux-хост для сервера управления и хост (или тот же) для шлюза. Комплект поставки — четыре программы: `aisec-server`, `aisec-gateway`, `aisec-cli`, `aisec-media` (анализ изображений и аудио появится на этапе 5), файл `aisec-manifest.json` с подписью `aisec-manifest.json.sig` рядом с ними.
- PostgreSQL 15 или новее. Сервер подключается к нему не владельцем таблиц; учётная запись для сервера и учётная запись для `aisec-cli migrate` разные.
- Сертификат и закрытый ключ TLS для сервера (корпоративный УЦ). Продукт не ходит в интернет и не проверяет обновления.
- Синхронизация времени хоста — [инструкция](../install/time-sync.md). Без неё не работают коды TOTP, сроки ключей и сопоставление событий.
- Браузер: актуальные Яндекс Браузер, Chromium, Firefox.

## 2. Установка и первый запуск
1. Выполните миграции: `AISEC_DATABASE_URL=… aisec-cli migrate`.
2. Создайте ключи установки: `aisec-cli init -dir /etc/aisec/keys` (каталог с правами `0700`, файлов ключей в нём ещё нет). Команда создаёт мастер-ключ, ключ данных, ключи подписи журнала и пакетов конфигурации, внутренний удостоверяющий центр шлюзов и **одноразовый токен первичной настройки**. Токен показывается один раз и действует 24 часа. Сохраните его и храните каталог ключей так же строго, как сам сервер: мастер-ключ расшифровывает секреты в БД.
3. Запустите `aisec-server` с флагами `-tls-cert`, `-tls-key`, `-keys-dir`, `-audit-signing-pub`, `-ca-cert`, `-ca-key` (полный перечень флагов и переменных `AISEC_SERVER_*` — в `aisec-server -h`). Консоль по умолчанию слушает `127.0.0.1:8444`, внутренний порт для шлюзов — отдельный (`-internal-listen`), с обязательным сертификатом шлюза.
4. Если сервер стоит за балансировщиком, перечислите его сети в `-trusted-proxies`: иначе в журнале и ограничителе частоты окажется адрес балансировщика, а не пользователя.

Права на файлы ключей: `0400`/`0600`, каталог — `0700`, пользователь ОС — отдельный, непривилегированный. При неверных правах программа не запускается и называет файл.

## 3. Первичная настройка
Откройте консоль, на экране первичной настройки введите токен, логин, отображаемое имя и пароль. Часовой пояс показа времени и режим хранения содержимого для новых приложений можно задать здесь же (по умолчанию «Europe/Moscow» и «masked»); позже они меняются в «Администрировании» → «Время и хранение». Первый пользователь получает роль «Администратор безопасности». Токен после этого погашается. Если токен потерян или просрочен, выпустите новый: `AISEC_DATABASE_URL=… aisec-cli init -reissue-setup-token`. Команда работает только пока первичная настройка не выполнена, гасит все прежние токены, показывает новый один раз (24 часа) и пишет запись `system.setup_token_reissued` в журнал аудита.

После входа сразу подключите второй фактор (TOTP): для администраторов он обязателен. Отсканируйте QR-код приложением-аутентификатором, введите код и **сохраните 10 кодов восстановления** — они показываются один раз.

## 4. Пользователи, роли и вход
Раздел «Администрирование» → «Пользователи», «Роли и разрешения», «Вход и сессии».

- Предустановленные роли: «Администратор безопасности» (политики, пользователи, роли, содержимое событий), «Администратор системы» (приложения, провайдеры, резервные копии; политики безопасности не меняет), «Аналитик» (события, экспорт), «Аудитор» (только чтение, включая журнал аудита и его проверку), «Владелец приложения» (только свои приложения). У пользователя одна роль. Своя роль — набор разрешений из каталога; предустановленные роли не меняются.
- Новый пользователь получает **временный пароль**: он показывается один раз, действует 72 часа по умолчанию, при первом входе его нужно сменить.
- Пароль: от 12 символов, три класса символов, история 5 паролей, срок 90 суток — значения меняются в «Входе и сессиях»; ослабление (короче пароль, выше порог, короче блокировка, отмена обязательного TOTP и т. п.) подтверждается паролем или кодом TOTP. Блокировка после 5 неудачных попыток подряд на 15 минут, бездействие — 15 минут, не больше 5 одновременных сессий. Сообщение об ошибке входа всегда одно и то же, чтобы нельзя было узнать, существует ли логин.
- Сброс второго фактора и пароля другого пользователя доступен тому, чьи права не уже прав этого пользователя. Себе второй фактор сбросить нельзя.
- **Токены API** для автоматизации выпускает сам пользователь («Токены»): нужен текущий пароль или код TOTP, срок до 365 дней, показывается один раз. Токен не получает права безопасности и права на токены.
- Если заблокированы все администраторы безопасности, на хосте сервера есть аварийные команды: `aisec-cli user unlock -login …`, `user reset-password -login …`, `user reset-mfa -login …`. Каждая пишет запись в журнал аудита.

## 5. Провайдеры и приложения
**Провайдеры** — пока только через API `/api/v1/providers` (экран провайдеров в консоли появится на этапе 3; без провайдера мастер подключения приложения не продолжится): адрес модели, корневой сертификат (если он корпоративный) и учётные данные. Учётные данные хранятся зашифрованными и после сохранения не показываются. Провайдер вне вашего контура помечайте «внешний» — тогда шлюз не передаёт ему идентификатор пользователя без псевдонимизации. Смена адреса или сертификата у внутреннего провайдера считается переносом данных на другой узел: провайдер становится внешним, а учётные данные сбрасываются и вводятся заново.

**Приложения.** «Приложения» → «Подключить приложение»: мастер из трёх шагов — «Приложение» (название, ID, среда, подразделение), «Провайдер и политика» (провайдер, разрешённые модели, политика, режим политики, хранение содержимого) и «Ключ»; владельцем становится тот, кто подключает. Режим «Мониторинг» и хранение «Не хранить» или «Полное» ослабляют защиту — мастер попросит пароль или код TOTP. Без явного выбора хранение берётся из «Администрирования» → «Время и хранение». Ключ приложения вида `aisec_…` показывается **один раз**: передайте его команде приложения и не сохраняйте в чате или таблицах. Срок действия — от 1 до 730 суток (365 по умолчанию), можно ограничить подсетями. Ротация выпускает новый ключ, а прежний работает ещё заданное перекрытие (24 часа по умолчанию), отзыв действует сразу. Приложение подключается к шлюзу как к OpenAI-совместимому API: меняется только адрес и ключ.

Политика, режим политики, хранение, режим отказа (`fail_mode`) и разрешённые домены для защиты от утечки существующего приложения меняются кнопкой «Защита» в списке приложений и требуют права «Политика, режим политики и режим хранения приложения»; словари приложения — пока через API (`PUT /api/v1/applications/{id}/protection`). Ослабление защиты (переход на мониторинг, на более слабую политику, `fail_open`, новый домен-исключение, хранение `none` или `full`) подтверждается паролем или кодом TOTP.

## 6. Политики
«Политики»: у каждой политики неизменяемые версии. Сохранить можно только корректную версию, и она сразу становится действующей (шаг «Опубликовать» не нужен); «Откатить» возвращает прежнюю версию как новую. Версия, которая ослабляет защиту (удалено правило, блокировка заменена записью, режим «Мониторинг»), — при сохранении, откате и импорте — подтверждается паролем или кодом TOTP. В «песочнице» проверьте правило на тексте до сохранения: её результат совпадает с тем, что сделает шлюз. Импорт и экспорт — YAML. Политику меняет только «Администратор безопасности».

Новые детекторы начинайте в режиме «Мониторинг» (запись без блокировки), посмотрите события за несколько дней и только потом включайте блокировку: так меньше ложных срабатываний.

## 7. Шлюзы
1. На хосте сервера выпустите токен регистрации: `aisec-cli gateway token -name gw-1 -ttl 24h`. Токен одноразовый, показывается один раз.
2. На хосте шлюза: `AISEC_GATEWAY_REGISTRATION_TOKEN=… aisec-gateway register -console https://сервер:8444 -console-ca ca-консоли.pem -out-dir /etc/aisec/gw -state-dir /var/lib/aisec/gw` (оба каталога `0700`). Закрытый ключ создаётся на шлюзе и не покидает его.
3. Запустите шлюз с `-server`, `-bundle-pub` (открытый ключ подписи пакетов `bundle-signing.pub`) и `-state-dir`. Флаг `-config` в этом режиме не используется: конфигурация приходит от сервера **подписанным пакетом**. Пакет подписан, версии только растут; подделанный или старый пакет шлюз отвергает и продолжает работать на прежнем.
4. Если пакет невозможно доставить, шлюз отвечает приложению 503 и сообщает причину серверу; «Состояние системы» покажет шлюз, который дольше 10 минут работает на другой версии.

Список и отзыв: `aisec-cli gateway list`, `aisec-cli gateway revoke -name gw-1` (отзыв окончательный: отозванное имя повторно не используется, для замены зарегистрируйте шлюз под новым именем; `-reregister` у `gateway token` — для действующего шлюза, у которого потерян ключ или истекает сертификат).

## 8. События и сроки хранения
«События»: таблица с фильтрами, карточка события с блоком «Почему принято решение», выгрузка в CSV и JSON (до 100 000 строк за 31 сутки; выгрузка попадает в журнал аудита).

Режим хранения содержимого запросов и ответов задаётся у каждого приложения (мастер подключения или кнопка «Защита»); умолчание для новых приложений — «Администрирование» → «Время и хранение»:
- `none` — содержимого нет, только метаданные;
- `masked` — содержимое с замаскированными персональными данными и секретами (по умолчанию);
- `full` — полное содержимое, зашифрованное; включайте только при необходимости и с ограниченным сроком.

Содержимое видит только «Администратор безопасности», каждое обращение требует причину и пишется в журнал аудита. **Сокращение срока хранения** подтверждается паролем или кодом TOTP и необратимо удаляет старые данные.

## 9. Журнал аудита
«Администрирование» → «Журнал аудита»: действия пользователей, отказы в доступе, смена настроек, выпуск и отзыв ключей. Журнал только добавляется: права СУБД и триггеры запрещают правку и удаление.

- Целостность цепочки проверяется при запуске сервера, раз в час и по кнопке «Проверить цепочку» (аудитор или администратор безопасности, не чаще 5 раз в минуту). Нарушение сервер не останавливает: в «Состоянии системы» появляется оповещение, в аудит — запись `audit.chain_broken`.
- Срок хранения по умолчанию 365 дней (30–3650). Старше срока записи переносятся в подписанный архив: `aisec-cli audit archive -keys … -out …` (проверяется до удаления). Сам архив проверяет `aisec-cli audit verify-archive`.
- Выгрузка на внешний носитель — `aisec-cli audit export -out … [-from … -to …]`.
- Заполнение хранилища журнала отслеживается: предупреждение при 80 % от 20 ГиБ (флаги `-audit-storage-limit`, `-audit-storage-warn-percent`).
- Время в журнале хранится в UTC; консоль показывает его в часовом поясе установки («Время и хранение»).

## 10. Целостность и самотест
- Сервер и шлюз при запуске и раз в час проверяют свой исполняемый файл и встроенную консоль по подписанному манифесту. Реакция — флаг `-integrity-action`: `alert` (по умолчанию, оповещение) или `stop` (остановка; для пилота с повышенными требованиями).
- На хосте можно проверить установку вручную: `aisec-cli verify` (код выхода 3 — нарушение). Кнопка «Проверить целостность» в «Состоянии системы» проверяет сервер сразу, а действующим шлюзам передаёт запрос: каждый шлюз проверит себя при следующем контакте с сервером (обычно в течение минуты), итог появится в «Состоянии системы» и журнале аудита.
- Выпуск старше уже проверенного (откат) — тоже нарушение. Если откат намеренный (например, возврат после неудачного обновления), примите его на хосте: `aisec-cli verify -accept-rollback`, для шлюза — `aisec-cli verify -accept-rollback -gateway ИМЯ`. Принятие пишется в журнал аудита.
- Сборка с тестовым ключом манифеста видна в «Состоянии системы» предупреждением «Сборка не для поставки». В пилот и поставку идёт только сборка `RELEASE=1`.
- Шлюз и сервер при запуске проверяют каждый детектор на двух эталонных входах; провал не даёт шлюзу работать при `-selftest-action stop`, у сервера — оповещение.
- Результаты — в «Состоянии системы» (сервер и каждый шлюз отдельно).

## 11. Состояние системы
Показывает компоненты и версии, шлюзы и их последнюю связь, итоги проверок целостности и самотеста, состояние цепочки аудита, заполнение журнала, число блокировок и отказов в доступе за 24 часа, синхронизацию времени. Оповещения о важных изменениях пишутся в журнал аудита как `system.alert`. Доставка по каналам (почта, syslog, webhook) — этап 3.

## 12. Резервная копия
Копия конфигурации снимается и восстанавливается командой `aisec-cli backup`; подробности, состав и порядок восстановления — [docs/install/backup.md](../install/backup.md). Главное: парольную фразу храните отдельно от файла, без неё копию не восстановить; события и журнал аудита в копию не входят. После восстановления токены API выпускают заново (они восстанавливаются отозванными), а всё, что отозвали, деактивировали и сменили после даты копии, повторяют по журналу аудита.

## 13. Время
Часы синхронизирует операционная система хоста, продукт сам этого не делает. Часовой пояс показа времени в консоли — «Администрирование» → «Время и хранение» (меняет «Администратор безопасности»); хранится время в UTC. Настройка chrony — [docs/install/time-sync.md](../install/time-sync.md). Рассинхронизация видна в «Состоянии системы».

## 14. Ротация ключей
Все ключи установки меняются без переустановки (ТЗ 10.4, ADR-0018). Команды `aisec-cli keys …` запускайте на хосте сервера под логином владельца схемы БД (`AISEC_DATABASE_URL`), `-dir` — каталог ключей установки (`0700`). Файлы, созданные `aisec-cli init`, не меняются: новые ключи пишутся рядом с идентификатором в имени. Две ротации одновременно не выполняются. Каждая ротация попадает в журнал аудита.

| Ключ | Команда | Что дальше |
|---|---|---|
| Мастер-ключ | `aisec-cli keys rotate-master -dir /etc/aisec/keys` | Перезапуск не нужен. Прежний файл сохраняется как `master.key.<время>.retired`: он нужен, чтобы восстановить дамп БД, снятый до ротации. Удалите его, когда такие дампы больше не нужны. |
| Ключ данных (секреты TOTP, учётные данные провайдеров, содержимое событий) | `aisec-cli keys rotate-data -dir /etc/aisec/keys` | Перезапуск не нужен: сервер переходит на новый ключ сам. Команда перешифровывает все секреты и удаляет прежний ключ. Если она прервалась, повторите с `-resume`. |
| Ключ подписи пакетов конфигурации | `aisec-cli keys rotate-signing -dir /etc/aisec/keys [-overlap 720h]` | Передайте новые файлы пользователю службы и перезапустите сервер. Шлюзы узнают о новом ключе из пакета; прежний ключ они принимают до конца перекрытия (по умолчанию 30 суток). Прежний `bundle-signing.<id>.key` (или `bundle-signing.key`) удалите после перезапуска. `-bundle-pub` у шлюзов не меняется. |
| Внутренний УЦ (корень сертификатов шлюзов) | `aisec-cli keys rotate-ca -dir /etc/aisec/keys [-overlap 720h]` | Перезапустите сервер. Шлюзы сами получают новые сертификаты при heartbeat и переходят на них без перезапуска (файл `client.pem` в каталоге состояния). Сертификаты прежнего корня принимаются до конца перекрытия. Прежний `ca.key` удалите после его конца. Сервер ищет файлы нового корня рядом с `-ca-cert`. |
| Ключ подписи журнала аудита | `aisec-cli keys rotate-audit -dir /etc/aisec/keys` | Перезапустите сервер. Новые контрольные точки подписываются новым ключом, старые проверяются прежним. Прежний закрытый ключ больше не нужен; **все открытые ключи `audit-signing*.pub` храните всегда** — по ним проверяются архивы (`audit verify-archive -keys`). |
| Ключи приложений, токены API | Ротация и отзыв в консоли (разделы 4 и 5). | — |
| Сертификат шлюза (365 суток) | Перевыпускается автоматически за 30 суток до истечения. Если ключ шлюза потерян: `aisec-cli gateway token -name … -reregister`, затем `aisec-gateway register` заново. | — |
| Токен регистрации, токен первичной настройки | Одноразовые, выпускаются заново. | — |
| Ключ подписи манифеста | Принадлежит производителю и меняется только с новой версией поставки. | — |

Проверить результат: `aisec-cli keys status -dir /etc/aisec/keys` покажет версии ключа данных, действующий ключ подписи пакетов и корни УЦ со сроками перекрытия, ключ аудита.

**При компрометации** ключа подписи пакетов или УЦ используйте `-overlap 0`: прежний ключ перестаёт приниматься сразу. Шлюз, который был недоступен и не получил новый пакет, примет новый ключ только после того, как вы замените его `-bundle-pub` на `bundle-signing.<id>.pub` нового ключа. Если шлюз пропустил больше 8 ротаций ключа подписи, сделайте то же самое.

**Регистрация с ключом получателя.** Запускайте `aisec-gateway register` с `-state-dir` — тем же каталогом, что потом передадите шлюзу. Тогда сервер сразу закрепит ключ, которым шлюз расшифровывает учётные данные провайдеров, и не отдаст их по другому ключу. Без `-state-dir` ключ закрепляется при первом запросе пакета. Сменить ключ можно только перерегистрацией шлюза.

## 15. Что делать при нарушениях
- **Подозрение на подмену файлов** («Состояние системы» показывает нарушение целостности): остановите компонент, сверьте файлы с поставкой, при необходимости переустановите из подписанной поставки. Запись в журнале аудита не удаляйте.
- **Цепочка журнала нарушена**: сохраните выгрузку журнала (`audit export`), БД не правьте, обратитесь к специалисту по ИБ и производителю.
- **Утерян ключ приложения**: отзовите и выпустите новый. **Утерян токен API** — отзовите в разделе «Токены».
- **Утерян доступ администратора**: аварийные команды из раздела 4.

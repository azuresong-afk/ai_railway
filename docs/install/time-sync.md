# Синхронизация времени на хосте

Время для AISec обеспечивает операционная система хоста. Продукт часы не настраивает и не меняет: сервер не имеет права менять системное время и не обращается к NTP-серверам (правило «Сеть» в `CLAUDE.md`, решение Р11, [ADR-0014](../adr/0014-sinkhronizatsiya-vremeni-adjtimex.md)). Он только показывает состояние часов в «Состоянии системы» и поднимает оповещение при рассинхронизации (ВРМ.1).

**Требование к установке:** все хосты с компонентами AISec (сервер, шлюзы, СУБД) синхронизированы с доверенным источником времени организации. Точность до сотен миллисекунд достаточна; важнее, чтобы часы не прыгали и не расходились между хостами.

## Зачем это нужно
- Метки времени журнала аудита и событий: по ним расследуют инциденты, сопоставляют с журналами других систем и считают срок хранения.
- TOTP принимает код текущего шага 30 с и соседних (±1 шаг). Расхождение часов больше 30 с делает вход невозможным; использованный шаг повторно не принимается (задача 2.8).
- Срок действия сертификатов mTLS, ключей приложений и токенов API, блокировки и окна ограничения частоты.
- Корректный порядок записей между сервером и шлюзами.

## Выбор источников
1. Предпочтительно 2–4 внутренних сервера времени организации, лучше — собственные серверы с ГЛОНАСС/GPS-приёмником (в закрытом контуре без выхода наружу иных источников нет).
2. Публичные пулы не включены по умолчанию. Если организация их разрешает, включайте осознанно и с аутентификацией (NTS).
3. Не меньше двух источников (`minsources 2`): один источник не позволяет обнаружить его собственную ошибку.
4. Аутентификация: NTS для внешних источников; для внутренних — симметричные ключи chrony или защита сети (отдельный сегмент, фильтрация UDP/123 по адресам источников).
5. Исходящий UDP/123 к этим адресам — единственное сетевое требование. Откройте его только до заданных источников.

## Настройка chrony (рекомендуется)
1. Установите `chrony` из пакетов ОС и отключите прочие службы времени (`systemd-timesyncd`, `ntpd`): одновременно работать должна одна.
2. Возьмите [`deploy/time/chrony.conf.example`](../../deploy/time/chrony.conf.example), замените адреса-заглушки `*.example.internal` и сохраните как `/etc/chrony/chrony.conf` (в некоторых дистрибутивах — `/etc/chrony.conf`).
3. Перезапустите службу: `systemctl restart chrony` (или `chronyd`).

## Запасной вариант: systemd-timesyncd
Если chrony поставить нельзя, подойдёт `systemd-timesyncd` (простой SNTP-клиент, без оценки качества источников и без NTS). В `/etc/systemd/timesyncd.conf`:

```ini
[Time]
NTP=ntp1.example.internal ntp2.example.internal
FallbackNTP=
```

Пустое `FallbackNTP=` запрещает встроенные публичные серверы дистрибутива. Затем `systemctl enable --now systemd-timesyncd` и `timedatectl set-ntp true`.

## Проверка
| Команда | Что смотреть |
|---|---|
| `chronyc tracking` | `Leap status : Normal`; `System time` — смещение, обычно доли секунды; `Reference ID` — не `00000000` |
| `chronyc sources -v` | Хотя бы один источник со `*` (выбран) и достаточное число `+` (годных); колонка `Reach` — 377 |
| `chronyc sourcestats` | Малая погрешность и стабильный дрейф |
| `timedatectl` | `System clock synchronized: yes`, `NTP service: active` |

В консоли: «Состояние системы» → синхронизация времени. Значение «Синхронизировано» берётся из ядра (`adjtimex`, флаг `STA_UNSYNC`) и совпадает с `System clock synchronized: yes`; рядом показана оценка ошибки. Если демон остановлен или не видит источников, ядро через несколько минут снимет признак синхронизации, сервер покажет «Рассинхронизировано» и поднимет оповещение `system.alert` (задача 2.20). Состояние «Неизвестно» означает, что ОС не отдала данные (не Linux, нет прав на вызов); оповещения при этом нет.

## Контейнеры и стенд разработки
- В контейнере часы — часы ядра хоста: внутри контейнера демон времени не нужен и не настраивается, настраивается хост (в Docker Desktop и WSL — виртуальная машина Docker, которая обычно берёт время у хостовой ОС).
- `make dev` запускает контейнеры стенда: состояние «Рассинхронизировано» на стенде без демона времени допустимо и не мешает разработке.
- Виртуальные машины: отключите синхронизацию с гипервизором в пользу NTP-демона гостя либо наоборот, но не обе сразу; после приостановки машины подождите, пока демон вернёт часы в норму.

## Что не делать
- Не задавать время вручную на работающей системе и не использовать `makestep` без ограничения: скачок назад ломает порядок записей и окна ограничения частоты.
- Не давать серверу AISec права `CAP_SYS_TIME` и не запускать его с ними.
- Не включать несколько источников, зависимых от одного физического (например, три «зеркала» одного сервера).

## Если время всё же ушло
1. Исправьте часы через демон (перезапуск службы, проверка источников) и убедитесь по `chronyc tracking`, что смещение мало: при расхождении больше 30 с вход с TOTP невозможен, пока часы не вернутся в норму.
2. Скачок времени назад: проверьте цепочку журнала аудита (`aisec-cli audit verify`). Цепочка опирается на порядковые номера и хеши, а не на время, но метки времени у записей около скачка могут идти не по порядку: отметьте это в расследовании.
3. Запишите в журнал смены время обнаружения и устранения.

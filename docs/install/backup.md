# Резервная копия конфигурации

Черновик раздела руководства администратора (ТЗ 7.7, РВ.1; задача 2.19 этапа 2; решения — [ADR-0017](../adr/0017-rezervnaya-kopiya-konfiguratsii.md)).

Копия конфигурации — один зашифрованный файл. Из него конфигурацию можно восстановить на новой установке, в том числе после потери сервера, БД или мастер-ключа. Копию снимает и восстанавливает `aisec-cli` на хосте сервера под пользователем ОС, у которого есть доступ к каталогу ключей и строке подключения к БД.

## Что входит в копию
- Политики со всеми версиями.
- Приложения: настройки, ключи (только хеши), сроки и отзыв ключей.
- Провайдеры с учётными данными (в файле они зашифрованы).
- Пользователи: хеши паролей, история паролей, второй фактор (секрет TOTP), хеши кодов восстановления, состояние блокировки.
- Токены API (только хеши) и свои роли с разрешениями.
- Название организации, настройки входа, журнала аудита, сроков хранения событий, часовой пояс и режим хранения по умолчанию.
- Ключ псевдонимов пользователей (HMAC). Без него после восстановления псевдонимы в новых событиях не совпадут со старыми.

**Не входят:** события и их содержимое (у них свои сроки хранения), журнал аудита (его архивирует `aisec-cli audit archive`), сохранённые фильтры событий, сессии консоли, шлюзы и их сертификаты, пакеты конфигурации, ключи установки (`master.key`, ключи подписи, УЦ).

## Парольная фраза
Копия шифруется ключом, выведенным из парольной фразы (Argon2id, AES-256-GCM). Мастер-ключ установки в копии не используется, поэтому восстановить её можно и без него.

- Фраза не короче 16 символов. Лучше 4–5 случайных слов или строка из менеджера паролей. Для новой копии команда отклоняет фразу, где меньше 8 разных символов, повтор фрагмента (`qwerty12qwerty12`) или последовательность (`1234567890123456`), а также фразу, равную имени пользователя ОС или названию организации.
- Храните фразу отдельно от файла копии: в сейфе, в менеджере паролей, у двух ответственных. **Без фразы копию не восстановить**, сбросить фразу нельзя.
- Фразу вводят с терминала: команда спрашивает её без отображения, при создании копии — дважды. Для автоматического запуска фразу можно положить в файл с правами ровно `0400` и передать флагом `-passphrase-file`. В аргументах командной строки фраза не принимается.

## Создание копии
```sh
export AISEC_DATABASE_URL='postgres://aisec@db.example:5432/aisec'
aisec-cli backup create -keys /etc/aisec/keys -out /var/backups/aisec/config-2026-10-22.aisec-backup \
    -user-hmac-key /etc/aisec/user-hmac.key
```
- `-keys` — каталог ключей установки из `aisec-cli init`. Мастер-ключ нужен, чтобы расшифровать секреты в БД перед шифрованием ключом копии.
- `-user-hmac-key` — тот же файл, что шлюзы получают флагом `-user-hmac-key`. Если псевдонимы пользователей не используются, вместо него укажите явно `-no-user-hmac-key`.
- Файл создаётся с правами `0600`. Существующий файл не перезаписывается.
- Копия снимается одним согласованным снимком БД. В журнал аудита пишется `backup.create` с хешем файла и числом объектов, без содержимого.

Рекомендации: снимайте копию по расписанию и после значимых изменений политик и пользователей. Храните несколько последних копий вне хоста сервера. Раз в квартал проверяйте восстановление на тестовом стенде.

## Восстановление
Копия восстанавливается в **новую** установку. Сервер на время восстановления должен быть остановлен.
1. Установите сервер той же или более новой версии.
2. Примените миграции и создайте ключи: `aisec-cli migrate`, затем `aisec-cli init -dir /etc/aisec/keys`. Токен первичной настройки не нужен: первичную настройку не выполняйте.
3. Восстановите копию:
   ```sh
   aisec-cli backup restore -keys /etc/aisec/keys -in config-2026-10-22.aisec-backup \
       -user-hmac-key-out /etc/aisec/user-hmac.key
   ```
   `-user-hmac-key-out` обязателен, если ключ псевдонимов есть в копии. Файл создаётся новым, с правами `0600`.
4. Запустите сервер. Пользователи входят со своими паролями и вторым фактором. Сессии и токены первичной настройки прежней установки не действуют.
5. Зарегистрируйте шлюзы заново (`aisec-cli gateway token`, затем `aisec-gateway register`): ключи шлюзов и внутренний УЦ не восстанавливаются. Передайте шлюзам файл ключа псевдонимов.
6. **Обязательно: сверка с журналом аудита.** Копия возвращает установку в состояние на дату копии. Ключи приложений, учётные записи, их пароли и блокировки восстанавливаются такими, какими были тогда. Выгрузите журнал за время после копии из архива или старой БД (`aisec-cli audit export -out ФАЙЛ -from ДАТА_КОПИИ`) и повторите всё, что сделано после неё: отзывы ключей приложений, деактивации и блокировки пользователей, сбросы паролей и второго фактора. Дата копии и её возраст в часах есть в выводе команды и в записях `backup.restore`.

**Токены API** восстанавливаются отозванными (причина `backup_restore`): токен, отозванный после даты копии, не вернётся в силу. Владельцы выпускают токены заново в консоли. Флаг `-keep-api-tokens` оставляет токены как в копии; используйте его, только если уверены, что после копии токены не отзывали. Флаг попадает в запись аудита.

**Старая копия.** Копия старше 7 суток восстанавливается только с флагом `-accept-old-copy`: чем старше копия, тем больше отозванного и изменённого вернётся.

**Проверка объектов.** До записи в БД команда проверяет объекты копии правилами этой версии: свои роли и токены — по каталогу разрешений (токену нельзя права безопасности), политики — по каталогу детекторов, приложения — словари, псевдонимы, квоты и совместимость с политикой. Если копия снята другой версией и что-то не проходит, восстановления нет: код 3 и перечень объектов. Исправьте объекты в исходной установке и снимите копию заново.

Сначала проверяется подлинность файла и фраза, затем версия формата, затем содержимое. Неверная фраза и повреждённый или подменённый файл дают один и тот же отказ с кодом возврата 3. Установка при этом не меняется.

**Непустая установка.** Если в установке уже есть пользователи, приложения, провайдеры, политики, свои роли или токены, восстановление отклоняется. Флаг `-allow-nonempty` разрешает добавить объекты копии к существующим. Если какой-либо объект копии уже есть (тот же ID, логин, slug или префикс ключа), восстановление отклоняется целиком. Название организации и настройки установки при этом не меняются: копия переносит их только в пустую установку. Затереть существующие объекты восстановлением нельзя: пользователи, приложения и версии политик не удаляются. Откатить политику на работающей установке можно версиями политик в консоли.

В журнал аудита пишутся `backup.restore` до начала (`stage: started`), после успешного завершения (`stage: done`, в той же транзакции, что и данные) и при каждом отказе (`stage: refused` с причиной).

## Если что-то пошло не так
- «установка не пустая» — восстановление выполняется в новую установку; проверьте, что указана нужная БД.
- «схема БД старше копии» — выполните `aisec-cli migrate` той версией, которая не старше версии, снявшей копию.
- «в установке нет ключа данных» — не выполнен `aisec-cli init`.
- «копия … старше 7 суток» — проверьте, что нет копии новее; если нет — повторите с `-accept-old-copy` и выполните сверку с журналом аудита (шаг 6).
- «похоже, сервер работает» — в установке есть сессии консоли с активностью за последние 5 минут. Остановите сервер и повторите.
- «объекты копии не проходят проверки этого выпуска» (код 3) — см. «Проверка объектов» выше.
- Код 3 — неверная фраза или файл повреждён. Проверьте фразу и хеш файла (он записан в аудите `backup.create`).
- «исход неизвестен» — связь с БД оборвалась на фиксации. Найдите в журнале аудита запись `backup.restore` со `stage: done`: если она есть, восстановление выполнено.

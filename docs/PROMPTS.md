# Промпты для Claude Code

Промпты рассчитаны на ТЗ версии 0.5. Требования и правила живут в `CLAUDE.md` и `docs/SPEC.md`, поэтому промпты короткие: они запускают шаги работы, а не пересказывают ТЗ.

## Как пользоваться
1. Положите в корень пустого репозитория `CLAUDE.md`, папку `docs/` и скрытую папку `.claude/` (настройки и сабагент `cert-reviewer`). Сделайте первый коммит.
2. Запустите Claude Code в корне репозитория. Для промптов 0, 1 и 3 включите режим планирования (Shift+Tab): Claude покажет план и ничего не изменит.
3. План каждого этапа хранится в `docs/plans/stage-N.md` со статусами задач. Между задачами очищайте контекст командой `/clear`, а новую сессию начинайте с промпта «Продолжить работу».
4. Коммитьте после каждой проверенной задачи. Код просматривает человек — это требование безопасной разработки, а не формальность.
5. Если меняется решение — сначала ТЗ или ADR, потом код.

## Основной цикл

### Промпт 0. Знакомство и вопросы
```
Прочитай CLAUDE.md и docs/SPEC.md полностью. Код пока не пиши.

1. Перескажи в 10–15 пунктах, что мы строим, для кого первые пилоты (ТЗ, 1.6) и какие ограничения из-за будущей сертификации ты обязан соблюдать с первого коммита.
2. Объясни, как ты будешь работать с матрицей обнаружения (ТЗ, 5.16): как её строки связываются с тестами и чего нельзя обещать в интерфейсе.
3. Найди в ТЗ противоречия, пробелы и рискованные места, со ссылками на разделы.
4. Задай вопросы: сначала открытые из раздела 16, потом свои. Не больше 12, по убыванию важности. К каждому предложи вариант по умолчанию на случай, если я не отвечу.
```

### Промпт 1. План этапа 0
```
Мои ответы: <вставьте ответы>. Где ответа нет, бери свой вариант по умолчанию и отметь это.

1. Обнови docs/SPEC.md по ответам: в разделе 16 отметь закрытые вопросы, поправь затронутые разделы, добавь строку в историю версий.
2. Составь план этапа 0 (ТЗ, раздел 14) и сохрани его в docs/plans/stage-0.md. Задачи по 0,5–1 дню; для каждой — результат, файлы, проверки, документы из раздела 9, статус.
3. Отдельным списком — зависимости и инструменты, которые хочешь поставить: назначение, лицензия, почему не хватает стандартной библиотеки. Я подтвержу списком.

Жди моего подтверждения.
```

### Промпт 2. Выполнение задачи
```
Выполни задачу <номер> из docs/plans/stage-<N>.md. Работай по CLAUDE.md: тесты вместе с кодом (для строк матрицы — с ID строки в имени теста), make check перед завершением, обновление затронутых документов. Отметь статус задачи в плане.

В конце: что сделано, что мне проверить руками, что осталось.
```

### Продолжить работу (начало новой сессии)
```
Прочитай CLAUDE.md, docs/plans/stage-<N>.md и последние 15 коммитов. Кратко: на какой задаче мы остановились, что в ней осталось, есть ли незакоммиченные изменения. Предложи следующий шаг и жди подтверждения.
```

### Промпт 3. Закрыть этап и спланировать следующий
```
1. Проверь критерии приёмки этапа <N-1> (ТЗ, раздел 14) и покрытие матрицы 5.16 для этого этапа. Отчитайся списком: выполнено, не выполнено, что мешает.
2. Если этап закрыт, переходим к этапу <N>. Прочитай разделы ТЗ, на которые он ссылается, и посмотри текущее состояние кода.
3. Выпиши строки матрицы 5.16, которые реализуются на этапе <N>, и тест, который покроет каждую.
4. Составь план задач по 0,5–1 дню и сохрани его в docs/plans/stage-<N>.md.
5. Отдельно: нужные зависимости, решения с меткой [Решение] и ADR, риски.

Жди подтверждения.
```

## Экономный режим
Как тратить меньше токенов:
- **Одна сессия — одна-две задачи.** Длинная сессия пересылает весь контекст на каждом ходу и сжимается. Состояние держать в репозитории: статусы и раздел «Открытые вопросы» в `docs/plans/stage-<N>.md`.
- **Проверки.** Во время работы — тесты затронутых пакетов; `make check` — один раз перед коммитом, вывод в файл, в чат — только итог.
- **Ревью `cert-reviewer` — по плану этапа**, на диапазон коммитов, без перезапуска проверок, не больше 15 замечаний.
- **Модель.** Рутинные задачи (документы, корпуса, метрики, mock-llm) — на более дешёвой модели (`/model`). Задачи с безопасностью (политики, псевдонимизация, конвейер, auth, crypto) — на основной.
- **Короткие отчёты:** до 10 строк, промежуточные сообщения — одной строкой.

### A. Начало сессии: задача по плану
```
Экономный режим (docs/PROMPTS.md). Возьми следующую незавершённую задачу из docs/plans/stage-<N>.md (или задачи <N1> и <N2> — отдельный коммит на каждую).
Контекст — только: строка задачи и решения этапа в плане, раздел «Открытые вопросы», нужные разделы ТЗ через оглавление, затрагиваемые пакеты.
Если задача касается auth, crypto, audit, integrity, сборки или зависимостей — сначала короткий план и жди ответа; иначе делай сразу.
Во время работы — только тесты затронутых пакетов, в чат — только итоги и ошибки. Перед коммитом — один раз make check с выводом в файл, в чат — итог.
Документы по DoD, статус в плане, коммит, push в рабочую ветку; PR не создавай.
Промежуточные сообщения — одной строкой. Отчёт до 10 строк: что сделано, коммит, метрики, что проверить руками, вопросы.
```

### B. Ревью и исправления
```
Экономный режим. Запусти cert-reviewer на диапазон <база>..HEAD. Передай ему итоги make check: проверки не перезапускать, только чтение диффа и кода; не больше 15 замечаний, блокирующие и важные подробно, незначительные — по строке.
Исправь блокирующие и важные одним коммитом fix:, незначительные — если правка в 1–2 строки; остальное запиши в «Открытые вопросы» плана. Отчёт до 10 строк.
```
Если замечания уже записаны в «Открытые вопросы» плана — без запуска ревьюера:
```
Экономный режим. Исправь замечания ревью из раздела «Открытые вопросы» docs/plans/stage-<N>.md: важные — все, незначительные — если правка в 1–2 строки. Один коммит fix:, раздел обнови. Отчёт до 10 строк.
```

### C. Конец сессии
```
Завершаем сессию: обнови статусы и «Открытые вопросы» в плане, закоммить и отправь. В ответе — 3 строки: где остановились, что дальше, что ждёт моего решения.
```

## Служебные промпты

### Ревью перед коммитом
```
Вызови сабагента cert-reviewer для изменений относительно <ветка или коммит>. Исправь замечания уровней «критично» и «важно», по остальным дай мне список.
```

### Новый детектор или правило оповещения
```
Хочу добавить: <что должно выявляться>.
1. Предложи строку для матрицы 5.16 (следующий свободный ID): механизм, реакция, этап, OWASP, группа БДУ.
2. Предложи примеры для корпуса — синтетические, на русском и английском, включая безопасные тексты, похожие на атаку, — и порог качества.
3. После моего подтверждения: реализация, тесты с ID строки в имени, fuzz-тест, обновление docs/detectors.md и docs/taxonomy.md.
```

### Покрытие матрицы
```
Построй отчёт о покрытии матрицы 5.16: для каждой строки с этапом не выше текущего — есть ли тест, какой именно и проходит ли он. Отдельно перечисли строки без тестов и места, где интерфейс или документация обещают то, чего нет в матрице.
```

### Идентификаторы БДУ
```
Вот текст раздела БДУ «Угрозы безопасности информации систем ИИ»: <вставьте текст>.
Сопоставь строки матрицы 5.16 с угрозами и способами реализации из этого текста и заполни docs/taxonomy.md. Используй только идентификаторы из текста, ничего не придумывай; УБИ.218–222 не используй. Строки без соответствия перечисли отдельно.
```

### Нужна новая библиотека
```
Для <задача>, возможно, нужна библиотека. Не ставь её. Сравни реализацию на стандартной библиотеке с 2–3 кандидатами: лицензия, активность проекта, транзитивные зависимости, поверхность атаки. Дай рекомендацию. После моего согласия — запись в docs/cert/components.yaml.
```

### Дизайн-система (перед вёрсткой экранов)
```
Прочитай ТЗ, раздел 6.
1) Предложи уточнённые токены: цвета обеих тем, шрифт из двух кандидатов, типографическую шкалу, отступы, радиусы. Сверь их с брифом 6.1 и списком 6.10. Что получилось шаблонным — исправь и объясни, что поменял.
2) После моего подтверждения собери страницу /dev/ui-kit со всеми базовыми компонентами в обеих темах.
```

### Экран
```
Сверстай экран «<название>» по ТЗ 6.4 на компонентах из ui-kit. Данные — через API; если эндпоинта нет, сначала обнови api/openapi.yaml. Покрой основной сценарий e2e-тестом и проверь работу при CSP из 6.9.
```

### Перед пилотом
```
Проверь готовность к пилоту у коммерческого заказчика:
1. Установи продукт по руководству на чистую ВМ и засеки время (цель — не больше часа). Если в твоём окружении это невозможно, пройди руководство и отметь неясные шаги.
2. Прогони сценарии S1–S4 и S8–S10 (ТЗ, 1.4) и путь «ложное срабатывание → исключение → запрос больше не блокируется».
3. Сформируй отчёт «Итоги пилота» на демо-данных.

Составь список проблем, которые заметит заказчик, по убыванию важности.
```

### ADR: движок OCR (этап 5)
```
Подготовь план эксперимента для ADR о выборе OCR-движка в aisec-media (ТЗ, 5.17): Tesseract или ONNX-модели OCR. Критерии: ошибки распознавания (CER) на русском и английском, качество строк DM-45 и DM-46 на корпусе testdata/corpus/media/, время на 4 vCPU, объём заимствованного кода, лицензии, поддержка анализаторами. Ничего не ставь без моего согласия.
```

### Изменилось решение
```
Мы решили: <решение>. Обнови docs/SPEC.md (назови разделы), оформи ADR и перечисли, какой код и документы это затрагивает. Код пока не меняй.
```

### Сверка с нормативкой (раз в квартал и перед сертификацией)
```
Проверь по актуальным источникам, не изменились ли документы из раздела 17 ТЗ: редакции приказов ФСТЭК и ФСБ, методики, статус проекта изменений в приказ № 117, раздел БДУ об угрозах ИИ. Составь список расхождений с ТЗ и матрицей 5.16 и предложи правки. Ничего не меняй без подтверждения.
```

### Перед передачей в лабораторию
```
Проверь полноту артефактов из раздела 9 ТЗ: что отсутствует, что устарело относительно кода, где нет трассировки «функция безопасности → код → тест» и «строка матрицы → тест». Выдай отчёт списком.
```

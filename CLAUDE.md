# CLAUDE.md — AISec (рабочее название)

Мы делаем платформу безопасности ИИ для российского рынка. Это шлюз-посредник между приложениями и LLM (фильтрация запросов и ответов, маскирование ПДн, защита от промпт-инъекций, контроль ИИ-агентов) и веб-консоль с дашбордами, оповещениями и инцидентами. Продукт пойдёт на сертификацию ФСТЭК России (целевой уровень доверия — 4). Требования безопасной разработки действуют с первого коммита, а не «потом».

Первые пилоты — у коммерческих заказчиков (ТЗ, 1.6). Поэтому в приоритете быстрое подключение, мало ложных срабатываний и наглядный результат. Требования безопасности и сертификации при этом не ослабляются: госсектор и КИИ — следующий шаг.

## Как работать
1. Сначала план. Для любой задачи шире одного файла: что меняется, какие файлы, какие тесты, какие документы обновить. Жди подтверждения. Всё, что касается `internal/auth`, `internal/crypto`, `internal/audit`, `internal/integrity`, обновлений, сборки и зависимостей, — только через план.
2. Маленькие шаги: одна логическая задача — один коммит. Не смешивай рефакторинг с новой функциональностью.
3. Тесты вместе с кодом: позитивные, негативные, граничные. Для каждого разборщика входных данных — fuzz-тест (`go test -fuzz`).
4. Прежде чем сказать «готово», запусти `make check` и приведи итог. Если что-то падает — скажи прямо.
5. В конце задачи: что изменено, что человеку нужно проверить руками, что осталось.
6. Неясное или противоречивое требование — спроси, не додумывай. Решение, которое трудно откатить, оформи ADR: `docs/adr/NNNN-kratkoe-nazvanie.md` (контекст, решение, альтернативы, последствия).
7. После значимых изменений вызывай сабагента `cert-reviewer` на дифф.

## Жёсткие правила (продиктованы сертификацией)
- **Зависимости.** Новую библиотеку — только с моего явного согласия. Сначала объясни: зачем, почему не хватает стандартной библиотеки, лицензия, активность проекта, сколько транзитивных зависимостей она тянет. После согласия — запись в `docs/cert/components.yaml`. Разрешены: MIT, BSD-2/3-Clause, Apache-2.0, ISC, OFL (шрифты). MPL-2.0 и LGPL — только отдельным решением. Запрещены: GPL, AGPL, SSPL, BUSL, Commons Clause, код без лицензии. Версии фиксируются точно, Go-зависимости вендорятся (`go mod vendor`).
- **Криптография** — только в `internal/crypto`, через криптопрофиль (`standard` / `gost`, ТЗ, раздел 10). Никаких собственных реализаций алгоритмов. Импорт `crypto/*` и `golang.org/x/crypto/*` вне `internal/crypto` запрещён и ловится линтером depguard. Если нужен объект из `crypto/*` (например, `*tls.Config`), получай готовый из `internal/crypto`.
- **Сеть.** Никаких внешних обращений, кроме явно настроенных администратором (провайдеры LLM, SMTP, syslog, webhook). Никакой телеметрии, «звонков домой», проверки обновлений через интернет, CDN, внешних шрифтов и скриптов.
- **Логи.** Секреты, ключи, пароли, токены и содержимое промптов не попадают в технические логи. Содержимое запросов и ответов сохраняется только через модуль событий с учётом режима хранения (ТЗ, 5.5).
- **Ввод и вывод.** SQL — только параметризованный. Любой вход — с ограничением размера и валидацией. Любой исходящий вызов — с контекстом и таймаутом.
- **Доступ и аудит.** Каждый новый эндпоинт — с проверкой прав (RBAC) и тестом на отказ в доступе. Каждое новое действие администратора пишет запись в журнал аудита.
- **Поверхность атаки.** Изменились внешние интерфейсы (порты, эндпоинты, форматы файлов, переменные окружения, аргументы CLI) — обнови `docs/cert/attack-surface.md`. Изменились функции безопасности — `docs/cert/security-functions.md`.
- **Проверки.** Не отключай и не ослабляй линтеры, SAST и тесты ради «зелёной» сборки. Ложное срабатывание SAST размечай с обоснованием в `docs/cert/sast-triage/`.
- **Go.** Без `unsafe`, без `reflect` в обход типов, без `os/exec` в серверных компонентах, без `math/rand` в чём-либо, связанном с безопасностью. Секреты сравниваются только за постоянное время.
- **Фронтенд.** Без `dangerouslySetInnerHTML`, `eval`, `new Function`. Токены не хранятся в localStorage/sessionStorage. Шрифты и иконки — только локально. Интерфейс обязан работать при строгом CSP из ТЗ, 6.9.
- **Медиа.** Изображения и аудио из запросов декодируются и анализируются только в изолированном процессе `aisec-media` (ТЗ, 5.17). В шлюзе и сервере — никакого декодирования недоверенных медиа; cgo там — только по ADR. ffmpeg и C-декодеры изображений не используются; лимиты размеров проверяются до декодирования.
- **Тестовые данные.** ПДн в тестах — только синтетические: валидные контрольные суммы, но не принадлежат реальным людям.

## Стек (обоснование — ТЗ, раздел 11)
- Backend: Go (версия фиксируется в `go.mod`), в первую очередь стандартная библиотека; PostgreSQL через pgx; миграции на чистом SQL.
- Frontend: TypeScript, React, Vite, Tailwind CSS, Radix UI, TanStack Query/Table/Virtual, Apache ECharts.
- ML-детекторы (этап 4): ONNX Runtime; способ интеграции выбирается через ADR.

## Структура репозитория (полная — ТЗ, 11.3)
```
cmd/aisec-gateway   шлюз (data plane)
cmd/aisec-server    сервер управления, API, раздача веб-консоли
cmd/aisec-cli       инициализация, миграции, резервное копирование, проверка целостности
cmd/aisec-media     изолированный анализатор изображений и аудио (этап 5)
internal/           gateway, providers, detect, policy, events, alerting, incidents,
                    auth, audit, integrity, crypto, compliance, notify, store, api, config, media
api/openapi.yaml    контракт API — источник истины
web/                веб-консоль
testdata/           корпуса для тестов (синтетические ПДн, примеры атак RU/EN)
tools/              SBOM, манифест целостности, проверка лицензий
docs/               ТЗ, архитектура, ADR, артефакты сертификации
```

## Команды

## Definition of Done
- Код и тесты написаны, `make check` зелёный.
- Обновлены затронутые документы: `docs/cert/*`, `api/openapi.yaml`, ADR, README.
- Новый детектор или правило оповещения отражены в матрице обнаружения (ТЗ, 5.16), а тест ссылается на ID строки (`DM-NN`).
- Тексты интерфейса на русском и по правилам ТЗ, 6.7.
- Нет новых предупреждений линтеров и SAST без разметки.
- Итоговое сообщение: что сделано, что проверить, что осталось.

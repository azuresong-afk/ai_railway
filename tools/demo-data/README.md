# demo-data — демо-данные для демо-стенда

Генератор синтетических событий, оповещений и инцидентов (задача 3.29 этапа 3). Не входит в поставку.

## Как работает
Утилита отправляет запросы в Check API шлюза (`POST /guard/v1/check`) от имени приложений стенда — так же, как это делает приложение заказчика. События пишет шлюз, оповещения и инциденты рождают правила сервера (встроенные правила DM-01, DM-16, DM-08 и др.). В таблицы БД утилита ничего не пишет.

План строится по зерну детерминированно: то же зерно, те же флаги и тот же корпус — тот же план запросов. Генератор псевдослучайных чисел (splitmix64) нужен только для воспроизводимости демо; к безопасности он не относится, ключей и секретов из него не берётся (`math/rand` в репозитории запрещён, поэтому генератор свой, десять строк).

План на `-days` суток (по умолчанию 30), в среднем `-events-per-day` запросов в сутки (по умолчанию 40, разброс от ½ до 1½):
- 72 % — обычные рабочие запросы;
- 18 % — запросы с синтетическими ПДн (СНИЛС, ИНН, карта, телефон, почта, паспорт) из `internal/detect/pii`: контрольные суммы верны, значения не принадлежат реальным людям (ИНН и СНИЛС с нулями в начале, телефоны `+7 300`, почта в зарезервированных доменах);
- 7 % — атаки из `testdata/corpus` (инъекции, секреты, скрытый Unicode) на вход;
- 3 % — атаки на ответ модели (exfil);
- раз в неделю (сутки 4, 11, 18…) один пользователь серией из 12 попыток обходит защиту: оповещения «инъекция заблокирована» и «серия срабатываний»;
- раз в десять суток (сутки 6, 16, 26) в ответе модели встречается канарейка (DM-08): инцидент.

**Метки времени.** Шлюз ставит событию время приёма, поэтому все события получат время запуска, а не сутки плана: сутки определяют состав и порядок запросов, а не дату. Чтобы дашборды показывали историю за 30 суток, нужно либо запускать генератор раз в сутки с `-days 1`, либо вернуться к задаче после появления тестового режима с подстановкой времени (отдельное решение, ADR). Правила «аномалия» (обучение 14 суток) и «бюджет» на таких данных не срабатывают.

## Запуск
Нужны запущенный стенд, корневой сертификат его УЦ и файл ключей приложений (`приложение=ключ`, по строке, права 0600; приложения должны быть заведены в консоли и иметь ключи).

```
make demo-data DEMO_CA=ca.pem DEMO_KEYS=keys.txt
make demo-data DEMO_CA=ca.pem DEMO_KEYS=keys.txt DEMO_DAYS=14 DEMO_SEED=7 DEMO_FLAGS=-dry-run
go run ./tools/demo-data -gateway https://127.0.0.1:8443 -ca ca.pem -keys keys.txt -rate 10
```

Правила безопасности:
- адрес шлюза — только `https`; если хост не `localhost` и не IP-литерал loopback, утилита отказывает, пока нет `-allow-remote`. Имя в адрес не разрешается: `localhost` считается локальным по имени;
- доверяется только корню из `-ca`; системное хранилище не используется; редиректы не выполняются;
- ключи читаются из файла, а не из аргументов (argv виден в списке процессов), файл должен быть закрыт для остальных (0600);
- ключи, тексты запросов и ответы в вывод не попадают, печатается только состав плана и число решений шлюза.

`-dry-run` строит план и печатает его состав, ничего не отправляя. Квоты приложений действуют: на 429 утилита ждёт секунду и повторяет до трёх раз.

## Тесты
`go test ./tools/demo-data`: детерминизм по зерну, состав плана, отказ на не-loopback адрес, файл ключей, проверка контрольных сумм всех ПДн плана (`ValidSNILS`, `ValidINN10/12`), запрос к стенду на `httptest`. Fuzz: `FuzzReadKeys`, `FuzzReadCorpusFile`.

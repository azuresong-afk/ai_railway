# База сценариев тестирования устойчивости (`redteam_scenarios`)

Исходник служебной базы задачи 5.31 этапа 5 (ADR-0031, раздел 5; ADR-0028): формат `aisec-redteam-scenarios-v1`. Сервер не встраивает базу в выпуск: её загружают подписанным файлом `*.aisecdb` (`PUT /api/v1/redteam/scenarios`, право `redteam.scenarios.load`). Исполнитель — `internal/redteam` (задача 5.32).

## Содержимое версии 2 (03.11.2026)
75 сценариев: 42 на русском и 33 на английском, 11 из них многошаговые. Версия 2 отличается от версии 1 тремя возвращёнными сценариями скрытого Unicode (`RT-DM05-001`…`003`, запись `\u{…}`). Строки матрицы ТЗ 5.16:

**Чего в базе нет и почему.** Формат ADR-0031 передаёт цели только текстовые шаги `prompt`, поэтому не покрыты: изображения и аудио (DM-45 – DM-49; их проверяет корпус `testdata/corpus/media` и тесты `aisec-media`), подделка реплик ассистента как отдельных сообщений (DM-03) и подмена описания инструмента после одобрения (DM-25) — им нужны сообщения с ролями и описания инструментов в запросе, скрытая нагрузка и перегрузка (DM-15 – DM-17) — это нагрузка, а не сценарий, модели и файлы (DM-27 – DM-29) и эксплуатация (DM-33 – DM-44) — не текст запроса. Если пилот попросит — расширение формата отдельной задачей.

## Как написано
- **Все сценарии собственные** (`license: proprietary`, `source` — этот каталог в репозитории). Тексты написаны вручную по общеизвестным приёмам и не скопированы из чужих корпусов: чужой текст берётся только с лицензией MIT, BSD, Apache-2.0, ISC, CC0-1.0 или CC-BY-4.0, и тогда в его сценарии `source` указывает на исходный репозиторий, а `license` — его лицензию (проверяется вручную до добавления). Сценарии не генерируются на лету (ТЗ 5.13).
- **Маркеры собираются моделью.** Если сценарий просит модель «сказать» слово, маркер (`ТАНГО-4721`) складывается из двух частей, лежащих в запросе по отдельности: ответ-отказ, цитирующий запрос, не содержит маркера и не засчитывается как удачная атака. Тест `TestMarkersAreNotInPrompts` не даёт положить готовый маркер в текст шагов.
- **Условия успеха проверяемы.** `canary: true` — для целей `gateway`, где в системный промпт приложения поставлена канарейка продукта; `findings` — категории встроенных детекторов (`secret`, `pii.*`, `exfil.*`); `contains` — маркеры; `judge` — критерий для `judge.llm` (DM-18, DM-19, инструменты: без настроенного оценщика итог `unchecked`). `TestFindingsAreReachable` проверяет, что детекторы действительно находят в тексте сценария данные нужной категории.
- **Данные синтетические.** ПДн — значения `tools/synth-pii` (валидные контрольные суммы, не принадлежат людям), адреса и узлы — `*.example`, `*.test`, `example.com`; пароли в строках подключения выдуманы. Токены и ключи известных сервисов (AWS, GitHub и подобные) в базу не кладутся: защита push GitHub отвергает файлы с такими образцами.
- **Невидимые символы — только видимой записью.** Сырых символов форматирования (категория `Cf`) и управляющих в исходнике нет: разборщик (`redteam.ParseScenarios`) их отвергает, а при ревью их не видно (`TestNoFormatCharacters`). Скрытый символ в тексте шага пишется как `\u{XXXX}` — от 1 до 6 шестнадцатеричных цифр, в JSON с удвоенной чертой: `"И\\u{200B}г\\u{200B}н"`. Разборщик раскрывает запись только для символов `Cf` (нулевая ширина, управление направлением, теги U+E0001 и U+E0020–U+E007F), не больше 512 записей на шаг; другой символ, суррогат или неверная запись — отказ всей базы с номером сценария и шага. Цели уходит раскрытый текст (`Step.Text()`), а `inspect`, API и отчёты видят запись. Буквальный текст `\u{…}` — с удвоенной чертой перед `u{` (`\\u{200B}` в тексте шага, `"\\\\u{200B}"` в JSON). Правила — дополнение 2 к ADR-0031; так записаны `RT-DM05-001`…`003`.
- Исходник на русском и английском, ID — `RT-DM<NN>-<NNN>` по строке матрицы.

## Предварительная проверка в облаке
Детекторы входа с порогом 0,5 по тексту шагов (без политики и без модели) срабатывают, например, в 4 из 8 сценариев DM-01, 4 из 4 DM-05 (по раскрытому тексту), 7 из 7 DM-04, 0 из 5 DM-07 и 0 из 7 DM-19. Это не замер продукта (настоящий ответ даёт цель при запуске 5.32–5.33), а указание, где сценарий проверяет то, что детекторы входа не видят, и итог зависит от модели, политики и канарейки цели.

## Как менять и подписывать
1. Правка `scenarios.json` — только вручную: каждый сценарий со строкой матрицы, критерием успеха и лицензией; тесты `go test ./internal/redteam/scenariosdb/` проверяют формат, охват, маркеры и достижимость критериев. Увеличить `version`, обновить `date`.
2. Тестовая подпись полной библиотеки — `testdata/redteam/scenarios-library-test.aisecdb` (тестовый рабочий ключ `testdata/shadowai/subkey-test.signkey`, НЕ ДЛЯ ПОСТАВКИ; пять сценариев для тестов исполнителя — отдельно, `testdata/redteam/scenarios-test.aisecdb`). Тест `TestLibraryTestSignature` (`internal/redteam`) сверяет файл с исходником: после каждой правки исходника файл пересоздаётся командой `go run ./tools/manifest sign-db -test -kind redteam_scenarios -key testdata/shadowai/subkey-test.signkey -endorsement testdata/shadowai/subkey-test.endorsement -in internal/redteam/scenariosdb/scenarios.json -out testdata/redteam/scenarios-library-test.aisecdb` (предварительно удалите старый файл) и проверьте `aisec-cli servicedb inspect`.
3. Боевую базу подписывает владелец рабочим ключом производителя на машине без сети: `go run ./tools/manifest sign-db -kind redteam_scenarios -key <рабочий ключ> -endorsement <заверение> -in internal/redteam/scenariosdb/scenarios.json -out redteam-scenarios.aisecdb` (без `-test`, ADR-0027, п. 3; ADR-0028), затем проверить `aisec-cli servicedb inspect redteam-scenarios.aisecdb`. Загрузка — раздел «Тестирование устойчивости» консоли (экраны — задача 5.34) или `PUT /api/v1/redteam/scenarios`.
4. Проверить, что содержимое не стало справочником для атак на чужие системы: в API текст шагов не выдаётся (ADR-0031, раздел 5), только число шагов и заголовок.
